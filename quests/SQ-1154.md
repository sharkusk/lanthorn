## The mechanism, traced but NOT yet reproduced

Read off the code, not measured on a running game. **Reproduce before fixing** — the reasoning below is a hypothesis with a clear shape, and this repo's own history says a self-consistent chain of reasoning is exactly what produces a confident wrong answer.

`$2C`/`$2D` hold colour NUMBERS, not RGB (§8.3.3), so the host's own default page and ink have to be expressed as a number. `colors::host_default_colour_pair` does that with `nearest_standard_colour`, which searches `STANDARD_COLOUR_RGB15` — the **§8.3.1 Standard** table — for the entry nearest the terminal's probed RGB.

Meanwhile `startup.rs` sets the palette from the MEDIUM. Its own comment says why, and the reason is good:

> the palette is set either way, being a table the artwork's colour numbers resolve through rather than a claim about the default page

So on a release floppy the round trip crosses two tables:

1. terminal RGB → nearest **Standard** number
2. that number → RGB through the **machine's** palette (Amiga, Macintosh, IBM CGA)

The two agree on a bare story file, where the palette is `Standard`, and disagree on original media. `--colour terminal` then reports a colour that is not the terminal's, which is the symptom.

Neither half is wrong alone. The palette MUST be the machine's or the artwork's colour numbers resolve wrongly, and that is settled. The gap is that the RGB→number step does not know which table its answer will be read back through.

## The three arms are not equally affected

* `--colour machine` is unaffected by construction — the pair comes from the machine and is read back through the machine's own table.
* `--colour terminal` and `--colour theme` both go through `host_default_colour_pair`, so both should be wrong on original media in the same way. **Check `theme` too**; the report named only `terminal`.

## Likely fix, and the thing to be careful of

Choose the nearest entry in the **palette that is actually in force** rather than always the Standard one — `nearest_standard_colour` becomes nearest-in-a-given-table, and the caller passes the live palette.

Two cautions:

* **A machine palette may not span the space.** IBM CGA at two colours cannot express an arbitrary terminal grey at all, and the honest answer there may be "this launch cannot report the terminal's colours", not "here is the least-bad index". Decide that deliberately rather than letting `min` decide it.
* **The palette is process-global** (`zvm::screen::set_palette`) and this repo has a long scar from that — see the palette-lock discipline in CLAUDE.md. Any test written for this must take the shared lock via `app::v6_palette`, and reading a colour without stating a palette is itself the SQ-0958 defect.

## Verification

The oracle is a real launch, not a unit test: run the same story as a bare file and off its release medium with `--colour terminal`, and compare what `$2C`/`$2D` end up holding and what the pane actually paints. `/dump-windows` and `/dump-cells` are the two instruments. Pin BOTH `honor_game_colours` modes — a colour area with one mode pinned has masked every game-colour regression in this repo's history.

Related: SQ-1082 built the three-source chain; SQ-0956 and SQ-0958 are the palette scars.

## Scope confirmed by the user, and the good news: precedence is already right

> "make sure we apply the same fix for `--colour theme`. this argument should always take precedence over the machine colors, but still allow the game colours to be used (unless that is also disabled)"

Three claims, and **two of them already hold**. Checked rather than assumed:

**1. `theme` needs the same fix — yes.** Both `Theme` and `Terminal` go through `host_default_colour_pair`, so both express their answer as a §8.3.1 Standard number and both get it read back through the machine's table on original media. The reported symptom is `terminal`; `theme` is broken identically and has simply not been noticed. Fix both, test both.

**2. The argument already beats the machine — verified, no change needed.** `colors::host_default_colours` gives `Theme` the themed style and `Terminal` a deliberate `Style::default()` (dropping the theme), and NEITHER arm consults the `machine` parameter at all. Only the `Machine` arm does. There is no fallback to machine colours to remove.

That holds on the restart path too, which is where this repo's scars are: `reset.rs:118` calls the same `colors::host_default_colours`. SQ-1082 collapsed the two copies of this chain into one function precisely so `--colour` could not be added to one and forgotten in the other — the SQ-1022 defect class (`reset.rs` re-deriving a boot fact differently from `startup.rs`) is already closed here.

One shape difference worth knowing, benign: `startup.rs` applies the two-colour card only `if colour_source == Machine`, while `reset.rs` folds the card into the `machine` argument (`card.or_else(|| machine_default_colours())`) and lets `host_default_colours` ignore it for the other two arms. Same net behaviour by two routes; the `reset.rs` shape is the tidier one and is worth preferring if this code is touched.

**3. Game colours stay live unless separately disabled — already true.** `honor_game_colours` is the other axis and short-circuits before any of this: `host_default_colours` returns `None` when it is off, which declares the interpreter colourless under §8.3.2 and leaves the VM's own black-on-white seed alone. `--colour` is inert while that is off, which is the documented intent and matches the requirement exactly.

## So the fix is narrower than the title suggests

Nothing about precedence or about game colours needs to change. The whole defect is the **table** the RGB→number step searches: it must be the palette actually in force, not always Standard. One function (`nearest_standard_colour`), its two callers inside `host_default_colour_pair`, and a decision about what to do when the live palette cannot express the colour at all.

**No, it is not.** My proposal — search the palette in force instead of the Standard table — keeps the machine's palette and picks the index that happens to render nearest the host's colour through it. That is COMPENSATION, not exclusion. Two problems with it:

* It cannot succeed on a narrow palette. IBM CGA showing two colours has no entry near an arbitrary terminal grey, so the answer degrades exactly where it would be most visible.
* It still leaves the machine's table deciding what the host's own default LOOKS like, which is the thing the requirement says to stop doing.

## The mechanism, now confirmed rather than hypothesised

Traced through the constructor: the resolved pair reaches `session.rs:956` as
`machine.set_default_colours(bg, fg)` — **colour NUMBERS** — and the renderer resolves numbers to RGB through the active palette. So the pane's default page and ink are painted by looking the host's answer back up in the machine's table.

On a bare story file the palette is `Standard` and the round trip is lossless, which is exactly why `--colour terminal` looks right there and wrong off a floppy.

## What the requirement actually asks for

The colour NUMBER is the wrong currency for the PAINT. There are two consumers of that pair and they have been conflated:

1. **What the story is told** in `$2C`/`$2D` — must be a number (§8.3.3), and a number is all the story can be given.
2. **What lanthorn paints the pane with** — needs no number at all. lanthorn draws that surface itself and can use the host's real RGB.

So under `--colour theme` / `--colour terminal` the pane's default should be the host's colour DIRECTLY, with the machine's palette not consulted for it. The story still gets a number in the header, because that is the only thing the header can hold — and any imprecision there is a claim to the story, not a wrong pixel on screen.

**Game colours are unaffected and must stay unaffected.** A story's own `set_colour` names a colour NUMBER and resolves through the machine's palette; that is a game colour, and the user's condition is explicit that those keep working unless `honor_game_colours` separately disables them. Only the DEFAULT page and ink change hands here.

## The right model, from the user — and it is implementable nearly literally (2026-08-30)

> "when `--colour theme | terminal` we use the raw z-machine path with native media. The opposite is true when we set `--colour machine`, then we use the media path with a raw z-machine file."

`--colour` selects which colour REGIME applies, independent of what the medium is. That is a far better statement of the requirement than either of my framings above, and it makes the fix smaller rather than larger.

**Half of it already works.** `--colour machine` on a bare story file is exactly SQ-0928's `--system-colours`, subsumed by SQ-1082: the opt-in that licenses a machine's §8.3.3 pair when the MEDIUM did not name a machine but `--interpreter` did. So the media-regime-on-a-raw-file direction is implemented and tested. Only the mirror is broken.

## Why the mirror is achievable: the artwork does not use this palette

Checked, and it is the fact the whole design turns on. `zvm::screen::set_palette` says it selects "the palette standard colour numbers resolve through, process-wide" — and the artwork does not go through it. `app::graphics` keeps its OWN `current_palette`, set per picture from the resource itself (`set_current_palette_from(resnum)`, the archive's PLTE). Pictures resolve through the archive's palette; only TEXT colour numbers resolve through `zvm::screen`'s.

So the text palette can be left at `Standard` under `--colour theme|terminal` — the raw-file path, exactly as the user describes — without touching a single pixel of artwork.

That also disposes of my previous note's proposal (separate the paint from the reported number, a renderer change). Unnecessary: with the text palette at Standard the round trip is lossless again, the header carries a number that means what it says, and the pane paints what the host asked for. **Prefer this over the renderer change.**

Note the consequence and accept it deliberately: a game's own `set_colour(4)` would then resolve as Standard red rather than Amiga red. That is the correct reading of the requirement — on the raw path it IS Standard red, and the user's rule is that theme/terminal means the raw path. Game colours keep working; they simply resolve through the table the chosen regime names.

## The one real edge: a two-colour card palette carries TWO facts

`Palette::IbmCga` is not only a table. CLAUDE.md and `startup.rs` both record that it also carries "the fact that the display has one bit", which `zvm::screen::two_colour_card_request` reads — and that answer decides whether the game asks for MONO or COLOUR plates.

So on a two-colour card press, swapping the text palette to `Standard` is not purely a text change: it could alter which artwork the story requests. That coupling has to be broken or explicitly excepted before this lands. Two candidate shapes, both needing thought rather than a coin toss:

* keep the display-depth fact where it is and make the text table separately selectable, so the regime changes the table without changing the declared depth; or
* except the two-colour-card case from the regime switch, and say so in the flag's own documentation, because a silent exception is how `--colour` stops meaning what it says.

## Solved on paper: it is ONE predicate, and it already exists (2026-08-30)

The user asked how the CGA coupling is handled on the raw path. The answer dissolves the last open question in this quest: **it is not handled, it is never reached** — and the thing that excludes it is the same gate that excludes the machine's colour pair.

`PictSource::two_colour_card_screen` needs three facts together, and the second is the one that matters:

> the LAUNCH may present its machine (`ProfileSource`'s licence, SQ-0928: a medium always, an asked-for machine on request, **a bare story file never**) — which is also what stops a `.cg1` opened beside a plain `.z6` from reaching here

And both machine-colour questions hang off that one predicate:

```rust
pub fn machine_colours_licensed(&self) -> bool {
    self.interpreter_source.licenses_machine_colours(self.system_colours)
}
pub fn machine_default_colours(&self) -> Option<(u8, u8)> {
    self.machine_colours_licensed().then(|| self.interpreter_profile.default_colours()).flatten()
}
// machine_two_colour_colours() is licensed by the same rule, and its own doc says so
```

## The fix

`--colour theme | terminal` should mean **this launch does not present its machine** — exactly the state a bare story file is in. Withhold that one licence and everything follows without a second change:

* `machine_default_colours()` → `None`, so the host's pair is what the story is told;
* `machine_two_colour_colours()` → `None`, so `two_colour_card_screen` returns `None`;
* `Palette::IbmCga` is therefore never installed and the text palette stays `Standard`;
* artwork is untouched — it resolves through `app::graphics`'s own per-picture palette, never `zvm::screen`'s;
* a game's own `set_colour` resolves through `Standard`, which is what it does on the raw path, and is the consistent reading of the regime.

**The "one real edge" recorded two notes above is withdrawn.** The two-colour card is not an exception to the regime; it is governed by the regime, through the same predicate. There is nothing left needing a measurement it cannot get from the existence proof.

## Which makes the symmetry literal

The licence is what makes a medium a medium, for colour purposes. `--colour machine` GRANTS it on a bare story file — already implemented, already tested, that is SQ-0928's `--system-colours` subsumed by SQ-1082. `--colour theme|terminal` should WITHHOLD it on a medium. One predicate, driven from both ends.

## Implementation notes

* Find where `interpreter_source` / `ProfileSource` is decided and let `--colour` override the licence, rather than special-casing `--colour` at each of the machine-colour call sites. The call sites already agree today because they all ask the one predicate; keep it that way.
* `startup.rs`'s `if cfg.colour_source == ColourSource::Machine` guard around the two-colour pair becomes redundant once the licence covers it. Removing it is the tell that the change landed in the right place — if it still has to be there, the licence is not doing the work.
* `reset.rs` needs nothing: it already asks the same predicate through the same helpers, which is what SQ-1082 unified.
* Tests: a medium press with `--colour terminal` must report the host's pair AND leave the palette `Standard`; a CGA press with `--colour terminal` must not install `IbmCga`; and `--colour machine` on a bare `.z6` with `--interpreter` must still do what it does today. Both `honor_game_colours` modes, and take the shared palette lock (`app::v6_palette`) — reading a colour without stating a palette is SQ-0958 verbatim.

AUDIT of the per-machine rules, answering "do any other machines behave this way?" — done by reading the table, not inferred.

`machine_rule` has exactly TWO callers in `crates/zvm/src/screen.rs`:

1. `amiga_global_colour_pair` (:1309) → `MachineProfile::global_colour_pens`.
   **Amiga alone.** Pinned by `the_amiga_is_the_only_machine_with_global_colour_pens`,
   asserting `pens == vec![AMIGA_INTERPRETER_NUMBER]` with "ZMSD §8.3 names the
   Amiga and no other". Apple IIe/IIc/IIgs, Macintosh, Atari ST, IBM PC, C64 and
   C128 all set it false. So the reported black ground is Amiga-only and cannot
   appear on another machine by this route.

2. `machine_screen_pair` (:1405) → `MachineProfile::v6_screen_page`.
   **TWO machines: Amiga and Macintosh** (SQ-0846's pair; the Apple rows state a

   the licence. NOT YET VERIFIED under a host regime.

THE DISTINCTION THAT MATTERS, and it is the general lesson of this reopening:
`machine_screen_pair` hands back `header_pair(mem)` — a VALUE, and the licence
already corrects that value (the lane's own case asserts `$2C`/`$2D` carry the
terminal's pair under a host regime). `global_colour_pens` gates a BEHAVIOUR —
"one pair for all windows, and a change to either recolours the whole screen" —
and correcting a value does not correct a behaviour. That is precisely why
Arthur's own `set_colour` black spread everywhere: nothing we withheld could
stop it, because we only ever withheld numbers.

So the predicate as shipped licenses VALUES and not BEHAVIOURS, and any future
per-machine rule that gates behaviour will have the same hole. Whatever fix
lands should make that explicit at `machine_rule` itself rather than at the one
call site Arthur happened to expose.
