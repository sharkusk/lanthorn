## The mechanism, traced but NOT yet reproduced

Read off the code, not measured on a running game. **Reproduce before fixing** — the reasoning below is a hypothesis with a clear shape, and this repo's own history says a self-consistent chain of reasoning is exactly what produces a confident wrong answer.

`$2C`/`$2D` hold colour NUMBERS, not RGB (§8.3.3), so the host's own default page and ink have to be expressed as a number. `colors::host_default_colour_pair` does that with `nearest_standard_colour`, which searches `STANDARD_COLOUR_RGB15` — the **§8.3.1 Standard** table — for the entry nearest the terminal's probed RGB.

Meanwhile `startup.rs` sets the palette from the MEDIUM. Its own comment says why, and the reason is good:

> the palette is set either way, being a table the artwork's colour numbers resolve through rather than a claim about the default page

So on a release floppy the round trip crosses two tables:

1. terminal RGB → nearest **Standard** number
2. that number → RGB through the **machine's** palette (Amiga, Macintosh, IBM CGA)

The two agree on a bare story file, where the palette is `Standard`, and disagree on original media. `--colour terminal` then reports a colour that is not the terminal's, which is the symptom.

Neither half is wrong alone. The palette MUST be the machine's or the artwork's colour numbers resolve wrongly, and that is settled. The gap is that the RGB→number step does not know which table its answer will be read back through.

## The three arms are not equally affected

* `--colour machine` is unaffected by construction — the pair comes from the machine and is read back through the machine's own table.
* `--colour terminal` and `--colour theme` both go through `host_default_colour_pair`, so both should be wrong on original media in the same way. **Check `theme` too**; the report named only `terminal`.

## Likely fix, and the thing to be careful of

Choose the nearest entry in the **palette that is actually in force** rather than always the Standard one — `nearest_standard_colour` becomes nearest-in-a-given-table, and the caller passes the live palette.

Two cautions:

* **A machine palette may not span the space.** IBM CGA at two colours cannot express an arbitrary terminal grey at all, and the honest answer there may be "this launch cannot report the terminal's colours", not "here is the least-bad index". Decide that deliberately rather than letting `min` decide it.
* **The palette is process-global** (`zvm::screen::set_palette`) and this repo has a long scar from that — see the palette-lock discipline in CLAUDE.md. Any test written for this must take the shared lock via `app::v6_palette`, and reading a colour without stating a palette is itself the SQ-0958 defect.

## Verification

The oracle is a real launch, not a unit test: run the same story as a bare file and off its release medium with `--colour terminal`, and compare what `$2C`/`$2D` end up holding and what the pane actually paints. `/dump-windows` and `/dump-cells` are the two instruments. Pin BOTH `honor_game_colours` modes — a colour area with one mode pinned has masked every game-colour regression in this repo's history.

Related: SQ-1082 built the three-source chain; SQ-0956 and SQ-0958 are the palette scars.

## Scope confirmed by the user, and the good news: precedence is already right

> "make sure we apply the same fix for `--colour theme`. this argument should always take precedence over the machine colors, but still allow the game colours to be used (unless that is also disabled)"

Three claims, and **two of them already hold**. Checked rather than assumed:

**1. `theme` needs the same fix — yes.** Both `Theme` and `Terminal` go through `host_default_colour_pair`, so both express their answer as a §8.3.1 Standard number and both get it read back through the machine's table on original media. The reported symptom is `terminal`; `theme` is broken identically and has simply not been noticed. Fix both, test both.

**2. The argument already beats the machine — verified, no change needed.** `colors::host_default_colours` gives `Theme` the themed style and `Terminal` a deliberate `Style::default()` (dropping the theme), and NEITHER arm consults the `machine` parameter at all. Only the `Machine` arm does. There is no fallback to machine colours to remove.

That holds on the restart path too, which is where this repo's scars are: `reset.rs:118` calls the same `colors::host_default_colours`. SQ-1082 collapsed the two copies of this chain into one function precisely so `--colour` could not be added to one and forgotten in the other — the SQ-1022 defect class (`reset.rs` re-deriving a boot fact differently from `startup.rs`) is already closed here.

One shape difference worth knowing, benign: `startup.rs` applies the two-colour card only `if colour_source == Machine`, while `reset.rs` folds the card into the `machine` argument (`card.or_else(|| machine_default_colours())`) and lets `host_default_colours` ignore it for the other two arms. Same net behaviour by two routes; the `reset.rs` shape is the tidier one and is worth preferring if this code is touched.

**3. Game colours stay live unless separately disabled — already true.** `honor_game_colours` is the other axis and short-circuits before any of this: `host_default_colours` returns `None` when it is off, which declares the interpreter colourless under §8.3.2 and leaves the VM's own black-on-white seed alone. `--colour` is inert while that is off, which is the documented intent and matches the requirement exactly.

## So the fix is narrower than the title suggests

Nothing about precedence or about game colours needs to change. The whole defect is the **table** the RGB→number step searches: it must be the palette actually in force, not always Standard. One function (`nearest_standard_colour`), its two callers inside `host_default_colour_pair`, and a decision about what to do when the live palette cannot express the colour at all.

## Correction: my proposed fix does NOT deliver the stated requirement (2026-08-30)

The user pushed back on the framing and was right. Recording it, because the note above would otherwise send the next reader down the wrong road.

> "essentially, when we specify theme or terminal as the colours, we should completely ignore the machine colours (similar to how a raw z-machine file is handled). Is that the fallout of your proposal?"

**No, it is not.** My proposal — search the palette in force instead of the Standard table — keeps the machine's palette and picks the index that happens to render nearest the host's colour through it. That is COMPENSATION, not exclusion. Two problems with it:

* It cannot succeed on a narrow palette. IBM CGA showing two colours has no entry near an arbitrary terminal grey, so the answer degrades exactly where it would be most visible.
* It still leaves the machine's table deciding what the host's own default LOOKS like, which is the thing the requirement says to stop doing.

## The mechanism, now confirmed rather than hypothesised

Traced through the constructor: the resolved pair reaches `session.rs:956` as
`machine.set_default_colours(bg, fg)` — **colour NUMBERS** — and the renderer resolves numbers to RGB through the active palette. So the pane's default page and ink are painted by looking the host's answer back up in the machine's table.

On a bare story file the palette is `Standard` and the round trip is lossless, which is exactly why `--colour terminal` looks right there and wrong off a floppy.

## What the requirement actually asks for

The colour NUMBER is the wrong currency for the PAINT. There are two consumers of that pair and they have been conflated:

1. **What the story is told** in `$2C`/`$2D` — must be a number (§8.3.3), and a number is all the story can be given.
2. **What lanthorn paints the pane with** — needs no number at all. lanthorn draws that surface itself and can use the host's real RGB.

So under `--colour theme` / `--colour terminal` the pane's default should be the host's colour DIRECTLY, with the machine's palette not consulted for it. The story still gets a number in the header, because that is the only thing the header can hold — and any imprecision there is a claim to the story, not a wrong pixel on screen.

**Game colours are unaffected and must stay unaffected.** A story's own `set_colour` names a colour NUMBER and resolves through the machine's palette; that is a game colour, and the user's condition is explicit that those keep working unless `honor_game_colours` separately disables them. Only the DEFAULT page and ink change hands here.
