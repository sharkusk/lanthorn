## What is missing, and what it costs

`ObjectWords` (SQ-1118) reads an object's **nouns**. On Infocom games it does not
read the **adjectives**, so Zork I's lantern answers `lamp`, `lanter`, `light`
but not `brass` — and `take brass lantern` is a thing players type.

Inform is unaffected: it stores adjectives in the same `name` array, so every
Glulx game and every Inform Z-machine game already has them for free. This is an
Infocom/ZIL-only gap.

## What the lane found, so this does not need re-deriving

The adjectives exist and were located:

- **V4+** stores them as a word array in a separate property. Zork Zero's
  "Dirigible Hangar" answers `hangar` under property 51 and
  `dirigible` / `large` under property 46. That property is **already
  identified** by `infocom_property`'s detection pass — it is the *runner-up*
  that containment discards, so the V4+ half is close to free.
- **V1-3** stores them as one-byte adjective **numbers**, not dictionary
  addresses. Zork I's `brass` is `flags=$22 d0=$dd`, and the lantern's property
  16 is the single byte `$dd`.

## Why it was refused rather than half-shipped, and why that was right

The V1-3 property number **has no detectable margin**. Hitchhiker's
object-count and adjective-coverage rankings pick *different* properties (p29:
131 objects, 125 of 220 adjectives; p30: 117 objects, 193 adjectives), and
Moonmist's top three are a coin toss.

Shipping only the V4+ half would make a word list mean *nouns plus adjectives*
on a v4 game and *nouns only* on a v3 one, while `ObjectWords.property` can name
only one source — a silently version-dependent answer, which is the defect class
this repo keeps logging (SQ-0901, SQ-1020, SQ-1022). Refusing beat guessing.

## Two ways forward

1. **Ship the V4+ half only, with the meaning made explicit** — a separate field
   or a variant so a caller can tell nouns from adjectives and knows when
   adjectives are simply unavailable. This is the tractable half and needs no new
   detection.
2. **Solve V1-3 properly.** The one-byte numbers index a table the game's own
   parser reaches through a compiled-in constant. Finding that table is the real
   work; the `$dd`-style values are a strong verification signal once a candidate
   is found, because the adjective a player types must resolve to the byte the
   object holds.

Do NOT merge adjectives into the noun list without distinguishing them.

## Verification, when it is done

The parser is the oracle, as SQ-1118 established: `take brass lantern` must be
accepted by `zvm-cli` on `stories/zork1-r88-s840726.z3`. A reader verified only
against itself proves nothing.

## A dependency this created (2026-08-28)

SQ-1042 shipped, and it works around the adjective gap in a way that will break
quietly on some story.

`ParseNames` on a ZIL game returns **nouns only** — `brass` is nowhere in Zork
I's lantern `SYNONYM` property, because Infocom keeps adjectives in a separate
property (the subject of this quest). So `vocab::typeable_name` recovers
adjectives through the **dictionary's DESC bit** instead, and `typeable_words`
offers them to completion on that basis.

**A story with no DESC bit would silently lose its adjectives** from both the
band's object columns and completion. The lane stated this rather than burying
it, and did not chase it.

That raises the value of doing this quest properly: solving the adjective
property removes a workaround rather than merely adding a feature. Whoever picks
it up should check how many corpus stories actually set the DESC bit, since that
is the measure of how load-bearing the workaround currently is — and if the
answer is "all of them", say so, because that turns a latent bug into a
documented assumption.

## Shipped: the V4+ half, with the meaning explicit (2026-08-30)

`grammar_model::Adjectives` is a two-variant enum carried on `ObjectWords`:

* `Unavailable` — this story keeps no separate adjective list, or keeps one this
  reader cannot locate. **Says nothing about whether the object has adjectives.**
  Every Inform story (adjectives are already in `words`), every Scott Adams item,
  and every V1–3 Infocom story.
* `Read { words, property }` — read, and from which property. An **empty**
  `words` is a real answer: this object has none, in a story that would have said
  so if it did.

So a caller tells nouns from adjectives by field (`words` vs `adjectives`), and
tells "cannot ask" from "has none" by variant. `ObjectWords::new` is unchanged at
five arguments and defaults to `Unavailable`; `with_adjectives(words, property)`
is the only way to say otherwise, so a reader with none is not asked to spell
that out and a reader with some cannot forget which property they came from.
`refers_to` answers over both (the parser does not distinguish them);
`describe()` renders `printed [nouns + adj: …]` only where there are any.

`ParseNames::adjective_property()` names it. Detection is the runner-up in the
same containment ranking that already picks the nouns, gated on **version ≥ 4**.

Verified on all fifteen V4–V6 titles in `stories/`: Zork Zero p51/p46, Shogun
p45/p32, Arthur p51/p45, Trinity p51/p49, AMFV p52/p51, Beyond Zork p49/p48,
Sherlock p44/p43, Bureaucracy p55/p47, Nord and Bert p63/p50, Border Zone
p51/p38, Wishbringer r23 p50/p40, and the four v5 InvisiClues re-releases.

**Parser oracle** (`zvm-cli`, verbatim):

```
zork1-r88-s840726.z3           take brass lantern → Taken.
zork1-invclues-r52-s871125.z5  take brass lantern → Taken.
trinity-r12-s860926.z4         examine baby prams → They're probably full of
                                                     British babies.
```

The two Zork I releases are the same game and the same object, and are the whole
argument: r52 (v5) answers `brass lantern [lamp, lantern, light + adj: brass]`
while r88 (v3) answers `Unavailable` — not an empty list.

**Falsified**: removing the `version >= 4` gate makes Seastalker r16 claim
property 19 (four objects of noise) as its adjectives, and the corpus case fails
on exactly that.

## The DESC-bit census the second note asked for

Over every Z-machine story in `stories/` (`unit_tests/` holds no story files at
all — only fonts and JSON maps):

* **All 34 V1–V5 Infocom stories set the DESC bit**, generously: 101 words in
  Zork III to 658 in AMFV, a fifth to a third of each dictionary. So the SQ-1042
  workaround is safe on exactly the stories where it is now the only source, and
  that is a documented assumption rather than a latent bug.
* **The three Infocom V6 games do not**: Zork Zero 11 of 1624, Shogun 17 of 1389,
  Arthur 9 of 1059 — and `zvm::grammar::decode_roles` does not even *decode*
  `adjective` for the V6 flag layout, which moved. So on those three the
  workaround yielded **nothing**, and they are precisely the games the property
  now answers for.
* Inform stories are in neither half: no DESC bit, adjectives in the `name`
  array beside the nouns, already reached by `refers_to`.

Pinned as `scope_completion::every_pre_v6_infocom_story_sets_the_desc_bit_the_fallback_depends_on`.
