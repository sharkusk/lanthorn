## What works and what does not

SQ-1085 made a zip a volume: entries are classified by CONTENT, so a zip carries any
format lanthorn runs, and a Blorb or hints file packed beside the story is found. That
is done and tested.

What it did not do — deliberately — is enumerate. A zip holding two games **plays the
first one, silently, with no way to ask for the other**, exactly the defect SQ-1078
fixed for compilation discs.

## Why it was held back: the save key, not the enumeration

The enumeration itself is easy. `picker::resolve_entries` would take a `zipped_stories`
analogue of `mounted_stories`, and `read_story_file` would honour a `want` by entry
name in about ten lines.

The blocker is that **a container-mounted story has no per-entry save key**. Verified
still true on `main` as of 2026-08-27:

```rust
// cli-host/src/storage.rs:218
pub fn story_key_for(story_path: &Path, build: Option<&DiskBuild>) -> String {
    match build {
        Some(b) => disk_story_key(b),
        None    => story_key(story_path),   // ← the zip's basename
    }
}
```

`DiskBuild` is the per-entry key that exists, and it is defined in terms of a
`blorb::medium::DiskImage` — which a zip does not have. So `story_key_for(zip, None)`
keys on the zip's basename and **two games in one zip would silently share a save
directory**. Enabling enumeration on top of that trades a visible limitation for an
invisible data defect, which is why the lane stopped rather than shipping three
quarters of it.

Call sites that would need to agree: `startup.rs:289`, `picker.rs:155/361/1378/1770`.

## Likely shape of the fix

Key a container-mounted story on `story_path.join(entry)` — whose `file_name()` is the
entry's basename, which is consistent with how loose files already key on basename
alone — threaded through **one helper** rather than the five call sites above. That is
the refactoring-policy shape: the facts that decide a save key travel together rather
than being reassembled positionally at each site.

Order that keeps it falsifiable: give the key its per-entry form first and prove two
entries of one zip get different save directories; only then enable enumeration and
`--story`, which becomes a small change once the key is honest.

## Related

- **SQ-1096** decided the neighbouring question for disk images: a downloaded zip of
  floppies is unpacked into the library rather than mounted in place, so it never needs
  a per-entry key. That is not a precedent for stories — a zip of raw stories is what a
  zip is FOR here, and unpacking every one into the library would be a different
  feature and a worse one.
- **SQ-1085** carries the fuller measurement of what a zip does today.

## Done — key first, then enumeration (commit a88f1d4c, branch worktree-agent-a580d1ab970138386)

Followed the quest's stated order. The key was settled and falsified BEFORE any
enumeration existed.

### 1. The per-entry key

`cli_host::storage::story_key_for` now takes one value, `StoryOrigin { path,
entry, build }`, and applies three rules rather than two:

- `Some(build)` -> `disk_story_key` (unchanged)
- `None` + `Some(entry)` -> `story_key(path.join(entry))`, i.e. the entry's
  basename — the quest's suggested shape
- `None` + `None` -> `story_key(path)` (unchanged; the loose-file promise)

`StoryOrigin` has no `Default` and no partial constructor, so a caller holding
two of the three facts gets a **compile error**, not a plausible key. The match
is exhaustive over the pair, so deleting the new arm does not compile either.

**Falsified twice, both at the reported symptom.** With the old rule restored
(`(None, Some(_)) => story_key(origin.path)`):
- `cli-host storage::tests::two_stories_in_one_zip_get_two_directories` fails
  `left: "infocom-pack.zip", right: "infocom-pack.zip"`
- `app zip_story_entries::two_stories_in_one_zip_get_two_save_directories` fails
  "one zip, one save directory, was the defect"

### 2. One helper, not five call sites

The quest listed `startup.rs:289` and `picker.rs:155/361/1378/1770`. Two of those
(`resolve_aux`, `compute_row_badges`) were re-deriving what
`StoryEntry::story_key()` already answers — they now call `entry.game_dir()`.
`StoryEntry::story_key` is the single place a row's key is worked out. The
remaining sites (`entry_from_loaded`, `startup::boot_story`, `zvm-cli`) state all
three facts at construction. `zvm-cli` states `entry: None` explicitly with a
comment saying why (it opens no zips).

### 3. Enumeration

- `hints::zipped_stories` — the `mounted_stories` counterpart, classified by the
  same `extract_story`, so the browser and the launch cannot disagree about what
  a story is.
- `hints::zip_story(path, want)` — `read_story_file` honours a `want` by entry
  name and **refuses** a name that is gone (or names a non-story) rather than
  opening the neighbour, matching the disk-image branch's SQ-0859 rule.
- `picker::resolve_entries` / `holds_several_games` treat a zip as the container
  it is, so `StorySource::of` opens the browser and `--story <n|name>` reaches
  the second game with no changes to `story_pick` beyond the noun.
- `story_pick::subject_of` says "this archive" for a zip source, not "this disk".

### Two adjacent facts found on the way

- **`dedupe_within_a_volume` relied on an invariant that stopped holding.** It
  asked `disk_entry.is_some()` to mean "came off a disk image" — true only while
  nothing else carried an entry. Tightened to require `disk_image` too, which is
  what its own comment always claimed. A `game.z5` and a `game.zblorb` in one
  download are not the byte-identical duplicates the fold is justified by, and
  already have two save directories under the basename rule; folding them would
  have dropped the copy that ships the artwork. It also made the two doors agree
  (`scan_stories` dedupes globally, `StorySource::scan` does not).
- A zip carrying one game plus its `.blb` is still ONE row, because a
  resource-only Blorb is not a story — pinned as a case.

### Residual, deliberately not fixed

Two DIFFERENT zips in the SAME directory that happen to pack the same entry name
(`a.zip/story.dat` and `b.zip/story.dat`) still resolve to one
`story.dat.save/`, because `game_dir` keys off the container's parent. This is
the quest's stated shape and is the same class the basename promise already
accepts; the alternative is a key nobody can read (`pack.zip.story.dat`). Worth
a decision if it ever bites — it is NOT the defect this quest was about, which
was guaranteed for every multi-story archive.
