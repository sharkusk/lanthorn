## What works and what does not

SQ-1085 made a zip a volume: entries are classified by CONTENT, so a zip carries any
format lanthorn runs, and a Blorb or hints file packed beside the story is found. That
is done and tested.

What it did not do — deliberately — is enumerate. A zip holding two games **plays the
first one, silently, with no way to ask for the other**, exactly the defect SQ-1078
fixed for compilation discs.

## Why it was held back: the save key, not the enumeration

The enumeration itself is easy. `picker::resolve_entries` would take a `zipped_stories`
analogue of `mounted_stories`, and `read_story_file` would honour a `want` by entry
name in about ten lines.

The blocker is that **a container-mounted story has no per-entry save key**. Verified
still true on `main` as of 2026-08-27:

```rust
// cli-host/src/storage.rs:218
pub fn story_key_for(story_path: &Path, build: Option<&DiskBuild>) -> String {
    match build {
        Some(b) => disk_story_key(b),
        None    => story_key(story_path),   // ← the zip's basename
    }
}
```

`DiskBuild` is the per-entry key that exists, and it is defined in terms of a
`blorb::medium::DiskImage` — which a zip does not have. So `story_key_for(zip, None)`
keys on the zip's basename and **two games in one zip would silently share a save
directory**. Enabling enumeration on top of that trades a visible limitation for an
invisible data defect, which is why the lane stopped rather than shipping three
quarters of it.

Call sites that would need to agree: `startup.rs:289`, `picker.rs:155/361/1378/1770`.

## Likely shape of the fix

Key a container-mounted story on `story_path.join(entry)` — whose `file_name()` is the
entry's basename, which is consistent with how loose files already key on basename
alone — threaded through **one helper** rather than the five call sites above. That is
the refactoring-policy shape: the facts that decide a save key travel together rather
than being reassembled positionally at each site.

Order that keeps it falsifiable: give the key its per-entry form first and prove two
entries of one zip get different save directories; only then enable enumeration and
`--story`, which becomes a small change once the key is honest.

## Related

- **SQ-1096** decided the neighbouring question for disk images: a downloaded zip of
  floppies is unpacked into the library rather than mounted in place, so it never needs
  a per-entry key. That is not a precedent for stories — a zip of raw stories is what a
  zip is FOR here, and unpacking every one into the library would be a different
  feature and a worse one.
- **SQ-1085** carries the fuller measurement of what a zip does today.
