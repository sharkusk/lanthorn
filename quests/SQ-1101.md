## What happens

`zvm::grammar::Grammar::load` (SQ-1040) reads five table shapes — Infocom ZIL fixed
and variable, Infocom Version 6, Inform GV1 and GV2 — and was verified against
`infodump -g` over 97 story files, 94 rendering identically.

Two modern stories are **refused**, not misread: `frankenfingers_260330.z5` and
`ImpossibleStairs.z8` both return `BadVerbTable`. Refusing is the correct behaviour
and the parser's falsification pass confirms it does not fabricate a table here.

## Why

Both tools assume **the grammar table sits at the base of static memory**. In these
files static memory begins with something else — a run of address/length pairs — and
the verb-pointer table is elsewhere. The address is not in the header, and a forward
scan for a monotone pointer table finds nothing, so guessing would be fabrication of
exactly the kind SQ-1040 was careful to avoid.

**`infodump` declines both files outright as well**, so this is a shared limitation of
the assumption rather than a defect in our reader.

## Why it is filed rather than fixed

Genuinely out of SQ-1040's scope: locating a table whose address is not recorded is a
different problem from parsing one whose address is known, and it needs a source for
where modern I7 actually puts it — the Inform 6 Technical Manual describes the table's
FORMAT, not its placement under I7's memory layout.

## When it matters

**Only if SQ-1041 needs modern Inform 7 coverage.** SQ-1041 offers the game's own
vocabulary when the parser rejects a word, and its first users will be playing the
Infocom corpus, which is fully covered. A story whose grammar cannot be read simply
gets no vocabulary offer — the feature degrades silently and correctly rather than
misbehaving. So this is a coverage gap, not a blocker.

Worth revisiting if the release's audience turns out to be playing modern IF as much
as Infocom's — which the "make IF accessible to people without nostalgia" goal on
SQ-1045 makes plausible, since a newcomer is at least as likely to start with
Photopia or Anchorhead (both of which DO parse — they are GV2) as with Zork.

## Bookkeeping note

This was found, judged, and then not filed because the parent's brief told the lane
that the no-orphan rule forbade filing. It does not — the rule bounds where work goes,
never whether it is recorded. See the corrected memory `no-orphan-spinoff-quests`.

## The next step, from SQ-1102's evidence: these are probably not Inform 6 output at all

The SQ-1102 lane (Glulx grammar tables) went back to the Inform 6 source to settle
where Glulx keeps its tables, and the same reading falsifies the framing of this
quest's title.

**Inform 6 writes the grammar table's address into the header itself.**
`Inform6/src/tables.c` sets `p[14]/p[15] = grammar_table_at` — so on the Z-machine
the grammar table *is* reachable from header word $0E and *is* at the base of static
memory, exactly as `zvm::grammar` assumes. The assumption is not a limitation of our
reader; it is Inform's own layout, stated by the compiler that produces it.

**And Inform 6 stamps its version as `6.NN` at header bytes $3C..$3F.** The two
refused files hold `1a01` (`frankenfingers_260330.z5`) and `0m03`
(`ImpossibleStairs.z8`) there instead, and the word at their static-memory base
points *below* static base — impossible for Inform's layout, in which the verb
pointer array is the first thing static memory contains.

So the title's diagnosis ("the table is not at the base of static memory") describes
the symptom correctly but implies a *variant Inform layout* that does not exist.
These two files are **not Inform 6 output**, which means there is no Inform grammar
table in them to find, and `BadVerbTable` is the right answer rather than a gap.

**The actual open question is therefore: what compiler produced them, and does it
emit a grammar table we could read at all?** Dialog is the obvious candidate — it
targets the Z-machine, is in active use for modern releases, and does not use
Inform's runtime. Answering that is what unblocks this quest; if the answer is "a
compiler with no Inform-shaped grammar table", the right outcome is to close this as
*correct behaviour, documented* rather than to implement anything.

Recorded here rather than filed separately: it is this quest's next step, not a new
one.
