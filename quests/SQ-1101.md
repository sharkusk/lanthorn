## What happens

`zvm::grammar::Grammar::load` (SQ-1040) reads five table shapes — Infocom ZIL fixed
and variable, Infocom Version 6, Inform GV1 and GV2 — and was verified against
`infodump -g` over 97 story files, 94 rendering identically.

Two modern stories are **refused**, not misread: `frankenfingers_260330.z5` and
`ImpossibleStairs.z8` both return `BadVerbTable`. Refusing is the correct behaviour
and the parser's falsification pass confirms it does not fabricate a table here.

## Why

Both tools assume **the grammar table sits at the base of static memory**. In these
files static memory begins with something else — a run of address/length pairs — and
the verb-pointer table is elsewhere. The address is not in the header, and a forward
scan for a monotone pointer table finds nothing, so guessing would be fabrication of
exactly the kind SQ-1040 was careful to avoid.

**`infodump` declines both files outright as well**, so this is a shared limitation of
the assumption rather than a defect in our reader.

## Why it is filed rather than fixed

Genuinely out of SQ-1040's scope: locating a table whose address is not recorded is a
different problem from parsing one whose address is known, and it needs a source for
where modern I7 actually puts it — the Inform 6 Technical Manual describes the table's
FORMAT, not its placement under I7's memory layout.

## When it matters

**Only if SQ-1041 needs modern Inform 7 coverage.** SQ-1041 offers the game's own
vocabulary when the parser rejects a word, and its first users will be playing the
Infocom corpus, which is fully covered. A story whose grammar cannot be read simply
gets no vocabulary offer — the feature degrades silently and correctly rather than
misbehaving. So this is a coverage gap, not a blocker.

Worth revisiting if the release's audience turns out to be playing modern IF as much
as Infocom's — which the "make IF accessible to people without nostalgia" goal on
SQ-1045 makes plausible, since a newcomer is at least as likely to start with
Photopia or Anchorhead (both of which DO parse — they are GV2) as with Zork.

## Bookkeeping note

This was found, judged, and then not filed because the parent's brief told the lane
that the no-orphan rule forbade filing. It does not — the rule bounds where work goes,
never whether it is recorded. See the corrected memory `no-orphan-spinoff-quests`.

## The next step, from SQ-1102's evidence: these are probably not Inform 6 output at all

The SQ-1102 lane (Glulx grammar tables) went back to the Inform 6 source to settle
where Glulx keeps its tables, and the same reading falsifies the framing of this
quest's title.

**Inform 6 writes the grammar table's address into the header itself.**
`Inform6/src/tables.c` sets `p[14]/p[15] = grammar_table_at` — so on the Z-machine
the grammar table *is* reachable from header word $0E and *is* at the base of static
memory, exactly as `zvm::grammar` assumes. The assumption is not a limitation of our
reader; it is Inform's own layout, stated by the compiler that produces it.

**And Inform 6 stamps its version as `6.NN` at header bytes $3C..$3F.** The two
refused files hold `1a01` (`frankenfingers_260330.z5`) and `0m03`
(`ImpossibleStairs.z8`) there instead, and the word at their static-memory base
points *below* static base — impossible for Inform's layout, in which the verb
pointer array is the first thing static memory contains.

So the title's diagnosis ("the table is not at the base of static memory") describes
the symptom correctly but implies a *variant Inform layout* that does not exist.
These two files are **not Inform 6 output**, which means there is no Inform grammar
table in them to find, and `BadVerbTable` is the right answer rather than a gap.

**The actual open question is therefore: what compiler produced them, and does it
emit a grammar table we could read at all?** Dialog is the obvious candidate — it
targets the Z-machine, is in active use for modern releases, and does not use
Inform's runtime. Answering that is what unblocks this quest; if the answer is "a
compiler with no Inform-shaped grammar table", the right outcome is to close this as
*correct behaviour, documented* rather than to implement anything.

Recorded here rather than filed separately: it is this quest's next step, not a new
one.

## Checked against SQ-1114, and they are not the same defect

SQ-1114's four blorbs (`advent.blb`, `narco.blorb`, `sensory.blorb`,
`photo201.blb`) turned out to be a **Glulx decoding** bug: Inform in Glulx mode
counted dictionary verb numbers down from `$FF` until v6.32 widened the base to
`$FFFF`, and `gvm::grammar` knew only the wide base, so four pre-6.32 stories
read as a complete grammar table with zero verb WORDS. Fixed in `e2c842e1`.

That is a different stage of the same pipeline from this quest:

| | SQ-1114 | this quest |
|---|---|---|
| engine | Glulx | Z-machine |
| compiler | Inform 6.21 | not Inform (see below) |
| symptom | `Ok`, tables located, no verb words | `Err(BadVerbTable)` |
| stage | DECODING a table already located | LOCATING a table |

**Re-confirmed on disk while there** (after the SQ-1114 fix, so this is current):
`stories/frankenfingers_260330.z5` and `stories/ImpossibleStairs.z8` still return
`BadVerbTable`, and their header `$3C..$3F` bytes are `1a01` and `0m03` — where
Inform 6 stamps `6.NN` (`stories/advent.z8` there reads `6.32`). The note above
about these two not being Inform 6 output stands, and nothing in SQ-1114 changes
this quest's diagnosis or its open question (which compiler produced them, and
whether it emits a readable grammar table at all).

Recorded from the SQ-1114 lane; nothing implemented here.

## Answered: Dialog, and there is no table — closed as correct behaviour, documented

Commit `bc9b6276`.

### What produced them, and how we know

Three independent lines, all agreeing:

1. **The header.** `frankenfingers_260330.z5` reads `*Dia1a01` at $38..$3F;
   `ImpossibleStairs.z8` reads `\0Dia0m03`. Those are not the four bytes the
   quest was reading — the signature is **seven**, starting one byte earlier.
2. **The compiler.** `dialogc`'s `src/backend_z.c`
   (<https://github.com/Dialog-IF/dialog>) writes it unconditionally:
   ```c
   if(VERSION[5] == '-' && VERSION[6] == 'd') { zcore[0x38] = '*'; }
   zcore[0x39] = 'D'; zcore[0x3a] = 'i'; zcore[0x3b] = 'a';
   zcore[0x3c] = VERSION[0]; zcore[0x3d] = VERSION[1];
   assert('/' == VERSION[2]);
   zcore[0x3e] = VERSION[3]; zcore[0x3f] = VERSION[4];
   ```
   The version is Dialog's own with the slash dropped, and `*` marks a `-dev`
   build. $38..$3F are "unspecified" in the ZMSD, so nobody else has a claim.
3. **The stories' own mouths.** Booted under `zvm-cli`: ImpossibleStairs prints
   "Dialog compiler version 0m/03. Library version 0.46."; frankenfingers prints
   "Dialog compiler version 1a/01-dev." The `-dev` matches the `*` exactly.

### Does Dialog emit anything grammar-table-shaped? No.

- The string **"grammar" does not occur anywhere** in the compiler's sources
  (`src/*.c`, all of them). It occurs 221 times in `stdlib.dg`, the library.
- Dialog's parser is library code: `(understand $ as $)` querying a
  `(grammar entry $ $ $)` predicate defined in `stdlib.dg`, compiled to the same
  predicate representation as any other rule. The manual's "table of grammar
  definitions … constructed at compile-time" is a **Dialog** table, not a
  Z-machine one — the compiler special-cases it nowhere.
- `backend_z.c` lays static memory out as: the optimised alphabet table (only
  when `optimize_alphabet`), then **wordmaps**, then data tables, then the
  dictionary. No verb-pointer array, at the base of static memory or anywhere.
  Those wordmaps are the "run of address/length pairs" the first note saw at
  `$38ee` / `$4710`.

So `BadVerbTable` was refusing for a *correct* reason by *accident*.

### What changed

`zvm::grammar::is_dialog` (the three-letter signature; version deliberately not
tested) and an early `Err(Absent)` in `Grammar::load`, **before** any shape
check. Not cosmetic: these two files happen to fail the shape checks, and the
next Dialog story's wordmaps need not — a fabricated grammar is the one outcome
this module exists to prevent. Falsified by disabling the early return: both
files go back to `BadVerbTable`.

`detect_format` is deliberately unchanged (it still answers `Inform5` for
Dialog), because `objects::ParseNames` reads it and the Inform branch is the one
that then *refuses* on `MIN_AGREEING_OBJECTS`; sending Dialog down the Infocom
branch would let a property tally pick something.

### The corpus census, which nobody had run

All **94** Z-machine stories in `stories/`, by header $3C..$3F:

| stamp | producer | count |
|---|---|---|
| all zero | Infocom / ZIL | 43 |
| `6.14`–`6.36` | Inform 6 | 49 |
| `1a01`, `0m03` (with `Dia` at $39) | Dialog | 2 |

No fourth producer. `crates/zvm/tests/dialog_grammar.rs` asserts that rule over
the whole directory every run rather than recording the counts, so a new
compiler in the corpus fails the case instead of passing silently.

### The consequence, measured

Both files boot, play, and degrade gracefully across all five grammar readers:

- `story_vocabulary()` → `None`; the vocabulary offer says nothing on three
  misses that would each draw a line out of Zork I.
- The command band keeps the built-in column under the **VERB — generic**
  header — the same already-pinned road Journey takes.
- The reveal arms and returns `Armed::Nothing`, leaving nothing stale behind.
- The meaning table and inflection lookup are only consulted through a
  vocabulary that does not exist here, so they are unreachable.

Pinned in `crates/app/tests/suites/dialog_story_degradation.rs` (added to the
`engines` group binary), with non-vacuity guards on every silence — the first
draft passed because the reveal was bailing at `NoText` with no frame drawn.

### One defect found → SQ-1150

`Armed::Nothing` is relayed as `[nothing on screen is a word this story takes]`,
which is a claim about the ROOM. For a story with no readable vocabulary the
truth is that we cannot tell, and the variant is carrying two meanings. Filed
rather than fixed because `reveal.rs` belonged to a concurrent lane; the new
case accepts either answer so it need not change twice.

### Docs

`docs/zvm-embedding-review.md` (the grammar reader's coverage) rewritten with
the above; `docs/features/interface.md` now names Dialog where it described "a
file that is not Inform or Infocom output"; the `ImpossibleStairs` sentence in
`zvm::objects::ParseNames::detect` corrected — it said "`UUID` where Inform
writes its version string", which is off by four bytes.
