## Root cause — the wrap measured ROMAN, the draw measured BOLD

Reproduced from the user's own state: `~/.lanthorn/saves/arthur-r54-s890606.save/bold-overflow.lanthorn`, restored onto **Arthur r54 / serial 890606** off `stories/Arthur - The Quest for Excalibur.adf` (Amiga, `char.data`, cell 8x20, art scale (2,2)), then perturbed with one `wait` — per the restore-test rule, since the frame immediately after a restore still looks correct.

### Where it was NOT

`zvm` is right. Its own `px_runs` break the line inside the window:

```
y=281 x=29 st=2 w=574px "[You have earned five experience points and two que"
y=301 x=29 st=2 w=114px "st points.]"
```

The engine has measured with the style byte since SQ-1009. So this was never the prose wrap in `cpu::exec` that SQ-1049 fixed.

### Where it was

The RASTER prose path does not draw `px_runs` — it wraps the host transcript itself, in `render::wrap_cache::raster_wrap_extend`:

```rust
if !cur.is_empty() && tf.run_px(&cur) + tf.advance(' ') + tf.run_px(word) > width {
```

`TextFace::run_px(s)` is **`run_px_styled(s, 0)`** — the roman pen. Meanwhile `v6_layout::draw_story_text` steps every glyph by `advance_styled(ch, row_styles[col])`. Two different questions about one row, and the answers differ by exactly `tf_BoldSmear` per character.

Measured on this floppy's own face (smear = 1 face px = 2 native):

| measure | width | vs the 584 px window |
|---|---|---|
| roman | **564 px** | fits — so the wrap kept all 62 characters on one row |
| bold | **688 px** | **104 px past the right edge**, thirteen characters' worth |

The quest's own hypothesis at filing was right: the bold run advances by `tf_BoldSmear` and that is the half that overran.

### The fix

Measure each candidate row at the bits it will be drawn with. `line_bits` was already materialised one block above (for `set_row_styles`) and simply never reached the measurement; two closures — `span_px(from, s)` and `gap_px(at)` — now walk it. A line with no emphasis takes `tf.run_px` exactly as before, and italic is byte-identical either way because `V6Metric::advance` widens for `STYLE_BOLD` only.

### Verification

`v6_arthur_amiga_proportional::a_bold_prose_line_wraps_at_the_width_it_will_be_drawn_at`, using the real floppy's face and the reported string alone so the wrap is the only variable. Two non-vacuity guards (roman fits, bold does not — otherwise the case proves nothing), a guard that the emphasis survives the wrap, and a re-join check so a truncation cannot pass as a wrap.

Falsified: restoring `run_px`/`advance` fails it with **one row of 688 px in a 584 px window** — the overflow as reported.
