--- note 2026-08-31T06:10:42Z ---

## The site

`hints::tests::read_zip_entry_caps_a_huge_inflated_entry` builds its scratch
directory as `bm-zipcap-{pid}` from a bare `std::process::id()`.

## Why it is not failing, and why that is the worrying part

`std::process::id()` alone is unique per PROCESS. Under nextest that is the same as
unique per test, so it always passes locally. Under `cargo test` — which is what CI
runs — it is unique per BINARY, so every caller of that path in the same binary gets
the SAME directory. Today there is exactly one caller, so nothing collides.

**That is the state SQ-1131 started from.** It cost eight consecutive red CI runs
against a local gate that printed 0 every time: `fs::write` truncates a neighbour's
fixture, and a case's closing `remove_dir_all` deletes what another is halfway
through reading — a correct fixture failing its own assertion, somewhere else,
intermittently. The second caller is what turns this from dormant to that, and the
person who adds it will have no reason to look at the first one's path.

## The fix

`app::scratch_dir("a-tag")`, which is unique per CALL by construction. `hints` is
inside `app`, so it is directly available — the `AtomicUsize`-beside-the-pid form is
only for `zvm`/`gvm`/`scott`, which take no dependencies.

## Why the existing guard did not catch it

`scratch_path_discipline` fails the bare `process::id()` form **in a helper**, and
fails two sites that name the same path. This is neither: it is the bare form
inlined in a single test with no second site to collide with. Worth deciding whether
that guard should also fail an inline bare-pid path — the fix is one call either
way, but the guard is what stops the next one, and CLAUDE.md's own corollary is that
a guard beats a convention.

## Verification

Per CLAUDE.md, a change touching a test that writes to disk wants
`cargo test --workspace` as well as the gate, and **wants it twice** — a race that
has been fixed passes once by luck as well.

Related: [[SQ-1131]] is the original and holds the eight-red-runs measurement;
[[SQ-1162]] is the lane that spotted this while fixing the Windows crash.

SCOPE CORRECTED, 2026-08-31 — measured after the user asked why this had not been actioned. It is much larger than "one test", and the title understates it.

**`scratch_path_discipline` only reads `crates/app/tests/suites/`.** Everything else
is unguarded, and the `src/` unit-test surface is where most scratch directories
actually live.

    process::id() occurrences outside tests/suites/ : 182   (needs triage — the
                                                             call has other uses)
    in crates/app/src/hints.rs alone                : 10

The `hints.rs` ten, for shape:

    1635 bm-hintidx-{pid}        2032 bm-zipcap-{pid}
    1647 bm-lsb-{pid}            2157 bm-route-{pid}
    1736 bm-zblorb-{pid}         2183 bm-gblorb-{pid}
    1754 bm-{tag}-{pid}   HELPER 2222 bm-resolve-{pid}
    2253 bm-{tag}-{pid}   HELPER 2238 bm-resolve-nosibling-{pid}

**The two HELPERS are the dangerous ones** and are exactly the form SQ-1131 named:
parameterised by `tag`, so two callers who happen to pass the same tag get the same
directory. `scratch_path_discipline` was written to fail precisely that shape — and
cannot see it here, because it does not look in `src/`.

`crate::scratch_dir(tag)` (`lib.rs:155`) is the cure and is already available inside
`app`: it appends a per-CALL `AtomicUsize`, so two callers with one tag still get two
directories. Note it also does `remove_dir_all` + `create_dir_all` itself, so each
call site's own setup/cleanup must be reconciled rather than left doubled.

## What the fix has to include

1. **Triage the 182** — `process::id()` has uses that are not scratch paths. Report
   the real count.
2. **Convert the scratch-path ones in `app`** to `crate::scratch_dir`. In
   `zvm`/`gvm`/`scott` (zero external dependencies) spell an `AtomicUsize` beside
   the pid, per CLAUDE.md.
3. **Widen the guard so `src/` is covered**, which is the durable half — otherwise
   the next unit test written in a source file reintroduces the whole class. That is
   this project's own corollary: a guard beats a convention, and this guard has a
   blind spot the size of the source tree.
4. Per CLAUDE.md, a change touching tests that write to disk wants
   `cargo test --workspace` as well as the gate, **twice** — a fixed race passes once
   by luck too.

## Why it sat unactioned

I filed it and then asked twice whether to dispatch it, against the standing rule
that a spin-off is fixed in the same effort or dispatched immediately. The user
caught it. Recorded because the rule exists to stop exactly this accumulation.
