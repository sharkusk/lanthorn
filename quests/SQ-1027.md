## The arithmetic, which is not in dispute

`render::bitfont::blit_glyph_styled` samples the 8x8 masters with

    let col = dx * 8 / cw;   // nearest source col

At the universal `cw == 8` that is the identity. At the **Macintosh's `cw == 7`**
(SQ-0917) `dx` runs 0..=6 and `col` takes the values 0,1,2,3,4,5,6 — `6 * 8 / 7 = 6`.
**Source column 7 is never sampled.** The rightmost column of every 8x8 glyph is
dropped on that machine.

The font-3 set is the part that cannot survive it, because font 3 is a
character-graphics set whose glyphs must TILE EDGE TO EDGE. `vga16` carries
letters only, so box drawing, block elements, the cursor arrows and the APL quad
all fall to the 8x8 chain — see `bitfont`'s own module header.

A full-width horizontal rule survives by luck: drop a column of an all-ink row and
it is still contiguous. **A corner does not.** `└`'s horizontal arm runs from the
stem out to column 7; drop that column and the arm stops one pixel short of the
cell edge, so it no longer meets the `─` in the next cell. Same for `┌ ┐ ┘ ├ ┤ ┬ ┴
┼` and for the block elements' right edge.

`bitfont::tests::the_vertical_rule_stays_one_pixel_wide` pins the vertical case,
which is the one that cannot break — the stem sits mid-cell — so the existing
coverage is precisely orthogonal to the defect.

## Not yet observed on screen, and that is the first job

This is derived from the sampler, not from a frame. Before fixing it, produce the
pixels: render a font-3 corner join at `cw = 7` and at `cw = 8` and compare. The
quest that introduced this floor (SQ-0917) has the standing lesson that reasoning
about glyph rendering without dumping pixels produces confident wrong answers —
two descender tests were written from a mental model and both PASSED with the bug
in place.

Which titles actually reach it also needs checking. *Journey* is v6 and ships the
font-3 set, and its box drawing is live in the raster path (SQ-0915); whether a
Macintosh press of it draws a join through this sampler is the question.
