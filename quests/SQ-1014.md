## Why now

`crates/zvm` is to be usable outside this project as the standard Rust Z-machine
implementation. That changes what `pub` means: it is a promise to strangers, not
a convenience for `app`. Nobody has yet read the surface as an outside consumer
would, and the crate grew under the assumption that `app` was its only caller.

## The three questions to ask of it

**1. What is `pub` that should not be?**
Things exposed because `app` happened to need them, which an embedder would
reasonably take for API and which would then be painful to change. `V6Cell`'s
methods, `write_screen_dims` / `write_screen_dims_px`, `Machine::set_v6_cell` /
`set_v6_screen_px` and the `ScreenState` internals are all recent and worth a
deliberate look — several were made `pub` this week for lanthorn's benefit.

**2. What is missing that an embedder needs?**
The known case is SQ-1013 (the Version 6 cell lives in `app`), but there will be
others. Useful test: could someone write a working v6 host against `zvm` alone,
without reading `crates/app`? Where they cannot, either the knowledge is
misplaced or the seam is missing.

**3. Do the docs read as written for a stranger?**
`zvm`'s comments are unusually good but frequently addressed to US — they cite
quest numbers, name lanthorn's own defects, and assume the reader knows what the
ring or the hybrid path is. A `SQ-0917` reference is meaningless to an embedder;
the ZMSD section number beside it is not. Prefer the spec citation first and the
quest as provenance.

## The seam question, which is the interesting one

The engine must not decide I/O, fonts or rendering — but it should DEFINE the
interfaces a host plugs into, because that is what makes it embeddable rather
than merely readable. Existing seams: `Output`, the picture/sound event queues,
`InterpreterProfile`-supplied colours.

The one SQ-0917 identified and did not build is `FontMetrics` — a host-supplied
answer to "how wide is this string, in the face I am actually painting". Under
the standard-implementation goal this stops being speculative: a GUI drawing
proportional text is the second consumer the goal anticipates. `V6Cell` already
documents the boundary it sits on (declared metric versus drawn), so the shape is
half-designed already.

**Do not build it as part of this review.** Decide whether it belongs, and file
it if so.

## Also worth deciding

- **Versioning and stability.** Pre-release today with no back-compat obligation
  (a standing project rule). At what point does `zvm` start owing semver to
  people who are not us?
- **Whether `gvm` and `scott` carry the same ambition.** The goal as stated names
  `zvm`; Glulx and Scott Adams may or may not follow, and the answer changes how
  much of this review generalises.
- **A doctest or example.** Every crate here sets `doctest = false`, which is free
  while nothing is public-facing and looks different for a crate meant to be
  embedded — a compiled example is the cheapest proof the API is usable.

## Related

- **SQ-1013** — the first concrete instance: the v6 cell is in the wrong crate.
- **SQ-0917** — where `V6Cell` and the declared-versus-drawn boundary came from.

## Review complete (2026-08-23). Ranked, with file:line.

Zero-dep rule verified clean: `crates/zvm/Cargo.toml` has an empty `[dependencies]` and no dev-dependencies at all. ~480 pub items across 16 modules. Doc coverage is genuinely better than most published crates — the naming findings below are about AUDIENCE, not absence.

### 1. Process-global palette and interpreter version — the biggest embeddability defect (BREAKING)

`screen.rs:1787` `static ACTIVE_PALETTE`, `screen.rs:1793` `static INTERPRETER_VERSION`, with `set_palette`/`palette`/`set_interpreter_version`/`interpreter_version`.

The justification is in the doc itself (`screen.rs:1778`): "the palette is a property of the machine **lanthorn** is pretending to be, and there is exactly one of those per run." That is a lanthorn premise, not a Z-machine one, and it is false for any embedder wanting two sessions — a GUI with two windows, a web front-end serving N players, a parallel harness, an Amiga-vs-IBM comparison tool.

Three reasons this ranks first:

* **The project already pays for it.** CLAUDE.md records four consecutive red-main incidents (SQ-0904/0958/0959/0987) and a whole lock-discipline apparatus — a mutex private to `app`, a panicking setter, and the source-scanning `palette_lock_discipline` case — existing solely to make a process-global survive `cargo test`. An embedder inherits the hazard and none of the apparatus.
* **zvm's own docs argue against it.** `screen.rs:2222`, on `V6Cell`: "it is emphatically not process-global — see `zvm::screen::set_palette` for what that costs." The cell was already moved onto `Machine`. The palette is the same kind of fact.
* **The plumbing exists.** `true_colour_in(p, n)` (`screen.rs:1918`) already takes the palette as a parameter; only `standard_true_colour` (`:1904`) and `ZColour::true_value` (`:70`) read the globals.

The doc's counter-argument names "four unrelated call chains", two of which are HOST chains (the terminal cell renderer, the CLI SGR path) that should take the palette from the session they are rendering — which is exactly the seam split.

Action: `Machine::palette` and `Machine::interpreter_version`; thread into `true_value`, which already takes `interpreter_default`. Deleting the statics also deletes all of `app::v6_palette*`.

### 2. `pub mod fixtures` ships a test loader in the release library (BREAKING, trivial)

`lib.rs:4` → `fixtures.rs:11` does `PathBuf::from(env!("CARGO_MANIFEST_DIR"))`, unconditionally public, baking the BUILD MACHINE'S absolute source path into every downstream binary. No users outside zvm's own tests. Gate behind `cfg(test)` or a feature — `header::tests_support` (`header.rs:84`) is the in-crate precedent.

### 3. No boot recipe — the ordering constraints live in the host (additive)

An embedder gets `Machine::new` → a dozen independent `set_*` → `init_caps()` → drive to first input, with the order documented only in lanthorn: `app/src/session.rs:818` ("`set_picture_dims` runs right after `set_sound_available`, before `init_caps()`") and `:823` for default colours. `init_caps` (`exec.rs:601`) says it must be called and names nothing that must precede it. The result is an eleven-parameter host constructor (`session.rs:868`) reconstructed by reading lanthorn.

Action: `Machine::boot(mem, BootConfig { .. })` owning the ordering; keep the setters for mid-run changes.

**Note the overlap with SQ-1022**, which is building `app::MachineBoot` right now. They are different layers and both are wanted: `app::MachineBoot` answers "what does this MEDIUM say the machine is" (the four-link std_window cascade + cell), `zvm::BootConfig` answers "in what order must a Machine be told things". SQ-1022 should leave room for the second.

### 4. No screen-state snapshot seam — every embedder re-hand-rolls it (additive)

Quetzal carries no screen state by design, so save-anywhere forces a host to serialise `ScreenState`/`V6Windows`/`ZWindow`/`V6Text`/`ZColour` itself. `app/src/archive.rs` is 2603 lines doing exactly that — `ScreenDto` (`:308`), `V6WindowOpsDto` (`:133`), `ZColourDto` (`:451`) — a hand-rolled mirror that must move in lockstep with zvm's types. zvm already hand-rolls a dependency-free binary format (`quetzal.rs`), so nothing blocks a versioned `Machine::screen_snapshot()`/`restore_screen_snapshot()`. Must stay backend- and terminal-neutral (native pixels, no cell coordinates), per CLAUDE.md.

### 5. `Machine`'s pub fields ARE the API, and the drain protocol is prose (partly breaking)

`exec.rs:212` says "Fields are `pub` so Tasks 11+ can attach I/O channels" — a retired planning scheme, ~40 pub fields as a result.

* Draining is `std::mem::take` on bare Vecs with no method: `pending_sounds` (`:273`), `pending_pictures` (`:282`), `pending_erase_fills` (`:312`), `diagnostics` (`:367`), `screen_trace` (`:402`), `exec_pcs` (`:407`), `v6_prose_retired` (`:328`). Miss one and it grows unboundedly.
* **The picture/fill interleave rule is correctness-critical and exists only as a comment.** `exec.rs:148` (`pics_before`) explains that draining the two queues separately replays a v6 turn in the wrong order and erases the artwork. Every embedder must reimplement that merge from prose. Should be `take_paint_events() -> Vec<PaintEvent>`, already merged.

### 6. zvm is doubling as lanthorn's shared-vocabulary crate (BREAKING)

* `ZColour::True24(u32)` (`screen.rs:53`) — doc says "used by the Glulx host". **No zvm code constructs it**; the only producers are `app/src/glk_backend.rs:75,788`. A Z-machine embedder writes a match arm for a structurally unreachable variant belonging to a VM this crate does not implement.
* `zvm::location::LocationMethod` is imported by `app/src/glulx_session.rs:27` — the Glulx adapter borrowing a zvm type as neutral vocabulary.

### 7. Missing seams

* **FontMetrics** — zvm names the gap itself (`screen.rs:~2210`): a proportional renderer "needs per-glyph advances, which is a `FontMetrics`-shaped thing supplied by the host". No such trait exists. `V6Cell` answers the DECLARED metric; there is no interface at all for the DRAWN one.
* **Resources are a pre-filled vec, not an interface.** `picture_dims: Vec<(u16,u16,u16)>` (`exec.rs:277`) forces a host to enumerate every picture before boot. A `trait Resources` would let a lazy/streaming host answer on demand. (Blorb living in a separate crate is right; the SEAM being a vec is the issue.)
* **`Output: Any` forces `'static`** (`io.rs:36`). A GUI sink borrowing a frame buffer cannot be used; hosts round-trip through `as_any_mut` downcasts.
* No RNG seam beyond `set_rng_seed` (`exec.rs:1038`). Minor.
* Save/restore file I/O is correctly host-side. No complaint.

### 8. More machine knowledge still in the host — same class as SQ-1013

Beyond `v6_font_cell` (`app/src/interpreter.rs:926`): `InterpreterProfile::std_window` (`:699`) with `MACINTOSH_STD_WINDOW` (`:1026`) and `AMIGA_STD_WINDOW` (`:1033`), plus `two_colour_colours` (`:765`), `row_number` (`:501`), `try_for_interpreter_number` (`:460`). `zvm::interpreter::MachineProfile` already carries number, default_colours, palette, period_look, v6_screen_page, one_screen_palette — std_window and the cell are the same kind of member. **Suggest folding both in one change rather than SQ-1013 alone**; `machines::table`'s exhaustive destructure forces the new columns to be printed, which is the built-in safety net.

### 9. Naming and docs

* **`lib.rs` has no crate-level `//!` docs at all.** docs.rs would show a bare module index with no statement of what zvm is, which versions it covers, or how to boot one. Cheapest high-value fix here.
* No `#![warn(missing_docs)]`, no lint attributes anywhere.
* **"lanthorn" appears in 18 published doc comments** across 5 files, plus types a reader cannot see (`GameSession::drain_turn` at `exec.rs:327,355`; "the `app` crate's `CaptureSink`" at `io.rs:46,61,64`) and a retired planning scheme ("Tasks 11+" `exec.rs:213`, "(Task 9)" `:279`, "(Plan 1b)" `:285`). None are wrong — all are load-bearing rationale — but each should name the ROLE with lanthorn as the worked example.
* `location.rs:1` is "Mapper-facing API" and `lib.rs:18` promotes six of its items to the crate root — the only such promotion — making `zvm::current_location` look like a VM primitive when it is a documented best-effort heuristic (`location.rs:19-21`). Keep the module; drop the root re-export.
* `machines.rs:1` opens by describing a CLI flag no embedder has.
* `screen.rs:1013` re-exports `AMIGA_INTERPRETER_NUMBER` mid-file, giving one constant two public paths for no stated reason.
* `amiga_global_colour_pair` (`:986`) / `machine_screen_pair` (`:1082`) / `amiga_screen_pair` (`:1038`) — three near-identical names for two different concepts.
* Undocumented pub items: `screen.rs:127,193,248,253,2154,2165,2449`; `dictionary.rs:14`; `objects.rs:132-138,460`; `exec.rs:807`; `state.rs:37`.

### 10. Stability hazards

* **Zero `#[non_exhaustive]` in the whole crate.** Enums with demonstrated or certain growth: `Palette` (`screen.rs:1626` — grew 2→5 across SQ-0719/0956), `ZColour` (`:49`), `StepResult` (`exec.rs:153`), `ZError` (`error.rs:5`), `LocationMethod`, `MachineLook`, `CursorShape`, `StatusBand`, `Provenance`/`Unit`/`CacheFmt`, `OpRole`, `Form`/`OperandCount`/`Operand`. Breaking now, free forever after — and pre-release is the moment.
* Host-READ-ONLY structs that should be non-exhaustive: `SoundEvent`, `PictureEvent`, `EraseFill`, `MachineProfile`, `PeriodLook`, `StackTrace`/`TraceFrame`, `Header`, `Token`, `ObjectSnapshot`.
* **Do NOT** mark `TextAttrs` (`io.rs:14`) or `V6Text` (`screen.rs:369`) non-exhaustive — hosts CONSTRUCT both. Give them constructors first if they must grow.
* **Opcode internals public with zero external users** (grepped app, zvm-cli, mapper): `cpu::state::{read_var, write_var, peek_stack, poke_stack, call_routine, return_value}` (`state.rs:52-208`), `State`/`Frame` with every field public (`:10-33`, including `pc`, `frames`, `eval_stack`) — which pins the call-stack representation forever — plus `Machine::do_branch` (`exec.rs:3642`) and `print_text` (`:4100`). `do_store` (`:4056`) is used externally but only from two tests.
* `Machine::out: Box<dyn Output>` is a pub field (`exec.rs:218`), swappable mid-run with no invariant.

### Suggested order

| # | change | breaking |
|---|---|---|
| 1 | palette + interpreter version onto `Machine`, delete the statics | **yes** |
| 2 | gate `fixtures` | **yes** (trivial) |
| 3 | crate-level `//!` docs | no |
| 4 | `BootConfig` owning the `init_caps` ordering | no |
| 5 | `take_*` drains + merged `take_paint_events()` | no |
| 6 | `#[non_exhaustive]` sweep | **yes** |
| 7 | fold `std_window` + `v6_font_cell` into `MachineProfile` (SQ-1013) | no |
| 8 | screen-snapshot format in zvm | no |
| 9 | privatise opcode internals and queue fields | **yes** |
| 10 | doc pass: de-lanthorn, drop the root re-export, decide `True24` | partly |
| 11 | `FontMetrics`, `Resources`, revisit `Output: Any` | partly |

1, 2, 6 and 9 get materially more expensive after a release. 3, 4, 5 and 8 are what an embedder feels on day one.

NEW — two bytes panic a public function.** `disasm.rs:313` is a bare `unreachable!()` on `Operand::Var` under `OpRole::JumpOffset`. `operand_role` (`:121`) maps 1OP `0x0C` (`jump`) to `JumpOffset` regardless of encoding, and `decode.rs:276` decodes short-form type `0b10` into `Operand::Var`. ### gvm / scott (brief)

**Neither has ANY process-global mutable state** — the palette problem is zvm's alone, which kills the "inherent to a VM core" defence.

**gvm has already built the seam zvm lacks:** `pub trait GlkBackend` (`glk.rs:540`), 34 methods of which only `as_any`/`as_any_mut` are required; `Machine::with_glk` (`exec.rs:762`) is the only constructor; explicit `StepResult`/`supply_*`/`deliver_*` protocol; pull-based timers (`exec.rs:5461`). `app`'s `AppGlk` implements it rather than defining it. **This is the model for zvm.** gvm's own costs: 99 KB disassembler pub in the release lib; `as_any` boilerplate exists so OUR suites can downcast to `TestBackend` (`glk.rs:539` says so); runtime faults escape only via a pub `diagnostics: Vec<String>` + `StepResult::Quit`, so an embedder can't tell a clean quit from a crash; **18** non-test unwrap/expect in `glk.rs` (`:1873`–`:2779`) that abort the host, contradicting the crate's own stated fault-and-continue policy (`error.rs:3-5`); `set_borderless` (`exec.rs:2880`) is terminal chrome inside a VM.

**scott is the tidiest and least documented:** all ~30 `Vm` fields `pub(crate)` with accessors, **zero** non-test panics. But `lib.rs` is 8 lines with no `//!`, two of four re-exports are GLOBS (`pub use database::*`, `pub use decompile::*`) so the surface is accidental — four unnamespaced constants at the crate root (`database.rs:48-51`); `pub use vm::Input` is DEAD (nothing constructs it; input arrives via `supply_line`); `restore` returns `Result<(), ()>` (`vm.rs:259`); `Vm::room_block()` (`vm.rs:952`) returns a pre-formatted display block whose doc describes lanthorn's top panel.

## CORRECTION + real panic audit (supersedes finding #5 of the previous note)

The previous note's finding #5 was **WRONG and is retracted**. A dedicated fuzzing pass (throwaway crate in scratchpad depending on zvm by path; `git status --porcelain -- crates/zvm` clean throughout) settled it properly. `docs/zvm-embedding-review.md` §6 and the ledger have been rewritten accordingly.

### Retraction

**`disasm.rs:313`'s `unreachable!()` is DEAD CODE, not a two-byte panic.** `Operand::Var` returns early eleven lines above, at `disasm.rs:295-301`, so the `JumpOffset` arm never sees a `Var`. My `0xAC 0x10` reproducer does not panic. All six non-test `unwrap`/`expect`/`unreachable!` sites in zvm are genuinely unreachable or `cfg(debug_assertions)`.

### What IS reachable — the mechanism is ARITHMETIC, not indexing

**`ZWindow::put_prop` (`screen.rs:667`) is the hole.** The v6 `put_wind_prop` setter writes the story's raw `u16` into every window field with **no clamp**: `1 => x_coord`, `5 => x_cursor`, `6 => left_margin`, `7 => right_margin`. Those fields are then combined with plain `+`:

| site | expression |
|---|---|
| `exec.rs:4256` | `w.x_coord.max(1) + w.x_cursor.max(1) - 1`, then `abs_x + fw - 1` |
| `exec.rs:4203-4204` | `w.y_cursor += fh` and `w.x_cursor = w.left_margin + 1` |
| `exec.rs:2776` | `self.screen.cursor_row = start_row + row` (`print_table`) |

Siblings at `exec.rs:3273`, `:3437`, `:4238`, `:4283`.

Reproduced — a v6 `main` of four instructions: `put_wind_prop w1 prop1=0xFFFF`, `put_wind_prop w1 prop5=0x7FFF`, `set_window 1`, `print_char 'A'` → `panicked at exec.rs:4256: attempt to add with overflow`. Property 6 instead → `:4204`. `exec.rs:2776` was found by blind fuzzing (3 of 12,000 random stories, debug; 0 of 12,000 release).

**All debug-only.** Release wraps silently. That is exactly the debug/release split CLAUDE.md warns about, and a library cannot choose its embedder's profile.

**The discipline already exists one file away, which makes this a "guard beats a convention" case verbatim:** `screen.rs:529` writes the IDENTICAL expression as `self.x_cursor = self.left_margin.saturating_add(1)`; `exec.rs:3995` writes `w.x_cursor.saturating_add(fw)`; `set_cursor` clamps (`exec.rs:2485-2486`). Only `put_wind_prop` doesn't. **Clamping inside `put_prop` — or privatising the four fields behind saturating accessors — fixes all six sites at once.**

### Three more

* **`V6Cell`'s guard is defeated by a struct literal.** `V6Cell::new` (`screen.rs:2237`) clamps each axis to ≥1 and its doc says why ("would otherwise panic somewhere far from the mistake"), but `w`/`h` are `pub` (`:2226-2227`), so `V6Cell { w: 0, h: 0 }` reaches the divisions at `exec.rs:4255` and `:3275`. **Division by zero panics in BOTH profiles.**
* **`DisasmCache` panics in RELEASE.** `code_region` (`disasm_cache.rs:551`) returns `(min(high_mem_base, boot_root), mem.len())` with no `start < end` check. A header `$04`/`$06` past EOF ⇒ `region_start > region_end` ⇒ `build`'s loop never runs ⇒ empty `units` ⇒ `unit_index_at` (`:251`) evaluates `self.units.len() - 1`. Debug: the `debug_assert!` fires. Release: the subtraction wraps and `next_addr` indexes `units[0]` on an empty vec. `DisasmCache::empty()` (`:96`) builds the same object by design. `app/src/session.rs:4102` navigates this cache.
* **One legal instruction is an unbounded DoS.** `print_table` (`exec.rs:2759-2778`) loops `height × width`, both story-controlled `u16`, uncapped. Measured in **release**: one nine-byte instruction ran **29.2 s** and peaked at **4.3 GB** RSS before faulting. The host cannot interrupt — `step()` IS the interruption point. `copy_table` same shape. `State::frames`/`eval_stack` (`state.rs:29-31`) have no depth cap, so runaway recursion is an OOM abort not a fault. The awareness exists: the v6 grid IS capped (`GRID_CELL_CAP`, `screen.rs:2323`, applied `exec.rs:2065`/`:3275`).

### What's genuinely strong (worth recording so nobody "hardens" it twice)

* **`memory.rs` has NO raw indexing of a story address.** `read_byte`/`read_word` (`:95`,`:124`) use `.get()`, return 0, latch `mem_fault`; `write_byte`/`write_word` (`:115`,`:141`) refuse writes ≥ `static_mem_base`, latch, leave memory untouched. Drained by `step()` at `exec.rs:1109-1120` → `StepResult::Fault`. The in-file test is named `oob_read_latches_fault_instead_of_panicking` and its comment says "Previously panicked (unchecked slice index)".
* **Dispatch is total** — catch-alls at `exec.rs:1509`/`:1637`/`:1767`/`:2853`/`:3584`; `decode_form` covers all 256 opcode bytes. All-`0xFF` story faults at step 61; all-`0x00` at step 1281; 12,000 random stories never wedged it.
* **`Machine::new` is clean on every malformed input** — 10-byte ⇒ `NotAStoryFile`; v1/v2/v9 ⇒ `UnsupportedVersion`; `static_mem_base` past EOF ⇒ `Truncated`. (Load-bearing coupling worth a comment: `with_output` does `mem.raw_bytes()[..static_mem_base]` at `exec.rs:531-532`, in-bounds only because `Memory::new` rejected it at `memory.rs:77-79`.)
* **0 panics** from 10,000 random stories through `dictionary`/`objects`/`text::decode`/`ifid`/`world`/`location`/`save_quetzal`, and from 2,000 hostile Quetzal buffers through `restore_quetzal`. Abbreviation expansion (`text/decode.rs:134-155`) is depth-capped, so the classic nested-abbreviation stack overflow is absent.
* Only **11 of 29.5k lines'** worth of functions return `Result`, 6 public — and that is CORRECT design, since the running-story channel is the fault latches.

### Bottom line

**Debug-built host: zvm is NOT safe to point at an untrusted `.z5`.** **Release-built: closer, but no** — `DisasmCache` still panics and one `step()` can burn 29 s / 4.3 GB uninterruptibly. The core (memory, decode, dispatch, quetzal) is genuinely well hardened; the damage is concentrated in the **v6 screen model** and **two helper APIs**.

No `fuzz/` dir anywhere in the workspace and no malformed-input corpus (zvm has zero deps by policy). The one adversarial test, `crates/zvm/tests/object_scan_eof.rs`, exists because `czech.z5` once panicked in `read_byte` — this bug class has bitten before and was patched at the symptom. **An in-repo `#[cfg(test)]` random-story harness costs no dependency and would have caught the `print_table` and `DisasmCache` bugs in seconds.**
