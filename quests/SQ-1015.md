## The size of the hole

**151 suites under `crates/app/tests/suites/` skip vacuously when `stories/` is
absent — 88 of them v6.** `stories/` is gitignored because it is commercial game
files, so on GitHub Actions all 151 report green having asserted nothing. The
local gate covers them; CI does not, and CI is what guards a merge.

That is not a defect to be fixed by committing the games. It is a gap to be
narrowed by making fixtures **we author**, which are redistributable by
construction.

## Why not just download the media in CI

Considered and rejected. Fetching a commercial floppy from a URL is the same act
of copying as committing it, with an extra hop — every Infocom v6 title is still
owned. The technical objections (network flake, a file changing under you, cache
management) are real but secondary; the licensing one is the blocker.

The repo already draws this line correctly: `unit_tests/` holds 56 freely
redistributable fixtures, which is why the Glulx suites test properly in CI while
the v6 ones skip.

## The first one, and the reason this was raised

SQ-1011 reads `FONT` 524 out of a Macintosh floppy's resource fork. A synthetic
**minimal HFS volume carrying a bitmap `FONT`** would exercise the whole path
end to end with no commercial content:

- `blorb::hfs::Hfs::mount` on a real volume structure
- finding the `APPL` entry
- `read_resource` pulling a fork out of a file whose DATA fork is zero bytes —
  the case that reads as an empty file if only data forks are reachable
- `ResourceFork::parse`
- `mac_font::parse` / `from_volume`
- `native_font::resolve`'s `fits` guard (dimensions match, not proportional)
- `blit_glyph_styled` sampling it 1:1

Everything except "does Zork Zero look right", which no CI can answer.

**It does not replace `native_disk_font.rs`.** That suite pins the REAL font —
7x15, baseline 12, 200+ glyphs — and is what proves we read *Infocom's* data
correctly. Synthetic proves the machinery, real media proves the data, and both
are needed. Keep the real ones skipping.

## Survey the rest — this is half the quest

Before building anything, work out which of the 151 are reachable this way. A
first cut of the categories:

- **Disk-image containers.** `blorb` parses HFS, ADF, ProDOS, D64, FAT12, ISO9660,
  2MG, and Infocom's own segmented `.D1`-`.D5`. Each has a mount/enumerate path
  that a small authored image would exercise. `blorb`'s own unit tests may already
  do some of this — check before duplicating.
- **Fonts.** The Amiga side too: `amiga_font::from_volume` reads `char.data` off
  an ADF, and an authored ADF carrying a `DFH_ID` font would cover it.
- **Archives.** `infocom_pics`'s flavours (`Pic.data`, `CPic.data`, `.mg1`, `.cg1`,
  `.eg1`) — a tiny authored archive per flavour would test the readers, though not
  the artwork.
- **Not reachable this way:** anything asserting a specific release's LAYOUT —
  `real_media_releases`, the frame-geometry suites, the profile corpus. Those are
  about particular commercial builds and must stay local-only. **Do not try to
  synthesise those**; a fabricated frame is exactly the SQ-0901 failure mode.

Expect the honest answer to be that a minority of the 151 are convertible. That
is still worth having, and knowing WHICH is worth writing down either way.

## Watch for

- **A synthetic fixture that passes while the real path is broken.** The fixture
  must be built by an independent route, not by round-tripping our own writer
  through our own reader — that tests a mirror. Hand-assemble the bytes, or
  generate them from the format spec, and pin the expected values by hand.
- **Non-vacuity.** Every new case needs a guard that fails if the fixture stops
  being read, or it joins the 151 rather than reducing them.
