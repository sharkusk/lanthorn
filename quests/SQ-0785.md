THE USER'S ASK: integrate this or an equivalent, gated by config, **defaulted ON** to help stabilise the map.

WHAT MUST BE MEASURED BEFORE ADOPTING, because the design's whole risk is here:
1. **Cost per move.** It snapshots the live game into a second session and runs a command in it, after EVERY directional move. Journey and the Glulx titles are the expensive cases; Counterfeit Monkey's init was 23.78M opcodes before SQ-0378's acceleration. An on-by-default feature that adds a silent turn to every move needs a measured per-move cost on the slowest engine, not an estimate.
2. **Which thread.** The standing direction is that only the story interpreter runs on the main thread and map work moves off it. A probe that snapshots and steps a second session on the main thread walks straight into that; the natural home is the mapper worker.
3. **Engine neutrality.** "Snapshot the live game" is the host-snapshot family (Save State), which must behave uniformly across zvm/gvm/scott. Verify the probe works on all three rather than only on the Z-machine, or gate it per-engine and say so.
4. **Side effects the snapshot cannot undo.** A silent probe turn advances the game's own clocks, daemons, and RNG inside the disposable copy — fine — but it must not touch anything outside it: no transcript, no sound, no autosave, no screen. The commit claims silence; that is the thing to falsify first.
5. **Correctness of the claim.** "Closing one-way map gaps without inventing reciprocity" is the valuable part and the part to test hardest: a probe that guesses wrong writes a WRONG edge into the map, which is worse than a missing one. Zork 1's maze and any title with asymmetric or conditional exits are the oracles.

RELATED: the mapper's layout/routing work, and the background-processing direction ([[background-processing-direction]] — the goal of moving graph ownership to a worker).

## Two decisions after the first pass (user, 2026-08-28)

The lane reported — correctly, rather than resolving it — that "always visible"
and "lives on the map pane's border" conflict: `draw_map_panel` is only reached
in the split layout, so with `show_map` false there is no pane and the control
vanishes.

**1. The feature is NOT disabled when the map is hidden.**

Hiding a view must not degrade the data behind it. The mapper keeps recording
rooms and edges with the pane closed, because it is driven by turns rather than
by rendering; a player who plays with the map hidden and opens it later would
otherwise find gaps they could never account for. And the feature is **opt-in and
default off** — someone who switched it on asked for a better map, and switching
it off because they collapsed a pane second-guesses an explicit choice.

The cost objection is weaker than it looks: the gate means a probe runs only
where no return path is known, and the persisted `probed` record means a room is
searched once per **map**, not per visit. The waste is bounded and decays.

**2. The control moves off the map pane, to sit BESIDE the map toggle** on the
story pane's bottom border, at the right where the map toggle already is.

That follows from (1) — a feature that runs with the map hidden cannot have its
only switch on the map pane, or you could not turn off something that is running.
It also groups the two map-related controls together: the toggle for the pane,
and the toggle for the thing that improves what the pane shows.

The user's observation that settles the width worry: **the title strip is on the
TOP border, so the bottom row has the full width to itself.** SQ-1123's give-way
threshold was measured for a centred *pair* with a title competing above; the
bottom row is under no such pressure.

Resulting bottom border: **band + guidance centred** (plus SQ-1107's flashlight
when it lands), **map + return probe at the right**.

**Not yet implemented** — folded into SQ-1107's lane, which is already editing
the same border layout. Two lanes editing that code concurrently would collide.

## Two defects found in play (2026-08-28), one fixed

Reported from a real Zork I session on **`zork1-invclues-r52-s871125.z5`** — the
InvisiClues release, and a **v5**, which is load-bearing: `detect_location` reads
global 0 on v1–v3 and the STATUS LINE from v4 on, so neither defect can exist on
the `zork1-r88-s840726.z3` every existing case in the suite drives.

### 1. The shadow inherited the previous probe's status line — FIXED

Symptom as reported: walking `N, N, N` from West of House (#68 → #143 → #247 →
#167), the first two crossings find their return path and the third does not,
though `S` out of the Clearing plainly returns to Forest Path. Two more of the
same shape: `#89 --E--> #134` and `#247 --E--> #33`.

**Mechanism.** `GameSession::save_state` is Quetzal, which archives no screen by
design, so `restore_state` brought memory and left the upper window holding the
LAST probe's status line. The story then repaints only as many columns as its new
room name needs, and the tail of the longer name it was painted over survives past
the end of it. The shadow's grid read:

```
try south -> loc=Some(1) | "Forest Path"
     upper-window room name = Some("Forest Pathse")
```

`Forest Pathse` matches no object, so `nearest_matching_ancestor` fails, the ladder
falls off `PlayerParent` onto the text rung, and `resolve_room_object` prefix-matches
**object 1 — the scenery object whose short name is `forest`** (`status_name_matches`
accepts a prefix ending on a word boundary; ties on normalized length go to the
LOWEST object number, and Zork's several `Forest` rooms all tie with it). The
identity test `1 == 247` then discards a real return path on the FIRST candidate the
priority order offers. `east`/`west` survived only because they land in rooms
actually named `Forest`, short enough that no leftovers extend past them.

**Fix.** `zvm::screen::UpperWindow::blank()` (content only, extent kept — the
restored game's fields were baked at the saving session's width, SQ-0681), called
from `GameSession::restore_state`. A caller with a real screen to restore
(`restore_screen`, the `.lanthorn` archive path) replaces the whole `ScreenState`
immediately after and never sees the blank.

**This was never probe-specific.** `restore_state` is shared, so every consumer
reading the shadow's screen was getting the same mixed grid — the vocabulary offer
reads shadow replies too, and this fix silently improves it. Worth knowing before
somebody rediscovers it there as a separate bug.

Cases: `session::tests::a_host_restore_blanks_the_upper_window_it_brings_no_screen_for`
and `return_probe::zork1_z5_finds_the_way_back_past_a_scenery_object_of_the_same_name`.
Both falsified — with `blank()` removed the real-game case reports `None` exactly as
reported in play.

Repro instrument: `crates/app/examples/return_probe_trace.rs` — boots a story, walks
a `--walk 'n;n;n'` path, and prints every probe attempt with its resolved location.
An EXAMPLE deliberately, not a test: `-p app` links all fourteen test group binaries
whatever the filter selects, so a filtered test run pays the full ~150s link to
answer a question an example answers in 26s.

### 2. The `probed` record is ORIGIN-BLIND — open

Reported next, and a separate defect: from `N, E, S, E, N, W, S` the return path
recorded out of South of House (#217) to West of House (#68) is **NW**, a diagonal,
when **W** is valid and ranks ahead of it.

W was not ranked below NW — it was **excluded**. That route visits #217 twice. On
the FIRST visit the question was "how do I get back to Behind House?", and the
search ran `N` (boarded), then `W` — which reached West of House, the wrong room
*for that question* — then `E`, which succeeded. `W` was marked `probed` on that
failure, and `probe_candidates` filters on `tried ∪ probed`, so on the second visit
`W` is gone and `NW` is the first survivor.

`probed` says "this direction was walked from here", but the answer it stands for is
"…and it did not reach THAT origin". Reused against a different origin it suppresses
the correct answer. The module doc's claim that "the cost of a wide list is paid once
per room in the life of a map" assumes the outcome is a property of the room; it is a
property of the room AND the question. Worse, the search HAD the right answer and
threw it away: `W → West of House` is a real passage between two rooms already on
the map.

**Agreed fix (user, 2026-08-29):** record the edge whenever a probe lands in **any
room the map already holds**, not only when it lands in `origin`, and keep searching
until it reaches `origin` or exhausts the list. The first visit then writes
`South of House --W--> West of House` immediately and the second visit's gate finds a
known return path and asks nothing. Same probe count, no invented edges, and the
no-leak invariant is untouched — every room involved is one the player has stood in.

Ordering changes alone cannot fix this; `W` is excluded, not deranked.

## Both defects fixed and committed — `499e4f9a`, NOT pushed (2026-08-29)

Defect 2 above is no longer open. One commit carries both, because they share the
suite file and splitting it would have left an intermediate commit whose tests fail.

`deliver` now records the passage on a landing in ANY room the map already holds
and ends the search only on `origin`; `record_probed_passage` is what refuses an
unknown room, so the no-leak rule stays in one place rather than being restated at
the call site. `settle_return_search` changed with it — `deliver` clearing the
search is the end-of-search signal, and the passage has to be carried out of the
loop or the `while` drops it.

Gates, all run BEFORE the commit so the `buildinfo` relink did not invalidate them:

* `cargo nextest run --workspace` → grep gate printed **0**; `Starting 6626 tests
  across 59 binaries` → `6626 tests run: 6626 passed`, 12 skipped. One more than
  the 6625 before, which is the new diagonal case.
* `cargo clippy --workspace --all-targets -- -D warnings` clean, and the new
  example linted separately after it was rewritten.

Both falsified independently: `blank()` removed → the z5 case reports `None`
exactly as reported in play; `deliver` narrowed back to `landed == origin` → the
diagonal case finds `None` where `Some(68)` (West of House — the user's own room
number) belongs.

`zork1_learns_the_way_back_which_is_not_the_way_it_came` is untouched and still
asserts two rooms and no east edge. That is the case showing the broader recording
did not weaken the invariant: Behind House is unknown to the map at that moment and
is still declined.

**What only play can settle**, and why this stays `confirm` rather than `done`: the
diagonal fix changes which edges appear on a live map. It records strictly more —
every landing on a room already visited — so maps will carry more edges than
before, discovered without being walked. Whether that reads as a better map or as a
busy one is the user's eye, not a test's.

The commit carries no `Co-Authored-By`/`Claude-Session` trailers, matching this
repo's existing history rather than the harness default.
