## The measurement

pty capture, `stories/James Clavell's Shogun.adf` (Amiga, r295/890321), pane
132x60, hybrid, on the clue frame — 19 turns: 13 intro taps, \`hint\`, \`y\`,
Return x3.

* The game's clue window is **window 0, 500x330 at native (71,71)** — **62
  columns** at the Amiga's 8x16 cell.
* The hybrid ring gives it a **story viewport of 102x53 terminal cells at (16,8)**,
  cut from what the frame ART leaves rather than from the window's own box.
* Hybrid draws a Grid story window as terminal cells, one native column per
  terminal column, so the clue fills **62 of 102 columns** and the remaining 40
  are empty page.

On screen that is a block of text sitting in a much larger grey rectangle, which
is what "only the center portion of the screen is used" describes.

## Why it is not simply "make the viewport the window"

The viewport is deliberately the ART's clearance and not the declared box —
`story_text_native` insets the window until no edge touches opaque frame art, and
SQ-0896 is explicit that measuring against anything carrying the story's own plate
inverts the result. On this frame the art leaves a 102-column hole and the game
chose to use 62 of it. So there are two defensible readings and the evidence has
to pick one:

1. **The game's box is the truth** and the viewport should be clipped to it — the
   clue is meant to sit in a 500-px column, and the surrounding page is the
   frame's, not the story's.
2. **The viewport is the truth** and the text should fill it — the ring already
   promises the pane's clear middle to the story.

`machine-screenshots/amiga-shogun-hintshown.png` settles it and has not been read
for this yet: measure where the clue's left edge and its longest line sit against
the frame's own ornament, calibrate `native = image - 44` (the reddish frame spans
image x 44..683, 640 px at 1:1), and see whether the machine's clue starts at
native 95 in a 500-px window with the rest of the frame's interior empty. If it
does, reading 1 is right and the defect is the VIEWPORT, not the text.

## Half of this is fixed by SQ-1074; the other half is the real question and remains

SQ-1074 found that the hybrid ring was sending a story-slot **Grid** to `draw_grid`,
the v3–v5/Glulx grid renderer, which **centres** the region by column count. That is
one of the two things this quest measured, and it is now gone: the clue and the topic
list are drawn flush with the viewport's own first column, which is where
`machine-screenshots/amiga-shogun-hint.png` puts them (its topics start at image
x=108 → **native 71**, calibrated at native = image − 37, i.e. window 0's own left
edge). So the block of text no longer floats in the middle of the page.

**What remains is the fill, and it is a harder fact than "clip the viewport".**
Measured on the reporter's frame at 115x34:

* window 0 is 500 native px wide; the ring's story viewport is 89 terminal cells =
  712 device px = **495 native px**. So the viewport already IS the window's box, to
  within a cell — reading 1 in the note above ("clip the viewport to the game's box")
  is therefore a no-op, and the original diagnosis of "62 of 102 columns" was
  measuring the CENTRING, not a viewport that was too wide.
* the text is drawn one terminal cell per native 8px cell, so 62 columns come out
  **496 device px** — while the frame around them is magnified by the ring's
  **1.4375**. Drawn at the frame's rate those same 62 columns would be 713 device px,
  which is the whole viewport.

So the residue is not a placement error at all: **the glyphs are at scale 1.0 inside
a frame at scale 1.4375**, and a terminal cannot scale a glyph. That is the same
conflict `run_col`'s neighbours already describe — "a run is POSITIONED through the
ring scale but its characters then advance ONE TERMINAL COLUMN each, and the two
rates coincide only where a terminal column is one native 8px text cell".

Which means the options are not the two in the first note. They are:

1. **Accept it in hybrid** — text stays crisp at one glyph per cell and the game's
   page shows around it. This is what hybrid IS (`CLAUDE.md`: "text as text, art as
   art"), and the discrepancy shrinks to nothing as the pane approaches 1:1.
2. **Choose the ring scale so a terminal column IS a native text cell** on frames
   whose story window is a text grid — i.e. prefer scale 1.0 for the ring when the
   story is a Grid, letterboxing the art instead of the text.
3. **Send these frames to raster**, where the glyphs are drawn as pixels and scale
   with the frame. Raster is a destination and not a fallback, so this is a real
   option rather than a retreat.

Judge them against the machine capture rather than against each other, and note the
capture is 1:1 — it cannot by itself say what a magnified frame should do.

Not attempted here: SQ-1074's fix is the anchor only, and it stands on its own.
