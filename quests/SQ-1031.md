## The guard is a convention, and the code says so in its own words

`crates/zvm/src/screen.rs:2225`:

    pub struct V6Cell {
        pub w: u16,
        pub h: u16,
    }

    /// Guard against a zero axis reaching the divisions below. A profile that
    /// stated `0` would otherwise panic somewhere far from the mistake.
    pub fn new(w: u16, h: u16) -> Self {
        V6Cell { w: w.max(1), h: h.max(1) }
    }

The constructor states the invariant and enforces it. The struct definition makes
it unenforceable: `V6Cell { w: 0, h: 0 }` compiles, skips `new` entirely, and
reaches `y / cell.h` at `exec.rs:3275` and the sibling division at `exec.rs:4255`.

**This one panics in RELEASE as well as debug** — integer division by zero is not
a debug-only overflow check — which separates it from SQ-1030's arithmetic, where
release merely wraps.

This is CLAUDE.md's "a guard beats a convention" corollary with the roles
reversed: here a guard EXISTS and a public field routes around it. The fix is to
make the fields private with `w()`/`h()` accessors, which is breaking and
therefore free now and expensive after a release — the framing SQ-1014's ledger
is built on.

## Why it is scheduled and not started

`cell.w` and `cell.h` are read at well over a hundred sites across `zvm` and
`app`, and SQ-1009's proportional-pen lane currently has most of the `app` ones
open. Converting them now would collide with that lane on nearly every file it
holds.

Dispatch as soon as SQ-1009 lands. This is scheduled, not parked.

## Do not regex the conversion

`cell.w` is a field access that reads identically to a method call and appears
inside multi-line expressions throughout the render path. CLAUDE.md's refactoring
policy records three separate occasions where a regex sweep over Rust source here
produced code that compiled into something subtly different. Let the compiler find
the sites — privatise the fields first and fix what fails to build.

Related: SQ-1014 (the review that found it), SQ-1030 (the same class, but in
arithmetic rather than indexing), SQ-0917 (which gave the cell its own type).

## Shape chosen: private fields + `w()`/`h()`, inside a private `mod v6_cell`

Committed as `7ca93826` on `worktree-agent-ae3a4e35e916abc58`.

### The shapes weighed, and why the cheap ones lose

The brief asked for a cheaper shape than accessors if one gave the same
guarantee. Three were on the table; two fail, and they fail for the same reason.

- **`#[non_exhaustive]`** binds only ACROSS crates. `zvm`'s own four literals
  (`screen.rs`, two in `exec.rs`, `interpreter::MACINTOSH_V6_CELL`) would still
  compile, so the bar is not met inside the crate that owns the type. It also
  says "more fields may come", which is not the message here. Rejected.
- **A private sentinel field** (`pub w, pub h, _guard: ()`) blocks the literal
  outside `zvm::screen` and costs ~11 edits instead of ~224. Rejected anyway,
  because it leaves the hole open — see below — and leaks `_guard: ()` into the
  derived `Debug` unless `Debug` is hand-written.
- **Private fields + accessors.** Chosen.

### The hole neither cheap shape closes, and the finding did not name

`pub w` on a `Copy` type is a MUTABLE field. `let mut c = m.v6_cell(); c.w = 0;`
walks past `new` exactly as `V6Cell { w: 0, h: 0 }` does, reaches the same
`y / cell.h`, and panics in release the same way. `#[non_exhaustive]` does not
reach an assignment; a sentinel field does not reach an assignment. Only
privatising the fields does. There are zero such mutation sites today — that was
measured, along with zero destructuring patterns, zero `Debug`-string assertions
and zero serde — so this is a route closed before it is used, not a bug fixed.

### Why the extra `mod v6_cell` wrapper

Rust scopes a private field to the defining module **and its children**. Fields
merely private to `screen` would still be writable from anywhere in `screen.rs` —
four thousand lines of exactly the code most likely to construct a new cell, and
one of those lines (`V6Metric::fixed(V6Cell { w: 7, h: 15 })`, a test) already
was a bare literal. So the residual hole was not hypothetical. Wrapping the type
in a private module inside `screen.rs` and re-exporting it costs one `mod` +
one `pub use`, and makes the guarantee absolute: **the whole workspace now holds
exactly one `V6Cell` literal, inside `V6Cell::new`.**

`new` became `const fn` so `DEFAULT` and `MACINTOSH_V6_CELL` stay consts without
a second literal; the clamp is written longhand because `Ord::max` is not const.

**No source-level guard test was added, deliberately.** CLAUDE.md's corollary
says a guard beats a convention *where the wrong spelling cannot be made
unreachable*. Here it is unreachable — a compile error — so a
`palette_lock_discipline`-style grep case would be redundant machinery.

### The conversion was driven by rustc, not by a pattern

Measured, not estimated: **213 field reads and 11 literals across 25 files** (the
brief's estimate was 19 literal sites and 182 reads; `zvm` alone held 52 reads).

Every site came from an E0616 (read) or E0451 (literal) diagnostic that rustc
emitted *because the field belongs to V6Cell specifically*, with a byte-exact
span. Each span was re-verified against the source — text is exactly `w`/`h`,
preceded by `.`, not already a call — before `()` was inserted, right-to-left
within a line; anything not matching that shape would have been reported and
skipped rather than guessed. Nothing was skipped, because rustc does not offer
ambiguous sites. The 11 literals were converted by hand.

This matters concretely: the same `grep "V6Cell *{"` that located the 11 literals
also matched three `-> zvm::screen::V6Cell {` RETURN TYPES. A pattern-driven sweep
mangles those into calls, which is precisely the failure CLAUDE.md records three
times.

### The conversion was then checked back against the original

Two independent passes over `git diff -U0`, one alignment-sensitive and one not.
The decisive one: undo the accessor parens on BOTH sides of every changed line
and compare. Result — **164 lines byte-identical, 9 lines the literal→`new`
conversions, 0 unexplained changes.** `screen.rs`'s restructure was verified
separately with `git diff -w`, which shows only the intended edits under the
reindent.

### Tests

`a_zero_axis_cannot_reach_the_divisions` pins the clamp behaviourally (both axes,
the pass-through for non-zero, and that `row_of`/`col_of`/`row_of_origin0`
terminate) and carries its falsification. Falsified for real, not asserted:
removing the clamp made it FAIL with the reported symptom, and restoring it
passed. The compile-time half falsifies by restoring `pub` — which is exactly the
E0451/E0616 wave that drove the conversion.

Gates, all run before the commit: `cargo check --all-targets` clean; clippy clean
on `-p zvm --all-targets` and `-p app --all-targets`; zvm 738/738; app `--lib`
2908/2908; 177 v6 press cases (arthur, shogun, zork0, journey, render,
extended_frame, raster_reveal).
