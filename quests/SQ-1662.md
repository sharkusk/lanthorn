--- note 2026-10-01T06:20:08Z ---

Root cause confirmed via a two-session probe (session 1 plays far enough to lock the avatar via a confirmed pickup, persisting the SQ-1655 player-global sidecar; session 2 is a brand-new `fresh_start: true` boot reusing the same home dir — exactly what "New Game" does for a returning player):

At the SECOND boot, `introspect().player_object()` is already `Some(...)` immediately after the intro (correctly restored from the sidecar), before any command. But the live inventory panel shows raw word-salad names ("umbrella things green handle brolly bumbersho") instead of clean ones, matching the user's report exactly.

Two separate code paths are involved, confirmed by reading the source (not guessed):
1. `GlulxSession::seed_turn()` -> `glulx_item_observations()` (crates/app/src/glulx_session.rs:1805) DOES walk `self.contents(player)` for already-carried items, but filters each through `item_tracker_display_name(ow, prose, ...)` (same file, ~line 1848), which returns `None` (silently dropping the item from `items`) when the turn's own prose doesn't mention it by name — true at boot, since the intro banner never describes the avatar's starting equipment. So the mapper registry stays genuinely EMPTY for these items until a later turn's prose happens to supply resolvable names. This part is arguably correct/deferred-by-design, not the bug.
2. `render::transcript::inventory_items_with_keys` (crates/app/src/render/transcript.rs:1772) — the LIVE "Carrying:" panel's data source — calls `o.display_name()` directly (join-every-word), with NO smart fallback at all. This is the actual source of the jibberish. Contrast with its sibling `inventory_click_words` (same file, ~1799), which already prefers `crate::vocab::typeable_name(o, vocab)` and falls back to `display_name()` only when that fails — `inventory_click_words`'s own doc comment claims this mirrors `inventory_items`'s fallback chain, but `inventory_items_with_keys` never actually implements that chain; it only calls `display_name()`.

Fix direction (scoped, not yet implemented): give `inventory_items_with_keys` the same `vocab: Option<&crate::vocab::StoryVocabulary>` parameter `inventory_click_words` already takes, and the same typeable_name-preferring fallback. Production call site: crates/app/src/main.rs:764 (pass `state.vocab.get(engine)`, mirroring `render::inventory_dock::refresh_inventory_click_words`'s own pattern at inventory_dock.rs:81). Test call sites needing the new param: crates/app/tests/suites/inventory_dock_registry.rs, glulx_inventory.rs, item_tracking.rs, and crates/app/src/render/transcript.rs's own two in-crate tests (~6626/6628).

This does NOT touch the registry-population path (#1) at all — carried items will still show as "Elsewhere"-less / unregistered until a later turn's prose names them, same as today. It only replaces the LIVE panel's ugly multi-word fallback with the same short, typeable fallback already used for click targets, which is correct and sufficient for the symptom reported.
