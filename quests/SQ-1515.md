--- note 2026-09-15T23:19:40Z ---

2026-09-15: root cause found, confirmed by direct measurement, NOT platform/backend-specific. AppGlk's grid/buffer/graphics content is keyed by Glk window id; restore swaps in gvm's window model but never reconnects backend content, so an archive whose window ids don't match the live session (any archive taken after a prior restore/restart/panel-rebuild, since ids climb monotonically) leaves every non-primary window empty. Only the window's declared background colour survives (correctly round-trips through gvm), producing exactly the reported flat-colour symptom. Proven via A/B/C: same-session restore (ids match, fine), archive into a fresh session (ids collide, blank), user's real archive into the session it came from (ids match, looks right but shows stale content, not the actually-restored state — same shape as SQ-0901/1020/1022's self-consistent-but-wrong numbers).

Bigger finding: Glulx has NO screen-state persistence in the archive at all — zvm writes screen.bin, Glulx writes nothing equivalent. Violates the project's own persistence rule. Three fix directions (see full lane report in session history): (1) real Glk screen-state persistence, needs a Glk graphics display-list concept first since AppGlk only holds a rendered canvas today; (2) clear+push evtype_Redraw on mismatch, honest but leaves text panels blank since Glk can't ask a game to reprint a window; (3) re-key old content onto new ids, wrong. User needs to decide direction before dispatching a fix. Diagnostic harness and full captures saved outside the worktree at the session scratchpad (repro-harness.rs, diag.txt, diag2.txt, diag3.txt) since nothing was committed.

--- note 2026-09-16T04:07:06Z ---

2026-09-15 follow-up reading of the diag3 capture + code, ahead of choosing a fix direction:
- AppGlk's put_text_attr / grid_put_attr use entry(win).or_default(), so the game's OWN writes to a restored (unknown-to-backend) id DO land — the backend does not drop them. Restored windows are empty only until the game next writes them.
- glulx_session.rs restore_state delivers NO Arrange/Redraw after the model swap unless a resize happened to be deferred (apply_deferred_resize is a no-op otherwise). Machine::rearrange() (relayout + Arrange, and Redraw for graphics windows) already exists and is what a resize uses.
- In the lane's harness, a plain `look` after the restore left every panel (grid 113, buffers 101/81/…, all graphics) still empty — but that harness never delivered an Arrange, so it does not tell us whether Kerkerkruip would repaint on one.
- Glulx spec §1.8.5 (quoted in SQ-0556's notes) says window contents are never part of a save and the game must cope; the Redraw/Arrange handler is the game's own "recipe".
Middle path to evaluate before any display-list work: after the swap, drop backend content for ids absent from the restored model, then rearrange() + drive. DECIDING EXPERIMENT (cheap, reuse scratchpad repro-harness.rs): restore the user's archive into a fresh session, then Engine::resize to a different size (or call rearrange), settle, and dump panels — if Kerkerkruip's grid/buffers/graphics repopulate, the middle path is the fix; if only graphics do, the text-panel gap is the real remaining question.
