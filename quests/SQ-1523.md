--- note 2026-09-16T15:04:33Z ---

Investigated 2026-09-16, root cause confirmed, not yet fixed.

zvm-cli's 60 is the wrong number; lanthorn's picker 68 is correct. Verified by attaching LostTreasures2.iso directly (hdiutil) and confirming the actual disk contents: 8 titles have both a DOS and a Mac build on this release (A Mind Forever Voyaging, Border Zone, Bureaucracy, Cutthroats, Hollywood Hijinx, Nord and Bert, Plundered Hearts, Trinity), same as every other title on the disc. `cargo run -p lanthorn-zvm-cli --bin zvm-cli -- treasures/ISOs/LostTreasures2.iso` (mounted directly, no widening) correctly lists all 14 builds on that one disk. `cargo run -p lanthorn-zvm-cli --bin zvm-cli -- treasures/ISOs/LostTreasures1.iso` (which must widen across to LT2) drops the Mac build of exactly those 8 titles, landing at 60 instead of 68.

Root cause: crates/cli-host/src/disk_set.rs `stories_across_the_release`'s sibling-volume fold dedupes on `seen: Vec<(u16, String)>` — release and serial only, no machine/medium. These 8 titles are Infocom's later "combined build" era: the exact same Z-code bytes (same release+serial) were shipped for both DOS and Mac. When the function widens from LT1 to sibling LT2 and walks `sibling.stories()` (which itself correctly returns BOTH machines' builds — the per-disk mount does not fold across machines), the DOS entry gets pushed and its (release, serial) recorded in `seen`; the Mac entry immediately following in the same list collides on that key and is silently dropped, even though it is a different DiskImage/machine and a real row (this is exactly the "keyed on the machine as well as the build" principle the module's own doc comment on `stories_across_the_release` and picker.rs's `dedupe_within_a_volume` doc both already state, SQ-0878 — just not applied here).

Lanthorn's picker never hits this bug because it doesn't call `stories_across_the_release` at all for a directory scan: `scan_stories` iterates every sibling file in the directory independently (each via `resolve_entries`/`hints::mounted_stories`, which reads one disk's own native `disk.stories()` with no cross-machine fold), then `dedupe_within_sets` (keyed since SQ-1517 on `(set_idx, disk_image, ifid)`) correctly collapses only genuine cross-disk repeats of the same build+machine. `stories_across_the_release` is the ONLY caller-facing function with the bug, and it is what zvm-cli/gvm-cli/scott-cli's single-file-argument invocation depends on to widen across a release's siblings.

Fix direction: key `seen` (both its seed from `out` and the per-sibling insertion/check) on `(blorb::medium::DiskImage, u16, String)` instead of `(u16, String)`, using each story's own `image_for(&s.name)` (already computed for the `Reachable`'s `image` field — reuse it rather than calling twice). Verify against the real fixture, not just the two titles measured above: with the fix, `zvm-cli -- treasures/ISOs/LostTreasures1.iso` (no --story) should report 68 total, matching lanthorn's picker exactly, and the per-title menu should show 2 entries for all 34 titles except any that genuinely have only one build (re-verify against the real disk if the count doesn't land on 68 exactly — do not assume 68 is right without rechecking, this note is a lead not a spec). Also check gvm-cli/scott-cli for the same call path in case any Glulx/Scott compilation disk set exhibits the same shared-build-across-machines shape.

Do NOT regress the genuine cross-disk dedup this function also does (SQ-0941's Zork Zero pages identically across both floppies of a 2-disk set) — that case must still fold, and it will, since same build AND same image/machine still collide under the corrected key.
