--- note 2026-10-15T07:05:48Z ---

Findings at e7fe99050 (crates/app/src/fetch_worker.rs, ifid.rs):
- ifid::compute_ifid gives a Scott database with no embedded UUID `SCOTT-<fnv1a64>` (and UUID-less Glulx `GLULX-<fnv1a64>`). IFDB lists Treaty IFIDs (file MD5 for these formats), never our hash.
- link_from_store (unforced) links only via ifdb_store::tuid_for_ifid(cat, ifid) -> never matches a SCOTT- id. So a whole-library `r` sends one request per Scott COPY (each fetched via scott_ifdb_id's filename-stem table -> fetch_by_id), not one per game.
- link_listed_copies (SQ-1787, `f`) matches by tuid_for_ifid(t.ifid) == tuid -> never links other Scott copies.
Infocom works because ZCODE-release-serial-checksum is the Treaty form IFDB lists; Inform games with an embedded UUID work too.
Suggested fix: treat a Scott story's mapped TUID (picker::scott_tuid(stem), as scott_ifdb_id resolves it, incl. zip/disk entry stems) as its identity for linking: in fetch_one, when scott_id resolves to a tuid already in the store (unforced: current record; forced: fetched_this_run), link instead of requesting; in link_listed_copies, also link targets whose scott_ifdb_id == tuid. Avoid opening every story file for the check where the scan already knows it is Scott. UUID-less Glulx has no such table: either compute the Treaty MD5 IFID as an extra lookup key (app may take a dep) or leave it — decide at review.
Tests: two Scott copies of adv01 (raw .dat + inside a zip) -> library `r` makes ONE request and links the other; `f` on one links the other; a Scott game not in the table is unaffected.
