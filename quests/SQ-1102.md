## Where the three engines stand

Measured 2026-08-27, after SQ-1040 landed:

| engine | vocabulary | grammar | state |
|---|---|---|---|
| **Z-machine** | `zvm::dictionary` | **`zvm::grammar`** (SQ-1040) | done — 5 table shapes, verified against `infodump` over 97 files |
| **Scott Adams** | `scott::Database::{verbs, nouns, match_verb, match_noun}` | n/a — a two-word parser, the grammar IS `VERB NOUN` | **already done, for free**; SQ-1041/1042 can consume it today |
| **Glulx** | **none** | **none** | `grep -rln "dictionary\|grammar\|vocab" crates/gvm/src/` returns **nothing** |

So Glulx is the one engine the assist set cannot reach at all.

## Why it matters more than the corpus count suggests

`stories/` holds 94 Z-machine files against 10 Glulx — but the Glulx ten are
`CounterfeitMonkey-11`, `cragne`, `Kerkerkruip` (×2), `Eat_Me`, `Dr Ludwig and the
Devil`, `Game of Worlds Tournament`, `MidnightSwordfight` and kin. **They are the
modern games.**

SQ-1045's product goal is "make IF more accessible and less frustrating for people
who don't have nostalgia for these games". Someone arriving without nostalgia is at
least as likely to start with *Counterfeit Monkey* as with *Zork* — so the engine with
the fewest files is arguably the one where the assist features do the most good, and
today it is the one where they do nothing.

## Why it is mostly reuse

The tables are **the same Inform formats** SQ-1040 already reads — GV1 and GV2, the
same token values, `ENDIT`, the `$400` REVERSE bit, the same verb/preposition
numbering. Inform 6 emits them for both targets from the same compiler.

What differs is not the format but the **container**: Glulx is a different memory
model with 32-bit addressing, a different header, and no Z-machine packed-address
convention. `zvm::grammar::Grammar::load` takes `&zvm::Memory`; the equivalent needs
`&gvm::Memory`.

**The design question that should be settled before any code:** does the parser become
generic over a byte source, or is there a second copy in `gvm`? A hand-maintained
second copy of a table parser is exactly the shape CLAUDE.md's refactoring policy warns
about, and this project has been bitten by it repeatedly. But `zvm` and `gvm` share
nothing today and both take ZERO external dependencies, so a shared crate is not free
either. Options, none obviously right: a trait over "read a byte / read a word at an
address" that both memories implement; a third crate; or the parser taking a `&[u8]`
plus a base address and an addressing mode. Decide deliberately, and record the reason.

Note SQ-1040's `Grammar` deliberately returns a **self-contained snapshot** — no
borrowed memory afterwards — which was chosen for embedders and happens to make a
shared-parser design much easier. The output type may well need no change at all.

## Where Glulx's grammar table lives is the real unknown

SQ-1040's reader assumes the Z-machine convention that the grammar table sits at the
base of static memory. That assumption is Z-machine-specific and almost certainly does
not carry. Glulx's header names its own segments; whether the verb table is findable
from them, or whether it needs the same forward scan, is the thing to establish first —
and it is the same question that defeated **SQ-1101** (modern Inform 7 on the
Z-machine), where the address is not recorded anywhere and both lanthorn and
`infodump` decline.

If it turns out Glulx has the same problem, say so early: that would make SQ-1101 and
this quest one problem with one answer, rather than two.

## Verify against a source, never from memory

The rule that governed SQ-1040 governs this: a unit test sharing the implementation's
wrong assumption passes anyway. SQ-1040 worked from the **Inform Technical Manual
§§8.5-8.6** (fetched, not recalled) and **ztools `showverb.c` / `tx.h`**, and validated
against `infodump` — including exporting its own synthetic tables to disk and putting
those through infodump, so the oracle was itself validated.

`infodump` reads Z-machine files only, so **that oracle does not exist here**. Say what
you used instead. Glulx's own tooling and the Glulx specification are the places to
look, and the absence of a reference implementation is itself a finding worth
reporting.
