Investigated, no code change shipped — genuinely ambiguous, needs a product decision.

Empirically probed real reachable (no printed name) objects across King of Shreds and Patches, Superluminal Vagrant Twin, and Anchorhead (gitignored stories/, via contents()/room_objects() same as production). Findings:

- WordRoles' `noun` dictionary bit is useless here: true on every word in every object tested (including "john" and Inform's own kind-plural filler words), so there is no parts-of-speech signal to lean on.
- "Pick the LAST word" (mirroring typeable_name's own existing printed-name rule "the noun is the last word") fixes the reported case cleanly: King of Shreds' letter -> "letter" (was "john"), printworks key -> "key" (was "printwork").
- But "last word" is NOT universally better: Anchorhead's umbrella object has words ["umbrella","things","green","handle","brolly","bumbersho"] (bumbersho = truncated "bumbershoot", 9 chars = that story's dict cap). Last word is the truncated fragment "bumbersho" -- a regression. Worse: this EXACT object is the subject of a deliberate, already-shipped regression test from SQ-1659/1662 (crates/app/tests/suites/item_tracking.rs::anchorhead_inventory_dock_shows_the_clean_registry_name_not_the_joined_word_list) that hard-pins the correct answer as "umbrella" -- the FIRST word -- because a real user reported seeing the raw joined list ("umbrella things green handle brolly bumbersho") and SQ-1662 fixed it to show "umbrella" cleanly.
- A refined "last word, excluding words whose length equals truncated_at" still fails this test (picks "brolly", not "umbrella").
- Also found that Inform 7's Standard Rules inject kind-plural filler words ("things" confirmed directly; likely "people"/"containers"/etc. by analogy but unverified) into individual objects' own word lists at unpredictable positions -- not reliably first or last -- so no position-based rule is safe in general.
- No positional heuristic (first, last, longest, shortest, apostrophe-exclusion, truncation-cap-exclusion) satisfies both the King of Shreds case (wants late/non-first word) and the Anchorhead case (wants the first word, already deliberately tested) without a hand-built, ultimately guessed exception list.

Per this quest's own brief ("if genuinely ambiguous... STOP and report... do not commit a guess"), no code was changed; the worktree was left clean. A real fix likely needs either (a) accepting the King of Shreds imperfection as a low-priority cosmetic residual, or (b) threading the turn's own prose into typeable_name's fallback the way session.rs's item_tracker_display_name already does for its own last-resort pick (grep that for prior art) -- a materially bigger change touching inventory_click_words/inventory_items_with_keys/command_band.rs call sites, not a fit for this quest's "keep it simple" scope.
