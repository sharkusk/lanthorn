## A fourth control: the view switch (user, 2026-08-30)

Add a **view-map** control alongside the other three — switching between the normal map view and **matrix** view.

Worth noting how it differs from its neighbours, because it changes what the control has to express. Toggle-room-numbers is a boolean, centre-map is a one-shot action, and zoom is a scalar. The view switch is a *mode*, and lanthorn already has a precedent for exactly that on the story pane: `ControlGlyphs`' `render_hybrid` / `render_raster` / `render_extended` is a three-state control drawn from one icon family (`md-monitor`, `md-monitor_shimmer`, `md-monitor_star`) precisely so a mode change reads as a shape change rather than a weight change. The view switch should follow that pattern.

One thing to settle when this is picked up: `MapView::Matrix` is a **derived default** (`layer.rs:57`), not a mode the player selects — a maze layer resolves to it. So a manual control has to decide what it means to switch away from a view the map chose for you, and whether the player's choice then sticks for that layer or is re-derived on the next crossing. That is a state question, not a rendering one, and it wants answering before any glyph is picked.

--- note 2026-08-30T21:39:59Z ---

DECIDED by the user, 2026-08-30 — the state question this quest said had to be answered before any glyph was picked.

**A manual view switch STICKS PER LAYER and is remembered.** Switching away from a
derived `MapView::Matrix` becomes an override for THAT layer, and re-entering the
layer later keeps what the player chose. Derivation (`layer.rs:57`) supplies only
the INITIAL value for a layer nobody has ruled on; once a player has ruled, the
derivation no longer speaks for that layer.

Consequences to build to, rather than discover:

- The override is per-layer state on the MAP, so it belongs with the map's own
  persisted state and rides into a save with it. A player who chose a view for a
  maze and reloads should find it still chosen.
- "Nobody has ruled" and "ruled, and chose the derived value" are DIFFERENT states
  and must be stored differently. If a player explicitly picks Matrix on a layer
  that already derived Matrix, and the layer later stops deriving Matrix, their
  choice still stands. Storing `Option<MapView>` where `None` means unruled gets
  this right; storing the resolved view alone does not.
- Rejected: per-visit (re-derives on return, which silently undoes a deliberate
  choice and reads as a bug) and one global session override (simplest state, but
  fixing the view on one maze changes how every other layer draws).

The rest of the quest stands: four controls — toggle room numbers (boolean), centre
map (one-shot), zoom (scalar), view switch (MODE). The view switch follows
`ControlGlyphs`' three-state precedent from the story pane
(`render_hybrid`/`render_raster`/`render_extended`, one icon family so a mode change
reads as a shape change rather than a weight change), and every control is
styleable via `style.toml` per the standing rule.

Ready to dispatch. Trailer: `Confirm: SQ-1148` — border controls are a look and a
feel.

## The shape-rule departure, recorded rather than left to be inferred

This is the FIRST two-mode control on a pane border whose state is carried by
colour rather than by shape. `return_probe` and `reveal` are not the precedent —
they are single-glyph because they have no opposite mode to draw, and room
numbers do have one. The exception was taken for coverage and legibility, not
inherited from theirs.

Colour-only was considered and accepted because it is not in fact colour-only:
`panel.control:lit` is `alert` PLUS BOLD (registry.rs:282,
`mods(true, false, false, false)`), so a colour-blind player or a low-contrast
theme still reads a WEIGHT change; and the default pair is `muted` = DarkGray
against `alert` = Yellow, which separate by BRIGHTNESS in every standard ANSI
palette rather than by hue. That BOLD is already asserted by
`every_on_state_is_lit_from_the_alert_role_and_every_off_state_is_muted`, and
commit ad313557 writes the whole trade into that case's doc — including that
dropping the BOLD assertion is what would make room numbers unreadable, so it is
not the redundant line beside the colour check that it looks like.

PATCHED preset keeps the distinct pairs and the PLAIN preset collapses.**

    plain    room_numbers_on '#'                room_numbers_off '#'
             view_matrix     'M'                view_drawn       'M'

    patched  room_numbers_on md-numeric F03A0   room_numbers_off md-numeric_off F19D3
             view_matrix     md-grid    F02C1   view_drawn       md-grid_off    F02C2

The house rule is that a two-mode control changes SHAPE. A patched font can
express that, so the patched preset obeys it outright. ASCII cannot — it has no
off-shape for a `#` or an `M`, and Geometric Shapes offers none better covered
than the on-shape. So colour-carries-state in the plain preset is a
**DEGRADATION forced by a vocabulary, not a new house pattern**, and the type's
doc now says that once at the cluster rather than twice as separate exceptions.

**`md-numeric_off` (U+F19D3) is RESTORED.** 77f4a700 dropped it on the argument
that a patched pair against a plain single would make the presets disagree about
what the control IS; that sign-off is withdrawn. All seven codepoints re-verified
by the SQ-1141 method before shipping — name→codepoint, reverse lookup unique,
non-empty outline — **7/7 across every patched -Regular family installed here.**

## What now exists

Five controls on the MAP pane's bottom border — `┤# ¤ − + M├`, numbers · centre
· out · in · view — through SQ-1123's mechanism. `BorderControl` gained
`RoomNumbers`, `Centre`, `ZoomOut`, `ZoomIn`, `ViewMode`; `map_controls_for(state,
view)` builds them; both panes' hits land in one `border_controls_out`, so
`control_at`, the click dispatch and the hover hint are unchanged code paths.

## The two strains in the existing shape, solved rather than routed around

**1. `command()` widened to `ControlCommand { name: &'static str, arg:
Option<&'static str> }`** with a `Display` that spells the line. Both halves are
load-bearing and neither is recoverable from the other: `slash::COMMANDS` is
keyed by `name` alone, so the `Context` lookup must have it unqualified, and
`zoom-map` bare is an ERROR, so what a click puts through the pipeline is the
whole line. Returning one string every caller re-splits was the alternative and
has nothing to fail if a caller forgets.

The knock-on nobody had flagged: **key routes must match the whole line too.**
`Keymap::primary_key` matches the command NAME, `+` is bound to `zoom-map in`
and comes first, so a name lookup answers `+` for zoom OUT as well — a hint
advertising a key that does not reach the control, exactly the defect SQ-1142
fixed. Added `Keymap::primary_key_exact`, and the leader-panel lookup switches
on `arg` the same way. `no_hint_advertises_a_key_that_is_not_bound` now walks
both clusters and would have caught it.

**2. `placement()` was pane-relative and said nothing about the pane.**
`BorderControl::pane() -> ControlPane { Story, Map }`, read from the control
rather than implied by the list it was found in, plus
`every_control_is_drawn_on_the_pane_it_says_it_rides`. Without it a map control
listed by `controls_for` would compete for the story pane's `BottomCentre` anchor
and fail as a layout oddity rather than an error.

## Placement and state readings

All five are ONE centred group on the map pane's bottom border — none of them
points anywhere, they all act on the pane they are drawn on (guidance's and the
reveal's reasoning), and one group means the cluster stands or falls whole rather
than half of it surviving a narrowing. The top border keeps the layer tabs.

They may live on a pane that disappears where the return probe could not
(SQ-1107): every one acts on a map that is on screen, so there is nothing to
switch when there is no map. Written into the module doc.

Lit readings: room numbers lit when shown; view lit on MATRIX (the drawn map is
how a layer arrives, so it reads as idle — the v6 render cycle's `hybrid`
reading); centre and the two zooms are one-shots and never lit, because a lit
one-shot claims a state it does not have.

`persists()` is FALSE for all five, and the reason is written at the site rather
than left as a group: centre and zoom are one-shots, room numbers is a session
flag seeded from the global `show_room_numbers`, and **the view switch DOES
remember — in the map archive, per layer** (`LayerMeta.view`), which is a
different store from the per-game sidecar that method is about. Answering `true`
would point the guard at a sidecar that will never hold it. `the_reveal_is_a_trigger_and_says_so`'s
"only one trigger" claim is now scoped to the story pane and states this beside it.

## Per-layer view: used, not overwritten

`/view-map` bare already did exactly the decided thing, so the click runs it and
nothing new was written. Drawing the cluster only READS `effective_view`;
`the_view_control_rules_one_layer_and_only_by_being_clicked` asserts a render
leaves `layer_view_choice` at `None` and that a click writes `Some(_)` on the
active layer alone. `None` vs `Some(derived value)` survives.

## The test shape, which is the point of this round

`main::draw_story_panel`'s body moved into
`controls::draw_pane_with_controls` — both panes go through it, one place for the
zero-area filter, and (the reason it is in the LIBRARY) a cluster drawn only from
`main` is a cluster no test can render. That is the mechanical cause of the three
lost rounds, not just the missing case.

SIX cases fail when the map pane draws no cluster — falsified by stripping
`map_controls_for` and the main.rs call and watching them go red:

- `the_map_pane_draws_its_own_control_cluster` — the non-vacuity case. Spelled as
  GLYPHS (`┤# ¤ − + M├`) rather than counted, because a count passes on five of
  anything; also asserts each hit is on the bottom row, off both corners, and
  reachable through `control_at`.
- `main_draws_the_map_pane_through_the_control_seam` — a source guard, because
  `main` is a binary and the reversion is one line. It reads the 500 chars
  BEFORE the map pane's own `area: pane_layout.map`, since the hover-hint path
  also names `map_controls_for` and a whole-file `contains` would pass a bare
  border. That weakness was found by the falsification, not by review.
- `every_map_control_runs_the_command_that_does_its_job` — each click's line

  toggle both ways, out-then-in returns to the starting zoom (which one cycling
  slot could not), centre moves `scroll` and clears `char_pan`, view switches.
- `the_view_control_rules_one_layer_and_only_by_being_clicked`
- `room_numbers_and_the_view_switch_carry_their_state_in_colour` — the lit/muted

- `the_patched_preset_changes_shape_where_the_plain_one_changes_colour`

pane guard. The registry, persistence, pane and hint guards all walk BOTH
