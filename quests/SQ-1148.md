## A fourth control: the view switch (user, 2026-08-30)

Add a **view-map** control alongside the other three — switching between the normal map view and **matrix** view.

Worth noting how it differs from its neighbours, because it changes what the control has to express. Toggle-room-numbers is a boolean, centre-map is a one-shot action, and zoom is a scalar. The view switch is a *mode*, and lanthorn already has a precedent for exactly that on the story pane: `ControlGlyphs`' `render_hybrid` / `render_raster` / `render_extended` is a three-state control drawn from one icon family (`md-monitor`, `md-monitor_shimmer`, `md-monitor_star`) precisely so a mode change reads as a shape change rather than a weight change. The view switch should follow that pattern.

One thing to settle when this is picked up: `MapView::Matrix` is a **derived default** (`layer.rs:57`), not a mode the player selects — a maze layer resolves to it. So a manual control has to decide what it means to switch away from a view the map chose for you, and whether the player's choice then sticks for that layer or is re-derived on the next crossing. That is a state question, not a rendering one, and it wants answering before any glyph is picked.

--- note 2026-08-30T21:39:59Z ---

DECIDED by the user, 2026-08-30 — the state question this quest said had to be answered before any glyph was picked.

**A manual view switch STICKS PER LAYER and is remembered.** Switching away from a
derived `MapView::Matrix` becomes an override for THAT layer, and re-entering the
layer later keeps what the player chose. Derivation (`layer.rs:57`) supplies only
the INITIAL value for a layer nobody has ruled on; once a player has ruled, the
derivation no longer speaks for that layer.

Consequences to build to, rather than discover:

- The override is per-layer state on the MAP, so it belongs with the map's own
  persisted state and rides into a save with it. A player who chose a view for a
  maze and reloads should find it still chosen.
- "Nobody has ruled" and "ruled, and chose the derived value" are DIFFERENT states
  and must be stored differently. If a player explicitly picks Matrix on a layer
  that already derived Matrix, and the layer later stops deriving Matrix, their
  choice still stands. Storing `Option<MapView>` where `None` means unruled gets
  this right; storing the resolved view alone does not.
- Rejected: per-visit (re-derives on return, which silently undoes a deliberate
  choice and reads as a bug) and one global session override (simplest state, but
  fixing the view on one maze changes how every other layer draws).

The rest of the quest stands: four controls — toggle room numbers (boolean), centre
map (one-shot), zoom (scalar), view switch (MODE). The view switch follows
`ControlGlyphs`' three-state precedent from the story pane
(`render_hybrid`/`render_raster`/`render_extended`, one icon family so a mode change
reads as a shape change rather than a weight change), and every control is
styleable via `style.toml` per the standing rule.

Ready to dispatch. Trailer: `Confirm: SQ-1148` — border controls are a look and a
feel.

Reasoning per slot: № says "number" in one mark and · is the label collapsed to

is a ring with four spokes, i.e. a reticle; it is the well-covered lookalike of
⌖ POSITION INDICATOR, which is the semantically perfect mark and is carried by
exactly ONE of sixteen faces. − and + need no learning and are the two best-
covered characters in the survey. ╬ and ┼ are ONE family (box-drawing crosses)
and the mode change is a SHAPE change — one junction becomes a lattice, not a
heavier stroke — which is the rule ControlGlyphs states for its own pairs; and
they are the map's own alphabet, since the drawn map IS junctions and the matrix
IS rows and columns.

None of the seven collides with the thirteen taken. Every one beats the median
of the shipped set. Drawn in all five stock faces, Set A loses exactly one glyph
in one face (╬ in Monaco) — see the second PNG.

## Findings for whoever implements the cluster

- The DECIDED per-layer state is ALREADY BUILT. `mapper::layer::LayerMeta.view:
  Option<MapView>` exists with `None` = unruled, `#[serde(default)]` so it rides
  the save, and `effective_view()` = `view.unwrap_or(if maze { Matrix } else {
  Drawn })`. That is exactly the model this quest decided on, shipped under
  SQ-0666. No state work is needed.
- All five commands already exist in `slash::COMMANDS`: `toggle-room-numbers`,
  `center-map`, `zoom-map out`, `zoom-map in`, `view-map` (bare cycles).
- NO NEW STYLE SELECTOR IS NEEDED. `panel.control`, `panel.control:lit` and
  `panel.control:hover` are pane-neutral and already cover a second cluster.
- What IS still blocked on symbols.rs: a glyph home. Wanted shape is a
  `MapControlGlyphs` beside `ControlGlyphs`, seven fields (`numbers_on`,
  `numbers_off`, `centre`, `zoom_out`, `zoom_in`, `view_matrix`, `view_drawn`),
  presets "plain" (Set A above) and "nerdfont" (the seven verified codepoints),
  resolved from the same `control_icons` key so the font check reaches it — the
  way `TipGlyphs` already shares that key.
- `BorderControl::command()` returns a BARE command string, and zoom needs an
  ARGUMENT (`zoom-map in` / `zoom-map out`). Whoever adds the map cluster has to
  widen that return, and `every_control_names_a_real_bare_slash_command` in the
  border_controls suite reads it.
- `toggle-room-numbers` has no leader letter, so once the cluster lands the
  border control is the only route to it besides typing the command.

## The shape-rule departure, recorded rather than left to be inferred

This is the FIRST two-mode control on a pane border whose state is carried by
colour rather than by shape. `return_probe` and `reveal` are not the precedent —
they are single-glyph because they have no opposite mode to draw, and room
numbers do have one. The exception was taken for coverage and legibility, not
inherited from theirs.

Colour-only was considered and accepted because it is not in fact colour-only:
`panel.control:lit` is `alert` PLUS BOLD (registry.rs:282,
`mods(true, false, false, false)`), so a colour-blind player or a low-contrast
theme still reads a WEIGHT change; and the default pair is `muted` = DarkGray
against `alert` = Yellow, which separate by BRIGHTNESS in every standard ANSI
palette rather than by hue. That BOLD is already asserted by
`every_on_state_is_lit_from_the_alert_role_and_every_off_state_is_muted`, and
commit ad313557 writes the whole trade into that case's doc — including that
dropping the BOLD assertion is what would make room numbers unreadable, so it is
not the redundant line beside the colour check that it looks like.
