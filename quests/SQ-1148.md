## A fourth control: the view switch (user, 2026-08-30)

Add a **view-map** control alongside the other three — switching between the normal map view and **matrix** view.

Worth noting how it differs from its neighbours, because it changes what the control has to express. Toggle-room-numbers is a boolean, centre-map is a one-shot action, and zoom is a scalar. The view switch is a *mode*, and lanthorn already has a precedent for exactly that on the story pane: `ControlGlyphs`' `render_hybrid` / `render_raster` / `render_extended` is a three-state control drawn from one icon family (`md-monitor`, `md-monitor_shimmer`, `md-monitor_star`) precisely so a mode change reads as a shape change rather than a weight change. The view switch should follow that pattern.

One thing to settle when this is picked up: `MapView::Matrix` is a **derived default** (`layer.rs:57`), not a mode the player selects — a maze layer resolves to it. So a manual control has to decide what it means to switch away from a view the map chose for you, and whether the player's choice then sticks for that layer or is re-derived on the next crossing. That is a state question, not a rendering one, and it wants answering before any glyph is picked.

--- note 2026-08-30T21:39:59Z ---

DECIDED by the user, 2026-08-30 — the state question this quest said had to be answered before any glyph was picked.

**A manual view switch STICKS PER LAYER and is remembered.** Switching away from a
derived `MapView::Matrix` becomes an override for THAT layer, and re-entering the
layer later keeps what the player chose. Derivation (`layer.rs:57`) supplies only
the INITIAL value for a layer nobody has ruled on; once a player has ruled, the
derivation no longer speaks for that layer.

Consequences to build to, rather than discover:

- The override is per-layer state on the MAP, so it belongs with the map's own
  persisted state and rides into a save with it. A player who chose a view for a
  maze and reloads should find it still chosen.
- "Nobody has ruled" and "ruled, and chose the derived value" are DIFFERENT states
  and must be stored differently. If a player explicitly picks Matrix on a layer
  that already derived Matrix, and the layer later stops deriving Matrix, their
  choice still stands. Storing `Option<MapView>` where `None` means unruled gets
  this right; storing the resolved view alone does not.
- Rejected: per-visit (re-derives on return, which silently undoes a deliberate
  choice and reads as a bug) and one global session override (simplest state, but
  fixing the view on one maze changes how every other layer draws).

The rest of the quest stands: four controls — toggle room numbers (boolean), centre
map (one-shot), zoom (scalar), view switch (MODE). The view switch follows
`ControlGlyphs`' three-state precedent from the story pane
(`render_hybrid`/`render_raster`/`render_extended`, one icon family so a mode change
reads as a shape change rather than a weight change), and every control is
styleable via `style.toml` per the standing rule.

Ready to dispatch. Trailer: `Confirm: SQ-1148` — border controls are a look and a
feel.

PLACEMENT, stated explicitly by the user 2026-08-30 because the previous note could be misread: **all four controls go on the BOTTOM BORDER OF THE MAP PANE.** They are not added to the story pane's existing cluster, and they do not move it.

The story pane's cluster is referenced in this quest for ONE reason only — the
three-state `ControlGlyphs` pattern (`render_hybrid` / `render_raster` /
`render_extended`, one icon family so a mode change reads as a shape change rather
than a weight change) is the precedent the view switch should FOLLOW. That is a
borrowed pattern, not a shared location. Toggle-room-numbers, centre-map, zoom and
the view switch all live on the map pane's own bottom border, beside each other.

So the map pane gets its own control cluster, built on SQ-1123's clickable
pane-border mechanism, exactly as the story pane has one. Two clusters, one
mechanism.

GLYPHS — surveyed against the user's own installed fonts and decided with them, 2026-08-30. Do not re-derive these; they are measured, not proposed.

## Patched (nerdfont) candidates, VERIFIED

Read from each font's own `cmap` under its own glyph name across the NINE patched
families installed here (0xProto, FiraCode, IosevkaTerm, JetBrainsMono, ProggyClean,
SauceCodePro, SymbolsNerdFont and friends). Every entry below resolves in ALL nine at
the SAME codepoint:

| control | kind | glyph name | codepoint |
|---|---|---|---|
| room numbers ON | boolean | `md-numeric` | U+F03A0 |
| room numbers OFF | boolean | `md-numeric_off` | U+F19D3 |
| centre map | one-shot | `md-crosshairs` | U+F01A3 |
| zoom out | one-shot | `md-magnify_minus` | U+F034A |
| zoom in | one-shot | `md-magnify_plus` | U+F034B |
| view = matrix | mode | `md-grid` | U+F02C1 |
| view = normal | mode | `md-grid_off` | U+F02C2 |

`md-grid` / `md-grid_off` is the pair to use for the view switch: ONE family, so the
mode change reads as a shape change rather than a weight change — the rule
`ControlGlyphs` states for `render_hybrid`/`raster`/`extended`. Do not pair a map
glyph against a grid glyph; two families is exactly what that rule forbids.

Still verify these yourself before shipping (SQ-1045 — the codepoint comes from the
font, never from a note, and that includes THIS note): confirm the name resolves,
the reverse lookup is unique, and the glyph rasterises with real ink at the size the
border actually draws. SQ-1159's method is the model, and it rejected
`md-alpha_z_box_outline` on exactly that last check.

## ZOOM — DECIDED by the user: TWO controls, − and +

`md-magnify_minus` and `md-magnify_plus` as two adjacent ONE-SHOT triggers, each lit
briefly on click the way `reveal` is. Directly manipulable and reversible.

So the cluster is FIVE slots, not four: numbers · centre · − · + · view.

Rejected: one control that cycles (one slot, but no way back except all the way
round, and the glyph cannot show which level you are on), and one control with a
mouse-wheel affordance (reversible but invisible — a player who never scrolls over
it never finds it).

Note this makes zoom the set's first SCALAR, and it is expressed as two triggers
rather than as a state report. That is consistent: `return_probe` and `reveal` are
already single-glyph controls precisely because they report no state.
