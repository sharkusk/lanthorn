--- note 2026-09-09T00:18:36Z ---

Reproduced headlessly and fixed.

ROOT CAUSE (not Glulx-specific in mechanism, only in incidence): `startup.rs`'s opening-banner arm was `state.pager.arm(0)`, so `pager::activation_target` counted the blank rows a story opens with as output the reader must not miss. Every Inform 7 Glulx story prints two or three newlines before its prologue (measured: chlorophyll 3, Magpie 3, Anchorhead 3, Kerkerkruip 3, Eat_Me 3, CounterfeitMonkey 4, advent.blb 6), and on a pane where the prose fits exactly, those blanks are the WHOLE overflow.

Measured before the fix (real renderer, `render_story_pane`):
- chlorophyll.gblorb 80x30: total_rows=31, viewport_rows=29, prompt_rows=1, leading blank rows=3 -> engage, park scroll=3.
- Alias 'The Magpie'.gblorb 120x44: total_rows=44, viewport_rows=42 (2-row status grid), leading blank rows=3 -> engage, park scroll=3.

Both overflow by exactly two rows and the overflow is entirely the blanks. The parked frame (dumped cell-by-cell) puts the three BLANK rows across the top of the screen and pushes three rows of real prose below the fold — strictly worse than not paging — and, with a `Line` read pending, `input::key_to_command`'s pager gate turns the player's first character into `Action::PagerDismiss`. That is the report, including "plenty of screen remains": the screen the player is looking at literally opens with blank rows and still says [more].

Not SQ-1411/1416/1420. `pager.arm(0)` has stood since bfa50080 (2026-07-28, SQ-0532 wave-5) and is byte-identical in v0.4.2, v0.5.1 and v0.5.3, as is `activation_target`'s `added <= viewport_rows` rule. The scratchpad bisect binaries were not present, so the bisect is by source archaeology plus a behavioural falsification: running the current tree with the baseline forced back to 0 (v0.5.1's exact arithmetic) reproduces `pager.active == true` and the swallowed key on both games. Present in every release from v0.4.2 onward.

FIX: `pager::opening_baseline(&state)` — the banner arm starts at the first row of boot output carrying prose. A blank line wraps to exactly one row, so leading blank LINES count leading blank ROWS; a line carrying an inline image stops the count. Two lines of production change (`pager.rs` + the `startup.rs` call site). Mid-game arming, `baseline_before`, `activation_target` and SQ-1411's `baseline_stale` calibration are untouched.

Both metrics — total_rows and viewport_rows — were verified correct for the Glulx path (the status grid is excluded; win_rects show Grid 80x1 / Buffer 80x29 for chlorophyll and Grid 120x2 / Buffer 120x42 for Magpie). No Glk arrange, wintype_Blank or missing transcript surface is involved.

TESTS: `crates/app/tests/suites/sq1434_glulx_opening_pager.rs` in the `zmachine_screen` group — 5 cases. Both reproducers assert `!pager.active`, `transcript_scroll == 0` and that a typed `x` resolves to `Action::InputChar('x')` through both `key_to_action` and `key_to_command`, with non-vacuity guards pinning that the banner really did out-measure the viewport and that the overflow is entirely blanks. A third case pins the other half of the ruleset (Magpie at 80x30, where fifty rows of prologue genuinely overflow a 28-row viewport, still pages). A Mini-Zork I control (tracked fixture, runs on CI). A source guard asserts `startup.rs` arms via `opening_baseline` and not a literal, because the behavioural cases mirror the startup arm rather than calling that 2,000-line function and so cannot see the call site regress.

Falsified both ways: neutering `opening_baseline` to 0 fails both Glulx cases on "the pager must not engage"; reverting the call site to `arm(0)` fails the source guard with the offending line quoted.
