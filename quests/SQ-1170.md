## The measurement that prompted this

`style.example.toml` is generated from `REGISTRY`, so it documents a line for **181
rows**. Measured 2026-08-31:

| layer | count |
|---|---|
| rows the template documents | 181 |
| sections `toml_schema::parse` actually reads | all of them |
| rows that reach a real consumer | **179 / 181** |
| rows named in *some* test | 181 / 181 |
| rows proven END TO END (a style.toml string in, an observable effect out) | **14** |
| …of those, via the uncomment-the-shipped-file guard | **8** |

**The 181/181 is the misleading number.** It is the registry completeness tests naming
every row to prove it EXISTS. That is not the same claim as "setting it does
something", which is why a user's correct `[tooltip] background = { parent = ... }`
parsed, resolved, emitted no warning, and changed no pixel, with every test green.

## The guard already exists and is pointed at eight things

`style_example_toml_presets_take_effect_when_uncommented`
(`crates/app/src/style.rs:1424`) is the right shape and was written for exactly this
failure (SQ-0559 / SQ-0309, when documented keys turned out unreachable). It reads the
shipped `style.example.toml`, rewrites `# key = <default>` as `key = <non-default>`,
and asserts the value lands. It covers eight keys:

    box_style  arrow_set  path_style  portal_path_style  diagonal_corners
    badge_save  badge_hint  badge_hint_available

**Generalised to sweep every documented line it would have caught the tooltip defect
outright**, and both dead rows below.

## Two rows are DEAD — documented, parsed, read by nothing

    dialog.input_preview
    map.background

Zero references anywhere outside `registry.rs` and the template generator. Checked for
indirect lookups too: there is exactly one constructed selector family in the app
(`format!("glk.{win}.{name}")` at `render/mod.rs:217`) and no `theme.get(<variable>)`
route that could reach either. `dialog.input_preview`'s own comment says it styles an
`"Input: <text>_"` line that appears nowhere in the codebase.

Decide per row whether to WIRE it or RETIRE it — do not assume retire. `map.background`
may be a genuine gap (the map pane may simply never paint a ground), which is a
different fix from deleting the row.

## What to build

A test that, for EVERY key the generated template documents, uncomments it with a
non-default value and asserts the resolved theme/symbol set actually changed. Notes:

- **Drive it off the generator, not a hand-written list**, or it goes stale exactly the
  way the crate-list gate did (see CLAUDE.md on `--workspace`). A row added to
  `REGISTRY` must be covered without anyone remembering to add it.
- The per-kind assertion differs: `Kind::Style` rows want a colour/modifier change,
  `Kind::BorderGlyphs` a border style, `Kind::Placement`/glyph-set rows a preset swap,
  `Kind::GlyphSet` an override. Route by the row's `Kind` rather than special-casing
  names.
- **Choosing a non-default value generically is the hard part.** For a colour, any
  colour the default is not. For a preset, any other member of that preset's set —
  which means asking the preset type for its members rather than hardcoding a second
  name.
- Rows that legitimately cannot be asserted this way should be named in an explicit
  ALLOW-LIST with a reason each, so the exemption is visible and reviewable rather than
  a silent gap. Keep that list as short as you can defend.
- The `parent` channel needs its own coverage: today it is one case
  (`user_parent_reroot_override_resolves`) on `panel.title`, whose Delta is
  `Delta::EMPTY` and which therefore cannot expose SQ-1169's pin-masks-parent bug.
  `a_reroot_moves_the_colours_of_a_row_that_used_to_pin_them` now covers the shape for
  one row only.

## Relationship to SQ-1169

**SQ-1169 is the resolver-semantics defect** (a `parent` re-root is a no-op on the
seven rows that still pin an fg/bg) and is UNSETTLED — three options written up there,
the user's call. This quest is the COVERAGE that makes such defects visible.

They overlap: a generalised sweep that exercises `parent` on every row would fail on
SQ-1169's seven rows. Whoever does this should expect that and coordinate — either
land the sweep with those seven allow-listed and a pointer to SQ-1169, or wait for
SQ-1169's decision. Do not silently "fix" the seven by picking one of SQ-1169's
options; that decision is the user's.
