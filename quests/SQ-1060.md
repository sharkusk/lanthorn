--- note 2026-08-24T22:08:54Z ---

THE COMMENT. `crates/app/src/render/screen.rs:7069-7074`, on `stamp_runs_over_art`:

    /// Colour comes from [`v6_layout::chrome_run_ink`], **the same rule that decides
    /// what the RASTER would have drawn, so the glyph is the rasterised glyph made
    /// crisp rather than a second opinion about it.**

The RULE (`chrome_run_ink`) is genuinely shared. What is not shared is the ARGUMENT it is asked with, and SQ-1052 changed it on one side only.

BOTH SIDES.

  RASTER, after SQ-1052 (commit 6d4937a4) — crates/app/src/render/v6_layout.rs:1699-1712:
      for ch in t.text.chars() {
          let adv = tf.advance_styled(ch, t.style);
          ...
          let span_w = adv.max(font_w);
          let (fg, bg) = chrome_run_ink(t, ..., || region_has_opaque(&art, pen, py, span_w, font_h));
          ...
          pen += adv;
      }
  Per GLYPH, at the pen, one advance wide.

  CELL PATH — crates/app/src/render/screen.rs:7146-7153:
      let span_w = t.text.chars().count().max(1) as u32 * font_w;
      let (px0, py) = (t.x.max(1) as u32 - 1, t.y.max(1) as u32 - 1);
      let (ink, block) = chrome_run_ink(t, ..., || region_has_opaque(gfx, px0, py, span_w, font_h));
  Per RUN, at the declared origin, `chars * cell.w` wide — the exact expression SQ-1052 removed. Its own comment at :7112-7114 says so deliberately: "Grouped by run rather than flattened so the colour rule — whose over-art arm costs a region scan — is asked ONCE per run and not once per character."

A third spelling of the same question sits at screen.rs:6272-6277 (`ChromeRowOracle::over_art`, `self.v6_cell.run_px(&t.text)`), also per run. Those are now the only two production callers of `V6Cell::run_px` (the DECLARED span) left in the tree; `V6Metric::run_px` / `TextFace::run_px` (the PEN) is the other method of the same name, which is its own trap.

OBSERVABLE DEFECT, AND ITS LIMITS — stated honestly.

`region_has_opaque` answers "is ANY pixel in this rectangle opaque?", so asked of a whole run one stray opaque pixel anywhere beneath it decides for every cell. A chrome run that straddles the edge of the frame art therefore resolves its block once for its whole length in the cell path and per cell in the raster: same frame, same game, two backends, two ribbons. That is SQ-1052's symptom, in hybrid.

Two things bound the blast radius, and neither makes it inert:
  * `stamp_runs_over_art` fires only when `backend_layers_glyphs_over_art(picker)` is true, and that is `ProtocolType::Halfblocks` ALONE (screen.rs:7024-7026). Kitty and sixel — the user's own terminals per MEMORY — never reach it. `ChromeRowOracle::over_art` is not so gated, but it classifies a whole terminal ROW, where a single answer per row is the model rather than a defect.
  * `pen_chains` — the joining that turned SQ-1052 from harmless into visible — runs only on the raster path (`v6_layout.rs:1607`, `:1873`; no caller in screen.rs). So the cell path still sees a v6 grid's one-run-per-character publication, where per-run and per-glyph coincide. What is left exposed is a game printing a genuinely multi-character `px_text` across the art boundary (Arthur's map captions and inventory column labels are the shape to look at).

NOT EXHIBITED ON A REAL FRAME. The divergence is confirmed by reading both sides; a specific mis-rendered capture is not. Settling it needs a half-blocks harness driving a frame whose chrome run straddles opaque art, compared against the same frame in raster — cheapest is probably a synthetic canvas in the style of `v6_layout`'s own SQ-1052 case (`the_over_art_question_belongs_to_a_glyph_not_to_a_joined_chain`, added in 5a0e19a1), which was written precisely because real Macintosh media needs a boot disk the repo cannot carry.

SUGGESTED FIX (not applied — audit lane). Either ask per cell in `stamp_runs_over_art` — the loop already walks `cells` one at a time and already looks `ground` up per cell, so the block arm can join it — or, if the per-run grouping is kept for the region-scan cost the comment cites, amend the doc so it stops promising equivalence with a raster that no longer answers the same way.
