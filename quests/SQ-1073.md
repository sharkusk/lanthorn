## What broke

Reported live on both Shogun presses, both render paths: the score and move
counts render into the story area instead of the status band.

Measured on `stories/James Clavell's Shogun.adf` (Amiga, r295/890321), one `look`
from a fresh boot, window 1's painted runs:

```
before (HEAD~1)                     after SQ-1071, broken
 1 503 48 "Score:"                   1 503 48 "Score:"
 1 586  8 "0"      <- the value      1 586  8 " "       <- a pad space
17 503 48 "Moves:"                  17 503 48 "Moves:"
17 586  8 "1"                       17 586  8 " "
                                    33  47  8 "1"      <- wrapped OUT of the band
```

Window 1 is 548 px at native (47,1), so its right edge is 594 and the game
right-aligns each value to the last column — native 586..593, ending exactly on
that edge.

## Why

`limit_px` was `grid.cols * cell.w`. **548 is 68.5 cells**, so the limit came out
68 * 8 = **544**, four pixels short of the window. The final glyph ended at
window-relative 547 against a 544 limit, tripped the character wrap, and the value
printed after it went to the next line — off the bottom of a two-row band and into
the story.

The comment that code carried predicted this in as many words:

> **If a declared width is ever chosen that does NOT divide, this has to become
> the window's own `x_size - right_margin`**

Shogun had chosen one all along. Nothing consulted the limit on that window until
SQ-1071 gave the Amiga a wrap regime, so a latent defect became a visible one on
the first live run.

## Fix

`limit_px` is the window's own `x_size - right_margin`, in pixels — the right
margin included because §8.8.3.2.1 puts it there ("if a window has character
wrapping, then text is clipped to stay inside the left and right margins"). The
CLIP bound stays the window's bare edge, because that branch is the window with no
wrapping.

`limit_cols` is that pixel limit rounded UP to a cell, so the column measure never
binds before the pixel one on the partial cell a non-dividing width leaves: 548 px
is 69 columns of which the last is half a cell, and the pixel limit is what stops a
glyph from using it.

Verified: both presses' bands are byte-identical to `HEAD~1` again, and the two
`v6_hint_clue_wrap` cases still match their captures (the Amiga clue breaks at 500
px either way; 496 and 500 fall between the same two words).

## The coverage gap this exposed

**The full gate was green with the score in the wrong place.** No suite pins the
value's position — `v6_shogun_status_alignment` pins the labels and the columns,
not the right-aligned numerals. A case that does is part of this quest.
