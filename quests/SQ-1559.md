Current code (rev a64394b5):
- crates/app/src/input.rs:3495 `Action::ConfigSave` applies a saved config to the live game inline: sets `state.config`, lowers the `_base` values (`honor_game_colours_base` and the SQ-1161 bases), releases one-run holds (SQ-0860: `game_colours_cli`, `artwork_declines_colours`), rebuilds the sound sink / `pending_vm_sound`, mirrors `show_status_bar`/`show_room_numbers` onto AppState, reconciles the style watcher, then reloads style.
- None of that is callable from outside the TUI's key handler, so a non-terminal host that edits config.toml (or a per-game sidecar) while a game runs has to copy this logic key by key — and drift from the TUI the next time a key gains a base or a pin.

Change: move the body into the lib as a host-facing function, e.g. `host::settings::apply(state: &mut AppState, global: Config, per_game: Option<&PerGameConfig>)` (name/shape your call), returning what changed (at least: whether a style reload / full repaint happened, whether Glulx window borders changed so the host can relay out). `Action::ConfigSave` calls it. Per-game overrides (the `.save/config.toml` sidecar) should layer exactly as they do at boot.

Acceptance:
- Lib test: with a running AppState, applying a config that flips `honor_game_colours`, `guidance`, `show_room_numbers`, `period_look` and a per-game `guidance` override leaves the same AppState as the TUI's ConfigSave path does (compare the relevant fields), and a one-run hold on an untouched key survives.
- TUI's ConfigSave behaviour unchanged (existing tests pass).
