## FONT 524 is Monaco, not the body face

A Macintosh `FONT` id is **family x 128 + size**. So:

    FONT  512  = family 4, size 0    the FOND family-name record (no bitmap)
    FONT  524  = family 4, size 12   ** Monaco 12 **
    FONT 1033  = family 8, size 9    the font-3 graphics set (SQ-1017)

Family 4 is Monaco, the classic monospaced Mac face, and `mac/xzip.lst` names it
in exactly that role:

    ZSTD:  TextFont (stdFont)      { stdFont := geneva }
    ZALT:  TextFont (8)
    ZMONO: TextFont (monaco)

**So SQ-1011 gave the Macintosh its ZMONO alternate to draw body text with.** That
was a real improvement over `vga16` — a 7x15 face for a 7x15 cell, blitting 1:1
where the 8-wide substitute crowded — and it is still not the face the machine
used.

## The machine painted proportionally, and that is measured

`machine-screenshots/mac-zorkzero-hint.png`: the same `WING` glyph run starts at
**x=137 in `EAST WING` and x=139 in `WEST WING`**, because `W` is wider than `E`
(SQ-0917). No uniform 7-wide face can produce a 2 px difference between two runs
of the same four trailing characters.

`colWidth := 7` is therefore Geneva's AVERAGE ADVANCE declared to the story, and
the declared-versus-drawn split is the same one Arthur's Amiga press turned out to
have — a proportional face painted under a fixed declared metric. That parallel is
not a coincidence; it is how both machines worked.

Our parser reporting `proportional=true` for 524 is the accented-range artifact
SQ-0916 documented: over printable ASCII its advance is uniformly 7, which is why
`native_font::fit` classifies it `Cell`. That classification is CORRECT for
Monaco. The defect is upstream of it — Monaco is the wrong face to be reaching for.

## The blocker: Geneva is a system font

`font_scout` over `InfocomMasterpieces.img` (ARTHUR FOLDER) lists every `FONT` on
the platter: 512, 524, 1033, and nothing else, in every application's fork. There
is no Geneva. There cannot be — `stdFont := geneva` resolves against the SYSTEM
file, present on every Macintosh and shipped with none of these games.

So unlike the Amiga, whose typeface is a file on its own floppy, the Macintosh's
body face cannot be recovered from the media at all.

## Routes, and none of them is obvious

1. **An open-source proportional substitute at 7x15**, chosen the way SQ-1016
   chose misc-fixed 7x14 — by licence first and metrics second. Geneva's own
   advances would need approximating, and a substitute with different advances
   declared under `colWidth := 7` reproduces the machine's SHAPE (proportional
   under a fixed declared metric) without reproducing its widths.
2. **Keep Monaco and say so.** It is a face the release genuinely shipped, it fits
   the cell exactly, and it is honest as long as the docs stop implying it is what
   the machine drew. Cheapest, and defensible.
3. **Synthesise Geneva's metrics from captures.** The hint screen gives per-glyph
   evidence, but recovering 94 advances from screenshots is a large job with a
   fabrication risk this repo has been bitten by.

Do not start any of them before SQ-1009's Amiga pen lands: the Macintosh cannot be
drawn proportionally until the pen exists, and the pen's design (grid column
decoupled from pixel cursor) is what makes it possible at all.

Landed in eab12272 by route 4, which none of the three above anticipated: **read the real Geneva off a user-supplied System disk** (SQ-1037's cascade), so there is no substitute to choose and no metrics to synthesise.

## The thing that turned out to be missing from the analysis above

The note reads as if Geneva should simply REPLACE Monaco. It must not. `machine-screenshots/mac-zorkzero-game.png` (Zork Zero r296/881019 off `stories/Zork Zero Disk.image`, twelve turns in) shows BOTH faces on one screen:

* the status bar's `Banquet Hall` steps a **uniform 7 px** per character — ink runs at image x = 70, 77, 84, 91, 98, 105, 112, then `H` at 126 after the blank;
* the prose two lines below advances **7, 7, 5** through `n`, `o`, `t`, and runs `nother frantic day at the castle; Lord Dimwit` from x = 169 to x = 448 — **280 px of ink for 44 characters**, where any 7-wide pen gives 308.

So `mac/xzip.lst`'s three selectors are not decoration: ZSTD (geneva) and ZMONO (monaco) are both live, and adopting Geneva alone would have regressed every status bar on the machine from correct to wrong. `FONT` 524 was never the wrong face — it was the right face in the wrong ROLE.

**How the two are told apart, and it is not the style word.** Zork Zero brackets its whole bar in `@set_font 4` / `@set_font 1` and leaves `text_style` at zero throughout, so a run carries nothing to distinguish it. `exec.rs` now folds font 4 into §8.7.1's fixed-pitch bit (`v6_run_style`), which is the standard's own name for exactly this request — a story asks for fixed pitch two ways (`@set_text_style 8`, or font 4) and means one thing. Everything downstream then asks one question: `V6Metric::advance` for the pen, `TextFace::face_for` for the face.

## What the declared cell does: nothing

Geneva 12 is fifteen rows and `mac/xzip.lst` declares `lineHeight := 15`, so the declared cell comes out 7x15 either way and the story's grid is untouched. That only holds through the TEXT scale (SQ-1039) — the colour press's `CPic.data` art scale of (2, 2) would declare it as thirty. Pinned on both presses in `system_face_cascade::geneva_leaves_the_declared_cell_alone_on_both_macintosh_presses`; reverting to the art scale fails the COLOUR press alone, exactly as SQ-1039 predicted.

The size is chosen BY the declared line height rather than guessed: a System 6.0.8 disk carries Geneva at 9, 10, 12, 14, 18, 20 and 24 point, and fifteen rows picks 12. `machine-screenshots/mac-zorkzero-game.png` measures consecutive prose baselines at y = 136, 151, 166, 181, 196, 211 — the same 15.

## Verification against the capture

Booted off `stories/Zork Zero Disk.image` with the user's own `MacOS_6.0.8_System_Startup.img`: body = `FONT 396` (15x15, proportional), fixed alternate = `FONT 524` (7x15), declared cell 7x15. The resolved pen measures that prose line at **282 px** against the capture's **280 px of ink** — the two-pixel difference being the first glyph's left bearing and the last one's trailing gap, neither of which a capture can show.

**Awaiting the user's eye** on the rendered frame, which is what a typeface always needs.
