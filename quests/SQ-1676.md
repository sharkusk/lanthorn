--- note 2026-10-02T14:16:51Z ---

Goal: one install serving several players in a household (each with their own saves, map, history and per-game settings) while IFDB metadata and covers are fetched once and shared.

Today: a game's info.json and cover.png live inside its save folder (<user dir>/saves/<story-key>.save/, e.g. cover.rs reads game_dir.join("cover.png")), next to the saves, map.json and per-game config.toml. So metadata and play progress share one folder, and two players cannot share metadata without also sharing saves.

Request (host-facing, keep TUI behaviour unchanged by default):
1. A metadata/catalogue location separate from the save folder: e.g. a configurable catalogue dir (default = the save folder, so the TUI and existing installs keep today's layout) that holds per-story info.json, cover.png and the IFDB link/relink state; all readers and writers of that metadata (cover.rs, ifdb.rs, ifdb_search.rs, metadata_import.rs, library listing) go through one resolver taking (catalogue dir, story key).
2. A per-player root: a way to run the lib with saves/maps/history/per-game config under a per-player directory (e.g. <data>/users/<player>/saves/...) and global settings layered as shared defaults + per-player overrides, without forking config.rs logic in each host.
3. Atomic writes for catalogue files, since two players may refresh the same story's metadata at once.
4. Migration: an existing single-player layout seeds the catalogue (copy/move info.json + cover.png out of each save folder) and becomes the first player, idempotently.
5. Lanthorn's own Docker serve mode (docker/web-session.js keys a ttyd session by a visitor token) could use the same split: per-visitor (or per-profile) save roots with one shared catalogue, instead of every visitor re-fetching IFDB data. Whether that mode should grow simple household profiles (a 'who is playing?' picker, optional PIN, stored server-side) instead of browser tokens is worth deciding there; a host-side profile store is enough for the lib.
Out of scope for the lib: login/profile UI, which is per host.

--- note 2026-10-02T14:20:09Z ---

Revised, preferred shape (replaces items 1 and 4 above; keeps full backwards compatibility, no migration):
- The DEFAULT player keeps today's layout exactly: <user dir>/saves/<story-key>.save/ holds saves, map, history, per-game config.toml AND info.json/cover.png/IFDB link state. The TUI and existing installs are unchanged.
- Additional players get their own save root, e.g. <user dir>/users/<player>/saves/<story-key>.save/, holding only per-player state: saves, map, history and their own per-game config.toml.
- Shared metadata for every player is read from and written to the DEFAULT player's save folder for that story key (so a fetch by any player lands where the default player sees it too). The lib change is one setting: where a session's metadata lives, defaulting to its own save folder; a host points non-default players at the default player's save root.
- Consequences to handle in the lib: (a) any action that deletes a whole save folder for the default player must keep info.json/cover.png/IFDB state, since other players depend on them (deleting saves only is fine); (b) a non-default player opening a story the default player never played creates a metadata-only folder under the default player's saves (harmless); (c) anything that lists games by scanning save folders must not rely on a non-default player's folder holding metadata.
Still wanted from the original list: per-player roots (item 2, now as above), layered global settings (shared defaults + per-player overrides), atomic writes for the shared metadata files (item 3), and the note about Lanthorn's Docker serve mode (item 5).

--- note 2026-10-02T14:25:15Z ---

Maintainer decision 2026-10-02 on layout: keep the existing structure. The catalogue (info.json, cover.png, IFDB link state) and the DEFAULT player's data stay in ~/.lanthorn/saves/<story>.save/. Non-default players live under ~/.lanthorn/users/<name>/. Reason: toggling between single- and multi-user must never produce two different structures or move files.

Coordinator's proposed refinement (not yet confirmed): users/<name>/ mirrors ~/.lanthorn's per-player shape, i.e. its own saves/<story>.save/ (saves, map, history, per-game config.toml) plus its own config.toml as per-player overrides layered over ~/.lanthorn/config.toml. One code path then serves both roots.

Consequences to implement (from the revised note): default-player deletes and resets keep catalogue files; metadata-only folders may appear under default saves; the library/catalogue always reads ~/.lanthorn/saves/. Still open: the full inventory of ~/.lanthorn files sorted into shared vs per-player (style.toml, keybindings, auto-resume, archive, fonts, command history…), and the Docker player picker (SQ-1318).
