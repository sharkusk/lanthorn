## Two defects, and the second is the one that matters

SQ-1121 shipped with this measured table:

| story | probes | time |
|---|---|---|
| Zork I r88 (.z3) | 4 then 10 | 12 ms an offer, boot included |
| Coloratura (Glulx, 1.4 MiB) | 2 | 26 ms |
| Counterfeit Monkey (Glulx, 11 MiB) | — | **2.1 s** to boot, **227 ms** a probe |

CM is declined entirely: the seam pays the boot once, latches `too_slow`, and
never vets again that session.

### 1. The boot measures the wrong thing (user, 2026-08-28)

**"Counterfeit Monkey boots quickly with the correct persistent data in place.
This was specifically debugged and diagnosed."**

Acceleration is NOT the explanation — `ShadowRecipe.acceleration` exists and its
own doc says off "would make the shadow's boot minutes long", so 2.1 s is the
*accelerated* figure.

The cause is that the shadow **boots from the story bytes**
(`hints::extract_story` → per-engine constructor), paying CM's full
initialisation, where the live session reaches the same place far faster. That
choice was inherited from the abandoned `return_probe.rs` and never questioned.

Find what the live path actually does — the earlier debugging is the record to
recover — and boot the shadow the same way. If the answer is that a snapshot can
be restored into a cheaply-constructed VM without replaying initialisation, the
2.1 s largely disappears and the `too_slow` latch stops firing on the corpus's
biggest game.

### 2. 400 ms on the MAIN THREAD is wrong at any size

`BUDGET` is 400 ms per offer, spent between the player's command and the game's
reply. Even Zork I's 12 ms is main-thread time bought for a feature that is
optional. **A budget is a cap on a stall, not a fix for one.**

Move probing off the main thread. This is the project's stated direction already
— *only the story interpreter belongs on the main thread* — and the transcript
can take a late arrival: `insert_above_prompt_at` (SQ-0270) already places an
app-generated line above the prompt, which is how the assist lands today. The
game's reply prints immediately; the offer arrives a beat later.

Doing this well probably retires `too_slow` as a concept. A slow game would
simply answer later, or not before the player types again — in which case drop
it silently, which is the existing silence discipline rather than a new rule.

## Watch for

- **A late offer must not attach to the wrong turn.** If the player has typed
  again, the answer is stale — discard rather than print.
- **The live engine must stay untouched**, which SQ-1121 proved for the
  synchronous case (`the_live_session_is_left_exactly_where_it_was`,
  `a_probe_writes_nothing_anywhere`). Threading must not weaken it; those cases
  should still pass unchanged.
- **Keep the measurements honest.** Re-measure all three stories after the boot
  change and report the new table beside the old, rather than asserting it is
  faster.

Related: [[SQ-1121]] built the seam; [[SQ-0785]] and [[SQ-1043]] want the same
fork-and-probe facility and inherit whatever this lands.

## Can a late line be inserted while the player is typing? Yes — checked

The mechanism exists and assists already use it synchronously, so this is new
*timing*, not new machinery.

`AppState::insert_above_prompt_at` (`state.rs:4329`):

```rust
(!self.config.command_bar && self.last_transcript_line_is_story())
    .then(|| self.transcript.len().saturating_sub(1))
```

**In-progress input is not in the transcript.**
`append_to_last_transcript_line` is called from exactly one place — `turn.rs:106`,
at submission. Until Enter, what the player typed lives in `state.input.value`
and is drawn as an overlay on the prompt line. So the last transcript line is
still the game's `>` line (`Story` kind), the guard passes, and the assist goes
**above** it without touching the typed text.

The pane is bottom-anchored, so inserting above the prompt scrolls *history* up
rather than pushing the prompt down — **the cursor does not move.**

In command-bar mode the guard's `!command_bar` fails, the line appends at the end
of the transcript, and the input is a separate widget nothing disturbs. Cleaner
again.

## The real risk is the WRAP CACHE, not the visuals

`touch_transcript(TranscriptEdit)` — its own doc says the argument "is the
difference between the wrap cache extending its rows and throwing them away
(SQ-1034)". An insert-above-prompt is **not** an append, so it invalidates the
cache and re-wraps.

Today that cost is paid inside a turn the player is already waiting on. Moved to
a background completion it lands **while they are typing**, which on a long
transcript in a narrow pane is exactly where a hitch would be felt.

**Measure this before shipping**: re-wrap time against transcript length at a
narrow width, and decide whether a late insert needs to defer to a keystroke gap.
Do not assume it is free because the synchronous version feels fine — the
synchronous version is hidden inside a turn.

## Two more things to get right

- **Scrolled-up players.** If the player has scrolled back to read, a late insert
  must not yank the view to the bottom. The existing scroll handling covers the
  synchronous case; confirm it still holds when the insert arrives unprompted.
- **Staleness is still yours to solve.** [[SQ-1125]] (a prompt-anchored hint,
  which would have made lateness invisible) is **parked** pending real use, so
  this quest must drop an offer that arrives after the player has typed again
  rather than printing it against the wrong turn.
