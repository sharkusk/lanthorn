--- note 2026-09-30T17:58:15Z ---

Validated empirically against the real stories/CounterfeitMonkey-11.gblorb before scoping: booted, took the R-remover, found its parent object (the true avatar) directly from the live object tree — that object's short_name is empty and it has NO readable parse-word array (names.of(mem, parent) == None), confirming it's exactly the player `find_player` can't see statically. Scanned the SAME 64KB globals window glulx_roomlock already scans for `location` (from ramstart) for any word holding that exact address: found exactly 2 candidate globals (ramstart+0x114, ramstart+0x12c), both stable across a subsequent `look` turn. Two is the expected shape (Inform's library keeps `player` plus something like `actor`/`real_location` both aliasing the avatar) — not noise, and either candidate resolves to the right object.

SCOPE, chosen over full parse_name bytecode interpretation: port glulx_roomlock's "learn a global by observation, no story-specific knowledge" technique to a second global identifying the PLAYER instead of the room. Key difference from room-lock: `location` changes every room transition, giving room-lock many correlated events to score against; `player` is expected to be constant almost the whole game, so the SAME correlate-across-many-changes scoring won't apply directly. Needs a different, single-or-few-observation validation signal instead — e.g. after a confirmed "take" action, the taken item's new parent (in the live object tree) should equal the candidate global's value; a candidate whose value is a valid situated object of the story (same `is_object`/`parent().is_some()` checks find_player already makes) AND matches that containment fact on a confirmed take is strong, low-false-positive evidence requiring very few turns, not a long correlation window.

Land it as a fallback ONLY: GlulxSession::player_addr() already tries parse_names().find_player(...) first; when that returns None, consult a new PlayerLock (sibling to RoomLock in glulx_roomlock.rs, or its own module) the same way location_addr() falls through to the room-lock's learned address. Must not change behavior for any story where find_player already succeeds (Anchorhead, HHGG, etc. all currently work — this is purely a safety net for stories like CM where the static scan comes up empty). Persist the learned address in the per-game sidecar the same way the room lock's learned global is remembered, so a story only ever relearns once.

Real-game regression test: CM's R-remover must appear in TurnResult.items/carried inventory once this lands, where today it's silently absent on every turn. Plus non-regression across the existing corpus (Anchorhead, HHGG, and whatever else already has passing item-tracking suites) — this must never override a working find_player() result.
