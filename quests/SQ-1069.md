## What the capture settles

* **The story window is a real primary `Buffer`** (`attrs=1111`, `model: Buffer`), so SQ-1026's promoted-grid guard is not involved — the same finding as SQ-1056.
* **`0 prose line(s)` and `0 paint run(s)` on win0.** The clue text is not in the model as window content; in raster the prose comes from the HOST transcript through `build_main_text`. So the "random text" bleeding through is almost certainly *scrollback* — the transcript re-wrapped into the story box — rather than anything the game drew.
* **The face is Geneva 12, proportional, 3–11 px against a declared 7.** Same press as SQ-1054.
* **Same session shape as SQ-1056**: a long run of `hybrid-ring` frames and modal overlays, then `raster`.

## The user's own read, which is the useful part

> this along with 1056 shows we have some screen contention entering and exiting out of the hint menu system. perhaps the type of window changes? However, the fact that hybrid works shows that we are not following the same logic, so we may want to start by eliminating the duplicate logic between hybrid and raster when it comes to window management, clearing, etc.

That is worth taking seriously as the framing rather than treating this as a third isolated bug. **SQ-1056, SQ-1069 and SQ-1070 are all raster-only failures on the InvisiClues path**, and hybrid is right in every one. The two paths do already dispatch differently on the story surface — `render_node` sends a `Buffer` to `render_transcript` and a `Grid` to `draw_grid`, while `build_v6_raster_canvas` has its own chain of early-return arms plus the guard SQ-1026 added — and that duplication is exactly the shape CLAUDE.md's refactoring policy names.

**Do not start by unifying them.** Establish first, on one frame, *which* decision the two paths make differently — the clear, the story box, the prose source, or the scroll — and fix that. Then judge whether the remaining duplication should become one owner. A rewrite driven by "hybrid works and raster doesn't" without knowing which branch diverges is how the last several of these went wrong.

## Does NOT reproduce headlessly — and that is the finding

`stories/Zork Zero Disk.image` — Macintosh, **release 296 / serial 881019** —
booted the way `startup.rs` boots and driven `hint`, `y`, Return, Return, Return
(6 steps including 14 intro taps), with **every `TurnResult` mirrored into a real
`AppState` the way `turn.rs` does**. That last part is what every earlier
reproduction was missing: raster draws the story from the HOST TRANSCRIPT, and a
harness whose transcript is empty cannot show a transcript defect.

On the clue frame the raster path's own story box reads:

```
[5] w0=468x322@(87,79) attrs=1111 texts=0 streamed=2 prose=0 | story=Buffer(primary)
    raster: clear=Some((86,78,468,322)) prose_box=Some((86,78,468,322))
            metrics=RasterMetrics { total_rows: 46, viewport_rows: 20, max_scroll: 26, first_visible_row: 42 }
    raster story box 66x21, 4 line(s):
      | 1>
      | Just DIVE UNDER A TABLE when everyone else does.
      | [No more hints.]
      |
```

**The `1>` prompt is there, the clue is there, and nothing is bleeding.** The
clear anchor is recorded (`anchor=Some(29)`, from the turn's transcript elems,
not from `erase_lower`) and `first_visible_row: 42` is the anchored top — the
post-clear slice, four rows, correct.

Rendering a HYBRID frame first and the raster frame second, in the same
`AppState`, changes nothing: no shared per-frame state poisons the composite.

## What that retires

* Not the window classification. `win0` is a real primary `Buffer` on every frame
  of the route; SQ-1026's guard never fires here.
* Not the prose SOURCE. Both paths read the same host transcript through the same
  `wrap_cache`, and the raster windowing produces the right rows.
* Not the clear anchor, the scroll, or the early-return arms.
* **Not \"duplicate hybrid/raster window-management logic\".** On this frame the
  two paths agree. Whatever is wrong is BELOW the model — the composite's encode,
  its placement, or its lifetime in the terminal.

Same negative result on SQ-1056, on a different press, by the same method. Two
independent raster-only InvisiClues failures whose models are both correct is
itself the evidence: the shared cause is in the placement layer, not the layout.

## Where to go next

`crates/app/tests/pty_stream/` — CLAUDE.md names it for exactly this case (\"the
model looks right and the screen doesn't\"), and the placement oracle
(`pty_stream/oracle.rs`) for the layer under that. The specific question worth
asking it first, because it explains BOTH quests and nothing else does: lanthorn's
placements are VIRTUAL (`U=1`), positioned by `U+10EEEE` placeholder cells, so
**the image IS the cell's content — printing a glyph into a covered cell deletes
the image and truncates the rest of that row's run** (SQ-0944, measured). Both
reporters' session histories run through modal overlays (`cell — modal overlay
open: palette`) immediately before the failing raster frames, and the cell path
writes real glyphs across the whole pane.

Note the asymmetry that makes this plausible: the HYBRID branch has an explicit
resume guard (SQ-0587) —

```rust
if state.v6_path_log.borrow().last().is_none_or(|(l, _)| l != \"hybrid-ring\") {
    state.graphics_render.borrow_mut().invalidate_chrome_bands();
}
```

— documented as \"resuming the pixel path after ANY frame that did not use it …
the terminal no longer holds our placements, but every band is a cache hit and
would send nothing\". **The RASTER branch has no counterpart.** `redraw_v6` does
re-emit its placement every frame, so this is not a plain cache miss, but the
transition it guards is the same one both reporters passed through, and nobody has
measured what the raster arm actually leaves on the terminal across it.
