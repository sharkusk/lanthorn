--- note 2026-09-09T05:55:03Z ---

Investigated `if-archive/scott-adams/games/c64/mystadv.zip` (183 KB) directly (public C64 1541 disk-image format, not GPL): MYSTADV1.D64 and MYSTADV2.D64 each hold a `BOOT` PRG (loads at $0801, an ordinary tokenized BASIC `SYS` stub — unremarkable) plus one PRG per game (`BATON`, `TIME MACHINE`, `ARROW I/II`, `PULSAR 7`, `CIRCUS` on disk 1; `EXPERIMENT`, `WIZARD OF AKYRZ`, `PERSEUS`, `INDIANS`, `WAXWORKS` on disk 2 — 11 games total, matching the Spectrum corpus). BATON's PRG loads at $4000 and its first bytes are `4C E3 48 53 0D 00 00 00 ...` — a 6502 `JMP $48E3` followed by a long run of zero bytes.

That's NOT a recognisable signature for a known third-party disk cruncher (Exomizer, Pucrunch, etc. all have distinctive, longer decompressor stub code at the load address) — this quick probe found no evidence of one. Two live possibilities: (a) the PRG is just a raw, uncompressed 6502 program + data memory image (the JMP is the program's own entry vector, and the zero run is legitimately-empty workspace/BSS), or (b) it uses the SAME kind of in-house text/data encoding SQ-1452 found in the Spectrum releases (word-tokenized text, e.g. an "mGBATON" prefix byte pair before the plain item name "BATON") — a per-title interpreter convention, not a general disk cruncher, and therefore a much bigger reverse-engineering job than the publicly-documented `.z80` container was.

Before any C64 loader work starts: determine which. If it's genuinely raw/uncompressed, extraction may be nearly free (a `blorb`-side PRG reader handing `scott` the raw bytes at their load address — `crates/blorb/src/d64.rs` already reads D64 track/sector layout for Infocom releases and is the model, though it is Infocom-specific and won't recognise a Scott Adams disk as-is). If it's the in-house tokenization, that's a format with no public spec to write from — same GPL-avoidance constraint as SQ-1452, but no independent published document to lean on this time, so it likely needs black-box behavioural comparison (run a C64 emulator, diff against a `.dat` conversion) rather than a from-spec decoder. `scott` stays zero-dependency either way: any D64/PRG extraction belongs in a host (app or a CLI), not in this crate.
