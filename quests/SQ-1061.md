OBSERVABLE DEFECT. Launch a v3/v4/v5 game whose status routine lays itself out once at boot — Zork 1 is SQ-0680's own named case — in a story pane that is not 80 columns. It boots correct. Type `restart`. The status line comes back laid out for 80 columns, and `declared_story_screen_dims`' floor jumps to 80 with it. Nothing re-seeds afterwards: `loop_tick::poll_zvm_screen_dims` runs post-boot, which is precisely what SQ-0680 established is too late for a boot-time layout.

NOT FORCED. Every input is on `state` at the restart site. `startup.rs:188-209`'s `pre_boot_host_screen` has to build a synthetic `AppState` from `cfg` because it runs before there is one; at restart the real one is in hand, so `app::render::screen::story_screen_dims(pane_layout.story, state)` (or the already-published pane) answers directly.

SUGGESTED FIX (not applied — audit lane). Give `reset.rs` the same seed. Better, per the refactoring policy: `host_screen` is a per-boot fact exactly like the five `MachineBoot` already carries, and it is the sixth positional argument of an eight-argument constructor. Either fold it into `MachineBoot` or give `new_for_machine` a request struct — a hole in a positional list is how both this and SQ-1058 happened in the same call.

FALSIFY. Boot Zork 1 in a pane of, say, 60 columns; `/dump-windows` or read `$22`; `restart`; read again. 60 then 80 is the defect.

--- note 2026-08-24T22:40:38Z ---

## Fixed

`startup::pre_boot_host_screen` has been split. The part that queries the live terminal, computes the pane layout and asks `story_screen_dims` is now **`startup::host_story_screen(&AppState)`**; `pre_boot_host_screen` builds its synthetic state (it runs before a real one exists) and calls it, and **`reset.rs` calls it with the real one**. One implementation, two callers — rather than a bare `None` under a comment promising "the same four links `startup.rs` resolves, in the same order".

## Verified — two halves, and the second cannot be behavioural

`reset::tests::the_host_pane_reaches_a_boot_and_reset_still_seeds_one`.

**The mechanism**, pinned on a real story: `GameSession::new_for_machine` with `host_screen = Some((24, 60))` writes **`$21 = 60`**; with `None` it writes `DEFAULT_SCREEN_COLS`. So the argument is not inert.

The specimen is **`beyondzork-r57-s871221.z5`**, not Zork 1. Zork 1 is SQ-0680's own report, but §8.4 only writes the screen size into `$20`/`$21` from **Version 4** on, so a v3 header has no width to read — the first draft asserted `$21 == 60` against Zork 1 and got `0`. The fact under test is that the pane reaches the boot at all, and a v5 is what can show it.

**That reset SUPPLIES it** is a source-level guard, for the reason CLAUDE.md gives for `palette_lock_discipline`: the wrong spelling cannot be made unreachable here. `host_story_screen` asks the LIVE terminal and a test process has none — it answers `None` in-process whatever `reset.rs` passes, so a behavioural restart case would be green either way and would prove nothing. The guard therefore watches that the call still names the shared helper. Its needle is assembled from two string pieces, because `include_str!("reset.rs")` reads the file the guard is written in and a whole literal would match itself.

Falsified: putting `None` back drops the count from 1 to 0 and the case fails.

## Not done, deliberately

The audit's larger suggestion — fold `host_screen` into `MachineBoot`, or give `new_for_machine` a request struct — was not taken here. `host_screen` is a HOST fact, not a machine one, so `MachineBoot` ("everything `GameSession` needs to be told about the machine it is running on") is the wrong home for it, and a request struct for an eight-argument constructor is a wider change than these two quests. The positional hole that produced both this and SQ-1058 in one call is still there; it wants its own quest.
