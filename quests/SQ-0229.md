WHY IT WAS WORTH DOING: every pre-existing save test restores through gvm's OWN reader, so layout drift cancels out — a blob no foreign interpreter could read would still pass. These assert bytes against spec §1.8.

FORMAT VERIFIED SOUND (no bugs found — this is a guard, not a fix):
  - push_chunk pads odd chunks to even and reports the UNPADDED length; parse_ifzs skips `len & 1`. Writer and reader agree.
  - save_quetzal = FORM IFZS + IFhd(128=mem[0..128]) + CMem(4-byte memsize + RLE of XOR-vs-orig over [RAMSTART,memsize)) + Stks(stack[0..sp]) + MAll(heap_start + count + count*(addr,len)). No GReg/Glk — correct for interop.
  - save_state = the same four PLUS GReg + `Glk `. Note there are TWO writers: save_state (host snapshot, exec.rs ~1575) and save_quetzal (@save, ~1638). Interop concerns save_quetzal ONLY; the earlier quest note conflated them.

MUTATION-TESTED (do this for any future format test — it found a real hole):
  - MUTANT leak GReg into save_quetzal  -> caught.
  - MUTANT off-by-one in CMem zero-run  -> caught.
  - MUTANT drop the IFF pad byte        -> SURVIVED at first! Every chunk a real save emits is even-length (IFhd 128, MAll 8+8n, Stks 4-aligned), so the pad path never executed and the container assertion was vacuous. Fixed by testing push_chunk/parse_ifzs DIRECTLY on odd data; the mutant now dies.
  - The fixture must STEP the machine: a fresh one has a pristine RAM image, so the CMem diff is all zeroes and every diff assertion holds vacuously. A non-vacuity assert pins it.

TEST-HARNESS GOTCHAS for the next attempt: opcode 0x0123 is @save (returns StepResult::SaveRequest), NOT copy — copy is 0x40. asm::Op has no Imm; use C8/C16/C32/Mem8/Mem16/Mem32/Stack/Zero. machine_with_body(&[(4,2)], body) gives a start frame with locals and RAMSTART 0x100.
