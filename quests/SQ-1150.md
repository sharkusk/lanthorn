## What happens

`reveal::arm` has two tiers. The strong one asks `vocab::objects_in_scope`; the
weak one falls back to the story's dictionary parts-of-speech through
`state.vocab.get(engine)`. When **both** are unavailable it returns
`Armed::Nothing`:

```rust
None => {
    let Some(v) = state.vocab.get(engine) else {
        state.reveal = None;
        return Armed::Nothing;      // crates/app/src/reveal.rs
    };
```

and `slash_dispatch.rs` relays that as

```
[nothing on screen is a word this story takes]
```

`Armed::Nothing`'s own doc says it means "Nothing on screen is a word this story
would accept. A real answer — a room of pure scenery gives it". That is exactly
right for the case it was written for and **wrong** for the case above: a story
with no readable vocabulary takes plenty of words on screen, and we simply
cannot say which. One variant is carrying two meanings, and the one the player
is shown is a claim about the STORY that the app is in no position to make.

## Where it bites

Measured on the two Dialog stories of SQ-1101 (`stories/ImpossibleStairs.z8`,
`stories/frankenfingers_260330.z5`): both reach `Armed::Nothing` on a drawn
`look` frame, so `/reveal` tells the player their perfectly ordinary room
contains no word the story takes. Any story where `Grammar::load` refuses and
`ParseNames::detect` declines lands here — Dialog's whole output, and
`stories/advent.z8`, whose dictionary declares zero entries.

Journey and the conformance suites reach the same variant and the wording is
TRUE for them, which is why this has never looked wrong.

## The fix, and the layer it belongs in

A fourth `Armed` variant — `NoVocabulary`, or similar — returned from that
`else` branch, with its own status line saying the app cannot read this story's
words rather than asserting a fact about the room. The caller re-deriving the
reason instead (`state.vocab.get(...).is_none()` in `slash_dispatch`) would be
the hand-maintained cross-file invariant the refactoring policy warns about:
`reveal` knows why, and should say so.

`crates/app/tests/suites/dialog_story_degradation.rs` already drives both
specimens to this exact point and will accept either answer; tighten its
`the_reveal_arms_without_a_grammar_and_lights_nothing_false` case to demand the
new variant when this is fixed.

## Why filed rather than fixed

The SQ-1101 lane's brief assigned `crates/app/src/reveal.rs` to a concurrent
lane, so the one-variant change could not be made there without a conflict.
Nothing else about it is hard.

## Fixed — Lane B, branch `worktree-agent-a65bfd05e7c2f41a2`, commit `b8e39398`

**Still reproduced after SQ-1153.** Measured before touching anything, on a drawn
`look` frame: both Dialog specimens answer `armed=Nothing`, `vocab.get(...)=None`
AND `all_object_words()=None`. `stories/advent.z8` answers identically. SQ-1153
changed which flag bits are read, not whether a story HAS a readable dictionary,
so it could not have resolved this.

**The fix.** A fourth variant, `Armed::NoVocabulary`, returned from that `else`
branch; `slash_dispatch` gives it its own status line, draft wording:

    [lanthorn cannot read this story's words]

sitting beside `[nothing on screen is a word this story takes]` (the room) and
`[no story text on screen to read]` (the frame). The reason stays in `reveal`;
the caller never re-derives it.

**One change beyond the letter of the quest, and why.** The dictionary is now
fetched INSIDE the `None =>` arm of the objects/dictionary match rather than
above it. It is the second tier's input only, so a story whose OBJECTS answer was
being turned away for want of a dictionary it never needed — and had that been
reachable, the new variant would have been lying in exactly the way `Nothing`
was. No specimen in `stories/` exercises it today (every story that lands in the
fallback answers `None` to both), but it makes the variant true by construction
rather than by luck.

**Test.** `dialog_story_degradation::the_reveal_arms_without_a_grammar_and_lights_nothing_false`
now asserts `Armed::NoVocabulary` exactly, with the two-tier unavailability
asserted BEFORE arming so it cannot go vacuous. Falsified: reverting the variant
to `Nothing` fails it with the reported symptom.

Docs: `docs/features/customization.md` gains the honest answer beside the
reveal's other status lines.

**Aside, not touched (SQ-1101/SQ-1138 territory).** The same paragraph in
`customization.md` still says the reveal "has nothing to light in v6 **raster**
mode", which SQ-1138 made false — `reveal.rs`'s own module doc describes both
surfaces. Left alone as out of scope.
