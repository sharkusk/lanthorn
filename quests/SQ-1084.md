## Measured, in the cell-buffer render — so it is not a cast or SVG artifact

The suspicion was that `svg-term` was misplacing text. It is not: the same frame
rendered through the gallery's rasteriser puts the title in exactly the same
wrong place, and the gallery reads lanthorn's own cell buffer.

`stories/anchor.z8` (Anchorhead, release 5 / serial 990206), the opening frame at
zero keypresses, no map pane. The title is `A N C H O R H E A D`, 19 cells wide.
Measured off the rendered PNG, in cells:

| pane cols | title spans | its centre | pane centre |
|---:|---|---:|---:|
| 82 | 15.2 .. 33.8 | 24.5 | 41.0 |
| 100 | 15.1 .. 33.8 | 24.4 | 50.0 |
| 122 | 20.1 .. 38.8 | 29.4 | 61.0 |

**Two things are wrong here and the second is the interesting one.**

The title never reaches the pane's centre at any width — it sits roughly where it
would if the game had been told the screen were about 49 columns instead of 100.

And between 82 and 100 columns it does not move **at all** — same start column to
within a tenth of a cell — while between 100 and 122 it moves by five. A centring
that were merely computed against the wrong number would still slide with that
number. One that does not move across an 18-column change, and then does across a
22-column one, looks like a width that is being quantized or clamped somewhere
rather than passed through.

## Where to look, and what would settle it

The game centres by computing `(width - len) / 2` from the screen width in the
header, so the question is what lanthorn writes there and when — `write_screen_dims`
and the pane rect it is derived from. Suspect the story pane's usable width (the
border steals a column on each side) against the width the header advertises, and
whether a resize rewrites it.

**Check it against a reference rendition before fixing anything** (the standing
rule): Anchorhead in Frotz or Gargoyle at 100 columns says where the title is
supposed to land, and internal measurement cannot. It is possible — not likely at
these numbers, but possible — that the game indents rather than centres and every
frame here is correct.

Reported alongside this: the Beyond Zork Character Setup menu looks off-centre too,
on the Amiga floppy at 100x32, which would make this general rather than one
story's quirk. Worth confirming as a second specimen.

## Correction: the two renders were NOT independent witnesses

The note above claims this is lanthorn's rather than the renderer's because it
reproduces in the cell-buffer render as well as the SVG. That is overstated. Both
come out of the SAME pty harness — `tests/pty_stream/driver.rs`. The gallery
rasterises the cell buffer the harness decoded; the cast serialises the same byte
stream. What was actually established is **"not svg-term"**, and nothing more.

A harness-level cause fits every measurement here. The standing rule in CLAUDE.md
is about exactly this shape — boot a harness the way `startup.rs` boots or you
measure a screen the app never draws — and it has been written down so far only
for the v6 chain (profile, `native_std_window`, `art_scale`). Whether a TEXT-ONLY
game has an equivalent chain the harness skips is an open question, and is the
first thing to check. **Reproduce in the real binary, by eye, before touching any
code.**

## The mechanism that would let this hide

lanthorn re-wraps prose: the transcript is reflowed to the pane through
`render::wrap_cache::raster_wrap_refresh`. Centring is not reflowable — it is
spaces the GAME emitted, computed from the screen width in the header, and they
land wherever that arithmetic put them.

So a wrong advertised width would be **invisible in every paragraph and visible
on every centred line**: titles, menus, boxed epigraphs. That is precisely the
reported pattern (Anchorhead's title and Beyond Zork's Character Setup menu, with
prose looking correct in both). It also means the defect cannot be found by
reading a transcript — only by measuring a column.

## What would settle it, cheapest first

1. Run the real binary: `lanthorn stories/anchor.z8` in a 100-column terminal and
   look at where `A N C H O R H E A D` sits. If it is centred, this is the
   harness and the quest is about the harness.
2. `/dump-terminal` — it reports what lanthorn measured against what it guessed;
   compare the width it advertises against the pane it drew.
3. Only then, against a reference rendition (Frotz, Gargoyle) at the same width,
   per the standing rule — to rule out the possibility that the game indents
   rather than centres and every frame is right.

The one datum that survives whichever way it goes: at 82 and 100 columns the
title starts at the same column to within a tenth of a cell. A centring computed
from a merely wrong width would still slide with the width. (Discount the 122
figure in the table above — that PNG came out 1048px tall against 1064, so the
sampled row band probably caught different content.)

## It is the harness, and the signature is "decoupled", not "miscalculated"

The user runs `anchor.z8` locally and the title IS centred (2026-08-26). So
production is fine and the pty harness is not. Everything below is measured on
`stories/anchor.z8`, opening frame, title `A N C H O R H E A D` = 19 cells.

**The one positive finding.** The width the game is told behaves as a CONSTANT of
about 49 columns, and does not track the pane at all:

| varied | title starts | implied screen width |
|---|---|---|
| pane 82 cols | 15.2 | 49.2 |
| pane 100 cols | 15.1 | 49.1 |
| kitty cell 16x32 | 15.1 | 49.1 |
| half-block cell 10x20 | 15.1 | 49.2 |
| map hidden | 15.1 | 49.1 |
| **map shown** | **15.1** | **49.1** |

The last pair is the sharp one. Showing the map halves the story pane, and the
number does not move by a single cell — so the pane width is not reaching the
story at all in the harness. A wrong-but-derived width would still have moved.

**Hypotheses tested and FALSIFIED — do not spend time on these again:**

- *svg-term is misplacing the text.* No: the gallery's rasteriser puts it in the
  same column. (This only ever proved "not the SVG"; the gallery and the cast
  share `driver.rs`, so they were never independent witnesses.)
- *Cell pixel size leaks into a text-only game's width.* No: identical at 16x32
  and at 10x20. For a text-only story the cell is irrelevant, as it should be.
- *The map pane / `split_ratio` is being counted when the map is hidden.* No: see
  the table — the number is the same either way.
- *The harness pins a virtual screen.* No: `gallery.rs:609` writes only
  `random_seed` (plus `v6_render` for a raster shot), and the cast tool the same.
  No `virtual_screen_cols` anywhere in `tests/pty_stream/` or `examples/`.
- *`FALLBACK_SCREEN_COLS`.* It is 80, and 80 would put the title at column 30.5.
  zvm's own fallback is 80x24 too. Neither produces 49.

**Where to look next.** `startup.rs:188` `pre_boot_host_screen` → `host_story_screen`
is what seeds the boot width, and `startup.rs:855` re-writes it only when a
virtual-screen key is set. The harness sets the pty winsize with `TIOCSWINSZ`
before spawn (`driver.rs:355`), which is what an ioctl-based measurement reads —
so if lanthorn measures some other way in this path, that is the gap. One thing
noticed and NOT yet chased: `driver.rs:478` answers every cursor-position report
with `\x1b[1;1R`, a hardcoded row 1 column 1. Any measurement that works by
parking the cursor at the far right and asking CPR would read a width of 1 here
and fall back to something. That is a guess, not a finding.

**Why this matters beyond one title.** If the harness boots text-only stories on
a screen the player never sees, every text-only gallery still and every cast is
framed wrong — the same class of defect as SQ-0901's fabricated Arthur frame,
on the side where nobody has written down what the boot chain must include. The
v6 chain is documented in CLAUDE.md; the text-only one is not.

## Correction: it is LOST LEADING WHITESPACE, not a wrong width

The "constant ~49 columns" reading in the notes above is wrong, and wrong in an
instructive way: it came from assuming the title was *centred* on some width and
solving for that width. It is not centred at all — it is **shifted left**, and
solving a shift as if it were a centring produces a plausible number that moves
with nothing.

`zvm-cli` is the control, same story, same width, and it is CORRECT:

    printf '\n' | COLUMNS=100 cargo run -q -p zvm-cli -- stories/anchor.z8

| line | zvm-cli @100 | app harness @100 | delta |
|---|---:|---:|---:|
| `A N C H O R H E A D` | **40** — exactly (100-19)/2 | 15 | -25 |
| `[Press 'R' to restore; …]` | **26** | ~1 | ~-25 |
| Lovecraft epigraph text | **28** | ~1 | ~-27 |

And at 80 columns zvm-cli puts the title at 30, which is (80-19)/2. So the game
centres on the screen width, correctly, at every width; zvm delivers it
correctly; and the width IS reaching the story. The whole "decoupled width"
framing is discarded.

What is left is narrow and testable: **the app drops roughly 25 columns of
leading whitespace on lines that begin with a run of spaces.** Prose is
unaffected, which is why this hid — a paragraph has no leading run.

`zvm-cli` as the control is the useful part of the method here: it drives the
same `zvm` with a different front end, so it separates "the engine or the game"
from "the app's own text path" in one command. Reach for it first next time.

## Where to look

The app's own wrap/transcript path, not zvm: `render::transcript.rs` and
`render::wrap_cache` (`raster_wrap_refresh`). A word-wrapper that trims or
collapses a leading space run when it re-flows a logical line would produce
exactly this, and would leave ordinary prose untouched. The 25 is suspiciously
close to a quarter of the 100-column pane, so check whether the amount lost is a
constant or scales with width before assuming either.

## Still unexplained, and it matters

The user reports the title IS centred when they run lanthorn locally. If the app
text path were simply dropping leading runs, production would be wrong too. So
either the harness perturbs that path, or the local build differs, or the local
observation was at a width where it looked right. **Do not start fixing until a
local run at a stated width is compared against `zvm-cli` at the same width** —
that pair, not internal measurement, is what says which of the two is broken.

## CONFIRMED in the shipped binary — the harness is exonerated

Ran `target/debug/lanthorn` under a **bare pty**: no gallery, no cast tool, no
`driver.rs`, no fake query responder. Just `pty.fork()`, a real `TIOCSWINSZ`, and
read the bytes. Nothing answers lanthorn's capability queries, exactly as a plain
terminal would not.

`stories/anchor.z8`, boot frame, `A N C H O R H E A D` = 19 cells. Column the
title is actually emitted at, against what `zvm-cli` produces at the same width:

| pane cols | lanthorn | zvm-cli | shortfall |
|---:|---:|---:|---:|
| 80 | **16** | 31 | 15 |
| 100 | **16** | 41 | 25 |
| 120 | **20** | 51 | 31 |

So this is not the test harness and it is not the renderer. **The plain binary
puts centred story text at a nearly fixed column while the correct position
tracks the width.** 16 at both 80 and 100 columns corresponds to a screen of
about 50; 20 at 120 corresponds to about 57.

Reproduction, no repo tooling involved — spawn `lanthorn <story> --user-dir <tmp>
--no-sound` on a pty, `TIOCSWINSZ` it to the width you want, read for a few
seconds, then find the last `ESC[row;colH` before the title and add the printable
run after it. The control is one line:

    printf '\n' | COLUMNS=100 cargo run -q -p zvm-cli -- stories/anchor.z8

## The one inconsistency left, worth keeping in view

In a HARNESS capture taken several keypresses in, the epigraph box was emitted at
`ESC[6;26H` — column 26, exactly `(100-47)/2`, i.e. CORRECT — while the title in
the same capture was wrong. In the bare-pty BOOT frame both are wrong (epigraph
at column 4). So absolutely-positioned window text is not reliably right either;
it was right in one frame and wrong in another. Whatever the cause, it is not a
clean "windows are fine, flow is broken" split, and a fix should be checked at
more than one moment in the game.

The user's local impression that the title looks centred is now the outlier and
should be re-checked at a stated width — most likely explanation is a different
terminal width where the fixed column happened to look plausible.
