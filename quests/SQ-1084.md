## Measured, in the cell-buffer render — so it is not a cast or SVG artifact

The suspicion was that `svg-term` was misplacing text. It is not: the same frame
rendered through the gallery's rasteriser puts the title in exactly the same
wrong place, and the gallery reads lanthorn's own cell buffer.

`stories/anchor.z8` (Anchorhead, release 5 / serial 990206), the opening frame at
zero keypresses, no map pane. The title is `A N C H O R H E A D`, 19 cells wide.
Measured off the rendered PNG, in cells:

| pane cols | title spans | its centre | pane centre |
|---:|---|---:|---:|
| 82 | 15.2 .. 33.8 | 24.5 | 41.0 |
| 100 | 15.1 .. 33.8 | 24.4 | 50.0 |
| 122 | 20.1 .. 38.8 | 29.4 | 61.0 |

**Two things are wrong here and the second is the interesting one.**

The title never reaches the pane's centre at any width — it sits roughly where it
would if the game had been told the screen were about 49 columns instead of 100.

And between 82 and 100 columns it does not move **at all** — same start column to
within a tenth of a cell — while between 100 and 122 it moves by five. A centring
that were merely computed against the wrong number would still slide with that
number. One that does not move across an 18-column change, and then does across a
22-column one, looks like a width that is being quantized or clamped somewhere
rather than passed through.

## Where to look, and what would settle it

The game centres by computing `(width - len) / 2` from the screen width in the
header, so the question is what lanthorn writes there and when — `write_screen_dims`
and the pane rect it is derived from. Suspect the story pane's usable width (the
border steals a column on each side) against the width the header advertises, and
whether a resize rewrites it.

**Check it against a reference rendition before fixing anything** (the standing
rule): Anchorhead in Frotz or Gargoyle at 100 columns says where the title is
supposed to land, and internal measurement cannot. It is possible — not likely at
these numbers, but possible — that the game indents rather than centres and every
frame here is correct.

Reported alongside this: the Beyond Zork Character Setup menu looks off-centre too,
on the Amiga floppy at 100x32, which would make this general rather than one
story's quirk. Worth confirming as a second specimen.

## Correction: the two renders were NOT independent witnesses

The note above claims this is lanthorn's rather than the renderer's because it
reproduces in the cell-buffer render as well as the SVG. That is overstated. Both
come out of the SAME pty harness — `tests/pty_stream/driver.rs`. The gallery
rasterises the cell buffer the harness decoded; the cast serialises the same byte
stream. What was actually established is **"not svg-term"**, and nothing more.

A harness-level cause fits every measurement here. The standing rule in CLAUDE.md
is about exactly this shape — boot a harness the way `startup.rs` boots or you
measure a screen the app never draws — and it has been written down so far only
for the v6 chain (profile, `native_std_window`, `art_scale`). Whether a TEXT-ONLY
game has an equivalent chain the harness skips is an open question, and is the
first thing to check. **Reproduce in the real binary, by eye, before touching any
code.**

## The mechanism that would let this hide

lanthorn re-wraps prose: the transcript is reflowed to the pane through
`render::wrap_cache::raster_wrap_refresh`. Centring is not reflowable — it is
spaces the GAME emitted, computed from the screen width in the header, and they
land wherever that arithmetic put them.

So a wrong advertised width would be **invisible in every paragraph and visible
on every centred line**: titles, menus, boxed epigraphs. That is precisely the
reported pattern (Anchorhead's title and Beyond Zork's Character Setup menu, with
prose looking correct in both). It also means the defect cannot be found by
reading a transcript — only by measuring a column.

## What would settle it, cheapest first

1. Run the real binary: `lanthorn stories/anchor.z8` in a 100-column terminal and
   look at where `A N C H O R H E A D` sits. If it is centred, this is the
   harness and the quest is about the harness.
2. `/dump-terminal` — it reports what lanthorn measured against what it guessed;
   compare the width it advertises against the pane it drew.
3. Only then, against a reference rendition (Frotz, Gargoyle) at the same width,
   per the standing rule — to rule out the possibility that the game indents
   rather than centres and every frame is right.

The one datum that survives whichever way it goes: at 82 and 100 columns the
title starts at the same column to within a tenth of a cell. A centring computed
from a merely wrong width would still slide with the width. (Discount the 122
figure in the table above — that PNG came out 1048px tall against 1064, so the
sampled row band probably caught different content.)
