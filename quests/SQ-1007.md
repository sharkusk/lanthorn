--- note 2026-08-22T15:24:24Z ---

## The diagnosis, from the Ctrl-Z clue

`startup.rs:1398 prompt_yes_no` reads a **line**:

```rust
print!("{question} [y/N] ");
let mut line = String::new();
match std::io::stdin().read_line(&mut line) {
    Ok(0) | Err(_) => false,
    Ok(_) => matches!(line.trim().chars().next(), Some('y') | Some('Y')),
}
```

`read_line` needs the console in COOKED mode — `ENABLE_LINE_INPUT` and `ENABLE_ECHO_INPUT` — because the console driver is what assembles a line and returns it on Enter. In raw mode those flags are off, so typed characters never form a line and the call blocks forever, which is exactly "all keyboard keypresses are ignored".

**Ctrl-Z is the confirmation, not a coincidence.** On Windows Ctrl-Z is the console EOF signal, and it is delivered even with line input disabled. `read_line` then returns `Ok(0)`, the arm above answers `false`, and startup proceeds to the story list — precisely what the user saw, including that "no" was the effective answer.

So the console was in raw mode before lanthorn ever asked the question. It runs BEFORE the app enables raw mode itself, so it inherits whatever the console was left in — and **a Windows console's input mode persists across processes in the same window**. The first run left raw mode on.

## Two things to fix, and the second is the real one

1. **Why the first run leaves raw mode on.** SQ-0998 audited every teardown path and found one `restore_terminal` that all of them funnel through, plus a panic hook — but it fixed the ORDER of the restore, not whether it happens. An exit that bypasses the funnel entirely (a hard kill, a Ctrl-C the handler misses, a crash before the hook installs) still strands the console. Worth confirming which exit the user actually took.

2. **The prompt must not depend on the previous process's hygiene.** Even with (1) perfect, one crashed run poisons every later launch in that window, and the user has no way to know that `reset`-equivalent is what they need. A prompt that reads a key through crossterm's event API — enable raw, read one `KeyEvent`, restore, echo the answer — works in either inherited state and needs no Enter. That is the fix that makes the report impossible rather than unlikely.

## Not yet ruled out, and it interacts with SQ-0770

SQ-0770 is *"on Windows the terminal colour queries are sent but never read, so their answers reach the game as keystrokes on every launch"*. Unread query replies sitting in the console buffer are another way a second launch's `read_line` misbehaves — it would consume them as a line rather than block. That fits "the prompt did something I did not type" better than "keypresses are ignored", so it is the weaker hypothesis here, but the two live in the same buffer and should be settled together. The user is on **0.2.0**, which predates SQ-0770's fix.

## What would confirm it

On the second (dead) launch: does typing echo? Raw mode says no. If characters DO appear on screen but Enter does nothing, the diagnosis above is wrong and the buffer hypothesis is right.

## CONFIRMED, and the earlier note's "which hypothesis" question is settled

The user supplied three observations that name the three bits in crossterm's `NOT_RAW_MODE_MASK` one at a time:

| observation | bit |
|---|---|
| nothing echoes | `ENABLE_ECHO_INPUT` off |
| keys never form a line | `ENABLE_LINE_INPUT` off |
| **Ctrl-C does not interrupt** | `ENABLE_PROCESSED_INPUT` off — Windows raises `CTRL_C_EVENT` only when it is set, and otherwise delivers a plain `0x03` byte |

All three cleared IS raw mode. The competing "unread query replies in the input buffer" hypothesis is dead: a full buffer would make `read_line` return something, not block, and would not stop Ctrl-C. `clear` not helping fits as well — it is output-only and cannot touch an input mode.

**"The shell is fine in between" is not evidence against it**, though it reads like it, and it nearly sent me somewhere else. PSReadLine reads key events itself and draws the line it is editing, so a console left raw behaves normally in PowerShell. lanthorn's own TUI is immune for the same reason — it sets raw deliberately. `prompt_yes_no` is the ONE cooked-mode consumer in the program, which is why it is the only thing that broke, on the one platform where console mode outlives the process.

Fixed in `4b6c4b55` — `crossterm::terminal::disable_raw_mode()` before the read. On Windows that SETS the cooked bits rather than restoring a saved mode, so it repairs a console this process never broke; on unix it restores the termios saved at `enable_raw_mode` and is a no-op when there is none, which is always at that point. Pinned at the source beside SQ-0998's cases, since the defect needs a console left dirty by a previous PROCESS.

## STILL OPEN, and not fixed by the above

**Something leaves the console in raw mode in the first place.** The prompt is now immune to it, which is the right property — one hard kill would otherwise poison every later launch in that window with no way for the user to know what to reset — but the underlying leak stands and could affect any other cooked-mode program run in that window afterwards.

SQ-0998 does not close it: it fixed the ORDER of the restore, not whether one happens, and `disable_raw_mode()` was always called. The lane that did it audited every path and found they all funnel through one `restore_terminal`.

Two candidates worth separating, and the first is a question for the user:

1. **How the first run exited.** A hard kill, or a Ctrl-C the handler missed, skips the funnel entirely. Cheap to ask, cheap to rule out.
2. **The picker's own probe.** `Picker::from_query_stdio` has a real Windows `enable_raw_mode` (CONIN$ + `SetConsoleMode`) and a reader thread doing a blocking read until the DSR answer; SQ-0770's audit noted its timeout path abandons a thread still parked in that read. If it sets raw on CONIN$ and the abandoned path never restores, that is a leak inside a normal, tidy run — which would explain why a first launch is clean and a second is not, with no untidy exit needed anywhere.

Candidate 2 fits the reported shape best and is upstream's code, so establish it before touching anything.

--- note 2026-08-22T15:59:57Z ---

## ROOT CAUSE FOUND, and my "candidate 2" was wrong — the picker probe is innocent

The user exits cleanly (Ctrl-Q in story, `q` at the story list), so no untidy exit is involved. It does not need to be. **A perfectly tidy exit left the console raw**, and it is our own teardown ordering.

crossterm's Windows mouse capture does not clear bits — it snapshots and restores a whole console mode:

```rust
enable_mouse_capture()  → init_original_console_mode(mode.mode()?);  // save CURRENT mode
                          mode.set_mode(ENABLE_MOUSE_MODE)
disable_mouse_capture() → mode.set_mode(original_console_mode()?)    // restore that snapshot
```

`startup.rs:1332` enables raw mode and only THEN enters the alternate screen and mouse capture, so `ORIGINAL_CONSOLE_MODE` is snapshotted with raw already on — it holds a RAW value.

v0.2.0's `restore_terminal` then ran:

1. `disable_raw_mode()` → sets the cooked bits ✓
2. `execute!(… DisableMouseCapture …)` → `set_mode(ORIGINAL_CONSOLE_MODE)` = the raw snapshot ✗

The second call overwrites the first, so the console ends raw on every clean exit. That is the whole report, and it explains why both quit routes do it and why no crash was ever needed.

**SQ-0998 already fixes it on main.** That quest reversed exactly this order — the `execute!` runs while raw mode still holds, and `disable_raw_mode()` goes last — so the cooked bits are now set AFTER the snapshot restore. It was written for a Unix mouse-report fragment on the shell prompt and closes this as a side effect, on a platform nobody was testing.

Retracting the earlier note's candidate 2: `Picker::from_query_stdio`'s abandoned reader thread is not implicated. It fit the "first launch clean, second broken" shape, which is why I reached for it, and it was wrong — the shape is fully explained by the snapshot above.
