Follow-up to SQ-1624 (0fe2bbac). crates/app/src/host/boot.rs ~1306-1311 picks resume_path by Meta::saved_at alone.
1. A clean quit (exit_clear_resume_save) writes an autosave with no resume point, which is always the newest slot, so the next boot starts fresh even when the player has a quick save. The point of the split was that a quick save survives as a place to come back to after quitting. Ask: choose the newest slot that actually holds a resume point (non-empty save), so after a quit the quick save resumes.
2. With (1), a host that starts a game over by clearing the autosave (the terminal's own new game is an in-session reset, but a host that restarts by rebooting clears default.* and boots) would then resume an older quick save instead of starting fresh. Ask: a host function or boot option for 'start this game fresh' that neither deletes the quick save nor gets overridden by it (for example a boot flag, or a fresh-start marker that counts as newest until the first autosave).
3. The choice is private to boot, so a host that labels which save 'Continue' will resume has to re-derive it. Ask: publish it, e.g. host::boot::resume_source(game_dir) -> Option<which slot> (autosave / quick save / none), used by boot itself so the two can't disagree.
4. Minor: saved_at has one-second resolution and newer means strictly newer, so a quick save made in the same second as the autosave loses; prefer the quick save on a tie (or use a finer timestamp).
Tests: quit with a quick save present, next boot resumes the quick save; start fresh with a quick save present, boot is fresh and the quick save still exists; resume_source agrees with boot in each case; same-second tie.
