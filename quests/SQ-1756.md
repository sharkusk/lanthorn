  IFDB documents: ranged requests (size probe, text preview, remote zip reads) go through ureq with Accept-Encoding gzip, so a host that compresses on the fly answers 206 with Content-Encoding: gzip and a Content-Range over the COMPRESSED body. Repro: https://allthingsjacq.com/intfic_clubfloyd_20071101.html (Lost Pig's ClubFloyd transcript on IFDB) with Range 0-16383 replies 206, Content-Encoding gzip, Content-Range bytes 0-16383/45112; the file is 302511 bytes. Effects: (1) the size probe reports 44 KB instead of ~295 KB; (2) the preview fails: ureq inflates the 16 KB slice to more than 16 KB, read_capped in fetch_range (ifdb_search.rs ~457) returns SearchError::TooLarge; (3) the shown text is 'Too large to download (over 100 MB)', because SearchError::TooLarge's Display always names MAX_DOWNLOAD whatever cap was hit. Suggested: send Accept-Encoding: identity on ranged requests (a range of an encoded representation is meaningless to every caller); a preview that receives more than it asked for should keep the first n bytes, not fail; TooLarge should carry or name the cap actually exceeded. Affects the TUI and any embedding host using the documents worker.
