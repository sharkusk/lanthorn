## Failure A — Windows STATUS_ACCESS_VIOLATION, arrived with SQ-1043

Runs 01:44 and 02:45, `test (windows-latest)`, step `cargo test`:

    error: test failed, to rerun pass `-p app --lib`
    Caused by:
      process didn't exit successfully: target\debug\deps\app-….exe
      (exit code: 0xc0000005, STATUS_ACCESS_VIOLATION)
    note: test exited abnormally

**A segfault, not an assertion.** The binary dies; no test reports a failure. macOS
and Linux pass the same commit.

The last test printed differs between the two runs (`config_screen_enter_at_default_
focus_fires_save` in one, `ifdb_search_modal::…` in the other), so **the last line is
NOT the crashing test** — `cargo test` runs a binary's tests on many threads and the
printed order is scheduling, not causation. Identify the real one rather than reading
the tail: `--test-threads=1` on Windows CI will serialise it and name the crasher.

FIRST HYPOTHESIS, to be checked not assumed: **stack overflow.** Windows threads
default to 1 MB where Unix gives 8 MB, and a stack overflow on Windows surfaces
exactly as `0xc0000005`. SQ-1043 added unit cases that exercise the return probe,
which FORKS A SESSION — a deep clone of machine state. `-p app --lib` is where those
unit cases live. That story fits every fact, including why only Windows dies, but it
is a hypothesis: this project has had two plausible mechanisms refuted by
measurement in as many days.

If it is the stack, the fix is a bigger explicit stack for the test thread (or the
worker), not shrinking the fixture — the same fork runs in production on a real
player's Windows machine.

## Failure B — macOS pty timing, arrived with SQ-1098

**Probably load-flakiness rather than a defect SQ-1098 introduced** — SQ-1098 touched

if it passes, the defect is the fixed 2500 ms deadline on a shared CI runner rather
than anything in the tree. A timing assertion with no retry and no headroom is a test
that will redden main at random.

## Why this quest matters beyond the two fixes

**The local gate was traded for CI on 2026-08-30**, and CLAUDE.md now says so. These
are the first failures under that arrangement and they are precisely the two classes
the local checks cannot see: a per-OS crash (we run neither Windows nor Linux
locally) and a `cargo test` shared-process/threaded behaviour that nextest's
per-test processes structurally cannot reproduce.

So the trade is working as designed — but it only works if red runs are NOTICED. The
user found these, not me, across six merges. The agreed cadence is a check once a
day; a night of six merges is exactly when that is not often enough. Worth deciding
whether a merge wave should end with a CI look regardless of the daily rhythm.

## Both localised, both fixed on `worktree-agent-aa002c1ba1fbfe08a` (83ed46ac). What is VERIFIED vs INFERRED is marked.

### Failure A — the Windows access violation

**The attribution in this quest was wrong, and worth correcting: this is SQ-1161, not SQ-1043.** SQ-1161 (`f34a8531`) merged at 01:41 and its own run (33348334228) was CANCELLED, so it never got a verdict; the first run that judged it is 33348484335 at 01:44, which also carried SQ-1043. Run 33343974595 (00:14) is the last **windows-latest SUCCESS** — so the window is `docs(boot)` + SQ-1161 + SQ-1043, and nothing in the evidence points at the return probe.

**Naming the crashing test without a Windows machine.** VERIFIED. `gh run view --log-failed` truncates the front of the step but keeps `app --lib` intact from its first case, so the completed set is real. The two red runs completed **792 and 793** cases, identical but for one. Diffed against `cargo test -p app --lib -- --list`, exactly five cases were started and never finished in BOTH runs; two are the `#[ignore]`d live-IFDB smokes, leaving three:

    hints::tests::a_glulx_game_past_the_old_four_mib_cap_still_opens_out_of_a_zip
    hints::tests::read_zip_entry_caps_a_huge_inflated_entry
    input::tests::config_save_queues_live_watch_style_reconcile

The two `hints` cases are slow by design (megabytes through a deflater) and would be in flight at any frontier; nothing in the window touched `hints.rs`; and both ran green on Windows at 00:14 unchanged. The third is in the region SQ-1161 rewrote — and **safe Rust cannot raise an access violation**. The only `unsafe` reachable from it is cpal's.

**What it does. VERIFIED, and it is the whole story.** `Action::ConfigSave` builds an `AudioBackend` lazily whenever `enable_sound` is on and the state holds none — which is every `AppState::default()`, since `default_enable_sound()` is `true`. **SQ-1161 added two more cases doing exactly that beside the existing one** (`config_save_applies_the_live_mirrors_and_the_global_bases`, `config_save_does_not_lower_a_pinned_value_into_the_global_base`), so where there was one real device open in that stretch there are now three, adjacent, on three libtest threads. Measured locally at the red commit:

| how those four cases run | wall |
|---|---|
| `--test-threads=1` (main thread) | **0.76s** |
| default threads (parallel) | **491.54s** |

That 646x is three real CoreAudio streams being torn down on threads they were not opened on — the exact cost `audio`'s own `TEST_SILENCE` doc comment warns about ("opening and, on macOS, tearing down a real stream costs many seconds per backend, and a test that constructs one blocks the whole test binary at drop").

**Why Windows dies instead of crawling. INFERRED, from cpal 0.15.3's source, not from memory.** `host/wasapi/device.rs` keeps a process-global `static ENUMERATOR: OnceLock<Enumerator>` holding a raw `IMMDeviceEnumerator`, while `host/wasapi/com.rs` initialises COM in a **thread_local** whose `Drop` calls `CoUninitialize()`. A libtest thread that opened the enumerator exits, its `CoUninitialize` runs, and — if nothing else holds COM at that instant — MMDevAPI is unloaded from under the global pointer; the next thread through calls a vtable entry in unmapped code, which is `0xc0000005` exactly. Concurrency is the new ingredient SQ-1161 supplied, which is why two non-adjacent constructions were survivable before and three adjacent ones are not. **Nextest cannot see any of this**: one process per test is never two threads. Windows was green at 00:14 with one such case in that stretch.

**The fix.** `audio` has said since it was written to call `disable_output_for_tests()` in any test that constructs a backend, and the rule cannot live at the call sites — a settings-screen case reaches `AudioBackend::new` without the word "audio" appearing anywhere in its body, and its author has no reason to suspect it. So it is said once, in `AppState::default()` under `#[cfg(test)]`, which every one of those cases starts from. The lazy construction still runs and is still asserted on (`TEST_SILENCE` only skips opening the device), and the shipped binary never compiles the line. **Not a shrunk fixture**: in production lanthorn builds at most one backend, on the main thread, which outlives the process — the hazard needs a thread that exits, which only libtest supplies. Those four cases now take **0.01s**, and the full `-p app --lib` is 2936 passed in 17s.

### Failure B — the macOS pty timing failure

**It is not a defect SQ-1098 introduced. VERIFIED both ways**: `gh run rerun --failed 33343974595` on the identical commit came back green on all three OSes, and twelve runs of the case plus eight runs of the whole 88-case `pty` group binary under twenty-four CPU hogs would not reproduce it locally.

**But "flaky" was not the diagnosis.** The timeline, measured out of a real capture: startup probe at 69 ms, Enter at ~1.07 s, the app's colour queries **seen at ~1.115 s**, boot frame at 1.30 s, deferred answers delivered at **2.015 s**. The command was typed after `Key::Wait(320)` — and `Wait` is silence-relative, not a sleep, so it means "320 ms of quiet after the launch key". On an idle machine that lands at ~1.6 s, inside the window. On a loaded runner the app can be silent for 320 ms **before it has processed Enter at all**, at which point `open mailbox\r` goes to the PICKER: the story still boots (so `assert_the_scenario_ran` passes), the answers are still held late (so that check passes), and the command is simply gone — which is the reported failure at line 164 precisely. Raising the number moves that edge without removing it.

**`Key::AwaitQuery { query, cap }`** holds the key until the app has ASKED the named query, which the harness's `Responder` already sees. The window is now entered by observation at any load — the same bargain `Spec::defer_queries` struck for the answers — and `cap` turns "the query never came" into a run that FAILS naming it rather than a vacuous pass.

**And the case now proves it typed inside the window.** `Capture::typed` records when each key really went out; the case asserts that against the first colour answer. Without it the interesting failure is invisible: a command sent after the answers land reaches the story for the dull reason that nothing was holding the terminal any more, and the old script passes that way while proving nothing. Both halves falsified — a query name the app never asks fails with the harness's own message after the cap, and swapping the wait back for a late `Wait` trips the new guard at 3.47 s against an answer at 2.02 s.
