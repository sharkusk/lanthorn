THE COMMENT THAT ANNOUNCED IT (three of them, all in the same recipe).

`crates/app/src/machine_boot.rs:43-45` — "the **interpreter number** and **default colours**, which at launch pass through `Config::advertised_interpreter_number` and the two-colour-card rule (SQ-0930, SQ-0956) and **at a restart are simply what the launch settled**."

`crates/app/src/reset.rs:85` — "The same four links `startup.rs` resolves, in the same order" (the SQ-1022 comment, still in place).

`crates/app/src/reset.rs:76-81` — "SQ-0719: a restart re-runs the same story on the same machine, so the interpreter profile resolved at boot supplies the same three answers it did there ... IBM PC (every Blorb-sourced story) supplies none of them and **this is the prior code exactly**." Written before SQ-0930 and never revisited.

BOTH SIDES.

  crates/app/src/startup.rs:766
      cfg.advertised_interpreter_number(),

  crates/app/src/reset.rs:154
      state.config.interpreter_number.or_else(|| profile.interpreter_number()),

`Config::advertised_interpreter_number` (crates/app/src/config.rs:1376-1386) is a THREE-rung cascade:
  1. an explicit `config.interpreter_number` wins;
  2. **IbmPc + ProfileSource::Medium -> IBM_PC_INTERPRETER_NUMBER (6)** — SQ-0930's whole point;
  3. else `profile.interpreter_number()`.

reset.rs reproduces rungs 1 and 3 and omits rung 2. It is not carrying "what the launch settled" either — the launch's answer is never stored; `config.interpreter_number` is the user's CONFIGURED number, which is `None` on a plain launch.

WHY IT IS NOT INERT. `InterpreterProfile::IbmPc.interpreter_number()` is `None` on purpose (crates/app/src/interpreter.rs:529), so reset falls through to zvm's default rule, `zvm::screen::default_interpreter_number` (crates/zvm/src/screen.rs:1783) — Frotz's: 6 for Version 6, **1 otherwise**. So for any non-v6 story off a DOS medium:

    launch    header $1E = 6   (IBM PC)
    @restart  header $1E = 1   (DECSystem-20)

A Version 6 story is masked, because both paths land on 6.

THE FRAME. `crates/blorb/src/medium.rs:584-586` and `Config::advertised_interpreter_number`'s own doc both name the same case: `BEYONDZO.DAT` sits on `floppy1.ima` (present in `stories/`), and *Beyond Zork* — a **v5** story — swaps Font 3's arrows for CP437 character graphics when it believes it is on an IBM PC. zvm gates that remap on interpreter number 6 (`crates/zvm/src/cpu/exec.rs`). So launching Beyond Zork off `floppy1.ima` renders CP437 box graphics, and `@restart` / `/restart` silently reverts it to Font 3 arrows mid-session. That is SQ-0930's defect re-entering through the restart door.

SUGGESTED FIX (not applied — this was an audit lane). Do not copy the third rung into reset.rs. Either pass `state.config.advertised_interpreter_number()` at reset.rs:154 — noting reset deliberately uses its own re-resolved `profile`, so if the two can differ the method needs the profile as an argument rather than reading `self.interpreter_profile` — or store the launch's advertised number on `AppState` so a restart genuinely is "what the launch settled", which is what machine_boot.rs's doc already claims happens. The second is what the doc describes; the first is smaller.

FALSIFY. Boot `stories/floppy1.ima`, read header $1E, `/restart`, read it again. `/dump-windows` or a headless harness modelled on `crates/app/tests/suites/interpreter_profile.rs:537` (which already calls `cfg.advertised_interpreter_number()`) is the cheap oracle. No existing test drives the reset path's number at all — `advertised_interpreter_number` appears in three suites, none of them a restart.

--- note 2026-08-24T22:40:26Z ---

## Fixed

`reset.rs` now calls **`state.config.advertised_interpreter_number()`** — the same one implementation `startup.rs` calls — instead of reproducing rungs 1 and 3 of it by hand. The audit's second suggestion (store the launch's answer on `AppState`) was not taken: `reset` already re-resolves its profile from `state.config.interpreter_profile`, which is exactly what the cascade reads, so re-asking the one implementation gives the launch's answer without a new field to keep in step.

`machine_boot.rs`'s doc claim was corrected in the same edit. It said the number "at a restart [is] simply what the launch settled", which was never true — the launch's answer is stored nowhere. It now says both paths ask the same call.

## Verified

`reset::tests::a_restart_advertises_the_interpreter_number_the_launch_advertised`, on **`stories/floppy1.ima`** (Beyond Zork, the DOS medium). Three premises are asserted rather than assumed — the medium resolves `IbmPc`, the source is `Medium`, and the story is **not** Version 6 (a v6 specimen masks the defect entirely, since both roads reach 6). Then: launch reads `$1E = 6`, `reset_game` runs, restart reads `$1E = 6`.

Falsified: restoring `state.config.interpreter_number.or_else(|| profile.interpreter_number())` fails the case at the **restart** assertion — launch 6, restart not 6, which is the reported defect.

No test drove the reset path's interpreter number before this; `advertised_interpreter_number` appeared in three suites, none of them a restart.
