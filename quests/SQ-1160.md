--- note 2026-08-30T21:56:19Z ---

DECIDED by the user, 2026-08-30: **"Get rid of those badges."** Retire them — do not
revive them by drawing them somewhere.

## What to remove

`badge_zcode`, `badge_glulx`, `badge_blorb`. All three are `[elements]` style keys
that reach NO PIXEL: SQ-0369 moved story type and Blorb into the picker's TYPE
column as text (`Z5 (blorb)`), and `picker_ui.rs` draws only the save and hint
badges — pinned deliberately at `picker_ui.rs:3751`. They have been themeable and
undrawn ever since.

## What to KEEP

`badge_save`, `badge_hint`, `badge_hint_available` are drawn and stay, along with
the `badge_icons` preset key (`plain` | `nerdfont`) that SQ-1159 added. The preset
survives with three members instead of six; its codepoints for the survivors were
verified across nine patched families and must not be re-derived.

## Sites, as of e1e8a857

`crates/app/src/config.rs` (the `default_badge_*` fns and their `#[serde(default)]`
fields), `symbols.rs` (`StoryBadges`, both the `PLAIN` and nerdfont sets and the
name/codepoint table around :1338), `style.rs`, `theme/registry.rs`,
`theme/template.rs`, `picker.rs`'s `BadgeGlyphs`, `crates/app/tests/suites/font_check.rs`,
`style.example.toml` (regenerated — `style_example_matches_generated_template`
asserts it byte-exact), and the paragraphs SQ-1159 just wrote in
`docs/features/interface.md` and `customization.md`, which currently explain that
three of the six are not drawn. That explanation goes with them.

## Two things to get right

**Pre-release, so break the format freely** — no back-compat shim, no tolerant
decoder for an old `style.toml` naming a retired key. But DO check what an existing
user file carrying `badge_zcode = "Z"` does on load: if an unknown `[elements]` key
is an ERROR rather than ignored-with-a-warning, retiring these turns a working
config into a failing one. State which it is; if it errors, that is a separate
defect worth its own quest rather than a reason to keep dead keys.

**Do not "tidy" the TYPE column while you are there.** SQ-0369's text rendering is
the shipped decision and this quest is only removing what it orphaned.

Trailer: `Completes: SQ-1160` — a config/style test settles it.

KEPT as instructed: `badge_save`, `badge_hint`, `badge_hint_available`, the

nine-family survey read them — not re-derived. The TYPE column was not touched.

ANSWER TO THE QUESTION THE QUEST ASKED — a `style.toml` carrying `badge_zcode = "Z"`
is **silently IGNORED**. Not a warning, not an error. Two independent halves both
drop it: `style::parse_style_toml`'s `[elements]` walk ends in `_ => {}` (its doc
comment already says "Unknown keys are ignored; `Err` only on TOML parse failure"),
and `theme::toml_schema::parse` reads only inline TABLE values from `[elements]`, so
a bare string is not even a candidate selector. `SymbolConfig` carries no
`deny_unknown_fields`, so the serde path drops it too. Retiring these therefore turns
no working user config into a failing one, and no separate defect needs filing.
Two new cases pin it rather than leaving it to inference:
`config::tests::a_retired_badge_key_is_ignored_not_an_error` and
`style::tests::a_retired_badge_key_in_elements_is_ignored_not_an_error`.

`picker_ui::tests::row_uses_configured_badge_glyphs` lost the two assertions that
could only be spelled with the retired keys; it still asserts the configured save
glyph is drawn and that the Blorb appears as the TYPE column's `(blorb)` suffix.

Docs: the SQ-1159 paragraph in `docs/features/interface.md` now describes three
badges and says the type/Blorb keys are GONE rather than themeable-and-unseen.
`customization.md` needed no change (it names only `badge_icons`).
