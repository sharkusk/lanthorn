--- note 2026-08-25T01:23:33Z ---

## The report

An auto-save made while playing **`stories/Arthur - The Quest for Excalibur.adf`** (Amiga) is picked up and auto-resumed by **`InfocomMasterpieces.img`, entry `InfocomMasterpieces/ARTHUR FOLDER/STORY.DATA`** (Macintosh).

## Why this is more than a filing mistake

CLAUDE.md is explicit that these are not the same game: *"A disk image is a different RELEASE, not the same story on other media."* The two Arthurs here differ in release and serial, and the archive is engine-neutral host state, not a Quetzal — a host Save State **swaps memory under a game that never learns it happened**, so restoring one release's snapshot into another's memory image is undefined at the VM level, not merely untidy.

It also crosses a MACHINE boundary, which today has more consequences than it used to:

* the two presses declare different cells — the Amiga 8x16 (or 8x20 with `char.data`), the Macintosh 7x15 (SQ-0917, SQ-1009);
* different faces, different pens, different art scales;
* `reconcile_restored_screen_size` exists to reconcile a restore into a different PANE, not into a different machine.

So a restore that "works" here is the dangerous case, not the safe one: it will look plausible and be laid out for a screen the story was never told about — the SQ-0901 shape.

## Where the key is decided

Saves live under `~/.lanthorn/saves/<key>.save/`, and the observed key for the Amiga floppy is `arthur-r54-s890606.save` — release and serial, no medium and no machine. If the Masterpieces Arthur resolves to the same release/serial it will land in the same drawer and the auto-resume will find it. **Check that first**: if the two presses really are r54/890606 on both media, the key is the whole defect and the fix is what to add to it. `crates/app/tests/suites/save_key_media.rs` and `disk_set_rows.rs` are the neighbours; `real_media_releases.rs` pins what each medium in `stories/` actually carries.

If the releases DIFFER and it still auto-resumed, the key is being computed from something weaker than release+serial, which is a larger question.

## What to settle before choosing a rule

Naming the machine or the medium in the key is not automatically right — a player who owns one game on two media may reasonably expect one set of saves, and the archive is deliberately *backend- and terminal-neutral* (`reconcile_restored_screen_size` exists precisely so a save moves between kitty/half-blocks and between terminal sizes). What must not happen is a snapshot of one RELEASE being restored into another. Settle whether the boundary is the release, the medium, or the machine, and say which on the evidence rather than picking one.

Also worth deciding separately: whether a mismatch should refuse, warn, or simply not auto-resume. Auto-resume is the silent path and the one that bit here.

## MEASURED — the save key is CORRECT, and the two Arthurs are the SAME BUILD

This quest was filed on the premise that *"these are not the same game"*. On the
evidence they are: one Z-code build shipped on two media. The keying is doing exactly
what it was designed to do, and the reporter's own hypothesis — *"this may be a
mistake in how we generate our save directory with collections that have multiple
stories"* — is also ruled out.

### Every story on the volume keys correctly

`stories/InfocomMasterpieces.img`, all twenty of them, each mounted and keyed:

```
InfocomMasterpieces/PLANETFALL                  r10  s880531  → planetfall-r10-s880531
InfocomMasterpieces/ZORK I                      r88  s840726  → zork-i-r88-s840726
InfocomMasterpieces/THE LURKING HORROR          r203 s870506  → lurking-horror-r203-s870506
…
InfocomMasterpieces/ARTHUR FOLDER/STORY.DATA    r54  s890606  → arthur-r54-s890606
InfocomMasterpieces/JOURNEY FOLDER/STORY.DATA   r26  s890316  → journey-r26-s890316
InfocomMasterpieces/ZORK ZERO/STORY.DATA        r296 s881019  → zork-zero-r296-s881019
```

No collisions, no basename fallbacks, one drawer each. The collection case works.

### And the Amiga floppy resolves to the same key because it is the same build

```
stories/Arthur - The Quest for Excalibur.adf                  → arthur-r54-s890606
InfocomMasterpieces.img : ARTHUR FOLDER/STORY.DATA            → arthur-r54-s890606
```

Both are **release 54 / serial 890606**. `storage`'s module doc names this as a
FEATURE, not an accident: *"a game that moves between disks in a set keeps them."*
Two media carrying one build share a drawer on purpose.

Note the contrast with the case CLAUDE.md warns about: Journey really does differ
across its media (r83/890706 against r30/890322), and here it does too — the
Masterpieces Journey is **r26/890316**, a third build again, and keys apart from
both. The rule is working in both directions.

**A methodological warning for the next reader**: an earlier probe of this same
question returned a basename fallback (`InfocomMasterpieces.img`) and looked like a
serious collection bug. That was the entry name being wrong —
`InfocomMasterpieces/ARTHUR` rather than `InfocomMasterpieces/ARTHUR FOLDER/STORY.DATA`.
Enumerate `MountedDisk::stories()` and use the name the volume itself spells; do not
type one.

## What is left, and it is a DIFFERENT question

One real hazard survives the above, narrower than what this quest was filed on: the
two presses are the same build on **different machines**, and the archive does not
record which.

```
Amiga floppy                    booted as Amiga      screen 320x200 → 640x400 native
Macintosh (PIC.DATA, B/W)       screen 480x300
```

A host Save State swaps memory under a game that never learns it happened, and it
carries v6 screen state in NATIVE pixels plus the palette — so an Amiga snapshot
restored into the Macintosh press restores a 640x400 screen into a 480x300 machine,
with the wrong palette and a face and cell the story was never told about. That is
the SQ-0901 shape: it will look plausible and be laid out for a screen the player
never sees. `reconcile_restored_screen_size` reconciles a restore into a different
PANE, not into a different machine.

`ArchiveMeta` carries an `engine` field and refuses a Glulx save fed to the Z-machine
(SQ-0532-era). There is no equivalent for the machine.

So the question to settle is **not** the key, which is right, but whether the archive
should record the interpreter profile it was made under and what a mismatch should do
— refuse, warn, or merely decline to AUTO-resume, which is the silent path and the
one that surfaced this. Worth filing separately rather than reopening this quest,
because nothing about the save DIRECTORY is wrong.
