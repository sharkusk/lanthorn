CORRECTED root cause direction, per user clarification: "without the quick-save, the screen doesn't clear, but I'm still missing the second question. It looks like this: Can you hear me? >> yes / >" — this is reproducible on a completely clean fresh boot (no reset-game/quicksave involved at all), which rules out the pager/top_anchor/scroll-anim theory entirely. The scroll-clears-to-blank symptom only showed up in the user's real session when going through /reset-game with a pre-existing quick-save — that may be a SEPARATE, second issue tangled up with SQ-1665's reset-game investigation; this quest should now focus on the always-reproducible text loss.

Direct evidence from my own headless probe (real `boot_story`/`finish_command_turn` path, CounterfeitMonkey-10.gblorb, fresh scratch home dir, answering "yes" to each Line prompt in sequence):

- Prompt: "Can you hear me? >>"
- Submit "yes" (turn 1): `result.transcript` == exactly `">"` — nothing else. State's transcript tail after this turn: [..., "Can you hear me? >> yes", ">"]. The expected reply text is NOT here.
- Submit "yes" again (turn 2): `result.transcript` == `"yes\nRight, we're Alexandra now. Before the synthesis, I was Alex. You were...\n\n>"` — the REAL reply to the FIRST "yes" shows up now, one full turn late, mixed in with the echo of the second "yes".

So CM's own printed reply to answering "Can you hear me?" is being delayed by exactly one turn at the engine level — captured by `GlulxSession` only on the NEXT `submit()` call rather than the one it was printed in response to. This smells like a Glk turn-boundary bug: CM likely does something unusual in how it resolves this specific prompt (possibly multiple glk_select cycles, or a deferred print) that our single-drain-per-submit model doesn't fully capture before returning control.
