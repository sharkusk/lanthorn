## What it is

`reveal.rs` states the limitation in its own docs:

> Version 6 raster draws its text as bitmap glyphs on a canvas… `visible_text`
> reads the CELL wrap cache, so on raster nothing lights and `arm` says so rather
> than appearing to work.

Reporting the failure rather than silently doing nothing was the right call in
SQ-1107, and it is why this is a known gap and not a mystery. But it means the
reveal is **dark on every graphical v6 title**, which is where Arthur in extended
mode lives, and the user hit it in play.

## Why it is worth more now than it was

Two things changed on 2026-08-29:

* **SQ-1135** makes the reveal annotate by VOCABULARY rather than by scope — the
  assist set's most visible surface, and the one that most directly serves the
  feature's stated purpose (making IF less frustrating for players without
  nostalgia for it). Dark on graphical titles is dark where the help is most
  wanted.
* **SQ-1107** is being redesigned so that persistent highlighting REPLACES the
  momentary reveal. If the reveal is the only path and the reveal is dark, a v6
  raster player loses the feature outright rather than losing a keypress.

Also worth remembering: **raster is a destination, not a fallback.** A raster-only
gap is a real gap, to be weighed as a full feature rather than as a compromise.

## The shape of the problem

Hybrid mode draws text as terminal cells, so there is a cell buffer to highlight.
Raster paints glyphs into a canvas, so there is no cell to restyle — the
highlight has to be composited into the image, at the position the glyph was
blitted to.

The pieces that already know those positions:

* `render::bitfont`'s per-glyph blit, which places each glyph;
* `TextFace`, which stores the face space and the declared cell;
* `V6FaceSpace::text_scale`, the only arithmetic that turns a provenance into a
  scale.

So the anchor data exists. What does not exist is a record of WHICH glyphs
belonged to which word, which is what a highlight needs — and that is the real
work: a run-level record produced at blit time, keyed the same way the cell path's
wrap cache is, so both surfaces answer the same question from the same shape
rather than growing two.

## Watch for

* **Art density and text density differ, and on the Macintosh colour press they
  disagree** — one native pixel means two different things in one frame. A
  highlight rectangle computed in the wrong space will be half-size or
  double-size on exactly one press and correct everywhere else, which is the
  hardest kind of wrong to notice. See the density table in `CLAUDE.md` and
  SQ-0917 / SQ-1039.
* **Never rasterise what the game printed as a character** (SQ-0750) — this is a
  highlight over glyphs the game drew, not a reason to redraw them.
* Pin both `honor_game_colours` modes: a highlight is a colour, and single-mode
  suites have masked every game-colour regression this repo has had.
