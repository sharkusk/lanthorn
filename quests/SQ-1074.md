## The report

Live, after SQ-1071 landed: *"hints are working, but there is still a black box in
middle of hint screen when showing a hint. this only happen on amiga, mac looks
correct."*

So SQ-1070's other two symptoms are gone — the clue wraps inside its window on
both presses now — and this is what is left. It was filed as SQ-1070's third
symptom with the note that it was "most likely its own defect, a repaint/erase
question"; that reading held, so it is split out rather than left riding on a
quest whose other halves are fixed.

## What is already known about the frame

From SQ-1070's `/dump-windows` capture (`~/Downloads/amiga-shogun-hint.txt`,
Amiga Shogun r295/890321, hybrid, pane 132x60):

* `win0 500x330 at (71,71)` — the clue window, `attrs=1110`, `model: Grid`. The
  story slot holds a **Grid**, so SQ-1026's guard makes the raster path ship no
  transcript prose here and the clue reaches the canvas through
  `build_chrome_canvas` instead. That is by design.
* `win2 169x48 at (235,337)` — **`0 paint run(s)`, `model: Grid — 0 run(s)`**.
  An empty 169x48 window sitting at native (235,337): dead centre-bottom of a
  640x400 frame, which is where a "black box in the middle" would be. It is the
  boot menu's window, left where the title screen put it. **Start here.**
* `win7 640x400` — the full-screen Graphics window.

## Where to look

The Macintosh press is correct on the same route, so the discriminator is
something the Amiga has and the Mac does not. Two candidates, both cheap to test
with `cargo run -p app --example hint_probe -- --windows`:

1. **win2's ground.** An empty window still gets its page filled —
   `fill_window_pages` (SQ-0704) in raster, `draw_erase_fills` / the window bg on
   the cell path. On the Amiga the machine's default page is colour 12 (blue) and
   `AMIGA_DEFAULT_BACKGROUND`/`FOREGROUND` differ from the Mac's, so a window
   whose pair resolves to black would paint a black rectangle where the Mac paints
   nothing or paints white. Check whether win2 is being filled at all, and with
   what, on each press.
2. **`erase_blank_cells_in_rect`'s ground rule (SQ-1054).** The neighbour named
   when this was first filed. A blanks-only erase gated on `Ground` could be
   leaving or laying a block here.

The user reports it in HYBRID (the original report said the black box appeared on
the second viewing; the re-check does not say which path). **Establish which
render paths show it before theorising** — SQ-1056 and SQ-1069 both taught that a
raster-only symptom and a both-paths symptom are different bugs.

## Reproducing

`stories/James Clavell's Shogun.adf` — Amiga, release **295 / serial 890321**.
Route from a fresh boot: 14 intro taps, `hint`, `y`, Return x4 reaches topic
*Erasmus*, hint 6. `crates/app/examples/hint_probe.rs` drives exactly this:

```
cargo run -q -p app --example hint_probe -- \
  --story "stories/James Clavell's Shogun.adf" --windows --runs 0,1,2 \
  --route 'T:14;L:hint;C:y;C:13;C:13;C:13;C:13'
```

State the turn count and the pane size; the original report said the box appeared
on the SECOND viewing of a clue, so drive Return at least twice past the first.

## It is NOT in the model, the composite, or the ring layout

`stories/James Clavell's Shogun.adf` — Amiga, **release 295 / serial 890321** —
driven to the SECOND viewing the original report names: 14 intro taps, \`hint\`,
\`y\`, Return x3 (topic *Erasmus*, hint 6), **\`M\`** back to the menu, then Return
x3 again. 19 turns to the first clue, 23 to the second. (\`M\` must be UPPERCASE;
lowercase \`m\` is ignored and just reveals the next hint, which is a good way to
think you have re-entered the menu when you have not.)

Three layers, all clean:

* **The hybrid pane**, cell by cell, on both viewings. The story viewport is
  ONE uniform ground — `Rgb(66, 66, 66)`, which is the dark grey
  `machine-screenshots/amiga-shogun-hintshown.png` shows — with the clue in white
  on it. No second ground anywhere in the pane.
* **The raster composite**, downsampled to one character per 8x16 native cell.
  Three colours in the whole 640x400 frame: `rgba(136,102,102)` the reddish
  surround, `rgba(66,66,66)` the page, `rgba(255,255,255)` the ink. No black
  rectangle, and the composite does not depend on the pane.
* **The ring's strips**, swept over panes 80x24, 100x40, 120x68, 132x60, 160x50
  and 200x70. Exactly three at every one — two flanks and a top strip — with the
  viewport covering everything else. So this is not a strip drawn where
  `strip_has_art` should have skipped it.

## The `win2` lead is dead, and here is why, so nobody re-opens it

The obvious suspect was `win2`: an empty 169x48 window at native (235,337),
`0 paint run(s)`, sitting centre-bottom of a 640x400 frame — exactly where a
"black box in the middle" belongs. Two things rule it out.

1. Its colours are `fg=Default bg=Default`, so neither `fill_window_pages`
   (SQ-0704, gated on an EXPLICIT bg) nor `fill_painted_window_pages` (gated on
   the window having been painted into) touches it.
2. The `/dump-windows` line `cells: 35x4 at (49,32) as grid (rasterised into the
   ring)` is **where the window MAPS to, not a draw**. `render::screen` says so in
   as many words at that call site: *"Two investigations read a chrome grid's
   full-canvas mapping as a second paint ... and chased an overlap that does not
   exist."* This would have been the third.

## Which puts it in the same place as SQ-1056 and SQ-1069

Model right, screen wrong. That is the placement layer, and CLAUDE.md names the
instrument: `crates/app/tests/pty_stream/`, then `pty_stream/oracle.rs`. Worth
attacking all three together rather than separately — they may be one defect.

## What would shortcut it

A `/dump-windows` taken **on the frame showing the box**, plus **which render mode
it is in**. Hybrid and raster put the middle of the screen on screen by completely
different means — terminal cells versus one virtual image placement — so a
box in one and not the other is a different defect from a box in both, and that
single fact would halve the search. SQ-1056 (raster-only) and SQ-1069
(raster-only) both turned on exactly that distinction.

## Instrument

```
cargo run -q -p app --example hint_probe -- \
  --story "stories/James Clavell's Shogun.adf" --pane 132x60 --paint --windows \
  --route 'T:14;L:hint;C:y;C:13;C:13;C:13;C:M;C:13;C:13;C:13'
```

`--paint` prints the hybrid pane keyed by cell GROUND and the raster composite
keyed by colour; `--windows` adds every live window's box, attributes and colour
pair, and the ring's strips.

## Not reproduced in HYBRID on either press — and the Mac control is now on record

Captured both presses through one identical route under the pty (132x60, hybrid,
`hint` → `y` → Return x3 to a shown clue):

* `stories/James Clavell's Shogun.adf` (Amiga r295/890321)
* `stories/Shogun.toast` (Macintosh r292/890314)

**Neither shows a black box.** Both draw the clue correctly — `6> You have to do
everything you can to keep your ship from…`, wrapped, on their own machine's page:
the Macintosh white, the Amiga dark grey. The two frames are structurally identical
apart from that page colour, which is each machine's own and correct
(`amiga-shogun-hintshown.png` shows the Amiga clue on a dark ground).

Worth stating because the report is \"only happens on amiga, mac looks correct\":
in HYBRID the two presses agree. So either the box is RASTER-only — which is where
SQ-1056 lives, and both were reported after switching modes — or it needs the
second viewing.

## The second viewing is still unreached under the pty

The route sends `text:M` to return to the menu and it does not register: the game
keeps revealing hints (6, 5, 4, then the `3>` prompt) rather than going back. The
same key works in the headless probe (`C:M`), so this is a pty timing or
key-delivery difference, not the game refusing it. Until it is solved the pty
cannot reach the frame the original report describes (\"second time the hint is
selected\").

Two ways forward, in order of cheapness:

1. **Capture in RASTER.** Slash commands work through the pty —
   `text:/set-v6-render raster,cr` at the story prompt before `hint` — which is
   how SQ-1056 was finally reproduced. Do the same here.
2. Solve the `M` delivery (longer waits, or a bare `text:M` with no surrounding
   keys) to reach the second viewing.
