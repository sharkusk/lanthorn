## The report

Live, after SQ-1071 landed: *"hints are working, but there is still a black box in
middle of hint screen when showing a hint. this only happen on amiga, mac looks
correct."*

So SQ-1070's other two symptoms are gone — the clue wraps inside its window on
both presses now — and this is what is left. It was filed as SQ-1070's third
symptom with the note that it was "most likely its own defect, a repaint/erase
question"; that reading held, so it is split out rather than left riding on a
quest whose other halves are fixed.

## What is already known about the frame

From SQ-1070's `/dump-windows` capture (`~/Downloads/amiga-shogun-hint.txt`,
Amiga Shogun r295/890321, hybrid, pane 132x60):

* `win0 500x330 at (71,71)` — the clue window, `attrs=1110`, `model: Grid`. The
  story slot holds a **Grid**, so SQ-1026's guard makes the raster path ship no
  transcript prose here and the clue reaches the canvas through
  `build_chrome_canvas` instead. That is by design.
* `win2 169x48 at (235,337)` — **`0 paint run(s)`, `model: Grid — 0 run(s)`**.
  An empty 169x48 window sitting at native (235,337): dead centre-bottom of a
  640x400 frame, which is where a "black box in the middle" would be. It is the
  boot menu's window, left where the title screen put it. **Start here.**
* `win7 640x400` — the full-screen Graphics window.

## Where to look

The Macintosh press is correct on the same route, so the discriminator is
something the Amiga has and the Mac does not. Two candidates, both cheap to test
with `cargo run -p app --example hint_probe -- --windows`:

1. **win2's ground.** An empty window still gets its page filled —
   `fill_window_pages` (SQ-0704) in raster, `draw_erase_fills` / the window bg on
   the cell path. On the Amiga the machine's default page is colour 12 (blue) and
   `AMIGA_DEFAULT_BACKGROUND`/`FOREGROUND` differ from the Mac's, so a window
   whose pair resolves to black would paint a black rectangle where the Mac paints
   nothing or paints white. Check whether win2 is being filled at all, and with
   what, on each press.
2. **`erase_blank_cells_in_rect`'s ground rule (SQ-1054).** The neighbour named
   when this was first filed. A blanks-only erase gated on `Ground` could be
   leaving or laying a block here.

The user reports it in HYBRID (the original report said the black box appeared on
the second viewing; the re-check does not say which path). **Establish which
render paths show it before theorising** — SQ-1056 and SQ-1069 both taught that a
raster-only symptom and a both-paths symptom are different bugs.

## It is NOT in the model, the composite, or the ring layout

`stories/James Clavell's Shogun.adf` — Amiga, **release 295 / serial 890321** —
driven to the SECOND viewing the original report names: 14 intro taps, \`hint\`,
\`y\`, Return x3 (topic *Erasmus*, hint 6), **\`M\`** back to the menu, then Return

lowercase \`m\` is ignored and just reveals the next hint, which is a good way to
think you have re-entered the menu when you have not.)

Three layers, all clean:

* **The hybrid pane**, cell by cell, on both viewings. The story viewport is
  ONE uniform ground — `Rgb(66, 66, 66)`, which is the dark grey
  `machine-screenshots/amiga-shogun-hintshown.png` shows — with the clue in white
  on it. No second ground anywhere in the pane.
* **The raster composite**, downsampled to one character per 8x16 native cell.
  Three colours in the whole 640x400 frame: `rgba(136,102,102)` the reddish
  surround, `rgba(66,66,66)` the page, `rgba(255,255,255)` the ink. No black
  rectangle, and the composite does not depend on the pane.
* **The ring's strips**, swept over panes 80x24, 100x40, 120x68, 132x60, 160x50
  and 200x70. Exactly three at every one — two flanks and a top strip — with the
  viewport covering everything else. So this is not a strip drawn where
  `strip_has_art` should have skipped it.

## The `win2` lead is dead, and here is why, so nobody re-opens it

The obvious suspect was `win2`: an empty 169x48 window at native (235,337),
`0 paint run(s)`, sitting centre-bottom of a 640x400 frame — exactly where a
"black box in the middle" belongs. Two things rule it out.

1. Its colours are `fg=Default bg=Default`, so neither `fill_window_pages`
   (SQ-0704, gated on an EXPLICIT bg) nor `fill_painted_window_pages` (gated on
   the window having been painted into) touches it.
2. The `/dump-windows` line `cells: 35x4 at (49,32) as grid (rasterised into the
   ring)` is **where the window MAPS to, not a draw**. `render::screen` says so in
   as many words at that call site: *"Two investigations read a chrome grid's
   full-canvas mapping as a second paint ... and chased an overlap that does not
   exist."* This would have been the third.

## Which puts it in the same place as SQ-1056 and SQ-1069

Model right, screen wrong. That is the placement layer, and CLAUDE.md names the
instrument: `crates/app/tests/pty_stream/`, then `pty_stream/oracle.rs`. Worth
attacking all three together rather than separately — they may be one defect.

## What would shortcut it

A `/dump-windows` taken **on the frame showing the box**, plus **which render mode
it is in**. Hybrid and raster put the middle of the screen on screen by completely
different means — terminal cells versus one virtual image placement — so a
box in one and not the other is a different defect from a box in both, and that
single fact would halve the search. SQ-1056 (raster-only) and SQ-1069
(raster-only) both turned on exactly that distinction.

## Instrument


## RETRACTION: the \"garbled header\" was my instrument, not the app

The previous note ended by reporting a garbled hint-screen header on both presses —
`What must I do to survive?` drawn twice, once overlapping `M for hint menu.` — and
suggested nobody had filed it. **That was an artefact of the capture, and there is
no such defect.**

`pty_capture --user-dir` defaults to a THROWAWAY temp directory. The Macintosh body
face comes from `MacOS_6.0.8_System_Startup.img` in the player's `~/.lanthorn/`
(SQ-1036) and the Amiga's topaz from `Kick12.rom` (SQ-1053), so a throwaway home
finds neither and the press falls back to a different face — a different PEN, and
so different run widths and overlapping text. Exactly the SQ-1052 trap, from the
other side.

Re-captured with those two files copied into the user dir, the header is CLEAN on
the Macintosh press: `InvisiClues (tm)` centred, `N for next item.` /
`P for previous item.` left, `(Or use mouse.)` centre, `Return for hints.` /
`Q to resume story.` right. No overlap anywhere.

**Any pty capture of a Macintosh or Amiga press must carry those files**, or its
text layout is of a screen the player never sees:

```
UD=\$(mktemp -d)
cp ~/.lanthorn/MacOS_6.0.8_System_Startup.img ~/.lanthorn/Kick12.rom \"\$UD\"/
cargo run -q -p app --example pty_capture -- --story … --user-dir \"\$UD\" …
```

Geometry read out of the MODEL or the chrome canvas is unaffected — that is how the
band widths and flank extents were measured today — but anything read off the PNG's
text is not.

## REPRODUCED and FIXED — and it is the same call as SQ-1075

### The route the earlier notes were missing

The original report said "the second time the hint is selected". Taken literally it
reproduces every time, under the pty, on `stories/James Clavell's Shogun.adf`
(Amiga, **release 295 / serial 890321**) at the reporter's own **115x34** pane:

```
13 intro taps · hint · y · Return (Erasmus) · Return (a question) · Return (the clue)
   · Q  (resume the story)
   · hint · y · Return (Erasmus)          ← the SECOND visit; the box is here
```

Earlier attempts failed for two separate reasons: they used **132x60**, and they
stopped at the FIRST visit. `text:M` does not deliver through the pty — that is
still true and still unexplained — but `Q` does, and going out to the story and
back in reaches the same screen.

### The measurement that named it

The user's screenshot and the pty capture agree to the pixel: a black rectangle at
device `(208, 324)` size `496x162` — **62 x 9 terminal cells at column 26**.

* **62** is `win0`'s grid width in COLUMNS (500 native px / 8 px per cell).
* **20** is its grid height in rows; 11 topics are drawn, and `20 - 11 = 9`.
* **26** is `13 + (89 - 62)/2` — the grid CENTRED in the 89-column story viewport.

So the rectangle is the undrawn remainder of window 0's grid, in terminal cells
instead of native ones, at a centred anchor.

### The cause: the v6 story Grid was going through the v3–v5 grid renderer

`classify_windows` resolves window 0 to a **Grid** on this screen — the InvisiClues
frame publishes no buffer at all, which is SQ-1026's shape. The hybrid ring then
calls `render_node(&story.node, …)` under a comment that says *"the story window as
real terminal text (primary-Buffer path)"*, and `render_node`'s Grid arm hands it to
`draw_grid`. That function is right for Glulx and v3–v5 and wrong for v6 in three
ways at once:

* it sizes the region as `grid.cols` **terminal** columns, when a v6 grid's columns
  are 8px **native** cells;
* it **centres** that region, when a v6 window has an absolute native origin;
* it **floods** the region with the theme's `upper_window` page — `Rgb(0, 0, 12)`,
  the black box.

This is SQ-1026's rule, unreached on the hybrid side: *"Every reader that wants a
BUFFER pattern-matches for one and declines otherwise; this was the one that did
not."*

### The machine settles both halves

`machine-screenshots/amiga-shogun-hint.png`, calibrated by its own frame (the
reddish border spans image x 37..676 = 640 px, so **native = image - 37**):

* its topic list starts at image **x=108 → native 71**, which is window 0's own left
  edge — **flush left, not centred**;
* the page runs the window's full height with nothing black anywhere in it.

### The fix

Draw a story-slot Grid with `draw_grid_transparent` — *"no border, no centering, no
viewport scroll; `area` IS the grid's absolute cell rect"*, painting only the cells
the game wrote. It is the renderer the v6 layered composite already uses, and it
states all three facts correctly. Metrics stay `None`, exactly as `render_node`'s
Grid arm reported before, so nothing downstream moves.

Three things came with it:

1. **The caret.** `draw_grid` drew one and `draw_grid_transparent` did not, so
   InvisiClues lost the block after its `6>` prompt. `draw_grid_transparent` now
   takes `show_cursor` and applies the same XOR rule; the layered composite passes
   `false` and is byte-identical.
2. **A REVERSED SPACE IS INK, NOT A GAP.** Reported by the user on the first build:
   *"reverse is not happening on the spaces between words"*, and then the tell that
   pins it — *"funny enough, the second time we enter the hint menu the spaces are
   reversed"*. A highlight block is spaces carrying the style bit with **no**
   background, so `ch == ' ' && bg == 0` read them as blank and punched the bar
   apart at every word gap; on the second visit those cells had inherited a real
   background from the clue screen's erase and so survived. The blank test now also
   requires `style & 0x01 == 0`. Same rule `draw_painted_screen` already states for
   the run path (SQ-0484). Before/after at the top of the selected row:
   `..............####################` (centred, solid because the flood filled
   behind it) → `..############################....` (flush left, solid on its own).
3. **The click map.** `v6_hint_menu_mouse` failed, correctly and usefully: SQ-0951
   had taught the map to CHASE the centring, and its wide-pane guard asserted the
   topic list sits ≥40 columns right of the viewport. With the centring gone the two
   arms collapse into one — the viewport's own first column, for prose and grid
   alike — which is what SQ-0951 wanted in the first place ("recorded from the SAME
   numbers the drawing used"). The guard now asserts the opposite property, flush
   left; the assertion between them, that the map equals the drawing, is unchanged
   and is the real subject.

### Tests

`render::upper_window::tests::draw_grid_transparent_paints_a_reversed_space_and_skips_a_plain_one`
and `…_does_not_centre_or_flood` — unit cases, no story fixture, so CI runs them.
Plus `v6_hint_menu_mouse`'s re-pointed guard on `zork0-r393-s890714.z6`.
