--- note 2026-08-27T01:00:18Z ---

## Measured

`stories/anchor.z8`, map hidden, bare pty, booted at 100 columns — where SQ-1084's
fix now correctly puts `A N C H O R H E A D` at column 40, matching `zvm-cli`.
Then a real `TIOCSWINSZ` while it runs:

| | title column |
|---|---:|
| boot at 100 | 40 |
| resize to 140 | 40 |
| resize to 70 | 40 |

So it never moves. That is not the SQ-1084 defect returning — the boot width is
right — it is the separate question of what happens to text already on screen.

## This is arguably CORRECT, and that is why it is filed rather than fixed

Those leading spaces are **characters the game printed**, computed from the width
it was told at the time. A real terminal does not reflow its scrollback either,
and no interpreter re-centres a title after the fact: the game would have to
reprint, and nothing asks it to.

It also runs straight into a principle this project already holds elsewhere —
*prose freezes where it was printed when its window moves* — which was decided
deliberately for v6 and would be contradicted by re-centring here.

## But there IS a real inconsistency behind the complaint

lanthorn re-wraps the transcript, which a plain terminal does not. So on a resize
the paragraphs reflow to the new width while a centred line keeps its original
leading run — and the result is a title sitting off-centre among prose that has
visibly adapted around it. Nothing is wrong per line; the frame as a whole looks
wrong. That is the honest description of what was reported.

## Options, with the cost of each

1. **Leave it.** Matches every other interpreter and the frozen-prose principle.
   Costs nothing and the oddity only shows after a resize.
2. **Re-centre a line that is entirely leading-space + content, on reflow.** Fixes
   the reported case and is a HEURISTIC: it cannot tell a centred title from
   deliberately indented verse, an ASCII-art block, a hand-laid table, or a menu
   whose columns the game aligned itself. Getting that wrong damages output that
   is currently correct, which is a worse failure than the one being fixed.
3. **Do not reflow the transcript at all on resize.** Consistent, and a large
   behavioural regression for ordinary reading.

Recommendation is (1) unless the reported case turns out to be common in practice,
with (2) only ever applied to a line the renderer can prove is a lone centred run
— and never to a block of consecutive indented lines, which is what verse, art and
tables all look like.

## Worth confirming separately, and NOT yet checked

Whether output printed *after* a resize centres at the NEW width. It should:
`declared_story_screen_dims` lets the declared width grow to follow a widened
pane, but deliberately never shrink below `boot_cols` (SQ-0679 — a v4/v5 status
routine reads byte $21 once and thereafter set_cursors to columns it derived from
it, so narrowing under it garbles the bar). So growing should re-centre new
output and shrinking should not. If new output does NOT follow a widened pane,
that is a real bug and a different one from this quest.

## The argument that settles it: we cannot know a line is centred

The user's point, and it is better than the trade-off table above.

**There is no "centre" in the Z-machine.** The story computes an offset from the
screen width in the header and prints spaces. What reaches the interpreter is a
run of spaces followed by text — and that is *bit-identical* whether the author
meant a centred title, an indented stanza, a hand-aligned menu column, an
ASCII-art block, or a paragraph the game chose to inset.

So option 2 above is not a heuristic that needs tuning; it is a guess at intent
the stream does not carry, and it can only be validated by eye, one game at a
time, for ever. Re-centring correctly on Anchorhead's title while silently
shearing a hand-laid table in some other story is a strictly worse outcome than
leaving both alone — the first is cosmetic and only after a resize, the second
corrupts output that is right today.

Recommend **discarded** rather than deferred: this is not "not now", it is "not
determinable from what the game tells us".

The one thing that would reopen it is a change of premise rather than of effort —
if the transcript ever retained the declared width in force when each logical
line was printed, a line could be re-centred by recomputing its ORIGINAL offset
against the new width instead of guessing whether it was centred at all. That is
a real design, not a heuristic, and it would also fix the reflow inconsistency
this quest actually describes. It is not worth building for this symptom alone.
