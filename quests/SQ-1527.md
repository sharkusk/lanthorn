Substantial investigation done, NOT completed — reporting honestly rather than shipping a fake/guessed reader. Worked against the real depacked memory image of Collection Disk 2's "INCREDIBLE HULK" entry (start=$0819, entry_point=$0819, 45099 bytes).

CONFIRMED, high-confidence findings (byte-exact verified, not guessed):
- Dictionary: fixed 5-byte cells starting at $78C3. Cell 0 = "ANY", cells 1-6 = "NORT"/"SOUT"/"EAST"/"WEST"/"UP"/"DOWN" — this lines up EXACTLY with what scott::Vm's run_turn requires (match_noun(word) in 1..=6 drives movement via room.exits[no-1] before the action table is ever consulted), so if the room table were decoded, movement parsing would already work off this dictionary. Synonyms are packed inline with a leading `*` at the same 5-byte stride (e.g. "*MYSE*SELF*BANN*HULK*YOU" = 5 synonyms of some canonical "myself" word, back to back, only the RUN's end is NUL-terminated).
- Room/message text pool: NOT NUL-terminated — LENGTH-PREFIXED strings (1 length byte + that many raw chars, no terminator). Starts at $7DCD right after the dictionary. Tokenizes perfectly for 20 consecutive entries (room numbers 0-19 positionally: entry 0 = "*I'm Bruce Banner, tied hand & foot to a chair" (46 bytes, literal per leading *), entries include "tunnel going outside", "field" x4, "cavern", "small underground room", "fuzzy area", ending entry 19 = "state of limbo" — then an empty entry, then the pool continues straight into game messages ("O.K.", "I see", "Nothing", "special", ...) with no visible header/boundary. So 20 rooms, room text READS solved.
- Item table: also length-prefixed but with an unresolved secondary structure — after a clean text entry (e.g. "Large dome", 10 bytes) some entries are single stray bytes that don't look like real text (e.g. a 2-byte "entry" containing 0x12,'B' right after "Mirror/MIRR/") while OTHER entries in the same stream are clean repeats ("Sign","Sign","Sign","."). Not resolved: is this item-location metadata interleaved at variable width, or something else. Items are NOT confirmed usable yet.

NOT FOUND despite substantial effort — the two blockers to actual playability:
1. ROOM EXITS (6 bytes/room x 20 rooms, or equivalent) — tried: literal-pointer search (exact and ±16-byte window) against every known table address, absolute-address code-reference scanning (LDA/STA/CMP/JSR abs operands landing in the table region — found candidates but none panned out, e.g. an LDA abs,X $8620 turned out to just be mid-message-text, not a table base), small-integer-run scanning (both all-zero-tolerant and variety-filtered, several value ceilings tried) — no candidate matched the expected 6x20 shape.
2. ACTION TABLE — not located at all; no attempt made once exits search stalled, since exits were the harder blocker.

Also tried a full 6502 emulation TRACE (not shipped code — investigation only, `mos6502` as a temporary dev-dependency, now removed): loaded the depacked image into a flat 64KB bus, intercepted $FFD2 (CHROUT)/$FFE4 (GETIN)/$FFE1 (STOP) as RTS stubs, ran from entry_point. Ran 555,578 real emulated instructions across 141 distinct PCs (genuine driver code, not garbage) before halting on an illegal-opcode read at $A7B3 — landed there because regenerator2000-core 0.9.20 ships NO default KERNAL/BASIC ROM images (unlike its newer unreleased main branch), and this driver's boot code disables interrupts (SEI) early, strongly suggesting it polls the CIA keyboard matrix directly rather than using KERNAL GETIN — meaning the scripted-keyboard approach likely never even engages, and the real divergence is from an unemulated hardware dependency. Fixing this needs either real ROM images (a provenance question worth its own thought, separate from this investigation) or CIA-register-level keyboard emulation — both are further, real engineering, not a quick fix.

Conclusion for the coordinator: dictionary and room-TEXT are solved cold; exits and actions are not, and neither static analysis nor an emulation trace closed the gap within the effort this quest can reasonably spend in one session. A `Database` reader built on what's confirmed would have correct room text but no connectivity — i.e. it would not actually be playable, only decorative. Recommending this stay open rather than be forced to a fake "done."
