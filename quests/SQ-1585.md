--- note 2026-09-25T21:13:24Z ---

Investigated at head 61601d48 (worktree agent-ab6853abda830f1aa). Could NOT reproduce in the real TUI code path — no fix written, nothing committed.

1. Traced the app-layer handling of an in-game (story-triggered) @restart:
   - zvm's Machine::restart() (crates/zvm/src/cpu/exec.rs:995-1091) reboots the VM in place and sets a bare `just_restarted: bool` field, consumed exactly once — crates/app/src/session.rs:1920-1945 (`drain_turn`) — which only clears v6 picture/canvas caches.
   - Nothing else in the app layer knows an in-game restart happened: no TurnResult field, no host/turn.rs branch, no `arm_opening_banner` call, no `reset_transcript_sidecars` call, no distinct RunStop/StepResult. `baseline_stale` (pager.rs) is set ONLY by `reset_transcript_sidecars`, which an in-game restart never calls — so the quest's "stale baseline" theory doesn't have a code path to fire through. An in-game restart's title-screen text is simply appended to the ordinary transcript and goes through the completely generic turn-apply path — architecturally distinct from host-driven Reset/Play-Again (host/reset.rs), which DOES call arm_opening_banner (SQ-1575).

2. Reproduced the reported steps against the REAL TUI functions (not just the lib's compose_v6_frame): booted scopa.z6 via `app::host::boot_story`, played to the player's turn, clicked scopa's own "abort" button (590,20) via `app::host::input::deliver_v6_click` — confirmed this returns to scopa's own title screen with a "Help" button (302,91), i.e. this genuinely is Scopa's in-game abort→title flow, not a host Reset. Clicked "Help" (which prints a ~126-row rules screen into the ordinary transcript, going through `apply_game_driven_result`). After EVERY click I called `render::screen::render_story_pane` + `pager::apply_frame` — the exact same pair `main.rs`'s real event loop calls after every drawn frame (main.rs:2156-2168) — so this exercises the actual turn+render+pager pipeline, not just GameSession in isolation.

Result: the pager armed and engaged CORRECTLY on the very first Help opening after abort — `pager.active=true`, parked at `transcript_scroll=97` of a ~126-row total in an 80x30 pane (i.e. showing the first unseen screenful, not the tail). Drained it with the keyboard PagerAdvance equivalent (app::input::page_scroll, mirroring main.rs's Action::PagerAdvance) — 4 steps to catch up, exactly as expected. Reopened Help a second time: pager again armed and engaged correctly (active=true, scroll=96). Both openings behave identically and correctly; no "opens at its last screenful with no [more]" symptom on either one.

Conclusion: with a faithful simulation of the real TUI's turn-processing + render + pager-apply_frame sequence, the reported symptom does not appear at current head. Either (a) the original "host-facing API" observation didn't call render_story_pane/apply_frame between the click and the check (which would produce exactly the reported numbers — pager armed-but-not-yet-activated reads as `active=false`/`scroll=0` until a render resolves it, matching a harness that clicks but never renders), or (b) it's specific to a different, non-lanthorn host's own pagination logic (the quest's "totalRows"/"firstRow" camelCase field names don't match any Rust identifier anywhere in this repo — grepped, zero hits), or (c) it was already fixed by unrelated recent work between d7fd62b7 and 61601d48 (e.g. 7ec7c5e5 "arm the opening pager on reset, like a fresh boot does" = SQ-1575). Did not attempt to distinguish between these three since none of them motivate a lanthorn code change without further evidence.
