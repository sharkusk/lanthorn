  Found while recording SQ-1428's baselines: zvm is 2.43x behind dfrotz on 20k minizork turns, and a macOS `sample` of the release build (6113 samples, 400k turns) puts roughly 47% of samples in malloc/free/realloc + RawVec growth and ~15% in core::fmt. Two per-instruction call sites explain most of it — exec.rs's `opcode_name()` returns a String for EVERY instruction (a `format!("op:{:?}/0x{:02x}", ..)` with a Debug and a LowerHex format for any opcode outside its eight-entry table) yet is consumed only when the instruction faults, and `decode()` builds a Vec&lt;Operand&gt; per instruction which `execute()` then collects into another. Both look fixable without touching semantics; `cargo run --release -p lanthorn-zvm --example bench` is the before/after oracle.
