Extend to cover a 7x12 fallback as well as the 7x15 — but note the two are NOT the same kind of problem, and a second text font is probably the wrong answer for the smaller one.

The Macintosh's 7x15 (FONT 524) is the body face. Its 7x12 (FONT 1033) is the ALT face: `mac/xzip.lst`'s `ZFont` maps `ZALT: TextFont (8)`, and a FONT id is family*128+size, so 8*128+9 = 1033. That makes it the Z-machine **font 3** face — a character-graphics set (box drawing, block elements, cursor arrows), not a typeface. See SQ-1017.

Consequences for this quest:

* X11 misc-fixed 7x14 substitutes for the BODY face cleanly (verified: 194/194 of our subset present, uniform `BBX 7 14 0 -2` / `DWIDTH 7 0`, "Public domain font.  Share and enjoy.", `FONT_ASCENT 12` / `FONT_DESCENT 2`; tarball sha256 702fd1cdef9123e1871622a897727977c0933a420c50c94198f5bb22de8f0f8a, 7x14.bdf sha256 e366d3c685659fb69ab05d5994d3d6debe897d89853f0188a1fca62d1132503f).
* It does NOT substitute for the ALT face. Font 3 glyphs must TILE edge to edge, which is a drawing constraint no text font satisfies. Kuhn's page also puts the extended Unicode repertoire (the box-drawing range) in 6x13/8x13/9x15/9x18/10x20 — the 7-wide fonts are "basic" — so a 7-wide open-source box-drawing set may simply not exist and we would be scaling our own 8x8 masters instead.

**Check first, because this may already be a live defect rather than a fallback gap**: `bitfont`'s font-3 path samples the 8x8 masters with `col = dx * 8 / cw`, which at cw=7 never reaches source column 7. Cropping a column out of a box-drawing glyph can break the join, so a horizontal rule on a Macintosh may be gaining a gap every cell today. `bitfont::tests::the_vertical_rule_stays_one_pixel_wide` pins the vertical case only. If that reproduces it belongs in its own bug, ahead of any font sourcing.
