## The idea

SQ-1041 offers words **this story's dictionary holds**. That is a real
guarantee, but a weak one: `light` being a word does not mean `light lamp` does
anything here. Several suggestions that all fail is worse than silence — the
player spends turns proving lanthorn wrong.

So before showing anything, fork the live game into a silent second session per
candidate, run the candidate command there, keep only what worked, and throw the
sessions away. None of it reaches the screen.

## The machinery already exists, and has been attempted once

- `Engine::save_state() -> EngineSave` / `restore_state()` (`engine.rs:850`) are
  **engine-neutral** and already in the trait — this is the host Save State
  family, not the game's `@save`.
- **[[SQ-0785]]** is the same mechanism for a different purpose (probing the way
  back after a move), tagged `release=0.4 theme=assist`, with a 336-line
  `return_probe.rs` on abandoned commit `5270882c`. **Establish why that was
  abandoned before rebuilding** — the quest says it may simply have lost a race
  with the mapper rework, but find out.
- **[[SQ-1043]]** (warn before an irreversible move) is fork-and-probe again.
  Three features, one mechanism: build it once, deliberately.

Prefer driving a **second session built from the snapshot** over
save/probe/restore on the live one. Restoring under a running game is exactly the
hazard SQ-0587/0588 documented — the game never learns it happened.

## The hard part is the success oracle, and prose is not it

A candidate is dictionary-valid by construction, so the failure being vetted is
*semantic*: "You can't see any lamp here", "That's not something you can open".
Do **not** hardcode English failure phrases — that is the fragility SQ-1041
deliberately escaped when it stopped reading refusal prose.

**Fingerprint the story's own refusals instead.** At session start, in a shadow,
type deliberate nonsense — a word not in the dictionary, and a valid verb with an
impossible noun — and record what the game prints. Those strings become *this
story's* signature of failure, discovered rather than assumed, and they work in
any language and any library. Compare a probe's output against them.

Structural signals worth combining with that, none sufficient alone:

- **The turn counter.** Most games do not advance it on a parser error — but
  `examine` usually does advance it on success, so this separates some cases and
  not others.
- **The object tree before and after.** A changed world proves success; an
  unchanged one proves nothing, since `examine` and `look` legitimately change
  nothing.

Report which combination you land on and what it gets wrong, rather than
claiming a clean oracle.

## Risks that must be handled, not noted

- **Isolation must be total.** A probe that reaches the filesystem, plays a
  sound, or writes an autosave has escaped. `@save`/`@restore` inside a probe
  would be catastrophic. Disable host I/O on a shadow session explicitly rather
  than assuming no game does it on turn one.
- **Daemons and timers advance.** The lantern burns, the thief moves. Harmless
  once discarded — but only if discarded.
- **Nondeterminism.** A game consuming RNG may succeed in the shadow and fail
  live. Rare, real, and worth saying out loud in the docs rather than pretending
  the vet is a guarantee.
- **Cost.** Candidates are already capped at three or four. A Z-machine snapshot
  is tens of KB; a Glulx one can be megabytes. Measure before assuming it is
  free, and this must not stall the turn — the offer appears between the
  player's command and the game's reply.

## The design question this changes, and it is not small

Vetting changes what an assist CLAIMS. Today it says *"this story knows this
word"* — verifiable, modest, and never wrong. Vetted, it says *"this would
work"*, which is far more useful and also a stronger promise that a nondeterministic
game can falsify.

It also touches the spoiler rule in `assist.rs`. The leak is mild — we only
filter suggestions we were already going to make, so the player learns nothing
about actions they did not reach for — but *silence now carries information*
("that wouldn't have worked"). Decide deliberately whether that is acceptable,
and whether the wording should change to match the stronger claim.

**Config-gate it.** SQ-0785 reaches the same conclusion for the same reason: this
is speculative execution of a game the player is in the middle of, and someone
will want it off.

## The wording, decided with the feature (user, 2026-08-28)

Once suggestions are vetted, the line stops describing the dictionary and starts
making a recommendation, and the words should say so.

**Ship: `try instead — light · turn on · burn`**

The user proposed *"you may want to try one of these:"* or *"try one of these
instead:"*. Two corrections applied, both from constraints already in
`crates/app/src/assist.rs`:

1. **Not "you may want to try".** That module forbids the story's second person
   and cites almost this exact sentence as the example — *"You could try turning
   on the lamp' is the game's voice"*. The story owns "you" (*"You are standing
   in an open field"*); a helper borrowing it is the impersonation the register
   exists to prevent. The imperative — *try* — instructs without narrating about
   the player, and is shorter besides.
2. **Not "one of these".** A single suggestion is the common case (Zork I offers
   exactly one for `illuminate`), and *"try one of these instead: light"* reads
   badly. `try instead — light` works at one item and at four, and keeps the ` ·
   ` separator the current line already uses.

## The wording is EARNED by the vetting — do not ship it early

Today's line is deliberately modest: *"this story knows — light"* states a fact
about the dictionary and promises nothing about whether it will work. That is
honest precisely because nothing is vetted.

`try instead` is a **recommendation**. Shipping it without SQ-1121's probe would
make the failure this quest exists to fix strictly worse — confidently telling a
player to try three things that do not work is more frustrating than saying
nothing, which is the user's own argument for the feature.

So: the wording changes **in the same commit** as the vetting, not before, and
the `assist_voice` case that pins the phrasing changes with it.

## Consequence for the silence rule

With vetting, a candidate that fails the probe is dropped, so an offer can shrink
to nothing and the line is not printed at all. That is correct and reinforces
SQ-1041's existing discipline — but note the count now varies for a *second*
reason (the probe, not just the ranking), so any test asserting an exact offer
must state which of the two it is exercising.

## Scope: the VERB panel is NOT vetted (user, 2026-08-28)

Vetting applies to the **suggestion** only. The command band's VERB column
(SQ-1111) keeps listing every spelling the story's grammar holds, unfiltered and
unprobed.

Three reasons, and they are not merely about cost:

**1. They answer different questions.** The suggestion is a *recommendation*
made unbidden, in reply to a failure, and it costs the player a turn to test —
so it should be right. The panel is a *reference*, opened deliberately, and it
answers "what does this story understand", which is a stable fact about the
story and true regardless of where the player is standing. Filtering it to "what
would work here, now" answers a question nobody asked of it.

**2. The cost is not close.** Zork I's column is 248 spellings. Vetting it means
248 shadow sessions, and the object columns already refresh **every turn**, so it
would be 248 per turn rather than once. The suggestion path probes three or four
candidates, once, after a failure.

**3. A vetted panel would be a hint system.** "These are the verbs that work
right here, right now" is very close to solving the room. `assist.rs` forbids
spoilers, and the suggestion filter escapes that rule only because it narrows
candidates the player already provoked by typing something. A panel that quietly
hid every verb that would not work would be telling the player what to do, which
is the hints' job — and the hints wait to be asked.

So: no probe on the panel, and no shared filter between the two paths. If a
future change makes them look like they want the same code, that is the signal
to re-read this note rather than to unify them.
