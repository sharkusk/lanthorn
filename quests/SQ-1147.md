## Re-scoped by the user, 2026-08-30: this is LIVE RE-THEMING, not a file format

> "with omarchy, themes can be selected dynamically and apply to running applications. so this is not support the theme file format, this is dynamically update. (This might be already since the terminal is already updated with the theme colors.)"

Omarchy switches theme at runtime and running applications follow. The question is not "can lanthorn read an Omarchy theme file" — it is "does a lanthorn already on screen change with everything else, or sit there in the old palette until you restart it."

## Checked: it splits three ways, and only the first is free

**1. Anything resolved to a `palette:N` index re-themes for free.** Four of the seven roles default to one — `line` and `accent` are `palette:6`, `muted` is `palette:8`, `alert` is `palette:3` — and an SGR index is recoloured by the terminal itself. Nothing in lanthorn has to notice. The user's intuition is correct for this half.

**2. The terminal DEFAULT foreground and background do NOT, and structurally cannot today.** `term_colors::query_terminal_default_colors` (OSC 10 / OSC 11) carries a hard constraint in its own doc:

> *"Must be called in the pre-UI query window (before the app's own raw-mode/alternate-screen, alongside the image-protocol Picker probe)."*

So they are captured **once**, in a window that no longer exists while the game is running. `text`, `chrome` and `heading` all resolve through `foreground`/`background`, and `resolve.rs` falls back per role to the terminal default when a scheme is absent. A theme switch mid-session leaves every one of them on the colours the terminal had at launch.

**3. Literal RGB never follows anything.** Some defaults are concrete triples on purpose: `sound_beep_high`, `dialog.shadow`, and — as of SQ-1139 tonight — `tooltip.background`, which is a warm pair precisely because no role means "a card lying on the page". Those are a deliberate choice against the palette and would stay put through any theme change. Whether that is right under live re-theming is a real question this quest has to answer rather than assume.

## Two things worth knowing before this is picked up

**The machinery for a live reload already exists.** `watch_style` watches the resolved `style.toml` and reloads on change, warnings and all, through `reload::reload_style` — and `sync_theme_colours` already pushes the re-resolved pairs into the Glulx backend every tick, so a mid-session palette change is not a new concept here. Omarchy points at its current theme with a path under `~/.config/omarchy/`; watching that pointer would reuse proven machinery rather than inventing a channel.

**The hard part is (2), and it may not need OSC at all.** If the Omarchy theme is readable from disk, its background and foreground can be read directly instead of re-queried from the terminal — which sidesteps the pre-UI window constraint entirely. Re-querying OSC 11 mid-session would mean either reclaiming the tty from the input loop or teaching that loop to recognise a colour reply among the bytes it is already reading; `query_sweep` knows how to classify those replies, but it is built for the boot batch.

Worth measuring first, before any design: start lanthorn, switch Omarchy theme, and see exactly which parts of the screen move. That answers "how much of this is already true" for free, and the answer is probably "the map and the accents follow, the page and the panels do not."
