## Reopened — the obvious rule is wrong, and there are now TWO frames that constrain it

An attempted fix landed and was reverted before commit, because the gate caught it
breaking a pinned behaviour. Both halves of the constraint are now known, which is
more than we had, so record them rather than re-deriving them.

### The defect (SQ-1009's "defect 2", user-reported)

Arthur's F3 inventory screen draws its two column RULES as a single reversed SPACE
per row — one white cell, stacked down the screen. So every row below the last
item is a "pure reverse-video row" carrying nothing but two one-cell ticks, and
SQ-0504's rule in `render::v6_layout::fill_reverse_row_gaps` floods the whole row
with the block. The empty rows come out reversed.

Falsifier: `machine-screenshots/amiga-arthur-inventory.png` is a DARK panel with
white text and two white rules — roughly 25,500 white pixels in a 582x398 panel,
against the ~200,000 a flooded one would carry.

### The fix that was tried, and exactly why it failed

The rule attempted: *a pure reverse-video row only floods if its runs REACH BOTH
EDGES of the window* (within the padding a game leaves at the ends of a band it
filled) — the same question `fill_explicit_bg_rows` already asks. Arthur's score
bar reaches both edges; two ticks at native 212 and 412 in a 28..612 window do not.

**It breaks `v6_journey_amiga_frame::journey_amiga_flank_border_is_a_stroke_not_a_
filled_block` on the IBM PC profile**, which asserts the opposite: *"the IBM PC
frame's side border must stay a solid block — it is a reverse-video SPACE in the
game's own output, and thinning it would be the same defect in the other
direction."* Confirmed by disabling the gate and watching that test go green, then
restoring it and watching it fail.

### Why the naive rule cannot work — read this before designing the next one

`fill_reverse_row_gaps` fills **only the gaps** — from x=0 to the first run, between
runs, and from the last run to the screen edge. It never paints the runs
themselves; the glyph loop does that. So **Journey's IBM PC flank border IS the
row-edge gap fill.** That row genuinely must flood edge to edge, while Arthur's
inventory row genuinely must not, and both are rows whose only content is narrow
reversed runs that do not reach both edges. The "reach both edges" predicate cannot
separate them because it is false for both.

Whatever distinguishes them is something else — candidates not yet tested: the
presence of an explicit background colour (`explicit_block`), the number or width
of the runs, whether the window is a status band or the story window, or what the
ART layer underneath says (`region_has_opaque`, which the existing over-art gate
already consults). **Do not pick one by reasoning. Both frames exist; make the rule
answer both before writing it.**

### The test that was removed with the fix, for restoration

`an_isolated_reverse_run_does_not_flood_its_row` in
`crates/app/tests/suites/v6_arthur_amiga_proportional.rs`. Its shape is worth
keeping: boot Arthur's Amiga floppy to the churchyard, `submit_char(135)` for F3,
assert non-vacuously that the upper window really does carry at least 8 lone
reversed spaces, render the raster canvas, then COUNT lit pixels across row 130
(30..610) against the score bar's own block colour and require fewer than 40 —
counted rather than sampled, so a rule cannot be mistaken for a flood or vice
versa.

Pair it with the Journey IBM PC case in the same lane so neither can be fixed
alone.

## A hypothesis for the rule, NOT yet tested

Recorded so the next attempt does not start from the same dead end. The failed
rule asked about ENDPOINTS — do the runs reach both window edges — and that is
false for both cases, which is why it cannot separate them.

**Try COVERAGE instead of endpoints.** How much of the row do the runs actually
account for?

* **Journey's IBM PC frame row** is a bordered frame line: reversed spaces down
  both flanks with the frame's own content between them, so the runs cover most of
  the row and the gaps being filled are narrow.
* **Arthur's inventory row below the last item** is two one-cell ticks at native
  212 and 412 in a 28..612 window — the runs cover about two cells out of
  seventy-odd, and the gaps are enormous.

So a predicate of the form "flood only when the runs already account for most of
the row" would flood the first and not the second, where the endpoint test flooded
neither.

**This is a hypothesis and nothing more.** I have not measured the coverage
fraction on either frame, and picking a threshold from two data points is exactly
how a number gets fabricated. Before writing it: measure the actual covered
fraction on both frames, check it against a third case (Shogun's status band and
Arthur's score bar both legitimately flood and should sit clearly on the flooding
side), and only then choose. If the two clusters do not separate cleanly, the rule
is wrong and something else distinguishes them — say so rather than tuning a
constant until the tests pass.

Other candidates not yet examined, in case coverage does not separate them: the
presence of an explicit background colour (`explicit_block`), the number of runs,
whether the window is a status band or the story window, and what the ART layer
underneath says (`region_has_opaque`, which the existing over-art gate already
consults).

## Root cause — the raster path took a promoted menu GRID for a prose box

The earlier notes on this quest (the reverse-row flood, Journey's flank border) describe SQ-1035's defect, not this one; they were filed here while the two were reported together. This note is about the quest's actual title.

Reproduced on **Shogun r295 / serial 890321** off `stories/James Clavell's Shogun.adf`, 24 intro taps → `look` → `hint` → `y`:

```
native=(640, 400) story=Some((70, 70, 500, 330, "Grid")) chrome=5
  win (0,0)     640x400  Graphics
  win (70,70)   500x330  Grid runs=23     <- the topic list, promoted to the story slot
  win (70,0)    500x70   Grid runs=10
  win (234,336) 169x48   Grid runs=0
raster_metrics = Some(RasterMetrics { total_rows: 78, viewport_rows: 19, max_scroll: 59, .. })
```

The InvisiClues screen publishes **no primary `Buffer`** — a full-screen graphics frame plus three grids — so `classify_windows` falls back to `ring_middle_grid` (SQ-0934) and the topic list becomes `layout.story`. That promotion is for the **rect**, so the ring has a viewport to lay out around; the grid stays in `chrome` so its own 23 runs still reach the canvas. `classify_windows`'s own doc says exactly that — *"a `Grid` in this slot contributes its rect and nothing else"* — and lists the readers that pattern-match for a `Buffer` and decline otherwise.

`build_v6_raster_canvas` was not one of them. It took the promoted grid's box as a prose box and stamped the host transcript into it: **78 rows of scrollback under the topics**, the `raster_metrics` above being the proof it was wrapping them.

The tell the user supplied is what settled it: their own `/dump-windows` output appeared **inside the menu pane**. The game never printed that — only the host transcript can put it there.

## Hybrid was already right

`render_node` dispatches the story surface on its node kind: `WinNode::Buffer(b) if b.primary` → `render_transcript`, `WinNode::Grid(g)` → `draw_grid`. So this is a restoration of parity, not an invented rule — which is also why the report was raster-only.

## The fix

One guard beside the existing `story_window_is_a_canvas` arm: if the story slot does not hold a `Buffer`, finish the canvas there. No prose box and no scroll metrics, exactly as when a plate owns the screen — there is no transcript on this frame.

## Verification

`v6_zork0_hints::a_promoted_menu_grid_is_not_a_transcript_surface_in_raster`, over **both** specimens the neighbouring case uses (Zork Zero r393, Shogun r322) and **both** `honor_game_colours` modes.

Asked by POISONING: a hundred rows of a marker string are fed to a frame that must not show them, and the canvas must not move. That says "the transcript does not reach this screen" rather than pinning a pixel. Guarded against passing vacuously on a blank canvas by requiring the menu's own topics to be inked.

Falsified: removing the guard fails it with `Some(RasterMetrics { total_rows: 100, max_scroll: 81, .. })` — the transcript wrapped into the menu, which is the report.
