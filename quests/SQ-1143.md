## The hang

`stories/sherlock-r26-s880127.z5` (release 26, serial 880127), **object 308**,
has property **43 listed twice** in its property table. ZMSD §12.4.1 mandates
descending numerical order; `get_next_prop` (§12.4.3, `objects.rs`) scans for the
given number and returns the one *after* it, so on a repeated number it returns
the SAME number and any `while prop != 0 { prop = get_next_prop(…) }` loop never
terminates. Measured chain: `51, 50, 47, 46, 45, 44, 43, 43, 43, …`

`zvm::objects::ParseNames::detect` → `candidate_properties` walks EVERY object's
property list, so it hits 308 on every call and never returns. `app`'s
`session.parse_names()` is a `OnceCell` initialised by the first `Introspect`
object query, so the command band's object columns, scope completion and the
momentary reveal all freeze lanthorn on Sherlock. `zvm::location`'s
`object_text_property` (the status-line room-text probe) has the same unguarded
loop and hangs if the room ever *is* such an object.

Two walks were already guarded and are the pattern: `app::session`'s debugger
walk (`if next >= prop { break; } // must strictly descend; else corrupt`) and
`zvm::world`'s scenery vote (a `guard < 64` counter).

`get_next_prop` itself must NOT change — it is the opcode implementation and
games depend on its exact semantics. The guard belongs in the readers.
