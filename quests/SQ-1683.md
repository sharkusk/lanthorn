--- note 2026-10-02T20:28:22Z ---

Two items from SQ-1679's original request that the shipped documents feature (documents.rs, ifdb_documents.rs) does not do yet. The per-game folder <user_dir>/documents/<Title> [<TUID>] and "link to IFDB first" for unlinked games stay as they are.

1. In-place discovery: documents the user already keeps next to a story file (same folder, matching the story's stem, e.g. Zork1.pdf beside Zork1.z3) or in a docs/ (or documents/) folder beside it are listed for that game WITHOUT being copied, alongside the per-game folder's files. DocEntry gains a source field (in the game's documents folder / found beside the story) so hosts can label them; documents::remove must refuse found-in-place files (never delete the user's own files). Since one documents folder serves every release of a game, a listing for a story should include in-place files found beside ANY known copy of that game in the library only if that is cheap; at minimum the copy being played.

2. Content de-duplication: documents::import and the IFDB download (save_document / DocJob::Download) compare against the folder's existing files (size first, then a hash) and skip a byte-identical file instead of writing "manual (2).pdf", reporting it as already present (a DocEvent/return value that says so). Also de-duplicate the combined listing in item 1 when an in-place file is byte-identical to one in the documents folder (show it once).
Tests: a re-download of the same manual adds nothing; an in-place PDF is listed, labelled and cannot be removed; a duplicate between the two sources lists once.

--- note 2026-10-02T20:29:52Z ---

Owner decision 2026-10-02: item 1 (in-place discovery of manuals beside the story file or in a docs/ folder) is DROPPED. Detecting them needs a naming convention and gets messy; users should move their files into the game's documents folder instead. Only item 2 (skip byte-identical downloads/imports, report them as already present) remains in scope.
