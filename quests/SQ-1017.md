## Measured: the Macintosh's own font-3 set does NOT fit lanthorn's Macintosh cell

Dumped from `InfocomMasterpieces/ARTHUR FOLDER/ARTHUR`, `FONT` 1033 (7x12, advance 6):

    code 54 (full block)   ######..  x 12 rows      cols 0-5, rows 0-11
    code 40 (vertical)     ...#....  x 12 rows      col 3
    code 38 (horizontal)   ######..  on row 7       cols 0-5
    code 65 (quadrant)     ####....  rows 4-11      cols 0-3

Every glyph advances **6** and is **12** tall. The cell SQ-0917 declares for this machine is **7x15**. So the "full block" covers 6 of 7 columns and 12 of 15 rows, and adjacent cells would show a 1px vertical and 3px horizontal gap. **Font 3's entire purpose is to tile**, so a set that leaves gaps is worse than no change at all, and making it fit means resampling 12 -> 15 — which is the defect SQ-1011 exists to avoid, and worse here, because a resampled quadrant boundary lands on a fractional row and the join breaks where a letterform would merely soften.

By contrast `bitfont`'s 8x8 masters are built to be sampled into an arbitrary `cw x ch`: the full block is `0xFF` on all eight rows, so every destination pixel inks at any cell size and it tiles exactly by construction.

## They agree on MEANING, which is why substitution is legitimate

`font3_translate` maps code 65 to `U+2596` (quadrant lower left); 1033's code 65 inks columns 0-3 of 6 and rows 4-11 of 12, which is that quadrant. Same standard repertoire, different drawing. So this is not "we are showing the wrong characters" — it is "we are drawing the right characters in our own hand", which for a graphics set that must tile is the better trade.

## Why the Amiga case is NOT this case

Journey's Amiga `Char.data` is **8x8** — exactly our master size — so it blits 1:1 with no resampling and is a genuine candidate for drawing that machine's own rules. The Macintosh's 7x12 in a 7x15 cell is not. `vga16`'s header pairs the two machines as one argument; on this evidence they are different questions and should stop being cited together.

## Before closing: one sweep still owed

Four glyphs were checked, not the whole set. Dump every code 1033 defines and compare against `font3_translate`'s 32..126 table, confirming there is nothing in the Macintosh's set that ours has no shape for. If that comes back clean this should be closed as **no change needed** rather than fixed — with the finding recorded, because "the release ships a font we ignore" will look like a bug again to the next reader.

Also worth noting, and unexplained: 1033 advances 6 where the declared `colWidth` is 7, and is 12 tall where `lineHeight` is 15. On a real Macintosh, font-3 runs therefore tile among themselves at a 6px pitch that does NOT align to the text column grid, and vertical rules would show a 3px gap per line. Either `mac/xzip.lst` sets a different line height under `ZALT`, or Macintosh v6 titles never draw continuous font-3 rules. Do not build on the current reading without settling that.

## The obvious hypothesis is FALSIFIED: Journey's Macintosh rules are not drawn from 1033

Measured off `machine-screenshots/mac-journey.png` (colour press, 652x421 window capture).

Journey is the title that unquestionably prints font-3 rules — CLAUDE.md's own SQ-0750 note has lanthorn rasterising "200 `|`s" per frame for it. So its Macintosh menu strip is where FONT 1033 should be visible if it is used anywhere.

**The menu strip runs on a 15-row line**, same as the prose:

    menu column x266..380   ink row tops 323, 337, 352, 382   pitches 14, 15, 30
    prose       x266..640   ink row tops 37, 52, 67, 97, ...  pitches 15, 15, 30

**And the vertical rules are unbroken.** Column x=386 over y=315..420 is a single run of 76 dark pixels; x=512 the same. A 12-tall glyph on a 15-row line must show a 3px gap every line, and there is not one.

So those rules are NOT FONT 1033's code 40 at the text line height. Either the interpreter draws font 3 by some other route (QuickDraw primitives rather than the bitmap face), or those particular separators are not font 3 at all.

## What this leaves

* **What 1033 IS is settled** — the bitmaps are unambiguous: 54 a full block, 40 a single column, 38 a bar on row 7, 65 a lower-left quadrant. It is a font-3 graphics set and not a typeface.
* **What any Macintosh story USES it for is unknown**, and the single most likely candidate has now been checked and does not match.
* `mac-arthur.png` adds nothing for it either: Arthur's border, knotwork and pillars are all ARTWORK, and its status bar is inverse text in the body face. No font 3 is visible on that frame at all.

## And it does not scale into any Macintosh cell we can observe

12 does not divide 15, and 1033's advance of 6 does not match `colWidth` 7. Every window measurable in either capture runs on a 15-row line. There is no observed Macintosh grid that a 6x12 glyph tiles into.

(Recorded and NOT built on: 480/6 = 80 and 300/12 = 25 exactly, so 6x12 would give the MONO press a clean 80x25. The colour press's 640x400 gives 106.7 x 33.3, so the fit is mono-only and 480/300 are divisible enough that this is probably coincidence. Do not reason from it without independent evidence.)

## Disposition

This strengthens **no change needed** considerably. We cannot demonstrate the Macintosh used this face for anything visible, our own 8x8 masters cover the same repertoire and tile at any cell by construction, and 1033 cannot be used at 7x15 without a resample that breaks the joins.

Before closing, the two things still owed are unchanged: the code-by-code coverage sweep against `font3_translate`, and — if anyone wants to settle the mystery rather than route around it — finding what `mac/xzip.lst` does between `ZFont(ZALT)` and the actual draw.

Relevant to the modelling question either way: `set_font` mirrors into window property **12** only. Property 13 (font size) is set once from the machine cell — `w.font_size = (cell.h << 8) | cell.w` — and never varies with the selected font. If a real interpreter reported a font-3 window's size as 12x6, a story reading prop 13 would get a different answer from us. No evidence yet that any story asks.

## Correction to my own note above

I wrote that "`vga16`'s header pairs the two machines as one argument". **That is wrong** — I checked, and that header's font-3 paragraph is Amiga-only and correct as written. No edit was made there. The overstatement was mine; the finding about the Amiga and the Macintosh being different cases still stands on its own.

The header that actually was wrong is `blorb::mac_font`'s, which called `FONT` 1033 one of "the fonts worth drawing with" and said it "gives every drawn character the same advance, so it drops into the cell model cleanly". Wrong twice — it is not text, and it does not fit. Corrected.

## Findings written down, quest deferred

## Why DEFERRED rather than closed

Closing it would say "no change needed", and the honest position is weaker than that: we know what the resource is, we know it does not fit our cell, and we do **not** know what the machine used it for. The one title that should have shown it does not. That is an unresolved question about the hardware, not a settled decision about our renderer — so it waits for evidence rather than being written off.

What would move it: `mac/xzip.lst`'s actual draw path after `ZFont(ZALT)`; a Macintosh capture of a frame that visibly uses font 3 (a map screen, or Journey at a different moment); or the code-by-code coverage sweep, which would at least bound what we could be missing.

Nothing about this blocks anything. Our 8x8 masters cover the same repertoire and tile at any cell by construction.
