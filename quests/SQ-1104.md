## Why a prompt at all: there is no mechanical oracle

lanthorn writes characters to a terminal; the font belongs to the terminal. No
escape sequence asks "do you have U+F1A60". The near-miss — writing a glyph and
reading the cursor position back — measures the terminal's assigned WIDTH, which
detects double-width emoji but **not tofu**, because a missing-glyph box is still
exactly one cell. `examples/gallery.rs` can report `NO GLYPH ANYWHERE FOR:` only
because it loads `.ttf` files directly as an offline dev tool.

So the human eye is the oracle. Measured on this machine (8 text faces, cmap scan):

| glyph class | faces carrying it |
|---|---|
| dingbat stars `✦ ✧ ✺ ✴`, `★`, `☀` | 2/8 |
| `☼` U+263C | 4/8 (missing JetBrains Mono, SF Mono, 0xProto) |
| `●` U+25CF | 6/8 |
| **Nerd Font lamp glyphs** | **6/8** (missing only Menlo and SF Mono) |

Every Unicode character that *looks like a light* scores 2–4. The Nerd Font icon
ties `●` and is the only option that reads as a lamp. Same trap as SQ-0989, where
`⊙`/`⊗` drew tofu in Fira Code.

## The design

**Ask by comparison, not yes/no.** A yes/no on one glyph invites "I see
*something*" — and the something may be the terminal's font FALLBACK drawing it
from another face at wrong metrics, which is a "yes" that yields a subtly
misaligned map forever. Show two rows, ask which looks right; tofu and
misalignment are both obvious side by side.

**Sample one glyph per source family.** The presets are not one font:
`Arrows::nerdfont` uses MDI chevrons (F0143), `PortalGlyphs::nerdfont` uses Font
Awesome (F111, F08B), stairs use MDI (F12BD). A partial patch may carry some and
not others.

**Write a preset NAME, not expanded overrides.** `[symbols] preset = "nerdfont"`,
one line — so a future improvement to the preset still reaches the user.
Expanding to forty `arrow.north = "3"` entries freezes them at today's
choices and makes the config unreadable.

**Esc means plain, and is recorded**, so it never asks twice. Re-runnable from
settings, because people change fonts far more often than they reinstall.

## The hazard: "no config.toml" is the NORMAL state of the test harnesses

Fourteen group binaries boot the app, plus `gallery` and `pty_capture`, mostly
against fresh temp user-dirs. A blocking first-run prompt keyed on a missing
config hangs them — and a tty check alone does NOT save you, because
`pty_capture` runs under a real pty by design. Decide this before writing the
prompt, not after the gate goes red.

Two guards, and both are wanted:

1. **`--font-check on|off`** — 3 touches total. `Opt::valued(&["--font-check"])`
   in `crates/cli-host/src/args.rs`, one branch in `startup.rs`, one line in
   `crates/app/tests/pty_stream/driver.rs`. Three states: absent = ask only when
   there is no config; `on` = ask now regardless (the changed-font case); `off` =
   never ask. Bare noun, no `set-` prefix — matching `--sound`, `--images`,
   `--accel`, `--guidance`.
2. **An empty `config.toml` written by the harness driver** — `driver.rs:576`
   already does `create_dir_all(&spec.user_dir)`; one more line makes the
   first-run condition false for every harness at once, and
   `config_template.rs:594` skips seeding when the file exists, so an empty file
   is respected rather than overwritten. `gallery.rs:897` and
   `pty_flank_alpha_seam.rs:134` already do this by hand.

Guard 2 is the durable one: a future harness building its own `Spec` inherits it
without knowing any of this. Guard 1 is the user-facing feature, and its real
value is the RE-CHECK, not the bypass.

**`/run-font-check`** is the slash spelling (verb-noun, per the registry
convention), and is the affordance that actually gets used — a CLI flag can only
ask at launch, while someone who just changed their font wants to check it
against the terminal they are looking at. Same routine behind both.
