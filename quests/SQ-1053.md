## Why the SQ-1037 cascade never fires on the Amiga

Not a defect in the cascade — the MEDIA. `font_scout` over the three Amiga floppies:

```
Arthur   char.data  10x10 proportional  <- in use   body Some((10,10)) from Some(Release)
Shogun   (no face detected)                         body None
Journey  Char.data  8x8                             body None
```

Shogun ships no typeface at all; Journey's `Char.data` is the 8x8 font-3 GRAPHICS set — box drawing, not letters — correctly declined (SQ-1017). And the user's Workbench 1.2/1.3 volumes carry **only `topaz/11` (8x11)**; everything else on them is a proportional display face (ruby, opal, sapphire, diamond, garnet, emerald) that no Infocom interpreter used. `font_scout` DOES consult `~/.lanthorn`, and returned `body None` for both — so the system rung was asked and honestly declined.

The face the Version 6 interpreter actually drew with is **topaz 8**, which lives in Kickstart ROM and was never on a Workbench disk.

## The face, measured

`machine-screenshots/amiga-shogun-game.png`, the word `Erasmus` in "This is the bridge of the Erasmus":

* **10 distinct scanlines across a 20-row band** — every face row is drawn twice, so the glyph band is **8 face rows** doubled to a **16-row line**.
* **~8 native px per character** (the underline spans 60px over 7 characters).

So topaz 8 is **8x8 at a TEXT SCALE of (1, 2)**, which lands exactly on the declared 8x16 cell. That is the 640x200 hires mode: a text pixel is 1:1 with the native 640 horizontally, and a square-pixel screen doubles it vertically to 400. Confirmed by the user.

## The ROM struct is locatable

`~/.lanthorn/Kick12.rom`, 262144 bytes, so the base is `0xFC0000` (a 512K image maps at `0xF80000`). Scanning for `TextFont`-SHAPED structures — ysize 6..12, xsize 6..10, `0 < baseline < ysize`, `lo < hi`, and both `tf_CharData` and `tf_CharLoc` pointing inside the image — finds exactly two:

```
TF@0x90bc   8x8  baseline=6  lo=32  modulo=192  chardata=0xfc90f4  charloc=0xfc96f4   <- topaz 8
TF@0x849a  10x9  baseline=6  lo=32  modulo=240  chardata=0xfc84d2  charloc=0xfc8d42
```

`topaz.font` as a string sits at `0x8498`, `0x18e12`, `0x1bd68`, `0x1bd74`, `0x2c94c`, with pointers to those at `0x84a8`, `0x90ca`, `0x18e0a`, `0x1bd58`, `0x1bd60`, `0x2c944` — usable as a tie-break, but note that decoding a `TextFont` at `name_ref - 10` does NOT line up, so the shape scan is the reliable route.

**Do not hardcode `0x90bc`** — other Kickstart revisions and sizes differ.

This is the same `TextFont` `blorb::amiga_font` already parses (`tf_CharLoc`, `tf_CharKern` + `tf_CharSpace`, `tf_BoldSmear` at `TF+28`). A ROM font is that struct with ABSOLUTE pointers rather than file-relative offsets, so it is pointer relocation, not a second parser.

## The wrinkle this exposes

`zvm::interpreter::V6FaceSpace` (SQ-1039) is keyed per MACHINE, and the Amiga row says `Art`. That is right for Arthur's `char.data` — authored in the 320-wide picture space, measured at (2,2), its 10 face rows becoming a 20-row declared line and its advances doubling (12, 10, 10, 10 native px steps). ROM topaz is authored in the 640-wide HIRES space and wants (1,2). **Two faces on one machine wanting different scales**, so face space has to become a property of the FACE's provenance rather than the row.

## Do not commit a Kickstart ROM

It is copyrighted Commodore code. Tests get a SYNTHETIC fixture with a generator script, the way `unit_tests/mk_sysfont_hfs.py` does.

--- note 2026-08-24T18:00:55Z ---

Landed in ff4227ec (branch: this worktree, not yet merged to main).

**Where the name pointer actually sits.** The note above is right that `name_ref - 10` does not line up: in Kick12.rom the `topaz.font` pointer is at **TF+14**, not the `ln_Name` offset of 10 that `struct Message` implies — both records agree, and both carry `0xC000000A` at +10 and `0x9414` at +18. Rather than assume +14 (which a different revision may move), `faces_in_rom` SEARCHES the 20-byte `tf_Message` preamble for the one word that resolves to a `<stem>.font` string. That doubles as the strongest filter: with FPF_ROMFONT + whole-array bounds + a resolvable `.font` name, a wide size band (ysize/xsize 1..64) over the whole 256 KiB yields exactly the two known records and no false positives.

**Base rule.** `0x1000000 - len`, accepted only for 256 KiB / 512 KiB / 1 MiB. No revision anywhere.

**Face space.** `V6FaceSpace::Hires` added (`text_scale = (1, art_scale.1)`); `MachineProfile::v6_face_space` renamed `v6_release_face_space`; `V6SystemFace::face_space()` carries the system half beside the name. `native_font::face_space(profile, origin)` is the single provenance→space rule and derives from the stored ORIGIN, so `reload.rs`'s re-test against a changed profile re-scales rather than carrying a stale answer.

**fit.** Now `fit(face, profile, scale)` with the fixed-pitch test asked of the FACE alone (all printable advances equal) and the cell test measured at the face's scale. Keeping those separate is what still refuses Journey's/Beyond Zork's 8x8 font-3 set — folding the cell into the pitch test would read it as proportional.

**Renderer.** `TextFace::draws_scaled(style)` routes a scaled FIXED face through `blit_metric_glyph`; the cell blit's `f.height == ch` filter would have declined an 8-row face into a silent vga16 fallback (the SQ-1011 shape).

**No new config key** — `system_font_disk` is a filename substring and covers `*.rom`.

**Fixture.** `unit_tests/kickfont.rom` (synthetic, 256 KiB) + `mk_kickfont_rom.py`; `/unit_tests/*.rom` gitignored with that one file negated, so a real Kickstart dropped there cannot be committed.

**Verified against real media** (`amiga_rom_face`, skips vacuously without it): Kick12.rom yields `["topaz/9", "topaz/8"]`, the production lookup over the real `~/.lanthorn/` offers `["topaz/9", "topaz/8", "fonts/topaz/11", "fonts/topaz/11"]` and the cascade admits the 8x8; Shogun r295/890321 and Zork Zero r366/890323 off their `.adf`s boot with no face of their own and come up on topaz 8 at (1,2), cell still 8x16.

Falsified four ways, each reproducing the reported symptom. Gates: nextest gate 0 with 6108/6108, clippy clean.

Left for the user's eye: how topaz 8 actually LOOKS in `/set-v6-render raster` on Shogun and Zork Zero (hybrid draws text as terminal glyphs, so it shows nothing).
