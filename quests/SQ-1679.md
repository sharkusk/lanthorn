--- note 2026-10-02T18:16:54Z ---

Goal: a game's physical-release extras (manual, feelies, maps, reference cards; usually PDFs, sometimes image scans) are found and listed by the lib, stored once per GAME, and shown by each host in its own way. Example: Zork I has several releases (r88, r52, Amiga/Mac disk copies...) but one manual; it must not be stored or listed once per release/save key.

Requests (host-agnostic):
1. Where they live: in the shared catalogue (SQ-1676), keyed by the IFDB game (TUID) so every release linked to that game shares one set; a story not linked to IFDB falls back to its own story key, and when it is later linked (or relinked) its documents move/merge into the game's set.
2. Discovery without copying: documents sitting next to the story file or in a docs/ folder beside it (common in IF Archive and Infocom bundles) are found in place and listed, not copied. Only files a host explicitly imports are copied into the catalogue.
3. De-duplication: identical files kept once (content hash), whether found in place or imported, so two copies of the same manual never list twice.
4. A public list function: for a story (or its catalogue dir/TUID), return its documents with display name, kind (pdf/image/text), size, absolute path, source (found beside the story / imported) and a stable id. Hosts decide how to show them.
5. Public import and remove functions for host-added files (remove only deletes imported copies, never the user's own files found in place).
6. Atomic writes, as for the other shared catalogue files.

TUI (optional, cheap; no PDF rendering needed): a Documents list in its info panel or a dialog; open the selected file with the system viewer (open / xdg-open); in terminals with OSC 8 support show file:// hyperlinks; in its Docker hosting serve the files over HTTP as download links next to the terminal.
Out of scope for the lib: viewers and upload UI, which are per host.

Maintainer decisions 2026-10-02:
- DROP discovery beside the story file entirely. Documents live only in a dedicated per-game folder that the user (or a host import) fills: ~/.lanthorn/documents/<IFDB TUID>/, in the shared catalogue, keyed by game across releases.
- lanthorn creates that folder AUTOMATICALLY, with a placeholder text file named "<game name>-docs-go-here.txt" (game name = the actual title), so the user knows where to drop files.
- The story info box shows the documents folder's location.
Still wanted from the request: the listing API (name, kind, size, path, stable id; the placeholder excluded), import/remove for host-added files, atomic writes.
Open (coordinator's proposals): create on first play or on IFDB link, not at library scan (no mass dirs); unlinked games get no folder until linked (avoids the move/merge on link); sanitise the title for the filename; content-hash dedup no longer needed with one user-managed folder per game; Docker download links deferred to their own quest.

FINAL PLAN (maintainer, 2026-10-02):
- Folder: <user_dir>/documents/<Title> [<IFDB TUID>]/, shared by every release and every player.
  - Found by the bracketed TUID, never by title, so an IFDB title change renames nothing and can't produce duplicates.
  - Title sanitised for filenames.
  - NO placeholder file; the readable folder name is enough.
- Created automatically as soon as a detected game has an IFDB TUID: at library detection for already-linked games, and when the background IFDB fetch, link or relink delivers one. Not on first play. Unlinked games get no folder.
- A relink to a different TUID creates the new game's folder and never touches the old one (the user's files).
- The story info box shows the folder path.
- Host API: list (name, kind, size, path, stable id), import, remove (imported copies only), atomic writes.
- Dropped: discovery beside the story, content-hash dedup, placeholder.
- Deferred: Docker HTTP download links (own quest), an in-TUI document viewer or list.
