## The report, with a machine control beside it

`stories/James Clavell's Shogun.adf` — Amiga, release **295 / serial 890321** —
on the CLUE screen (`hint` → `y` → Erasmus → a question → Return), hybrid-ring,
pane **110x42**. The user supplied `/dump-windows`
(`~/Downloads/amiga-shogun-hintcorruption.txt`), a screenshot of the frame, and the
matching machine capture. **Both render paths show it** — hybrid and raster alike,
because both rasterise the banner through `build_chrome_canvas`.

### What the machine draws (the control, user-supplied)

```
    ┌──────────────────────────┐
    │What must I do to survive?│   ← line 1, REVERSED (white block, dark ink), centred
    └──────────────────────────┘
        M for hint menu.          Return for a hint.
        (Or use mouse.)           Q to resume story.
```

### What lanthorn draws

```
       What must I do to survive?          ← line 1, NOT reversed: dark red on the
                                             reddish banner, nearly invisible
       M for hint menu. What must I do to int.   ← line 2: the title AGAIN, drawn over
                                                   "Return for a hint." — the visible
                                                   `int.` is that run's own tail
survive?    (Or use mouse.)     Q to resume story.  ← line 3: the wrapped remainder,
                                                      stranded at the far LEFT
```

So there are **two** faults on one run, and they may be one cause or two:

1. **The title's reverse block is missing** on line 1, where the machine draws a
   solid white bar with dark ink. Compare SQ-1074, where the same press's topic
   SELECTION lost the reverse on its inter-word spaces — a reversed space is a
   space with the style bit and no background, and more than one reader has treated
   that as blank. Check whether this is the same rule at a different site.
2. **The title is drawn a second time**, starting where `Return for a hint.` belongs,
   and **wraps** to the next line — `survive?` landing at column 0 of line 3 is a
   word-wrap, not a clip.

The wrap is the sharper clue. SQ-1071 established the Amiga's regime as
`BufferMode { unbuffered: CharClip }` — this machine ignores window attribute 0 and
follows `buffer_mode`, and an unbuffered window **clips at the right margin, it does
not wrap**. A run that wraps onto the next line in this window is therefore already
outside what §8.8.3.1.1 allows for it, whatever put it there.

Twelve runs in a four-row banner. **Print all twelve with their native x/y and
style bytes first** — if the title appears twice among them the defect is upstream
of the renderer (zvm's run recording, or the game genuinely printing twice into a
window whose box moved between the two); if it appears once, the second copy is
ours and the renderer is duplicating or re-flowing it.

Note `recent render paths`: `raster x62 · … · hybrid-ring x102`, so the session
crossed modes, and the user reports the fault in both.

## FIXED — the game had turned the SCREEN OFF and we printed anyway

Traced the banner's prints with their window, pen and stream state. Three
consecutive trace lines answer it outright:

```
@output_stream(-1)                                        ← stream 1, the SCREEN, OFF
PRINT win1 pen=(318,17) "What must I do to survive?"      ← printed anyway
@output_stream(1)                                         ← screen back ON
```

Window 1 sits at native x=70, so pen 318 lands at absolute **388** — exactly where
the duplicate run was measured. The game deselects the screen, prints the topic
title to walk the cursor to its width, and reselects. It is a measuring idiom, and
`stream1 = false` was set and **never consulted by the v6 paint branch**:
`self.streams.stream1` had exactly one reader in the whole engine, in the STREAMING
prose branch, several hundred lines below the paint branch's early return.

That is the whole of it. Everything else on this frame follows:

* `Return for a hint.` had already been drawn at 418..562; the hidden title
  overwrote it from 388, and what survived was the tail from the next character
  boundary — `int.` at 530, which is exactly the residue this quest's first note
  measured.
* The Amiga then **wrapped** the overflow, stranding `survive?` at the far left of
  the row below. The **Macintosh does the same thing** and was never a control: its
  window is 640 px rather than 500, so the whole title fits and it merely ate `Re`,
  leaving `turn for a hint.`. The first note's "both presses" was right and the
  wrap regime was a red herring — the wrap is downstream of a print that should not
  have happened at all.

### The fix

The v6 paint branch honours stream 1: no run, no grid cell. **The cursor still
advances**, which is the point of the idiom and is the rule the streaming branch
already states for its own diversion — *"Only the DESTINATION changes here.
Everything the game can observe — the window cursor (props 4/5) … — happens either
way."* Freezing it would hand the game a width of zero for a string it just printed.

Both presses now read exactly like `machine-screenshots/amiga-shogun-hint.png`:

```
        What must I do to survive?
  M for hint menu.        Return for a hint.
  (Or use mouse.)         Q to resume story.
```

Tests: `zvm::cpu::exec::tests::v6_a_deselected_screen_paints_nothing_but_still_advances_the_cursor`
and `…_writes_no_grid_cells` — pure engine cases, no story fixture. Falsified by
reverting the guard: both fail, the second with `got "HIDDEN"`.

Gate 0 (6139/6139), clippy clean.

## STILL OPEN — the title's reverse block, and the rule that suppresses it

Fault 1 of this quest is untouched and is a separate question. The title run carries
`style=3` (reverse set) with INHERITED colours, so `chrome_run_ink` takes its
SQ-0487 arm: *"inherited colours + reverse over frame art must NOT paint an opaque
block — the original renders dark ink directly ON the art"*. Over the reddish banner
`over_art()` is true, so we draw dark ink and no bar, while the machine draws a solid
light bar with dark ink.

**Two machine captures together falsify the current rule and constrain its
replacement**, and both are already in the repo:

* `machine-screenshots/amiga-zorkzero.png` — the game screen's ribbon. `Banquet
  Hall`, `Moves: 0`, `Flatheadia`, `Score: 0` are dark ink **straight on the scroll
  artwork, no block**. This is SQ-0487's own frame and its premise is CORRECT.
* `machine-screenshots/amiga-zorkzero-hint-result.png` — the same game's hint
  banner. `surviving Megaboz's attack` **is** a solid light block with dark ink, on
  the same reddish frame art.

So "is there opaque art behind the run" cannot be the discriminator: one machine,
one game, both answers. Do not simply invert SQ-0487 — that would put a block back
across Zork Zero's ribbon, which the capture above shows is wrong.

What to look for instead, in rough order of cheapness:

1. Whether the two runs really do both arrive with inherited colours, or whether the
   hint banner names a pair we are discarding — the Amiga's machine-global pair
   (SQ-0847, `v6_page_pair`) is a candidate for something that should count as
   explicit at this site and currently does not.
2. Whether the WINDOW differs in a way we already model (attributes, its own
   fg/bg pair) rather than the run.
3. What the run's own `fg`/`bg` are on each frame — print them for both, side by
   side, before theorising.

`machine-screenshots/amiga-shogun-hint.png` is a third data point: its
`InvisiClues (tm)` header is blocked too, and lanthorn draws that one unblocked as
well, so this reproduces on the topic list as well as the clue screen.
