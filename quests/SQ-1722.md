  lanthorn keeps everything under one home-folder dotdir, ~/.lanthorn (config.toml, saves/, documents/, cache/, the user's own system disks; data_roots / config::default_user_dir / system_fonts::user_media_dir). That is the classic Unix CLI convention but not current platform practice, which matters for any embedding host shipping a GUI app (and for future sandboxed or cloud-synced builds): macOS expects ~/Library/Application Support/<app> (config and data) and ~/Library/Caches/<app> (excluded from backups; a home dotdir is also impossible in a sandbox); Linux expects XDG dirs ~/.config/lanthorn, ~/.local/share/lanthorn, ~/.cache/lanthorn (honouring XDG_*_HOME); Windows expects %APPDATA%\lanthorn (settings, roaming) and %LOCALAPPDATA%\lanthorn (cache) — a leading dot doesn't hide a folder on Windows, so users see a stray '.lanthorn' in their profile. Ask: one place in the library that resolves the user's config, data and cache roots per platform (e.g. the 'directories' crate's ProjectDirs, or equivalent), used by every caller (config loading, saves, documents, cache, user_media_dir, ~ expansion), with: (1) backwards compatibility — if ~/.lanthorn already exists, keep using it unchanged so no existing user migrates anything (optionally a documented, opt-in move); (2) existing overrides (--user-dir, --data-dir, env) still win; (3) cache data (covers, IFDB fetches, anything re-downloadable) in the cache root, not alongside saves; (4) the TUI and any embedding host resolve the same roots so they keep sharing saves and config; (5) tests per platform. Related: SQ-1721 (HOME unset on Windows) — the same resolver should cover it. Wanted before hosts' first public releases, since changing defaults after users have data is harder.

--- note 2026-10-06T23:41:18Z ---

Addendum: the resolver should also let an embedding host supply the config, data and cache roots directly through the API (not only via env vars or --user-dir/--data-dir). Mobile hosts (iOS app container: Library/Application Support + Library/Caches; Android: filesDir + cacheDir) can't be found by desktop path conventions, and a host may want its own roots per build (e.g. a store build syncing saves with the store's cloud). The same split then maps onto their backup rules: data backed up, cache excluded.
