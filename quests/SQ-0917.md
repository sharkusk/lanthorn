## What this is, and why it is not the TUI's fight

babelmap advertises `V6_FONT_WIDTH = 8` / `V6_FONT_HEIGHT = 16` at header `$26`/`$27` and lays every v6 cell out on that grid. The machines Infocom shipped for did not:

| release | font | cell | advance |
|---|---|---|---|
| Macintosh v6 (all four) | `FONT` 524 | 7×15 | **7**, uniform over printable ASCII |
| Macintosh v6 (all four) | `FONT` 1033 | 7×12 | 6 |
| Amiga *Arthur* | `char.data` | 10×10 | **proportional, 2–8** |
| Amiga *Journey* / *Beyond Zork* | `Char.data` | 8×8 | 8 (this one is font 3, not a typeface) |

SQ-0911 and SQ-0916 landed the parsers for all of these — `blorb::{bitmap_font, amiga_font, mac_font, resource_fork}` and `Hfs::read_resource` — and then deliberately did NOT wire them to the renderer, because glyphs alone are not enough. Drawing a 7-advance face on an 8px grid costs a pixel of tracking on every character; the comparison renders under SQ-0916 show it, and it is not fixable by choosing better glyphs.

## Why it is genuinely hard, not merely tedious

`$26`/`$27` are not decoration. **The game reads them** and computes its own window geometry from them, so changing what we advertise changes where the story puts things — this is not a rendering-only change, it is a change to the conversation with the story file. On top of that the entire v6 test corpus is pinned at 8×16, and v6 geometry is the area of this repo with the worst track record (SQ-0901's fabricated Arthur frame, the ceil-vs-round trap in CLAUDE.md).

Arthur's font is worse still: it is genuinely proportional, so honouring it means abandoning a fixed cell for text altogether, which the Z-machine's own column arithmetic does not really support.

## Why a GUI is the better home (user's call, 2026-08-18)

The user's framing: *"we may not do it for this tui, but if we build a gui later it will make more sense."* That matches the earlier brainstorm in the same session about a separate application dedicated to playing Infocom v3–v6 as authentically as each platform had them — C64/C128, Apple II/IIgs, Macintosh, Amiga, DOS — with that machine's palette, resolution and system font. In a GUI there is no terminal cell to fight: the window is pixels, the font's own metrics are simply the metrics, and a proportional face is not a problem to be worked around.

In the TUI the cell is the terminal's, and every gain here is fighting that.

## What already exists to build on

- `blorb::bitmap_font::BitmapFont` / `Glyph` — one shape for both machines' fonts, rows MSB-leftmost, advance per glyph.
- `blorb::amiga_font::parse` / `from_volume` — AmigaDOS disk fonts, signature-matched (`DFH_ID`), never by filename.
- `blorb::mac_font::parse` / `from_fork` — `FONT`/`NFNT` including the left side bearing, which is the part that is easy to drop and makes uniform text look ragged.
- `blorb::resource_fork::ResourceFork` and `Hfs::read_resource` — SQ-0911.
- `machine-screenshots/` — the only oracle that can falsify a geometry claim rather than confirm it. It has Amiga Journey, Shogun, Zork Zero and Beyond Zork; **no Arthur**, which is the release whose metrics are most unusual.

## If it is ever picked up here rather than in a GUI

Start from the Macintosh, not the Amiga: `FONT` 524 is fixed-pitch over printable ASCII, so it needs a cell-size change and nothing else. Arthur needs proportional text layout, which is a different and much larger problem. And capture an Amiga Arthur screenshot first — pinning its geometry without one is exactly how SQ-0901 happened.

## A user-visible symptom, which this quest has never had before (2026-08-20)

Reported while testing SQ-0934's hint-screen work: on the Macintosh **black and
white** press, the hint system's rendered glyphs do not fit the upper banner —
they overrun it.

That is this quest's cell, showing on screen for the first time. Every previous
argument here was about fidelity in the abstract, and `v6_font_cell` declined the
change three times (EGA SQ-0790, Macintosh SQ-0838, Apple IIgs SQ-0857) on the
reasoning that nothing actually depended on it. Something does now.

### The arithmetic

The monochrome archive (`Pic.data`) puts the Mac on a **480x300** screen — that is
`ge.mono`, 1x, and `PictSource::native_std_window` carries it to the story ahead of
the profile. lanthorn advertises an **8x16** cell, so the game is told it has

    480 / 8 = 60 columns

where Infocom's own Macintosh interpreter set `colWidth := 7` and
`lineHeight := 15 {16}`, giving the machine

    480 / 7 = 68 columns

So the story lays its banner out for 68 columns and is handed 60. Eight columns of
text have nowhere to go, and a banner is exactly where that shows first: it is a
fixed-width strip with its content positioned by column, unlike prose, which simply
rewraps.

Note this is the MONO press specifically. The colour press takes `CPic.data` at 2x
onto a 640x400 screen, where 640/8 = 80 against the Mac's own 640/7 = 91 — the same
ratio, but the banner there has more absolute room to absorb it, which is why the
b/w one is the press that broke first.

### What this changes about the quest

Nothing about the difficulty — `$26`/`$27` are still read by the story, the whole
v6 corpus is still pinned at 8x16, and Arthur's Amiga face is still proportional and
still belongs in a GUI. But the "start from the Macintosh" advice at the bottom of
this quest is now the *recommended* path rather than merely the easiest one, and it
has a falsifiable acceptance test at last: the Mac b/w hint banner fits.

`FONT` 524 is fixed-pitch over printable ASCII, so the Macintosh needs a cell-size
change and nothing else. And SQ-0932 already landed the glyph half of this quest for
the raster path, so what remains for the Mac really is only the cell.

### Related

- SQ-0934 — the hint screen the symptom was found on.
- SQ-0937 — a DIFFERENT Mac-only hint defect found in the same session (an in-box
  run's column is device-mapped while its row is box-relative). Do not conflate
  them: SQ-0937 is a rounding boundary in the ring's run packing and is present at
  8x16; this one is the cell itself. Fixing SQ-0937 will not make the banner fit.

## The Amiga Arthur screenshot exists now, and it confirms the font (2026-08-22)

`machine-screenshots/amiga-arthur.png` — Arthur on an Amiga, gameplay frame
("Town square / St John's Day, Terce"). This is the capture this quest and
SQ-0901's lesson both asked for and did not have.

**It is a pixel-exact native capture, not a resample.** 320x200, 18 distinct
colours, and every channel of every colour is a multiple of 0x11 (0x44, 0x55,
0x99, 0xDD...) — a 4-bit-per-channel OCS palette with no blended values
anywhere. A downscaled or video-captured frame shows off-palette averages; this
one has none, so every measurement below is of real machine pixels.

### The cell is 10 tall, measured

White text pixel rows: 121-129, 131-139, 141-149, 161-169, 171-179. **Pitch
exactly 10.** The status bar (inverse, white ground) occupies rows 100-109 —
exactly one cell tall, independently. Glyphs use ~7 rows with descenders
reaching the 9th, inside a 10-row cell.

### The advance is proportional, measured per word

Prose line 1 is "You walk into the town square. The churchyard lies to the
north," — 64 characters spanning x=14..301, **288 px, 4.5 px/char average**.
Fixed-pitch at the nominal 10 would need 640 px on a 320-px screen, so
proportional is not a detail here; it is the only way the line fits.

Segmenting that line by inter-word gaps and dividing each word's span by its
letter count:

| word | span | px/char |
|---|---|---|
| You | 15 | 5.00 |
| walk | 20 | 5.00 |
| into | 16 | 4.00 |
| the | 13 | 4.33 |
| town | 21 | 5.25 |
| square. | 32 | 4.57 |
| churchyard | 50 | 5.00 |
| lies | 15 | 3.75 |
| to | 8 | 4.00 |
| the | 13 | 4.33 |
| north, | 26 | 4.33 |

A fixed-pitch face gives every word the SAME px/char. These range 3.75-5.25 and
track word content (`lies`, all narrow letters, lowest; `town`, with a `w`,
highest). That is the falsification, not merely a consistency check.

So `native_disk_font.rs`'s `arthur_carries_a_proportional_text_font` — 10x10
nominal, `FPF_PROPORTIONAL` set, advance 2..=8 from `char.data` on
`Arthur - The Quest for Excalibur.adf` (r54/890606) — now agrees with a real
machine and not only with its own parser. **Arthur's Amiga text was never
monospaced, confirmed externally.**

### The frame's band structure, for whoever pins geometry against this

At 320x200: rows 0-6 grey ground; 7-90 the knotwork border and illustration;
91-99 grey; **100-109 the inverse status bar (one cell)**; 110-120 grey;
121-179 prose at 10px pitch; 190-199 the input line. A green vertical rule runs
down x~314-319 the full height.

### A SEPARATE finding this raises — text size relative to art

`AMIGA_STD_WINDOW` is (320, 200) and `V6_ART_SCALE` doubles it to the 640x400
unit screen, where the 8x16 cell gives 80x25 characters. The machine in this
capture has **20 text rows** (200/10), not 25.

Expressed as a ratio, which is the part that does not depend on the doubling:
lanthorn's line is 16/400 = 4.0% of screen height; the Amiga's is 10/200 =
5.0%. **Real Amiga v6 text is ~25% larger relative to its artwork than
lanthorn draws it.** Columns are closer — the machine fits ~71 columns of
average-width text across 320 px against lanthorn's 80 — so the vertical is
where the doubling model actually costs something.

This is NOT a defect claim and should not be actioned from this note alone: the
2x unit-screen model is deliberate (SQ-0479) and Arthur's windows are laid out
from what we tell it, so a taller grid is not automatically a wrong one. It is
recorded because it is now measurable against a machine, which it was not
before, and because it says the Macintosh is the outlier by a wide margin while
the Amiga's model is merely a bit small.

### What it does NOT change

Arthur still belongs in a GUI as far as GLYPHS go. Adopting a proportional face
means `x_cursor += V6_FONT_WIDTH` becomes `x_cursor += advance(ch)` and the
$20/$21 character grid stops meaning anything — a far deeper change than making
the cell runtime state — and hybrid can never follow it, so raster and hybrid
would place the same game's text differently. The screenshot removes the
"unfalsifiable" objection to Arthur; it does not remove the structural one.
