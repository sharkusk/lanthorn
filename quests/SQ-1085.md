## What works today, measured

Real launches of the shipped binary through the pty harness, a zip in each shape:

| zip holds | result |
|---|---|
| `zork1.z3` at the root | **plays** — r88/s840726 read from the header, parser takes `open mailbox` |
| `Zork I/zork1.z3` in a subdirectory | **plays** |
| `zork1.z3` + `readme.txt` + `cover.png` | **plays** — the non-story entries are ignored |
| `zork1.z3` + `beyondzork.z5` | **plays Zork I**, silently, with no way to ask for the other |
| `journey.z6` + `Journey.blb` | **refused**: `no .z3/.z5/.z8 entry found in zip` |

So the README's claim is true, and much narrower than it reads.

## Both limits are in one function

`crates/app/src/hints.rs:821-834`, the `ZIP_MAGIC` branch:

    let pred = |name: &str| {
        let lower = name.to_ascii_lowercase();
        lower.ends_with(".z3") || lower.ends_with(".z5") || lower.ends_with(".z8")
    };
    match read_zip_entry(path, pred)? {
        Some(bytes) => Ok((bytes, None)),

**One.** The predicate names three extensions. Not `.z4`, not `.z7`, and not
`.z6` — so the one format whose whole point is that it ships artwork is the one
format a zip cannot carry. Nor `.zblorb`/`.blorb`/`.gblorb`, nor `.ulx`, nor a
Scott Adams `.dat`, all of which lanthorn opens perfectly well as loose files.

**Two, and this is the one the title is about.** That `None` is the resource
handle. The disk-image branch twelve lines above returns `Some(image)` — the
thing every reader downstream uses to find pictures, sounds and hints beside the
story. The zip branch hardcodes `None`, so even a Blorb sitting in the same zip
is never opened. There is no "beside the story" inside an archive unless
something constructs one.

## What it should do

Treat a zip the way a disk image is already treated: it is a **volume**, not a
wrapper around one file. The disk path enumerates, picks or offers a choice, and
hands back an image resources resolve against; the zip path should reuse that
shape rather than grow a parallel one. That also gets `--story` working on a zip
for free — the four-shape table above shows a two-story zip silently taking the
first, which is exactly the defect SQ-1078 fixed for compilation discs.

Order that keeps each step falsifiable: widen the predicate (cheap, and makes v6
loadable), then give the zip a resource handle so a Blorb inside it is found,
then enumeration and `--story`.

## Do not let this quietly become a format

Pre-release, so no compatibility burden — but a zip is a *convenience for what
somebody downloaded*, not a lanthorn container. The `.lanthorn` archive is the
container and it is already a zip (`archive.rs`), so the two must stay clearly
apart: whatever this grows into must not start looking like a save file.

## Steps 1 and 2 landed (merged a39507a4). Step 3 remains, and here is why it was held back

Landed: the zip branch classifies entries by CONTENT via `extract_story` rather than by three name suffixes, so v4/v6/v7, Glulx, Scott and Blorb containers all open out of a zip; a Blorb inside the archive is found and supplies pictures and sounds; a hints sidecar inside the story's own zip is found ahead of the sibling scan.

Two things found while doing it, both worth remembering:

- `MAX_ZIP_ENTRY` was 4 MiB with a comment reading "nothing lanthorn runs is this big". `Kerkerkruip.gblorb` is 21.1 MB and five other Glulx games in `stories/` are over 8 MB — so widening the classifier to accept Glulx would have been defeated by the cap, silently, reported as "no story file inside the zip". Now 32 MiB, with the corpus sizes NAMED and pinned by `const _: () = assert!(...)` at compile time rather than measured from `stories/` (which is gitignored, so a runtime check goes vacuous in CI — exactly how the stale cap survived).
- `main.rs::resolve_pict_blorb` is the only thing handing the **Glulx and Scott** sessions their resources, at launch and after `@restart`, and it called `blorb::resolve_resource_blorb` directly — its own doc comment promised "the same way at launch and restart", the SQ-1022 shape exactly. A zipped `.gblorb` therefore booted with no pictures and no sounds. Routed through `graphics::resource_blorb`, as was `picker.rs::resolve_aux`. A source-level guard, `graphics::tests::resource_blorb_is_resolved_through_this_module_only`, now fails any bare call outside `graphics.rs` — and asserts its own reach (>5,000 lines of `render/screen.rs`, >80,000 across `app/src`), because its first version latched on any `#[cfg(test)]` item attribute and was reading 58 lines of a 12,310-line file.

## Step 3, still open: enumeration and `--story` over a multi-story zip

A zip holding two games still plays the first one silently. The enumeration itself is easy — `picker::resolve_entries` would take a `zipped_stories` analogue of `mounted_stories`, and `read_story_file` would honour a `want` by entry name in about ten lines.

**What blocks it is the save key.** A row selected out of a container carries `disk_entry: Some(name)`, and the per-entry key that exists — `cli_host::storage::DiskBuild` — is defined in terms of a `blorb::medium::DiskImage`, which a zip does not have. So `story_key_for(zip_path, None)` keys on the zip's basename and two games in one zip would silently SHARE a save directory (`startup.rs:289`, `picker.rs:155/361/1378/1770`). Enabling enumeration on top of that trades a visible limitation for an invisible data defect, which is why it was not done.

Likely shape of the fix: key a container-mounted story on `story_path.join(entry)` — whose `file_name()` is the entry's basename, consistent with how loose files already key on basename alone — threaded through one helper rather than the five call sites above.

## Also found, not fixed

`startup.rs` labels a zip-interior Blorb "(sidecar)" because `own = path == story_path` is false for the synthetic `zip/entry` path. Cosmetic wording only.
