THE COMMENT. `crates/app/src/render/screen.rs:6326-6332`, on `ChromeRowOracle::region_has_art`:

    /// The device->native inverse of the ring's letterbox scale, asked of a rect
    /// rather than of a row, because SQ-0750's rule is to classify a strip by what
    /// is IN it and not by where it sits. **Shared with the caller's art test so the
    /// two do not drift** — SS6 of the pipeline document lists `strip_has_art` and
    /// `over_art` as two implementations of one question with different rounding,
    /// and a third would be worse.

It is not shared. A third is what was added.

BOTH SIDES.
  crates/app/src/render/screen.rs:6333-6347   `ChromeRowOracle::region_has_art`  (2 internal uses: :6497, and `class` via `over_art`'s siblings)
  crates/app/src/render/screen.rs:1403-1417   `strip_has_art`, a local closure     (7 uses: :1521, :1565, :1946, :2071, :2096, :2491)

The two bodies are BYTE-IDENTICAL modulo `self.` — same `cw`/`ch`/`s`, same `inv_x` with `as u32` truncation, same `top`/`bot`, same `region_has_opaque` tail. `strip_has_art` closes over `cell_px`/`scale`/`area`/`gfx`; `region_has_art` reads `self.cell_px`/`self.scale`/`self.pane`/`self.gfx`. Nothing in the language keeps them equal.

The third spelling is `ChromeRowOracle::over_art` (screen.rs:6272-6277), which asks the same question in EXACT native coordinates via `region_has_opaque` rather than through the truncating inverse.

HOW IT GOT HERE. `git log -S'Shared with the caller'` gives exactly one commit, c01dc724 (SQ-0894), whose own message says: "The row classifier moves out of `decompose_chrome_strips` into `ChromeRowOracle` ... and `region_has_art` joins it. SS6 of the pipeline document lists 'two places deciding the same thing by different rules' as a defect class this file already has; **the fix should not add a fourth instance of it**." The commit then pasted `strip_has_art`'s body into the oracle instead of calling it, leaving two. So the promise was false in the commit that wrote it — the same shape as SQ-1022, SQ-1054 and SQ-1052.

THE PRIOR ART IS ALREADY LOGGED. `docs/superpowers/specs/2026-08-15-v6-render-pipeline.md:551-556`, SS6 finding 4: "'Is there art here?' has two implementations with different inverse mappings ... The two are asked about overlapping regions on the same frame and can disagree by one native pixel at a boundary — which is the ceil-vs-round class of bug CLAUDE.md names as the usual cause of v6 geometry defects. Unclear whether this matters; would need a boundary-crafted fixture to settle." That finding predates the third copy.

STATUS: NO BEHAVIOURAL DIVERGENCE TODAY. The two truncating copies are currently identical, so nothing is mis-rendered by this right now. What is confirmed broken is the promise, and the hazard it disclaims. SQ-1020 is the precedent for why that matters, and it is in this same file: "`over_art` is the oracle's own predicate and this used to be a second copy of it — same question, written twice, and only one of them was converted when the Version 6 cell stopped being 8x16 everywhere. The copy passed `run_px(...)` for the width and a bare `16` for the height, in the SAME call." (screen.rs:1305-1311.)

SUGGESTED FIX (not applied — audit lane). Make `strip_has_art` call `row_oracle.region_has_art(*r)` and delete the closure; the oracle is already constructed and in scope at :1403. That leaves two implementations (truncating vs exact-native), which is SS6 finding 4's open question and a separate decision. Correct the doc comment either way — it currently tells the next reader that a guard exists where none does.
