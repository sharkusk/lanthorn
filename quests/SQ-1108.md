--- note 2026-08-28T03:10:17Z ---

## What is duplicated

SQ-1103 lifted the grammar answer TYPES (`Token`, `NounKind`, `Slot`,
`SyntaxLine`, `Verb`, `WordRoles`, `RoutineRef`) into `crates/grammar-model`,
which both readers now produce. It deliberately stopped short of the query
surface.

Eight methods on `Grammar` are line-for-line identical in `zvm::grammar` and
`gvm::grammar`, along with the `by_word` / `prepositions` / `roles` maps behind
them: `verbs`, `verb_for_word`, `is_verb`, `verb_words`, `prepositions`,
`is_preposition`, `roles`, `words`, `action_routines`, `verbs_accepting`. Only
`format()` (zvm, five table shapes) and `tables()` (gvm, derived addresses)
genuinely differ.

A shared `Vocabulary` core holding those maps, with each crate's `Grammar`
delegating to it, would remove the duplication.

## Why it was left, and why that judgement is right for now

Both readers had just been verified — `zvm::grammar` against `infodump` across 97
stories, `gvm::grammar` against `glulxdump` across 22, 6,911 grammar lines with
zero differences. Restructuring their internals immediately afterwards trades a
proven state for a tidier one, and the duplication is invisible to callers
because the method names are already identical on both sides. Nothing downstream
can tell.

So this is genuinely optional, and it should NOT block SQ-1041 or SQ-1107.

## When to do it

Good moment: alongside the next change that has to touch both readers' internals
anyway, so the verification cost is paid once rather than twice. Bad moment: on
its own, immediately before a consumer lands.

## Constraint if it is done

The two `grammar_tables.rs` suites are the safety net and must pass **unchanged**
— SQ-1103's whole conversion needed exactly one edit between them, and that was a
sanctioned rename. Any suite edit beyond an import path means behaviour moved,
and that is the signal to stop.

Related: [[SQ-1103]] did the types; this is the methods.

DESIGN SETTLED, 2026-08-30 — and the question it looked like it was asking turned out to be already answered.

## The home exists: `crates/grammar-model`

I began framing this as an architecture call — "a shared core has nowhere to live,
because `zvm`/`gvm`/`scott` take zero external dependencies and must not depend on
each other." **That question was settled under SQ-1103.** `grammar-model` is an
internal zero-dependency workspace crate that ALL THREE VM crates already depend on,
and each Cargo.toml says why in as many words: "an internal, zero-dependency
workspace crate, so this stays a zero-EXTERNAL-dependency crate exactly as before."

So there is no new crate to justify and no embeddability trade to weigh. The
precedent is in the tree.

## The duplication is smaller than the title says

`grammar-model` ALREADY holds the value types — `Verb`, `WordRoles`, `SyntaxLine`,
`Slot`, `Token`, `ObjectWords`, and `accepts`/`accepts_word`. So `Verb::accepts`,
which reads as duplicated when you diff the two files, is one implementation both
crates call.

What is genuinely duplicated is the **`Grammar` CONTAINER and its accessors**:

    shared, byte-identical fields in both:
        verbs:           Vec<Verb>
        by_word:         BTreeMap<String, usize>
        prepositions:    Vec<String>
        roles:           BTreeMap<String, WordRoles>
        action_routines: Vec<u32>

    zvm only:  format: GrammarFormat
    gvm only:  tables: Tables,  verb_base: u32

plus ten accessors whose bodies are identical character for character — e.g.
`verbs_accepting` is `self.verbs.iter().filter(|v| v.accepts(nouns, words)).collect()`
in both — and `GrammarError`.

The LOADERS are completely different and must stay per-VM: Z-machine dictionary
scanning against Glulx table location. Nothing there is shareable and no attempt
should be made.

## The shape

A `Vocabulary` (name to taste) in `grammar-model` holding the five common fields and
the ten accessors. Each VM's `Grammar` COMPOSES it and keeps its own loader and its
own extras:

    // zvm
    pub struct Grammar { format: GrammarFormat, vocab: Vocabulary }
    // gvm
    pub struct Grammar { tables: Tables, verb_base: u32, vocab: Vocabulary }

`GrammarError` moves too, unless the two error enums carry VM-specific variants —
CHECK that rather than assuming; if they differ, leave them and say so.

One sub-question for whoever takes it, worth stating rather than discovering:
whether the VM `Grammar`s delegate the ten accessors explicitly or expose
`vocabulary() -> &Vocabulary`. `Deref` to a non-pointer type is discouraged in Rust
and should not be used to dodge the choice. Explicit delegation keeps each VM's
public API self-describing, which matters for [[zvm-as-standard-rust-zmachine]];
an accessor is less code. Either is defensible — pick one and say why.

## Why it is worth doing

CLAUDE.md's refactoring policy names this exactly: a hand-maintained invariant
across files is the symptom, and the cure is a type. Ten identical bodies in two
crates drift the first time one is fixed and the other is not — and `WordRoles`
being wrong on V6 (SQ-1153) is a recent reminder that this area does get fixed.

Ready to dispatch; no further decisions needed.
