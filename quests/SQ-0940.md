## Where this came from

SQ-0936 landed a mode that quantises the v6 magnification so an art pixel occupies
whole device pixels. Rounding DOWN to a rung leaves a margin, and on the titles
that render as one full-frame composite it is most of the screen — scopa at a
120x36 pane locks to exactly 1.0 and fills 640x414 of a 960x612 pane.

The user is content with the margin being the theme's grey rather than the game's
page: it reads as "the game window ends here", which is information rather than a
defect. What is wrong is that the app's own chrome disagrees with it.

## Idea 1 — hug the pane border to the rendered game

`paneframe::draw_framed(buf, area, …)` frames the ALLOTTED pane. So the border
currently claims "the game is in here" while two-thirds of the inside is grey — it
asserts something the content does not honour. Handing it the letterboxed rect
instead makes the border tell the truth, and turns the grey from ambiguous unused
space into plainly-outside-the-game.

Three things that make it bigger than it looks, all decisions rather than unknowns:

  - **The frame carries the title.** "scopa" sits in the top border and would move
    inward with the art. Probably fine; at 1.0 on a wide pane it sits oddly far
    from the pane edge.
  - **It changes chrome for EVERY v6 frame, not just locked ones.** Free scaling
    letterboxes too. So either it always applies — a visible change to the four
    games that look fine today — or it is conditional on the mode, and conditional
    chrome tends to read as a glitch.
  - **The border would STEP when the scale steps.** On resize it jumps between
    rungs instead of gliding. Arguably a feature (you can see the lock working);
    only judgeable on a real terminal.

Usefully narrow: for the ring games the story text already flows inside the game
rect, so hugging is the SAME rectangle — invisible on Arthur, Shogun, Zork Zero and
Journey, dramatic on scopa and fmvpoker. It is really a fix for the titles that
publish no primary Buffer.

## Idea 2 — give the freed width to the MAP pane (user, 2026-08-20)

Better than hugging alone, and composes with it: since the frame generally grows to
the window vertically, the slack a locked scale frees is HORIZONTAL. Rather than
letterboxing it away, shrink the story pane to exactly `640·s x 400·s` and hand the
remainder to the map pane. The margin stops being waste and becomes screen.

One thing to design around: the locked scale is computed FROM the pane size, which
would now depend on the split, which depends on the scale — circular. Break it by
computing the scale from the maximum available story width first, then setting the
pane to exactly `scale · native` and giving what is left to the map. Worth checking
it is stable under resize rather than oscillating between two rungs.

Also worth deciding: what happens when the map pane is hidden. The freed width has
nowhere to go, so it falls back to the margin, which is idea 1's case.

## Related

- SQ-0936 — the lock itself, merged as `a7480915`.
- The `fill_pane_page` gap: for a title with no story window nothing paints the
  margin with the game's page. Deliberately NOT fixed — the user prefers the grey
  as a boundary signal, which is what makes idea 1 the right response instead.

## SCOPE, corrected by the user mid-flight — this changed the answer

> "940 doesn't really apply to fmvpoker and scopa as those are single pane games. it also doesn't matter when the map is toggled off for other games. it only matters for stories with the map panel enabled."

The quest's original framing leaned on scopa (locks to 1.0, fills 640x414 of a 960x612 pane) precisely because the waste is dramatic there — and that case is **out of scope**, because a single-pane game has no map to give the width to. Everything below is measured on the four ring games with the map OPEN.

Also: since SQ-0978 the pixel lock is **inert on half-blocks**, so this frees nothing there. Every measurement is on a kitty picker.

## THE WIN — large, and it grows with the terminal

Map open, lock on, kitty 8x18. Identical on all four ring games (all 640x400, all lock to `s = 0.5`):

| terminal | story: allotment → hugged | map: before → after |
|---|---|---|
| 98x37 | 49 → 42 | 49 → 56 (+7, +14%) |
| 120x36 | 60 → 42 | 60 → 78 (+18, +30%) |
| 162x53 | 81 → 42 | 81 → **120** (+39, +48%) |

The story pane is 42 columns at EVERY size, because that is what the rung is — half of 640 is 320 device pixels however big the terminal gets. The wider the terminal, the more a rung discards.

## THE COST — one unresolved defect, and it is the whole decision

**Journey loses a label: `Individual Commands` renders `Individual Comman`, at every pane size with the lock on.**

Mechanism: in hybrid the ring draws chrome text as GLYPHS, one cell per native character, while the art around it is scaled by `s`. A run's START scales; its LENGTH does not. So a run beginning late on the row overruns the game rect — today it spills into the letterbox margin, which is INSIDE the pane and therefore visible; once the pane ends at the game rect, the border clips it.

Arthur, Shogun and Zork Zero lose nothing (Zork Zero's status band is art, not glyphs). `the_hug_costs_journeys_command_label_and_nothing_else` ASSERTS the loss rather than forbidding it, so both a fix and a spread to other titles show up.

**The proper fix is a glyph-run floor** — floor the hugged pane at the widest glyph run. That needs run geometry threaded into the pane layout, machinery this quest did not buy. That is the recommended next step and the natural place to resume.

## HALF 1 ALONE IS A NO-OP IN SCOPE

Exactly as this quest's original note guessed. At the default (`v6_pixel_lock` off) a free letterbox is exact on its binding axis, which in a split is width — so Zork Zero and Journey with the map open render **byte-identical PNGs** with the feature on and off. The hug earns nothing by itself; all the value is in half 2 giving the width away.

## SIDE-EFFECTS — the user's stated concern, hunted rather than defended

**Found and FIXED:**
- **The splitter drag was broken by the hug.** `split_ratio` maps to an ALLOTMENT, but a drag anchored on the drawn pane asks for the ratio whose allotment equals the HUGGED width. Measured: a four-column drag threw the ratio 50% → 29% and the story pane 80 → 46 columns on the first pointer movement. `PaneLayout` now carries `story_alloc` and the drag inverts against that. Falsified both ways.

**Found and CHANGED:**
- Vertical centring looked wrong (a pane centred in its own slack floats down and stops sharing a top edge with the map, reading as come loose) → top-align. Out of scope anyway, `hug_rows` is false on every ring frame.

**Checked and fine:** map minimum width (the map only ever grows); mouse mapping (`last_v6_map` is built from the rect actually drawn, so clicks stay exact and the margin now falls outside the pane); terminals too small for the game (clamped, hug is a no-op — swept 4–24 x 3–8); resize oscillation (fixed-point sweep, 60–180 cols x 3 heights x 6 titles x both lock modes).

**Known and NOT fixed:**
- The pane title truncates when the pane narrows (`Zork Zero: The Revenge of Megaboz (zork` at 162x53). Existing `draw_top_inset` clipping, but the hug makes it common.
- Opening a modal makes the border snap back out for the duration, since the render falls to the cell path.
