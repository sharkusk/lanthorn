## The symptom, and the measurement behind it

Reported by eye the moment SQ-0917 landed: **Macintosh raster text looks worse
than the Amiga's.** It does, and the cause is not the cell being wrong — the cell
is right. It is that `render/vga16.rs` is an **8-wide face being drawn at a 7-wide
advance**, and the pixel that disappeared is the tracking, not the letter.

Census of the table over printable ASCII (0x21..0x7E), by rightmost inked column
in the 8-wide master:

| rightmost inked column | glyphs | examples |
|---|---|---|
| 3 | 1 | `'` |
| 4 | 6 | `, . : ; \` \|` |
| 5 | 9 | `! ( ) I [ ] f i l` |
| **6** | **76** | `" # $ % & + - / 0 1 2 3 4 5 …` |
| 7 | 2 | `* _` |

**78 of 94 reach column 6 or 7.** In an 8-wide cell their ONLY right-side gap is
column 7 — that column is the inter-character space. `blit_glyph_styled` resamples
`dx * 8 / cw`, so at `cw == 7` it samples columns 0..=6 and drops column 7
entirely: those glyphs now fill the cell edge to edge and touch their neighbours.

Vertically nothing is lost. `dy * 16 / 15` maps rows 0..=14 one-for-one and never
reaches row 15, and no glyph in the table inks row 15. **The defect is purely
horizontal crowding.**

Hybrid is unaffected — it draws terminal glyphs and never touches this face.

## The fix is already parsed, and its stated blocker is gone

`native_disk_font.rs::the_macintosh_font_is_fixed_pitch_but_narrower_than_our_cell`
pins the shipped face off `stories/Zork Zero Disk.image`:

- `FONT` 524, **7x15**, baseline 12, 200+ glyphs, covering Mac roman
- **fixed-pitch at 7** across printable ASCII
- carries left side bearings, which that case notes are load-bearing: previewing
  without them "flushed every glyph left and made evenly-advanced text look
  raggedly letter-spaced"

That is EXACTLY the cell SQ-0917 now declares, so it would blit **1:1 with no
resampling on either axis** — which is the property `vga16` was introduced to
provide (SQ-0932) and is precisely what it cannot deliver at 7 wide.

And the same case names the obstacle, which no longer exists:

> "So the obstacle to drawing with these glyphs is not the font. It is that using
> them properly needs the font's METRICS as well, which is a change to what
> `$26`/`$27` tell the game and moves every window the game lays out. Pinned so
> that stays measured rather than remembered."

SQ-0917 made that change. `$26`/`$27` say 15 and 7, every window is laid out from
them, and the gate is green. **The blocker SQ-0916 recorded has been removed by
SQ-0917, and this quest is what that unlocks.**

## A correction this carries

SQ-0917's own notes argue "the Macintosh needs the CELL and not the glyphs", and
that wiring `FONT` 524 into the renderer "would be wrong on its own terms, because
the real interpreter did not tell the story about proportional widths either."

**The first half stands and the second does not.** For the HEADER, the declared
metric is the whole story and 7 is right regardless of how anything is painted.
But the RASTER path still has to put an actual bitmap in the cell, and a face
drawn for an 8-pixel advance has nowhere to keep its tracking in a 7-pixel one.
Which bitmap to draw and what to declare are two questions, and that note ran them
together.

## Scope

- **Raster only.** Hybrid draws terminal glyphs by design.
- **Macintosh only.** Every other machine keeps the 8x16 cell where `vga16` blits
  1:1 already, and must not change.
- The face has to come from the mounted medium, so the fallback when there is no
  disk in hand (a bare `.z6`, CI with `stories/` absent) is still `vga16` — with
  the crowding, which is better than no glyphs. Worth deciding whether a bare
  Macintosh-profiled story should keep the 7x15 cell at all in that case.
- Left side bearings must be applied, per the pinned case above.
- Font 3 (character graphics) stays on `bitfont`'s 8x8 masters; `FONT` 524 is a
  typeface and carries none of it.

## Related

- **SQ-0917** — the cell, which made this both possible and necessary.
- **SQ-0911 / SQ-0916** — the parsers (`blorb::mac_font`, `resource_fork`, `Hfs::read_resource`).
- **SQ-1009** — the Amiga's declared metric. If that ever moves the Amiga off 8x16,
  the same question arrives for `char.data` — except Arthur's face is genuinely
  proportional, so it is a harder one.

## Correction: HYBRID IS AFFECTED TOO, and it is the default mode

The scope section above says "Raster only. Hybrid draws terminal glyphs by
design." **That is wrong**, reported by the user against Zork Zero's score band,
and it makes this quest more visible than first filed — hybrid is the shipped
default, so most players meet this, not just those who switched modes.

### The mechanism

Hybrid does not draw all text as glyphs. `render/screen.rs` builds the ring with
`v6::TextLayer::SkipGlyphRows(&glyph_rows)`, and `build_chrome_canvas` RASTERISES
every chrome text row that is not in that set. The set holds only:

- `text_run_tops` — the rows the ring is going to stamp as terminal glyphs;
- `over_art_runs` — text the game printed on its artwork, **and only where the
  backend can put a glyph in a cell the art covers.** The code says so directly:
  "`over_art_runs` is already empty on every backend that cannot, so this adds
  nothing there and the canvas keeps rasterising them exactly as before" (SQ-0944).
  So on half-blocks and sixel this contributes nothing at all;
- the rows the ring stamps inside the story box (SQ-0937).

Everything else is painted from `vga16` into the canvas — which on a Macintosh is
the 8-wide face squeezed into the 7-wide cell, letters touching.

### What follows for this quest

- **Scope is both modes**, wherever text reaches `build_chrome_canvas`'s text
  layer. The fix belongs in the shared blit path, not in a raster-only branch.
- **Severity is higher on half-blocks and sixel than on kitty**, because those
  backends cannot claim `over_art_runs` as glyph rows, so strictly more text is
  rasterised there. Check the Macintosh on half-blocks before calling this done —
  the kitty view is the most favourable one and will look the least wrong.
- It also means the SQ-0750 rule ("in hybrid, never rasterise what the game
  printed as a character") is an aspiration the ring has not finished reaching,
  and this quest sits on top of that gap rather than beside it. Worth reading
  those two together before choosing where the fix lands.

### Unchanged

The diagnosis and the remedy stand: 78 of 94 printable glyphs ink to column 6 or
7, column 7 is their whole right-side gap, `dx * 8 / 7` drops it, and the disk's
own `FONT` 524 is 7x15 fixed-pitch and would blit 1:1. Only the blast radius was
understated.

## Correction: the fallback worry above is nearly empty

The scope section says the fallback "when there is no disk in hand (a bare `.z6`,
CI with `stories/` absent)" is still `vga16`, and wonders whether a bare
Macintosh-profiled story should keep the 7x15 cell.

**A bare `.z6` does not select the Macintosh.** `InterpreterProfile::resolve_with_source`
reaches that variant exactly three ways, and only the last is the ordinary one:

1. `configured_interpreter_number == Some(3)` — an explicit `--interpreter 3` or a
   config key. `ProfileSource::Asked`.
2. `named_art` resolving to a Macintosh flavour — `--pictures Pic.data` beside a
   bare story file. Also `Asked`, and the code already notes that naming an
   archive this way "is not original media and does not license that machine's
   colours".
3. The MEDIUM's own interpreter number — an HFS disk image. `ProfileSource::Medium`.

With no overrides a bare story file falls through to `IbmPc`, which keeps 8x16 and
never reaches this quest at all. So the font is in hand **whenever the profile came
from the medium**, which is the entire default path.

### Which makes the fallback rule easy, and `ProfileSource` already carries it

The two `Asked` routes are the only ones that can produce a Macintosh cell with no
resource fork to read `FONT` 524 out of, and both are a deliberate instruction from
the player rather than something lanthorn inferred. `resolve_with_source` already
returns the distinction, so the renderer does not have to guess:

- `ProfileSource::Medium` -> the HFS volume is mounted, the fork is readable, use
  the disk's own face.
- `ProfileSource::Asked` / `Fallback` -> no fork; keep `vga16` and its crowding,
  which is a worse look for a configuration the player asked for explicitly.

That is better than the "worth deciding whether a bare Macintosh-profiled story
should keep the 7x15 cell" hedge above, which was reasoning from a case that does
not arise on its own. **Do not make the CELL conditional on whether a font is
available** — the cell is what the story is told and must not depend on which
glyphs the host happens to have. Only the FACE falls back.
