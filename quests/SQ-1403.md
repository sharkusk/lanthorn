Classic screen: nothing outside the blob (transcript prose is host-owned by design).

WHY NOT (A). zvm cannot decode a picture, so it can never run `display_list`'s replay-and-compare self-check (session.rs:1174) — the one mechanism that has caught every recording gap (SQ-0587). Moving the log to zvm makes that check a cross-crate hand-maintained invariant, which is the exact symptom CLAUDE.md's refactoring policy names. The cross-window erases would also export app's canvas model into the VM.

WHY (B). The engine-fact half is ~145 lines of pure `PaintEvent` folding (record_op 57, anchor_canvas_draw 14, the ordered walk 25, the erase/clear retire branches ~23, window_screen_rect 12, the restart clear ~12) interleaved inside ~640 lines of rasterisation. Every bug in it was a fold bug, not a raster bug: SQ-0587 (restored pixels have no history), SQ-0658 (restart kept the pre-restart list), SQ-0715 (interleave + strand), SQ-1396 (restart cleared pictures but not fills). zvm already emits BOTH an `EraseFill` and a `PictureEvent{number:0,erase:true}` per `erase_window` (exec.rs:2964, :2982) — the clear event kind is already latent in the stream.

SHAPE. `zvm::paint_log::{PaintOp, PaintLog}`: `apply(&PaintEvent)`, per-window `ops(win)`, retirement on whole-canvas erase / `erase_window -1` / restart / origin change, plus `encode()`/`decode()` bytes in the `screen_snapshot.rs` style — needed because `V6Op` derives serde and zvm takes no deps, so app stores `display.bin` opaque rather than re-growing the DTO mirror SQ-1401 just deleted. Native pixels only; no cell, canvas or terminal state.

ACCEPTANCE SUITES: `v6_display_list_restore` (4), `v6_restore_screen_layers` (4), `v6_restore_paint_ground` (4), `v6_restore_palette_replay` (1), `v6_display_list_capacity` (1), `v6_scopa_painted_cards` (2), `v6_archive_border_sweep` (7), plus `session.rs:8266` restart cases.

EFFORT: one lane. zvm +~300 (module + encode/decode + tests); app −~150/+~60. Archive SHRINKS, does not disappear: `display.json` → `display.bin` (ops) but `.palette`, the PNG fallbacks and `ground.png` all stay host-side. `CURRENT_FORMAT_VERSION` 9→10, no shim.

Also noted: `docs/internals/persistence.md` documents `screen.bin` (:165) and never mentions the display list, the painted ground or the PNG fallbacks — worth fixing under any option.

--- note 2026-09-08T14:30:13Z ---

2026-09-08 user decision: option B. zvm owns the FOLD as tested code (a per-window paint log fed by the same events as take_paint_events, with the SQ-0715 interleave and since-last-clear retirement built in, restart clearing it structurally, and its own encode/decode in the screen_snapshot.rs house style); the host owns STORAGE, the palette, the raster, the ground and the fallbacks, and keeps the save-time replay-and-compare self-check. The log lives on Machine (not a standalone helper the host feeds), so a host cannot forget to feed it; the screen snapshot blob does NOT carry it. One erase_window currently emits both an EraseFill and a PictureEvent{number:0, erase:true}; the log folds that into one clear entry. Rationale discussed: a host restore cannot invoke the game's own post-restore redraw (the snapshot PC is at a read, and the Z-machine has no expose signal), so the log replay is the host's stand-in for that redraw, kept as game-shaped as possible.
