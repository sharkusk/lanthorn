Classic screen: nothing outside the blob (transcript prose is host-owned by design).

WHY NOT (A). zvm cannot decode a picture, so it can never run `display_list`'s replay-and-compare self-check (session.rs:1174) — the one mechanism that has caught every recording gap (SQ-0587). Moving the log to zvm makes that check a cross-crate hand-maintained invariant, which is the exact symptom CLAUDE.md's refactoring policy names. The cross-window erases would also export app's canvas model into the VM.

WHY (B). The engine-fact half is ~145 lines of pure `PaintEvent` folding (record_op 57, anchor_canvas_draw 14, the ordered walk 25, the erase/clear retire branches ~23, window_screen_rect 12, the restart clear ~12) interleaved inside ~640 lines of rasterisation. Every bug in it was a fold bug, not a raster bug: SQ-0587 (restored pixels have no history), SQ-0658 (restart kept the pre-restart list), SQ-0715 (interleave + strand), SQ-1396 (restart cleared pictures but not fills). zvm already emits BOTH an `EraseFill` and a `PictureEvent{number:0,erase:true}` per `erase_window` (exec.rs:2964, :2982) — the clear event kind is already latent in the stream.

SHAPE. `zvm::paint_log::{PaintOp, PaintLog}`: `apply(&PaintEvent)`, per-window `ops(win)`, retirement on whole-canvas erase / `erase_window -1` / restart / origin change, plus `encode()`/`decode()` bytes in the `screen_snapshot.rs` style — needed because `V6Op` derives serde and zvm takes no deps, so app stores `display.bin` opaque rather than re-growing the DTO mirror SQ-1401 just deleted. Native pixels only; no cell, canvas or terminal state.

ACCEPTANCE SUITES: `v6_display_list_restore` (4), `v6_restore_screen_layers` (4), `v6_restore_paint_ground` (4), `v6_restore_palette_replay` (1), `v6_display_list_capacity` (1), `v6_scopa_painted_cards` (2), `v6_archive_border_sweep` (7), plus `session.rs:8266` restart cases.

EFFORT: one lane. zvm +~300 (module + encode/decode + tests); app −~150/+~60. Archive SHRINKS, does not disappear: `display.json` → `display.bin` (ops) but `.palette`, the PNG fallbacks and `ground.png` all stay host-side. `CURRENT_FORMAT_VERSION` 9→10, no shim.

Also noted: `docs/internals/persistence.md` documents `screen.bin` (:165) and never mentions the display list, the painted ground or the PNG fallbacks — worth fixing under any option.

--- note 2026-09-08T14:30:13Z ---

2026-09-08 user decision: option B. zvm owns the FOLD as tested code (a per-window paint log fed by the same events as take_paint_events, with the SQ-0715 interleave and since-last-clear retirement built in, restart clearing it structurally, and its own encode/decode in the screen_snapshot.rs house style); the host owns STORAGE, the palette, the raster, the ground and the fallbacks, and keeps the save-time replay-and-compare self-check. The log lives on Machine (not a standalone helper the host feeds), so a host cannot forget to feed it; the screen snapshot blob does NOT carry it. One erase_window currently emits both an EraseFill and a PictureEvent{number:0, erase:true}; the log folds that into one clear entry. Rationale discussed: a host restore cannot invoke the game's own post-restore redraw (the snapshot PC is at a read, and the Z-machine has no expose signal), so the log replay is the host's stand-in for that redraw, kept as game-shaped as possible.

--- note 2026-09-08T15:42:54Z ---

Implemented. Deviated from the investigation's SHAPE in two load-bearing ways, both found only by running the real-game acceptance suites (not by the zvm unit tests, which all passed against the wrong design too):

1. PaintLog is NOT fed automatically at opcode-execution time inside Machine, despite that being the explicit design goal ("so a host cannot forget to feed it"). A cross-window erase (one window's canvas erased by another window's clear — lanthorn's 8-canvas model of ZMSD's 1 shared screen) can only be computed by the host, from its own canvas state, during its OWN drain walk over take_paint_events — which runs strictly AFTER Machine::step() has already fed every engine-native event for the whole turn automatically. Feeding early therefore puts every cross-window entry after the whole turn's engine events regardless of true interleave, corrupting replay (8 real-game test failures: v6_side_border_tiling, v6_fmvpoker_hybrid x2, v6_adaptive_palette_arthur, v6_shared_screen_erase x2, reproduced and root-caused via targeted eprintln instrumentation). Fixed by making PaintLog::apply host-driven, called once per drained event from the same walk that also calls the new PaintLog::append_host_erase for cross-window entries — restoring correct interleave. Machine still owns storage/fold/restart-clear; only automatic feeding was dropped.

2. Added PaintOp::HostErase (not in the original shape) plus SQ-0592-style containment pruning on it specifically, after v6_display_list_capacity caught Shogun's cross-window erase entries accumulating unbounded (never reset by anything, since the window being cross-erased is never itself whole-cleared).

Both gaps were invisible to the zvm-only unit tests; only the real-game acceptance suites and the falsification step caught them. Full report with file/line detail relayed to the coordinator in-thread.

--- note 2026-09-08T17:33:09Z ---

CORRECTION to the 15:42 note: that describes the FIRST attempt, which the coordinator rejected because it contradicted the user's design (host-fed log, HostErase op exporting app's eight-canvas model into zvm). The commits that landed on main (9f144600, 2c5dcf61, merged as 0522973b) implement the decided design: PaintLog::apply is pub(crate) and called only from Machine (draw_picture, erase_picture, erase_window's clear loop, queue_picture_event) plus Machine::restart's clear, so no host can feed or forget it; PaintOp is Draw / ErasePicture / Clear only (each with win_box at issue time, plus at_cursor, margin_after and out_chars, which are Z-machine facts about the call the host needs to tell an inline float from a canvas picture); storage is one flat Vec<(win, op)> whose append order IS cross-window issue order, exposed as ops_in_order() and per-window ops(win); app derives cross-window erasure at REPLAY time by walking ops_in_order() through the same canvas-painting core live drawing uses, so a restored screen is a re-drain of the log. display.json's replay_order field from the first attempt is gone. A mid-rework regression (mysterious01's boot title card misclassified because the host's live out_chars counter had moved past the call) was fixed by carrying out_chars on the op. Full app gate 5170/5170 twice; falsification of the clear reset failed four zvm fold tests and v6_display_list_capacity. Old-archive behaviour (accepted break, no shim) is documented in docs/release/save-format-policy.md and CHANGELOG.
