READ OF IT, to be checked not assumed: all three symptoms are one fact — when the bottom band grows a row, the frame is re-laid-out and comes back on the RASTER baseline rather than the mode currently in force. Raster looks fine because raster is the baseline being fallen back to. That it self-heals on the next command says the mode is still recorded correctly somewhere; the recompute simply is not reading it.

This is the refactoring-policy shape described in CLAUDE.md — facts that must be considered together travelling separately, so a recompute that omits one gets a PLAUSIBLE answer rather than an error. --- note 2026-08-30T19:59:15Z ---

MEASURED, and the read in the first note was half right. Fixed on branch `worktree-agent-affcfde1dd01e9daf`, commit 6b746442.

WHAT IT IS NOT: nothing falls back to a "raster baseline". `native_extent` stays (640, 400), the hybrid ring's `image_scale` stays 1.25, and `RasterFrame::extended` still ASKS for canvas_h 896. The recompute reads the mode correctly throughout.

WHAT IT IS: one classifier changes its answer, and the two modes that consult it take different routes as a result.

Arthur prints parser errors into window 3, a band across the foot of his screen, shrinking window 0 to make room. Measured on `arthur-r74-s890714.z6` (release 74, IbmPc, 640x400, art_scale (2,2), 8x16 cell), twelve taps answering `n` then `look`:

    turn                  window 0        window 3            band
    look                  (28,208) 584x192  —                 0 rows
    frobozzle the grue    (28,208) 584x176  (28,384) 584x16   1 row
    was                   (28,208) 584x160  (28,368) 584x32   2 rows  ← wraps

`menu_strip_below_story` opens with "false as soon as the story reaches within ONE native text row of the screen bottom". `400 <= 384 + 16` holds and `400 <= 368 + 16` does not — so the ONE-row band was forgiven and the TWO-row band was classified as Journey's command menu. Everything downstream follows from that one bit:

  * HYBRID — `hybrid_bottom_plan` returned `Menu` instead of `Frame`, which is the plan for Journey's strip: `tiled_flanks` excluded, `flank_panels` taken instead, so Arthur's poles were drawn by the menu-panel recipe rather than tiled down the ring. That is the "side art changes size and overwrites the ring" the report describes. Measured: ring_plan `frame` → `menu` on the `was` turn, back to `frame` next command.
  * EXTENDED — `build_v6_raster_frame` declined the extension outright at its `menu_strip_below_story` gate: canvas 640x896 → 640x400, viewport 41 → 9. This is SQ-1132's defect recurring one row up; SQ-1132 fixed the ONE-row band and its `frobozzle the grue` fixture cannot reach a wrapped one.
  * RASTER — genuinely unaffected: it never extends, so the gate has nothing to decline. Correct for that reason, not because it is a baseline the others fall to.
  * `extend_raster_flanks` reads the same classifier and was also declining, so the flanks stopped tiling on the wrapped turn in both raster modes.

THE FIX. The band's height is transient and the frame's shape must not track it. What distinguishes Arthur's band from Journey's menu is not how tall it is but whose window it is: Arthur's lies wholly between the story window's bottom and the screen's, so the frame can carry it as a unit — which `bottom_anchored_chrome` (SQ-1132) already tests — while Journey's runs belong to a full-screen (0,0) 640x400 grid straddling the story that nothing can move. New `anchored_band_bottom` states that test's answer as a native row, and it is now what both callers ask: `menu_strip_below_story` is false for a band the frame carries, and `hybrid_bottom_plan` measures its enclosed-frame arm to the band's bottom (`reach`) rather than the story window's. The height proxy is gone.

`hybrid_bottom_plan`, `menu_strip_below_story` and `extend_raster_flanks` now take the chrome WINDOWS rather than the runs pulled out of them — a list of runs structurally cannot answer a question about the window they belong to, which is how a height proxy got written in the first place (the CLAUDE.md refactoring shape). `paint_runs` is the single derivation of runs from windows, so the two questions are asked of the same set.

RESULT, same fixture and boot, 100x50 pane on an 8x18 cell, bands of 0 / 1 / 2 rows:

    hybrid    plan frame, art 1.25 throughout   viewport 35 / 34 / 33
    raster    canvas 640x400                    viewport 11 / 10 /  9
    extended  canvas 640x896, lock 1.0          viewport 42 / 41 / 40

Frame height unchanged, art unchanged, exactly one row of prose yielded per row the band gains — the behaviour the user specified. Journey r83 unmoved (plan `menu`, extension still declined). `cargo run -p app --example v6_mode_digest` is byte-identical before and after across all six fixtures at four pane sizes, so nothing the corpus already drew has moved.

TEST: `v6_extended_frame::a_wrapped_parser_message_costs_one_text_row_and_moves_nothing_else` (group `v6_render`) drives the three band heights and asserts plan/scale/canvas-height equal and viewport exactly one row shorter per band row, in all three modes, with a non-vacuity guard on the band being 0/1/2 rows and the wrapped one carrying "rephrase". FALSIFIED: with the fix reverted it fails on the reported symptom — hybrid `frame` → `menu`, extended 640x896 → 640x400.

GATES: `cargo nextest run --workspace` prints 0, 6716 tests started / 6716 passed; `cargo clippy -p app --all-targets -- -D warnings` clean.

FOR THE USER'S EYE (why `Confirm:`): the hybrid flank treatment under the restored `Frame` plan is a pixel judgement no headless assertion settles. Play Arthur, type `was` in hybrid and in extended, and check the side art and the frame height hold still while the message wraps.
