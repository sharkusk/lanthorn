  SQ-1414/SQ-1464 landed crates/scott/src/saga_us.rs, which reads the US S.A.G.A. binary database but takes no disk images; the host still has to mount the container and hand the bytes over, and nothing in the app or scott-cli does that yet. What is needed, per docs/internals/scott-dialects-spec.md §12.3 and the extractions described in each stories/scott-dialects/*/db/README.txt: (1) ATARI 8-BIT — MountedDisk::mount(raw .atr).read_named(blorb::atr::IMAGE_ENTRY) gives the WHOLE image, ATR header and all, and the database is at file offset 0x04C1 of it; note the database is NOT a file in the disk's own directory, so contents() lists only DOS.SYS/AUTORUN.SYS (or nothing at all on four of the seven side-A images) and the picker must offer the image itself rather than an entry; side A holds the database and side B the pictures. (2) APPLE II — mount the BOOT side .dsk and read_named() the DOS 3.3 file whose normalised name is "DATABASE" or matches A?.DAT; measured on the seven specimens the names are A1.DAT, A2.DAT, A3.DAT, A4.DAT, DATABASE (The Count), A6.DAT and DATABASE (Claymorgue), each 10496 bytes, and the array starts at offset 0x135 of what read_named returns (the four-byte binary prologue is included). (3) COMMODORE 64 — MountedDisk::mount(QUESTPR1.D64).read_named("SHULK.DB") gives the 9,858-byte PRG including its two load-address bytes, and the array offset is 0. scott::detect_saga_us(bytes) answers which platform's offset fitted, scott::looks_like_scott_bytes() now answers true for all three, and Database::parse() reads them, so the wiring is a picker/mount question rather than a loader one. Two caveats: the Atari Mission Impossible side A is a damaged specimen and comes back as LoadError::BadDialectData, so the picker must show a "damaged" reason rather than hiding the disk; and Voodoo Castle, The Count and Claymorgue on the Apple II are the three "scrambled" titles, which affects only their PICTURES (§8.4) and not the database, so nothing special is needed to open them.
