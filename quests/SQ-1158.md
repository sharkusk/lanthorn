EVIDENCE, measured on the file itself:

    xxd -s 1024 -l 16 stories/Shogun.toast
    00000400: 4244 c43f 6b62 c836 c598 0100 0007 0003  BD...
    00000420: .... 0653 686f 6775 6e                   volume name "Shogun"

`BD` at offset 1024 is the HFS Master Directory Block signature. That is exactly
`DiskImage::Hfs` — "a Macintosh HFS volume, bare or inside a DiskCopy 4.2 wrapper" —
and `blorb::medium::DiskImage::detect` works on CONTENT, so the `.toast` extension
was never relevant. The user confirms it plays.

THE GAP. `crates/app/tests/suites/real_media_releases.rs` pins four Shogun media —
Amiga `.adf` r295/890321, bare `shogun-r322-s890706.z6`, `shogun_s1.dsk` ProDOS
r311/890510, `Shogun.po` ProDOS r311/890510 — and NOT the Macintosh press. No
comment explains the omission, so it reads as deliberate when it is not.

CLAUDE.md states the invariant outright: "The release every medium in `stories/`
carries is pinned in `crates/app/tests/suites/real_media_releases.rs` and tabulated
in `docs/features/interpreter.md`". That sentence is currently false.

WHY IT MATTERS MORE THAN ONE MISSING ROW — this is the "a guard beats a convention"
case, and it has already cost something. The SQ-1152 lane consulted the table,
found no Macintosh Shogun, and reasoned from that ABSENCE to "Shogun has no
Macintosh press in the corpus". It then justified a capture decision on that
premise and reported it as fact, and I relayed it to the user as fact. An absence
in a hand-maintained table is indistinguishable from a fact about the world, which
is the same failure mode as [[verify-dont-infer]]: a fact the system states outright
(the file's own MDB signature) was recovered instead by inference over a proxy (a
test table's contents).

## What solving it needs

1. **Pin the row.** Mount `Shogun.toast`, read its release and serial from the
   header the way the other rows were established, and add it. Do NOT copy a
   release number from a sibling medium — every Shogun press in the table so far
   carries a DIFFERENT release (295, 322, 311), which is exactly the point of
   CLAUDE.md's "a disk image is a different release, not the same story on other
   media". Tabulate it in `docs/features/interpreter.md` alongside.

2. **Add the guard**, which is the durable half. A source-level case that walks
   `stories/`, asks `DiskImage::detect` of each file, and fails on any detected
   medium the table does not name. It must SKIP VACUOUSLY when `stories/` is absent
   (gitignored commercial media, CI has none) while still failing loudly when the
   directory exists and holds an unpinned press — the pattern is
   `any_v6_story_present()` in `zmsd_screen_compliance.rs`.

3. **Check for other unpinned media** while there. Shogun is the one that surfaced;
   nothing suggests it is the only one, and the guard in (2) will say.

## Knock-on to check, not assume

SQ-1152 shipped `shogun-amiga-extended` (Amiga r295) and argued for omitting
`--v6-pixel-lock` partly from "Shogun has no Macintosh press". That premise is
false. Its OTHER argument stands on its own and should be re-checked rather than
discarded: `RasterFrame::extended` floors to whole DEVICE pixels per NATIVE pixel,
strictly stricter than the pixel lock's per-ART rung, so the SQ-1012/1024 half-rung
problem cannot arise in extended on any press. If that holds, the omission is still
right and only its stated reason was wrong.
