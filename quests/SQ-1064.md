--- note 2026-08-24T22:11:08Z ---

THE COMMENT. `crates/zvm/src/cpu/exec.rs:4065-4068`, in `v6_advance_prose_cursor`:

    // The bound is the window's own `x_size - right_margin` (SS8.8's property 7),
    // and the COLUMN limit rides along so a run can never outgrow the grid a cell
    // backend has to place it on — **the same pair, in the same order, that the
    // paint path passes.**

Only the ORDER matches. Neither value does, and there are two divergences, not one.

BOTH SIDES — the pair is `wrap_text`'s fourth argument `(limit_px, limit_cols)` and its third `(margin_px, margin_col)`.

  PROSE — crates/zvm/src/cpu/exec.rs:4069-4076
      let right_edge = w.x_size.saturating_sub(w.right_margin);
      let cols = u32::from(right_edge / cell.w.max(1));
      wrap_text(s,
                (x_cursor, grid_cursor.1),
                (u32::from(w.left_margin.saturating_add(1)), 1),                 <- margin_col is a literal 1
                if w.wrapping() { (u32::from(right_edge), cols) } else { (MAX, MAX) },
                ...)

  PAINT — crates/zvm/src/cpu/exec.rs:4288, 4323-4329
      let cols = w.grid.cols.max(1);                                            <- the FULL window width
      let (limit_px, limit_cols) = if wrapping { (cols * fw, cols) } else { (MAX, MAX) };
      let margin_px  = u32::from(w.left_margin.saturating_add(1));
      let margin_col = cell.col_of(w.left_margin.saturating_add(1)) + 1;        <- not 1

  1. RIGHT MARGIN. `w.grid.cols` is set at crates/zvm/src/cpu/exec.rs:3320 as `(x / cell.w).clamp(1, GRID_CELL_CAP)` — the window's full width. `right_margin` appears nowhere in the paint path; `grep -n right_margin crates/zvm/src/cpu/exec.rs` returns only 2838, 4065, 4069, 4317 and tests. So the paint path wraps at the full window width where the prose path wraps inside SS8.8 property 7's reserved margin.

  2. LEFT MARGIN COLUMN. Prose hardcodes `margin_col = 1`; paint computes `cell.col_of(left_margin + 1) + 1`. The two agree only while `left_margin < cell.w`.

THE PAINT PATH'S OWN COMMENT KNOWS. crates/zvm/src/cpu/exec.rs:4310-4322: "The two are the same number whenever the cell divides the window ... **If a declared width is ever chosen that does NOT divide, this has to become the window's own `x_size - right_margin`** — the bound `v6_advance_prose_cursor` already uses one screen regime over. A declared 16 for the Amiga, which its F4 score screen argues for, would leave 576 here and wrap the F5 description one word early."

So the two sites document the relationship in opposite directions and only the prose one claims they are the same. That is a hand-maintained invariant across two functions in one file, with a caveat in prose that a future edit is expected to honour — the shape CLAUDE.md's refactoring policy names, and the shape SQ-1054 was.

OBSERVABLE DEFECT. A window on the paint route (attributes not wrap+scroll — the split at crates/zvm/src/cpu/exec.rs:4259) that nonetheless has the wrap bit set and a nonzero right margin wraps at the full window width, running text into the margin the game reserved. NOT REPRODUCED on a shipped game: Shogun's large right margin — the case `v6_set_margins_snaps_cursor_past_right_edge` (crates/zvm/src/cpu/exec.rs:10583) cites — is on window 0, which is wrap+scroll and therefore takes the prose path that honours it.

CONFIDENCE. High that the comment is false; medium-low that any shipped v6 release hits the wrap-set + paint-mode + nonzero-margin combination. Settling the reachability half needs a v6 story driven to a `@set_margins` on such a window plus a `/dump-windows` capture of its attributes — Journey and Zork Zero are the candidates.

SUGGESTED FIX (not applied — audit lane). Compute the pair once, in one function both routes call, taking the window and the cell. That is the cure the policy prescribes and it removes the "if a declared width is ever chosen that does not divide" caveat along with it. Failing that, correct the prose comment so it stops asserting an equality that has to be maintained by hand and is not.
