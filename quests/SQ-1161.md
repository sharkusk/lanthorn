## The `font_check` row, raised by the user — and it needs a distinction the quest title does not yet draw

User: "we have a `font_check` setting with only run... as the option. not sure what's going on with that one."

MEASURED: `crates/app/src/render/config_screen.rs:54`. It is `ConfigRowKind::Action`
— **the only one of the 32 rows** — added deliberately under SQ-1104, and the enum
variant's own doc explains it fully: "A row that DOES something rather than holding
a value. Enter runs it; ← / → do nothing, because there is nothing to cycle. Its
value column says what the key does instead of what the setting is, and its effect
lands outside the working copy the Save button writes — which the row's own
description has to say, or Cancel looks like it would undo it."

So "only run… as the option" is the Action row kind showing through, not a defect.

**IT ALSO PASSES THIS QUEST'S STATED RULE.** The rule as filed is "anything in the
settings screen should be GLOBAL, not per-game", and the font check is global — its
answers land in `style.toml`, which is global, and the row says so.

**But it fails a DIFFERENT rule the quest's other half implies**, and this is the
distinction worth settling before anyone edits rows: "remove settings that have UI
buttons". `font_check` is not a setting at all, and it is reachable two other ways
already — the `/run-font-check` slash command, and `--font-check on` at launch. So
by the duplication half of the rule it is a candidate for removal; by the
global-vs-per-game half it is fine.

## What this quest actually needs decided first

Two rules were filed as one sentence and they select different rows:

1. **No PER-GAME settings in the settings screen** — they belong in the per-game
   sidecar and on the pane borders. This is the rule as titled.
2. **No DUPLICATES of things reachable from a border control or a slash command** —
   which is a different set, and is what catches `font_check`.

Rule 2 is much broader and needs care: nearly every setting is reachable from
`/`-commands by construction, since `slash::COMMANDS` is the one registry and the
border controls dispatch through it. Applied literally it would empty the screen.
So rule 2 probably means "has a BORDER CONTROL" rather than "has any slash
command" — worth confirming with the user rather than inferring, because the two
readings differ by roughly the whole screen.

`font_check` sits exactly on that seam: no border control, but two other routes.

## Recommendation to weigh, not a decision

Keep `font_check`. It is the one row whose action a player cannot discover any
other way at the moment they need it — a first-run player who does not know
`/run-font-check` exists is precisely who the row is for, and SQ-1104 put it there
for that reason. If it goes, check first that a first-run player still meets the
font check some other way; the dialog already offers itself on a first run when
there is no `config.toml`, so the row may genuinely be redundant — but that is a
measurement, not an assumption.

## What removing it takes with it

`ConfigRowKind::Action` becomes an unused variant — `font_check` is the only one of
the 32 rows that uses it. Removing the row therefore also removes the only reason
that variant exists (SQ-1104). Decide deliberately rather than leaving a dead arm:
either delete `Action` too, or keep it with a comment saying what it is for and that
nothing currently uses it. **Do not leave it undocumented and unused** — that is how
the next reader concludes it was an oversight and either deletes it blind or builds
on it wrongly.

Also drop `config_screen.rs:329`'s test, which positions itself by finding the
`font_check` row and asserting its kind, and check whether any doc names the row
(`docs/features/customization.md` and `interface.md` both describe the settings
screen).

This is now the first concrete row this quest removes; the rule-1-vs-rule-2 question
in the note above still wants answering before the rest of the screen is audited.

## THE GOVERNING RULE, stated by the user 2026-08-30 — this supersedes the two-rules confusion above

> "Action should be removed as well, this is 'Global Settings'. anything done here
> should be updated in the global config file (and if possible take effect
> immediately)"

So the screen's contract is one sentence: **every row is a GLOBAL CONFIG SETTING.
Changing it writes the global config file, and takes effect immediately where that
is possible.**

That single rule settles what the two rules in my earlier note could not:

- **Per-game settings are out** — they do not write the global config; they write
  the per-game sidecar. That was rule 1 and it survives.
- **Actions are out**, and `ConfigRowKind::Action` goes with them — not merely
  unused-but-kept, DELETED. An action does not hold a value, cannot be written to
  the global config, and is not part of Save. `font_check` is the only row using it
  and its own description already had to explain that its effect "lands outside the
  working copy the Save button writes" — that caveat WAS the smell.
- **"Has a slash command" is NOT the test.** My earlier note worried rule 2 would
  empty the screen, since every setting is reachable through `slash::COMMANDS` by
  construction. That worry dissolves: the test is not how else a thing can be
  reached, it is whether the row IS a global config setting. A setting with a border
  control and a slash command is still a global config setting and still belongs.

## The tension this creates, which wants settling before the screen is edited

The screen currently has **Save/Cancel semantics over a working copy** — that is
what `ConfigRowKind::Action`'s doc is warning about when it says an action's effect
lands outside what Save writes, "or Cancel looks like it would undo it."

"Take effect immediately" and "Cancel reverts" are in tension. Three coherent
resolutions, and one has to be chosen deliberately:

1. **Live-apply with Cancel restoring the snapshot** taken on open. Cancel keeps
   meaning what it says, at the cost of holding a before-image.
2. **Live-apply and drop Cancel** — the screen becomes direct manipulation, like the
   border controls, and Save disappears too because there is nothing deferred.
3. **Keep Save/Cancel and apply on Save.** Not immediate, but honest, and it is
   today's behaviour minus the Action row.

The user's "if possible" suggests 1 or 2 are wanted where feasible. Note some
settings genuinely cannot apply live (anything read only at boot), so whichever is
chosen must say what happens to those — a row that silently does nothing until
restart is worse than one that says "on next launch".

## Immediate, concrete work

Remove the `font_check` row, remove `ConfigRowKind::Action`, remove
`config_screen.rs:329`'s test that positions by finding that row, and update any doc
describing the settings screen (`customization.md`, `interface.md`). Confirm first
that a first-run player still meets the font check via the no-`config.toml` path.
