## The `font_check` row, raised by the user — and it needs a distinction the quest title does not yet draw

User: "we have a `font_check` setting with only run... as the option. not sure what's going on with that one."

MEASURED: `crates/app/src/render/config_screen.rs:54`. It is `ConfigRowKind::Action`
— **the only one of the 32 rows** — added deliberately under SQ-1104, and the enum
variant's own doc explains it fully: "A row that DOES something rather than holding
a value. Enter runs it; ← / → do nothing, because there is nothing to cycle. Its
value column says what the key does instead of what the setting is, and its effect
lands outside the working copy the Save button writes — which the row's own
description has to say, or Cancel looks like it would undo it."

So "only run… as the option" is the Action row kind showing through, not a defect.

**IT ALSO PASSES THIS QUEST'S STATED RULE.** The rule as filed is "anything in the
settings screen should be GLOBAL, not per-game", and the font check is global — its
answers land in `style.toml`, which is global, and the row says so.

**But it fails a DIFFERENT rule the quest's other half implies**, and this is the
distinction worth settling before anyone edits rows: "remove settings that have UI
buttons". `font_check` is not a setting at all, and it is reachable two other ways
already — the `/run-font-check` slash command, and `--font-check on` at launch. So
by the duplication half of the rule it is a candidate for removal; by the
global-vs-per-game half it is fine.

## What this quest actually needs decided first

Two rules were filed as one sentence and they select different rows:

1. **No PER-GAME settings in the settings screen** — they belong in the per-game
   sidecar and on the pane borders. This is the rule as titled.
2. **No DUPLICATES of things reachable from a border control or a slash command** —
   which is a different set, and is what catches `font_check`.

Rule 2 is much broader and needs care: nearly every setting is reachable from
`/`-commands by construction, since `slash::COMMANDS` is the one registry and the
border controls dispatch through it. Applied literally it would empty the screen.
So rule 2 probably means "has a BORDER CONTROL" rather than "has any slash
command" — worth confirming with the user rather than inferring, because the two
readings differ by roughly the whole screen.

`font_check` sits exactly on that seam: no border control, but two other routes.

## Recommendation to weigh, not a decision

Keep `font_check`. It is the one row whose action a player cannot discover any
other way at the moment they need it — a first-run player who does not know
`/run-font-check` exists is precisely who the row is for, and SQ-1104 put it there
for that reason. If it goes, check first that a first-run player still meets the
font check some other way; the dialog already offers itself on a first run when
there is no `config.toml`, so the row may genuinely be redundant — but that is a
measurement, not an assumption.

## THE GOVERNING RULE, stated by the user 2026-08-30 — this supersedes the two-rules confusion above

> "Action should be removed as well, this is 'Global Settings'. anything done here
> should be updated in the global config file (and if possible take effect
> immediately)"

So the screen's contract is one sentence: **every row is a GLOBAL CONFIG SETTING.
Changing it writes the global config file, and takes effect immediately where that
is possible.**

That single rule settles what the two rules in my earlier note could not:

- **Per-game settings are out** — they do not write the global config; they write
  the per-game sidecar. That was rule 1 and it survives.
- **Actions are out**, and `ConfigRowKind::Action` goes with them — not merely
  unused-but-kept, DELETED. An action does not hold a value, cannot be written to
  the global config, and is not part of Save. `font_check` is the only row using it
  and its own description already had to explain that its effect "lands outside the
  working copy the Save button writes" — that caveat WAS the smell.
- **"Has a slash command" is NOT the test.** My earlier note worried rule 2 would
  empty the screen, since every setting is reachable through `slash::COMMANDS` by
  construction. That worry dissolves: the test is not how else a thing can be
  reached, it is whether the row IS a global config setting. A setting with a border
  control and a slash command is still a global config setting and still belongs.

## The tension this creates, which wants settling before the screen is edited

The screen currently has **Save/Cancel semantics over a working copy** — that is
what `ConfigRowKind::Action`'s doc is warning about when it says an action's effect
lands outside what Save writes, "or Cancel looks like it would undo it."

"Take effect immediately" and "Cancel reverts" are in tension. Three coherent
resolutions, and one has to be chosen deliberately:

1. **Live-apply with Cancel restoring the snapshot** taken on open. Cancel keeps
   meaning what it says, at the cost of holding a before-image.
2. **Live-apply and drop Cancel** — the screen becomes direct manipulation, like the
   border controls, and Save disappears too because there is nothing deferred.
3. **Keep Save/Cancel and apply on Save.** Not immediate, but honest, and it is
   today's behaviour minus the Action row.

The user's "if possible" suggests 1 or 2 are wanted where feasible. Note some
settings genuinely cannot apply live (anything read only at boot), so whichever is
chosen must say what happens to those — a row that silently does nothing until
restart is worse than one that says "on next launch".

## Immediate, concrete work

Remove the `font_check` row, remove `ConfigRowKind::Action`, remove
`config_screen.rs:329`'s test that positions by finding that row, and update any doc
describing the settings screen (`customization.md`, `interface.md`). Confirm first
that a first-run player still meets the font check via the no-`config.toml` path.

## APPLY-ON-SAVE — settled by the user, 2026-08-30

> "no, live when we save, not while in dialog"

So of the three resolutions above, it is the third, with the "immediately" attached
to SAVE rather than to keystrokes:

- **Nothing changes while you are moving through the dialog.** Rows edit a working
  copy, exactly as today. No live preview, no partial application.
- **Save writes the global config AND applies the change to the running session** —
  no restart needed for anything that can be applied at runtime. That is what
  "take effect immediately" means here.
- **Cancel discards the working copy** and keeps its plain meaning. No snapshot or
  before-image is needed, because nothing was applied.

This is the resolution with the least machinery: it keeps today's Save/Cancel model
intact and only strengthens what Save DOES. Today some settings presumably require
a relaunch to bite; after this, Save applies everything it can.

**The one case that still needs stating:** a setting genuinely read only at boot
cannot be applied by Save however it is written. Those rows must SAY so — "on next
launch" in the row's own description — rather than silently doing nothing until a
restart. A row that appears to work and does not is worse than one that is honest
about when it lands. Whoever takes this should enumerate which settings those are
rather than assuming the set is empty.

Together with the rule above, the screen's full contract is now:

    Every row is a global config setting.
    Editing changes a working copy; nothing applies while the dialog is open.
    Save writes the global config file and applies what can be applied at runtime.
    Cancel discards.
    A row that can only land at boot says so.

No actions. No per-game settings. `ConfigRowKind::Action` and the `font_check` row
are removed.

## Lane A implementation (worktree `worktree-agent-a2bb412762c8f2243`)

Implemented the settled contract. Four files: `render/config_screen.rs`, `input.rs`,
`main.rs`, `docs/features/customization.md`.

### 1. `font_check` row and `ConfigRowKind::Action` — REMOVED

32 rows → 31. `Action` is deleted, not kept-and-documented; the four index tables
(`config_row_value`, `config_toggle_or_edit`, `config_cycle`, `one_run_key_for_row`)
were renumbered together, 30/31 → 29/30. `config_screen.rs:329`'s test is gone,
replaced by `every_row_holds_a_value_and_none_of_them_is_an_action` — a guard rather
than a convention, so the next writer cannot reintroduce one silently.

### 2. CHECKED: the first-run player still meets the font check

`startup.rs:110` `first_run = !cfg.config_file.exists()`, and
`should_ask_font_check(flag, first_run, pending)` (line 524) asks on
`first_run || pending`. Intact and untouched by the row. The three surviving routes:

- **first run** — no `config.toml`, the dialog offers itself;
- **owed note** — a launch that COULD NOT ask (piped/redirected) writes
  `font_check_pending = true` and the next interactive launch asks (SQ-1112);
- **`/run-font-check`** (`slash.rs:571`, Category::Style) and **`--font-check on`**.

**One population loses a discoverable route, and it is worth stating.** A player who
DISMISSED the first-run dialog with Ctrl-C is recorded as answered-by-refusal
(`FontCheckOutcome::Refused` writes nothing and owes nothing — re-asking is nagging).
If they later change terminal fonts, they must know `/run-font-check` or
`--font-check on` exists. That was true before the row too, except the row was a place
to stumble on it. Reported for the user's eye, not treated as a blocker.

### 3. Save now applies at runtime what can be applied

Three genuine gaps found; all three wrote `config.toml` and changed nothing on screen
until the next launch:

- **`show_status_bar` / `show_room_numbers`** — mirrored onto `AppState` at
  `startup.rs:1635-1636` and read from THERE by render (the toggle keys drive the
  mirror, not the config). Save now lowers both.
- **Four `_base` fields** — `guidance_base`, `return_probe_base`, `v6_pixel_lock_base`,
  `v6_render_base` are the GLOBAL default a per-story source overrides for one launch,
  and what `/set-guidance auto` (and siblings) fall back to. Only `honor_game_colours_base`
  was synced. Now all five are — but **only when nothing per-story is pinning the key**,
  because a pin means the row was NOT edited and lowering it would turn one game's
  choice into everyone's (SQ-0807).
- **`period_look` and the theme layers** — `ConfigSave` re-resolved the look with a bare
  global `load_style` + `resolve`, which dropped this story's `style.toml` overlay and
  its `garglk.ini` overlay from the live look and never recomputed `state.period_look`.
  It now goes through `reload::reload_style`, the single funnel startup, `/reload-style`
  and the watcher already use.

**Ordering matters and is the non-obvious part.** `reload_style` is called from
`main.rs`'s post-save block **after** `write_config_file`, not from `apply_action`.
It recomputes `honor_game_colours` from this game's sidecar and re-PINS the key, and
`ConfigDoc::put` skips a pinned key while the value is still the pinned one — so
calling it before the write would have silently dropped the honour row's own edit out
of the file it was just asked to write. That regression is real and was caught before
landing; the comment at both sites says so.

### 4. ENUMERATED: the settings Save genuinely cannot apply (the set is NOT empty)

Three, each consumed once when the story boots. Each row's description now ends with
"Takes effect on next launch", and `the_boot_only_rows_say_they_land_on_the_next_launch`
fails if one stops saying it:

| row | why |
|---|---|
| `user_dir` | `data_base = saves_dir(&cfg.user_dir)` is resolved at launch (`startup.rs:257`); this story's save/map/sidecar folders are fixed for the session. |
| `undo_levels` | `s.machine.undo_cap = cfg.undo_levels` at `startup.rs:1445` (and `reset.rs:207` on `@restart`). Reaching the live session needs an `Engine` method, and `session.rs` belongs to another lane this wave. |
| `interpreter_number` | header byte `$1E`, written when the session is constructed (`startup.rs:2065`). |

**Two rows are about launch and were left alone deliberately**: `auto_load` ("Resume
your last session automatically on launch") and `prompt_load_on_launch` ("Offer to
resume a found save on launch"). There is nothing for Save to apply because the
setting only ever describes a launch, and their existing wording already says so —
adding "on next launch" would be tautology, not honesty. Flagging the judgement call.

### 5. AUDIT of the 31 remaining rows for PER-GAME settings — none, and one bug

**No row on the screen is a per-game setting.** Six rows share a key with a per-game
sidecar override — `honor_game_colours`, `interpreter_number`, `v6_render`,
`v6_pixel_lock`, `guidance`, `return_probe` — but in every case the ROW writes the
GLOBAL default and the SIDECAR is the per-story override, which is exactly the
contract. The comments in `one_run_key_for_row` say it outright: editing the row "is
the user speaking about every game", so it releases the per-story pin. `docs/features/
v6-graphics.md:1104-1106` documents the same split for the pixel lock. The per-game
half is reached from the pane-border cluster (`BorderControl::persists`), which writes
the sidecar and never `config.toml`. **Nothing to remove.**

The audit did find one real defect, fixed here (one line + a test):
**`v6_render` (row 24) had no arm in `one_run_key_for_row`.** `startup.rs:1116-1121`
pins `V6_RENDER` from a per-game sidecar exactly as it pins the pixel lock — so
cycling the render mode in the settings screen released nothing, `ConfigDoc::put`
skipped the key as still-one-run, and the user's global choice was reported saved and
was not. `cycling_the_v6_render_row_ends_this_games_hold_on_it` covers it.
