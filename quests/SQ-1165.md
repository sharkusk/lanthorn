## The idea (user, 2026-08-31)

> "a composite image of one text only game running under the various machine types
> to show the color differences"

One story, no graphics, rendered once per machine, tiled into a single frame. A
TEXT-ONLY game is the right subject precisely because it removes the variable: with
no artwork in the pane, every difference between the tiles is the machine's own
colour.

## Why it earns a slot the existing 26 do not fill

`zvm::interpreter`'s table carries a MEASURED `period_look` for nine machines —
Apple IIe, Macintosh, Amiga, Atari ST, IBM PC, Commodore 128, Commodore 64, Apple
IIc, Apple IIgs — and `period_look_for(n, version)` resolves it per Z-machine
version. Every gallery frame today shows ONE machine, so the thing that distinguishes
them is invisible: you cannot see a difference in a picture of one thing.

It is also the natural showcase for SQ-1154, which made `--colour machine` on a bare
story file reach the machine's palette and pair. That is exactly the launch each
tile needs: `--interpreter N --colour machine` on a plain `.z3`/`.z5`.

## What has to be decided or built

**This is not a manifest entry.** Every shot in `gallery.toml` renders ONE frame of
the app; a composite needs the harness to render N and tile them. Decide whether
that is a new shot KIND, or a small separate example that reuses the capture path.
Say which and why — a second renderer that drifts from the gallery's would be worse
than either.

**Which story.** It must be text-only, must show colour in its first screen, and
must be present in `stories/` (gitignored, so the shot skips vacuously on CI like
every other real-media frame). Name the release and serial in the entry, per the
convention that a frame is a fixture.

**Which machines, and how many.** All nine is honest but nine tiles is a wall; a
representative set risks looking arbitrary. Whichever you choose, the tile must be
LABELLED with the machine — an unlabelled grid of similar terminals teaches nothing.

**The layout.** Grid or column, and at what per-tile size. A tile too small to read
the prose defeats the point; nine readable tiles is a very large image.

**And the non-vacuity guard.** The frame's whole subject is that the tiles DIFFER.
So the case must assert that — sample a pixel or the resolved pair per tile and fail
if two machines that should differ came out identical. Without it the shot passes
while rendering nine copies of the same colours, which is the exact failure SQ-1164
just found in the Journey shots (an `expect` that names something visible on the
wrong screen).

That guard is also a real test of SQ-1154's work, not just of the picture.

## Watch for

Per CLAUDE.md the palette is process-global and every writer must hold the shared
lock. A composite that boots nine machines in one process is precisely the shape
SQ-0904/SQ-0958 were filed for — take `app::v6_palette*` correctly, and note the
guard restores `Standard` on drop, so each tile must state its own table rather than
inherit the previous tile's.

Related: [[SQ-1154]] is what makes `--colour machine` reach a bare file;
`machine-screenshots/` holds real-hardware captures that can falsify a tile's colours
rather than merely confirming lanthorn is self-consistent.

## DECIDED with the user, 2026-08-31 — measured first, then chosen

### Six tiles, one per DISTINCT look

**Nine machines are not nine looks.** Measured off `crates/zvm/src/interpreter.rs`:

| machine | default pair (bg, fg) | reads as |
|---|---|---|
| Apple IIe / IIc / IIgs | (2, 9) | white on black |
| Macintosh | (9, 2) | black on white |
| Atari ST | (9, 2) | black on white |
| Amiga | (12, 9) | white on dark grey |
| IBM PC | (6, 9) | white on BLUE |
| Commodore 64 | — | ink `(0xFF,0xFF,0xFF)` white |
| Commodore 128 | — | ink `(0x55,0xFF,0xFF)` light cyan |

- **The three Apple rows share ONE constant**, `APPLE_PERIOD_LOOK`, referenced at
  :1131, :1408 and :1424. IIe, IIc and IIgs render pixel-identical tiles.
- **Macintosh and Atari ST share the same pair** and differ only in cursor shape —
  Mac `CursorShape::Bar`, ST `CursorShape::Block`.

**So the frame shows: Apple · Macintosh · Amiga · IBM PC · C64 · C128.** Every tile
shows something no other tile does, and 3x2 stays readable where nine tiles would
each shrink below comfortable reading. Atari ST was offered as a seventh and
declined — a tile earning its place on a cursor shape is not worth the width.

If a future reader wonders why the Apples and the ST are absent, this note is the
answer: not an oversight, a measurement.

### A v3 story, for the status line

The user chose a Version 3 game. The reason is that **a v3 has a status line as
well as prose — two coloured surfaces per tile instead of one** — and the
reverse-video bar is exactly where IBM PC's white-on-blue and the C128's cyan ink
show hardest. Prose alone would under-sell the difference the frame exists to show.

Present and suitable: `ballyhoo-r97-s851218.z3`, `cutthroats-r23-s840809.z3`,
`deadline-r27-s831005.z3`. Pick one that opens on a described room, name its release
and serial in the entry per the fixture convention, and drive the SAME moment in
every tile — only the machine may vary, or the frame proves nothing.

### Unchanged from the note above

Still to settle when built: whether this is a new shot KIND or a separate example
reusing the capture path; the tile size and labelling (an unlabelled grid of similar
terminals teaches nothing); and the non-vacuity guard, which must assert the tiles
DIFFER — sample the resolved pair per tile and fail if two machines that should
differ came out identical. Without it the shot passes while rendering six copies of
one palette, which is precisely the failure SQ-1164 found in the Journey frames.

And the palette is process-global: six machines booted in one process is the shape
SQ-0904/SQ-0958 were filed for. Each tile states its own table under the shared
lock; the guard restores `Standard` on drop, so no tile may inherit its neighbour's.

## BUILT — `machine-colours`, six tiles, 3128x1402 (branch `worktree-agent-a8723b08a86271967`, 5b9d966b)

Rendered frame: `target/gallery/machine-colours.png` (not committed — the recipe is).

### The two decisions that were mine

**A new shot KIND, not a separate example.** `machines = [2, 3, 4, 6, 7, 8]` on an
ordinary `[[shots]]` row makes the harness capture N frames and tile them. Everything
else a composite needs — the release and serial read off the mount, `expect`,
`expect_prose_cells`, the pinned seed and pixel lock, the burnt-in label, the proof
sheet, `gallery.json` — is what every other row already gets, so a second renderer
would have reimplemented all of it and then drifted, which the quest warned against.
`Shot::runs()` answers `[None]` for every ordinary row, so the example's per-shot body
became a loop over the same code rather than a second copy of it.

**Tiles: full 64x20 frames, 3x2, captioned above each.** `tile_columns()` is the
squarest grid that holds them (6 → 3 wide), so the picture is 3128x1402 — the same
order as `journey-huge`'s 2592x1696, and each tile is 1024x640, big enough to read the
prose at full size. The caption (`Amiga · interpreter 4`) is drawn in the BITMAP master
on the label's own ground, not the frame's face, so it reads as the harness naming what
is underneath rather than as part of the render; the number is there because it is what
a reader types to get that tile back. A 14px gutter, because the Macintosh tile is white
to its edge and the Apple tile beside it is black.

**Story: `deadline-r27-s831005.z3`.** The other two candidates open on a wall of intro
prose that needs `[MORE]` paging in a 17-row pane; Deadline opens on four banner lines
and a six-line described room with the prompt already up. So `keys = "wait:4000"` — zero
keypresses — which also leaves the CARET on screen, and the caret is the only thing
separating the Apple tile from the Commodore 64 one.

### THE FINDING: two of the decided six share a body pair, and it is not an error

The decision note's table lists the C64 as "ink `(0xFF,0xFF,0xFF)` white" with no page,
which reads as distinct from the Apple's "(2,9) white on black". Read off
`interpreter.rs` in full, they are the **same screen**: `APPLE_PERIOD_LOOK` is
`page (0,0,0) / ink (0xFF,0xFF,0xFF) / FullReverse / Block`, and the C64 row is
`page (0,0,0) / ink (0xFF,0xFF,0xFF) / FullReverse / Underscore`. They differ only in
caret shape — which is exactly the relation that got the **Atari ST declined** as a
seventh tile.

The measurement is not wrong, so no machine was added or dropped: the six stand. What
it means is that **six tiles show five body pairs**, and the guard had to be shaped
around it rather than against it. `check_machines_differ` derives its obligation per
PAIR from `period_look_for` — page, ink and status band, caret deliberately excluded,
since a rendered tile cannot be compared on a glyph — so it demands a difference only
where the table states one. A guard spelled "every tile must differ" would refuse a
perfectly correct frame, and whoever hit that would have weakened the guard instead of
reading the table.

### The guard, and its falsification

`gallery::pane_look` reads each tile's dominant page, dominant ink and full set of
`(bg, fg)` pairs off the STORY PANE content rect (the same rect `prose_cells` uses —
lanthorn's header and help bar are painted in the theme whatever the machine did). SGR 7
is undone rather than carried, which is the only way a v3's reverse-video status band
enters the reading at all; that band is the whole reason a Version 3 story was chosen.

**Falsified for real, not argued.** Swapping the appended `--colour machine` for
`--colour theme` in `lanthorn_args_for` collapses all six tiles onto the terminal
default (`page default ink #c0c0c0`), and the run fails naming **eleven** pairs and
dropping the PNG — while correctly saying nothing about interpreter 2 against
interpreter 8. Restored and re-rendered afterwards. So this is a live test of SQ-1154's
licence reaching a bare `.z3`, exactly as the quest hoped.

Nine more cases in `gallery_manifest.rs`, all CI-safe (no gitignored media): the
validator refusals, both halves of the launch flags, per-tile user directories, the grid
shape, `pane_look`'s reading against a synthetic screen, the guard's two branches, the
label. Plus `the_composite_shows_one_tile_per_distinct_period_look`, which recomputes the
six-tile argument off `zvm::interpreter` rather than trusting the comment in
`gallery.toml` — it would fail if a future editor added an Apple IIc.

### On the process-global palette

**There is none to guard here, and that is worth recording so nobody adds a lock that
does nothing.** Each tile is a separate `lanthorn` subprocess under the pty driver, so
six machines never share a process; and the only in-process call the new code makes is
`zvm::interpreter::period_look_for`, which resolves the IBM PC's pair through
`true_colour_in(palette, n)` — the palette passed by ARGUMENT, never read off
`ACTIVE_PALETTE`. `palette_lock_discipline` passes both halves. Verified beyond the
lane's brief anyway: `cargo test -p app --test pty` (the shared-process, many-threads
shape nextest structurally cannot see) is 100/100.

### Gates

`cargo check --all-targets` clean · `cargo clippy -p app --all-targets -D warnings`
clean · `gallery_manifest` 41/41 · `--test pty` 100/100 under both nextest and
`cargo test` · `palette_lock_discipline` and `scratch_path_discipline` pass ·
`zork1-map` and `journey-blorb` re-render unchanged through the restructured loop, so
the ordinary path is intact. No existing shot deleted.

`docs/architecture.md`'s gallery section carries the composite, the six-versus-nine
measurement and the derived-obligation reason.

**Measured on the frame:** 367 alphanumeric cells per tile inside the 62x17 pane;
`expect_prose_cells = 240` is the floor, which refuses a tile that never narrated and
tolerates one that wraps a line differently.
