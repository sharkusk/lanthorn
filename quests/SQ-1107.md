## The problem

The oldest frustration in the genre: a room description mentions a dozen nouns
and two of them are implemented. Players learn to probe blindly, and the ones
without nostalgia for that simply stop. This shows which words the parser would
actually accept — the inverse of SQ-1041, which helps only *after* a word is
rejected.

## Use the story's own tokeniser on the story's own prose

`zvm::dictionary` already exposes `tokenise(&Memory, &[u8]) -> Vec<Token>` and
`lookup(&Memory, &str) -> u16` (0 = unknown). Feeding prose to `tokenise`
instead of a command line is **not an approximation** of what the parser knows —
it is the identical code path, so Z-encoding, the separator characters and the
v1-3 six-character / v4+ nine-character truncation are all handled the way the
game will handle them. Do not hand-roll a word splitter.

`transcript_runs: Vec<Vec<StyleRun>>` (`state.rs:2230`) already carries per-span
styling inside a line, so the rendering side costs no new machinery. Compute at
reveal time, not on every pushed line — a viewport is trivial to tokenise and
per-turn precomputation would be waste.

## Three tiers; ship 2, and 3 with SQ-1042

1. **Dictionary membership.** Trivial, and too noisy to ship alone: "You are in
   an open field west of a white house" lights `open` (a verb), `west` (a
   direction) and possibly `with`. The prose becomes a ransom note and says
   nothing.
2. **Filtered by part of speech.** `WordRoles` from SQ-1040 / SQ-1102 gives verb
   / preposition / noun, so highlight nouns and adjectives and drop the rest.
   This is the first real consumer of the grammar readers and is unblocked today.
3. **Scope-aware.** Only light words naming an object *currently in scope*.
   Strongest signal by far, because dictionary membership only proves a word
   exists SOMEWHERE — a sceptre named in room 1 and lying in room 40 would
   otherwise light misleadingly. Needs object property 1 (`p_name`) walked per
   object, which `zvm::objects` does not expose today (it has `short_name`,
   `object_snapshot`, tree walking — no parse-name reader). **That is the same
   missing piece SQ-1042 needs, so build the reader once, in one lane.**

## Scrollback: the viewport answers it, and there is no policy to invent

Reveal **exactly what is on screen**, judged against the **current** game state.
Scroll and press again to light a different screenful. That matches the
point-and-click convention this borrows from — you light what you can see — and
it means "how far back do we go?" is answered by the scroll position rather than
by a constant somebody has to defend.

The apparent objection dissolves on inspection. Judging *old* visible text
against *present* scope looks wrong, but the player's question is present-tense:
*of the words I can see, which work right now?* A sceptre described fifty turns
ago and still in scope SHOULD light; one since taken away should not. The reveal
is a property of the screen and the moment, and the age of the text is
irrelevant to it.

## It cannot be hold-to-reveal

Terminals do not report key **release** without the kitty keyboard protocol, and
lanthorn never pushes keyboard enhancement flags — `input.rs` sees
`KeyEventKind::Press` only. Enabling them would work on kitty/Ghostty/foot and
not on Windows Terminal, so a held key is not portable.

Model it as a **momentary toggle**: one keypress lights the viewport, and it
clears on the next keystroke, the next turn, or a short timer. Same feel, no
protocol dependency. (`docs/glyphs.md`-style graceful degradation is not enough
here — a feature that silently does nothing on Windows is worse than one that is
a toggle everywhere.)

## Risks to weigh before building

- **It changes difficulty.** For some players, working out what is implemented
  *is* the game. Opt-in, under the Guiding Light switch, and momentary rather
  than a permanent restyle — the player chooses the moment, which is most of the
  answer to the "this ruins discovery" objection.
- **Truncation causes real false positives.** In a v3 game `candle` and
  `candlesticks` are the same six bytes. Unavoidable — it is what the parser
  does too — but say so in the docs rather than letting it look like a bug.
- **v6 raster draws text as bitmap glyphs**, where per-word styling is a
  different problem. Scope to the normal text path first and treat raster as its
  own question; do not block on it.
- Other engines: `gvm::grammar` gives Glulx the same roles, and `scott` exposes
  `verbs`/`nouns` directly, so all three can reach tier 2.

## Sequencing

After **SQ-1041** (the simpler consumer of the same grammar data, and the one
that proves the seam), and paired with **SQ-1042** for the tier-3 parse-name
reader. Do not start it before SQ-1103 settles the shared grammar types, or it
hardens against one crate's spelling.
