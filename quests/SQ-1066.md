--- note 2026-08-24T22:12:55Z ---

ALREADY KNOWN TO THE AUTHOR — filed for the record only. The audit lane was explicitly told: "Include it in your report with a severity judgement, but do not fix it — it changes canvas geometry globally and many suites pin (640, 400)." Nothing was changed.

THE SITE. `crates/app/src/render/v6_layout.rs:265-269`, inside `native_extent`:

    if let WinNode::Grid(g) = &it.node {
        for t in &g.px_texts {
            let n = t.text.chars().count() as u32;
            let right = (t.x.max(1) as u32 - 1) + n * font_w;

`font_w` is the DECLARED cell (`cell.w`), so this is `V6Cell::run_px` written out longhand. Every run the extent is grown for is DRAWN by the pen — `build_chrome_canvas` steps `tf.advance_styled` (`v6_layout.rs:1699-1712`) — so the canvas is sized by a measure nothing draws with. Reported measurement: the Macintosh Zork Zero hint frame comes out 658x400 instead of 640x400, ~18 px of canvas past the screen the machine declared.

SAME CLASS AS SQ-1054, ONE STAGE EARLIER. SQ-1054 fixed a declared-cell rect that a pen-drawn run had to fit inside; this is a declared-cell rect that a pen-drawn run has to grow. Both `V6Cell::run_px` production callers left in the tree after that fix (`crates/app/src/render/screen.rs:744` and `:6276`) are on the CELL path, where one terminal column per character is the drawing model and the declared measure is right. This one is on the raster path and is not.

SEVERITY — moderate, and not merely cosmetic. `native_extent`'s answer is the unit screen every downstream stage divides by: `crates/app/src/render/screen.rs:802` and `:3025`, `crates/app/src/slash_dispatch.rs:793`. A 658-wide unit screen changes `s = min(pane_px / 658, ...)`, so the WHOLE frame is scaled to a screen 18 px wider than the machine's and then letterboxed against it — everything shrinks slightly and sits slightly off-centre, on exactly the press that has a proportional face. It is not a clip, so no ink is lost; it is a frame the player never sees drawn at a scale the machine never asked for, which is the SQ-0901 shape.

Note the direction is not fixed: Geneva 12 advances 3-11 px against a declared 7, so for a given run `n * 7` may be narrower OR wider than the pen. The defect is not "too small" or "too large" — it is that the extent is not the extent of what is drawn.

WHY IT IS NOT A ONE-LINE FIX. Substituting `tf.run_px_styled(&t.text, t.style)` needs a `TextFace` where `native_extent` currently takes a bare `V6Cell`, and changes the unit screen for every v6 press with a proportional face. Many suites pin `(640, 400)` — including `crates/app/src/reset.rs`'s own restart case ("launch sizes the v6 unit screen") — and each would need re-measuring rather than re-pinning. Do this as its own quest with the corpus re-measured through `ring_scout`, not as a rider on anything else.

--- note 2026-08-25T01:20:19Z ---

## Fixed, and smaller than the filing feared

The note above says "many suites pin (640, 400) ... each would need re-measuring rather than re-pinning". **They did not, and the reason is worth recording**: `V6Metric::advance` answers the declared cell for every style on a fixed pen, so `tf.run_px_styled(s, style)` is *identical* to `V6Cell::run_px(s)` on every fixed-pen press. Ninety-odd suites reach `native_extent` through a `cell_only` face and are therefore byte-identical. The only frames that move are the ones that were wrong.

Measured across every press in the corpus that has a face:

| press | pen | before | after |
|---|---|---|---|
| Macintosh Zork Zero, hint frame (Geneva 12) | proportional | **658x400** | **640x400** |
| Arthur, Amiga floppy (`char.data`) | proportional | 640x400 | 640x400 |
| Shogun, Amiga floppy (topaz/none) | fixed | 640x400 | 640x400 |

So Arthur's proportional press was never mis-measured on the frames driven here — the runs happen to reach no further than their declared cells — and the defect was reachable on the Macintosh alone.

## What changed

`native_extent(items, cell: V6Cell)` became `native_extent(items, tf: &TextFace)` — the value that already carries the cell, per the refactoring policy, which is what makes the pen reachable at all. 109 call sites; 5 pass the live `&state.v6_text`, the rest a `TextFace::cell_only(...)` of the cell they already passed.

The substitution was done with a **paren-aware** pattern (`native_extent\(((?:[^(),]|\([^()]*\))+), zvm::screen::V6Cell::DEFAULT\)`) rather than a naive one, per CLAUDE.md's rule about regexing Rust; the four sites it could not recognise — a multi-line call, two with a local `cell` binding, and the crate-path split between the lib and the binary modules — were converted by hand, and the compiler settled every one.

## Verification

`render::v6_layout::tests::native_extent_grows_a_grid_run_by_the_pen_not_the_declared_cell` — a synthetic proportional face whose advances run 7..11 against a declared 7, so the pen reaches further than the cell. It asserts the extent is the pen's AND names the declared answer alongside, so the two cannot be confused for one. Falsified at 119 (declared) against 161 (pen).
