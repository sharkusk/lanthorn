## Lane A — measured, and the note's hypothesis is REFUTED (2026-08-30)

Commit `e8846b85` on branch `worktree-agent-a4031224e1d6e61af`, `Confirm: SQ-1155`.

### What the story actually issues

Driven headless with `trace_screen` on `arthur-r74-s890714.z6`, twelve intro taps
answering `n`, then `look` and `wa`. **Arthur never erases window 0.** The whole
of the `wa` turn:

    @scroll_window(win=0, pixels=16)
    @window_size(win=0, y=176, x=584)     <- window 0 loses ONE row, 192 -> 176
    @move_window(win=3, y=385, x=29)      <- his message window opens in the row
    @window_size(win=3, y=16, x=584)         window 0 just gave up
    @window_style(win=3, flags=0b0101, op=1)
    @erase_window(win3)
    @set_window(win3)                     … "You don't need to use the word 'wa.'"

So the fault is ours, and it is not an erase of the wrong window: it is SQ-0697's
prose RETIREMENT. Window 0's one-row shrink strands exactly one of its sixteen
streamed runs (measured: `streamed` 16 → 15, `prose_retired = Some(0)`,
`transcript = ""`). That run is genuinely outside the new box and correctly
becomes paint — window 3's erase then paints over it, which is why nothing looks
stranded.

### The defect

`GameSession::finish_turn` emitted a `TranscriptElem::ScreenClear` for ANY
retirement. The app answers that with `mark_screen_clear`, which sets
`clear_anchor = transcript.len()` — everything above becomes scrollback. The turn
prints nothing into window 0 (the rejection goes to window 3), so the player is
left with a blank pane and one line at the foot of it. Bottom placement explained:
the message is window 3's, and window 3 is at native y=385.

The file already knew this for the other half of the same statement — `frozen_head`
(dropping the head text) is gated on `froze_whole`, with a comment saying a partial
retirement "keeps every line". The BOUNDARY was not gated. It is now
(`prose_cleared_at = prose_retired_at.filter(|_| froze_whole)`), which is one
`.filter`. `TurnResult::prose_retired` is unchanged, so nothing that reads the flat
offset moves.

### The hypothesis on this quest is wrong, and the correction is worth keeping

"The erase happens EVERY time and is only visible when the window had content" —
no. `prose_retired` is `Some` on the first `wa` and `None` on the second. The
difference is the leading `@scroll_window(win=0, pixels=16)`: after the first `wa`
the content has already been lifted clear of the row about to be given up, so the
second strands nothing. The report's "conditional on there being something to
clear" is literally true, and the condition is *whether the bottom row is
occupied*, not whether the pane looks empty.
