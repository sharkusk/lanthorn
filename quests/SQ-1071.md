## The authority

ZMSD §8.8.3.1.1, verbatim:

> \"Wrapping\" is the continuation of printed text from one line to the next. Text
> running up to the right margin will continue from the left margin of the
> following line. If \"wrapping\" is off then characters will be printed until no
> more can be fitted in without hitting the **right margin**, at which point the
> cursor will move to the right margin and stay there, so that any further text
> will be ignored.

…and §8.8.3: \"All text and graphics plotting is always **clipped to the current
window**.\"

And §8.8.3.1.2.2's commentary carries a table that settles the harder half —
what the ORIGINAL interpreters did, which is not what the standard prescribes:

```
                  Apple II      MSDOS         Macintosh   Amiga
A0 off,  A3 off   char clip(LR) char clip()   ---         ---
A0 off,  A3 on    char clip(LR) char clip(LR) ---         ---
A0 on,   A3 off   word wrap     char wrap     ---         ---
A0 on,   A3 on    word wrap     word wrap     ---         ---
buffer_mode off   ---           ---           char wrap   char clip(L)
buffer_mode on    ---           ---           word wrap   word wrap

                  Standard
A0 off,  A3 off   char clip(LR)
A0 off,  A3 on    char clip(LR)
A0 on,   A3 off   char wrap
A0 on,   A3 on    word wrap
```

> Here \"---\" means that the interpreter **ignores** the given state […] The Amiga
> behaviour may be due to a bug and two bugs have also been found in the MSDOS
> implementation.

**The Macintosh and the Amiga ignore attributes 0 and 3 entirely.** Their
behaviour is driven by the `buffer_mode` opcode, which defaults to ON — so on
both machines a v6 window WORD WRAPS whatever the wrapping attribute says.

## What lanthorn does instead

`crates/zvm/src/cpu/exec.rs` — the v6 paint path:

```rust
let wrapping = w.attributes & 1 != 0;
let word_wrap = w.wrapping() && w.buffered();
let (limit_px, limit_cols) = if wrapping {
    (u32::from(cols) * u32::from(fw), u32::from(cols))
} else {
    (u32::MAX, u32::MAX)          // never breaks
};
…
if !wrapping {
    let abs_x = u32::from(w.x_coord.max(1)) + u32::from(w.x_cursor.max(1)) - 1;
    if abs_x + u32::from(adv) - 1 > u32::from(screen_w_px) {
        continue;                 // clipped at the SCREEN edge; cursor pinned
    }
}
```

Two departures, and they compound:

1. **The regime is read off attribute 0 on every machine.** Every press these
   quests are about is a Macintosh or an Amiga, and neither machine's own
   interpreter reads it.
2. **The clip bound is `screen_w_px` (header \$22), not the window's right
   margin.** No row of the standard's table clips at the screen: the Apple II
   and the standard itself say `char clip(LR)`; MSDOS's `char clip()` and the
   Amiga's `char clip(L)` are named as BUGS, and even those clip at a margin
   they merely got wrong, not at the screen.

`crates/zvm/src/screen.rs` already carries `ZScreen::buffer_mode` (default true,
set by `@buffer_mode`), so the fact the two machines actually key on is modelled
and simply unread on this path.

## Measured, on the reported press

`stories/James Clavell's Shogun.adf` — Amiga, **release 295 / serial 890321** —
driven `hint`, `y`, Return ×3 (see the instrument below). The game itself issues
`@window_style(win=0, flags=0b0001, op=2)` — clear wrapping — sizes window 0 to
**500x330 at native (71,71)**, and prints hint 6:

```
run @(  71,  71) w=   8  \"6\"
run @(  79,  71) w=  16  \"> \"
run @(  95,  71) w= 544  \"You have to do everything you can to keep your ship from sinking bef\"
run @(  71,  87) w=   8  \"5\"
run @(  79,  87) w=  16  \"> \"
```

95 + 544 = **639** — one pixel short of the 640-px screen, and 69 px PAST the
window's own right edge at 570. The clue is cut mid-word at `bef` because 68
characters is what fits between the cursor and the screen edge. That is SQ-1070's
\"the hint renders off the right side of the screen\", exactly, in both render
paths — it is one over-long paint run, so hybrid and raster draw the same wrong
thing.

## The consequence that is bigger than the clip

`crates/app/src/session.rs` routes a v6 window between the two MODELS on the same
attribute:

```rust
let prose_idx = { … if v6.windows[cur].attributes & 0b11 == 0b11 && !diverts { cur } else { 0 } };
…
// \"Window 0 is normally the scrolling transcript Buffer — but with its wrapping
// attribute CLEARED it is in positioned paint mode …\"
let node = if i == prose_idx && win.attributes & 1 != 0 { WinNode::Buffer(…) } else … WinNode::Grid(…)
```

…and `cpu::exec`'s `paint_mode` gate (`attributes & 0b11 != 0b11`, SQ-0459)
decides on the same bits whether the text streams to the host transcript at all.

So attribute 0 is not merely a wrap flag here: **it is the switch that flips
window 0 between a Buffer fed by the host transcript and a Grid of paint runs**,
and it is read on two machines that ignore it. That is why every quest in this
family is a hint screen — the InvisiClues code is the one place these games
clear it.

## What this does NOT license

Do not just make the two machines wrap. Removing the A0 test would send Shogun's
and Zork Zero's InvisiClues topic lists into the host transcript, which is
SQ-1026's defect (\"the whole scrollback was re-wrapped into it\") arriving from
the other side. The paint-vs-stream routing needs a discriminator that is not the
wrapping attribute; the WRAP REGIME and the MODEL ROUTING have to be separated
before either can follow the table.

Order of work:

1. **Clip at the window's right margin, not the screen.** Narrow, spec-backed,
   and true on every machine including the ones that ignore A0. Watch the
   counter-example the current comment names: Shogun's boot menu paints through
   a 1-px-wide caret window and relies on running rightward — settle what that
   window really is before changing the bound under it.
2. **Give `InterpreterProfile` a `v6_wrap_regime()`**, alongside `v6_font_cell`,
   `release_face_space` and `period_look` — the table above is per-machine data
   and the profile is where per-machine data lives. `Standard` for everything
   the table calls `---` on the A0 rows; `BufferMode` for Macintosh and Amiga.
3. **Only then** revisit the model routing, with the falsifier in hand.

## Falsifier still missing

`machine-screenshots/` has `amiga-shogun-hint.png`, `mac-zorkzero-hint.png` and
`amiga-arthur-hint.png` — **all three are the topic MENU, none is a clue page**.
Nothing in the repo shows what a real machine does with a clue longer than its
window. A capture of one clue page on the Amiga or the Macintosh would settle
step 1 outright.

## Instrument

`crates/app/examples/hint_probe.rs` (scratch, uncommitted at the time of
writing): boots a press the way `startup.rs` does, mirrors every `TurnResult`
into a real `AppState` the way `turn.rs` does — which is what previous
reproductions were missing, an empty transcript cannot show a transcript
defect — and prints per step the window attrs, geometry, model kind, both paths'
decisions and the raster story box's own lines.

```
cargo run -q -p app --example hint_probe -- \\
  --story \"stories/James Clavell's Shogun.adf\" --route 'T:14;L:hint;C:y;C:13;C:13;C:13'
```
