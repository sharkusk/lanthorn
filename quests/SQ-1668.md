--- note 2026-10-01T21:47:01Z ---

Full design worked out in conversation (not yet implemented, not yet fully spec'd for a lane — this is a capture of the agreed shape, several open questions remain before dispatch):

## What's overridable, and what isn't

- **N/S/E/W (plain compass directions): both ends fully locked.** No ambiguity exists, no override needed or offered.
- **Diagonals (NE/SE/NW/SW): departure side has exactly 2 options** — the two box sides flanking the corner the connector exits from. Today this is hardcoded by dominant-axis rule (crates/mapper/src/router.rs's module doc: "NE → Top (north component wins over east)... This is a conservative choice"). The override would let the user pick the other of the 2.
- **One-way arrivals (any direction): destination side is free** — any available slot on the destination room, not just the restricted "faces the origin" alternatives `entry_side_alternatives` (crates/mapper/src/route/mod.rs:880) currently computes. A one-way has no reciprocal edge forcing a specific destination side, which is exactly why the router already treats this as a candidate-list problem internally (`entry_side_alternatives`, `oneway_entry_side` at route/mod.rs:750) — the override needs to go beyond that function's current restriction to origin-facing sides, to any genuinely available one.
- **Up/Down/In/Out (stub directions): free on BOTH ends.** These are "non-planar" today (`side_for` in router.rs returns `None` for all four — confirmed by reading the code) and get no routed box side at all by default; even the one special case the lane router adds (Up→Top, Down→Bottom) is hardcoded. Both the origin's departure side and the destination's arrival side would be user-choosable.

## Persistence

Keyed by (origin room id, direction) — confirmed sufficient by the user ("generally we only show one possible path, so this should fall out automatically"): the app only ever renders one connector per edge today, so this key is unambiguous in practice. Needs to survive relayout/regraph the way other per-room/per-edge flags already do (tried, distorted, etc. in MapGraph).

## UI / interaction model

Click the path to select/arm it (highlighted); the relevant room(s) then show their available slots as clickable markers; click a marker to commit the override, click elsewhere or Esc to cancel. User confirmed no separate persistent "edit mode" is needed — this is purely additive: checked crates/app/src/state.rs's `MapClick` enum, which TODAY only ever resolves a press to `Room(RoomId)` or `Empty` — a connector/path is not a clickable thing at all currently, hit-testing only knows about room boxes. So the first foundational piece, before any override mechanics, is adding connector hit-testing/selection to the map click model — nothing today collides with it.

Per the scope rules above: for a one-way, only the DESTINATION room shows slot markers when the path is armed (departure stays fixed). For a diagonal, the ORIGIN room shows exactly 2 markers (the two corner-flanking sides). For Up/Down/In/Out, BOTH rooms show markers.

## Explicitly NOT yet settled (raise before implementation, don't guess)

- What a "slot marker" actually looks like on screen (glyph, color, how multiple available markers on one room box are visually distinguished from each other and from existing real exits).
- What happens visually while a path is armed (does the rest of the map dim, does only the relevant room highlight, etc.) — no visual design done yet.
- How an override interacts with auto-layout when the graph changes around it later — e.g. a new room appears adjacent to a room with an overridden slot, does the override still make sense, does it get invalidated/re-checked, does the router silently ignore an override that's become geometrically invalid (the destination side is now occupied by something else)? This needs real design thought, not an assumption.
- Exact mechanism for what counts as "available" at a given moment (a side not already occupied by another fixed compass connector, presumably — needs to be nailed down against the real `Side`/box-occupancy model in router.rs/route/mod.rs before implementation).

## Likely scope for a first lane (not yet dispatched)

Research/investigation first, given the open questions above — this is NOT ready to hand to an implementation lane yet. A reasonable first step would be a design/prototype pass confirming the visual language (slot markers) and the override-invalidation behavior, probably worth a design conversation + a small prototype render before a full implementation brief is written.

--- note 2026-10-01T21:48:24Z ---

RESOLVED (was an open risk, now confirmed by reading the code): does this feature stay compatible with ongoing room discovery during play? Yes, and it composes with the existing architecture rather than fighting it:

- Room POSITION and connector SIDE-ATTACHMENT are already two independent layers. `place_incremental` (crates/mapper/src/layout/incremental.rs) — the per-turn placement that runs on every newly discovered room — only tracks whole-CELL occupancy (`occupied_cells_in_layer`) and has no concept of which side of a room a connector attaches to. Its own test `incremental_observe_does_not_move_existing_rooms` (mapper.rs) confirms ordinary play never repositions existing rooms. So overrides never interact with the position layer at all — nothing in this feature needs to touch incremental.rs.
- Routing/attachment-side selection (router.rs / route/mod.rs) is recomputed fresh from current edges + (stable) positions, and it ALREADY has to track "what side is taken by another connector" to make its own automatic cost-based choices. An override just needs to participate in that same occupancy accounting as a hard fact (like a fixed compass exit occupying a side) rather than a cost-ranked candidate — not new conflict-resolution logic, an extension of logic that already exists.
- The only real conflict scenario: two different one-way/stub connectors on the SAME room, one already overridden to slot X, a later discovery adds another that also wants "any available slot." Handled for free as long as the override counts as occupied in whatever "what's available" check already runs today — needs verifying exactly where that check lives when implementing, but no new design problem.

This resolves the "how does this interact with auto-layout when the graph changes around it later" question from the first note — down-ranked from an open risk to an implementation detail to verify against the real occupancy-check code when this gets built.

--- note 2026-10-01T21:50:02Z ---

IMPORTANT CORRECTION/ADDITION to the previous "resolved" note: that note only verified safety against ORDINARY incremental room discovery (`place_incremental`), which never repositions existing rooms. The user separately asked about surviving a full RE-LAYOUT/TIDY pass, which is a materially different and harder case:

`relayout_auto`/`relayout_auto_observed` (crates/mapper/src/layout/mod.rs) re-derives ALL room positions from scratch on every call (stress-majorization + VPSC constraints, 5 stages) — this is the real "tidy" the user means. Room IDs stay stable across it (so the override's persistence KEY is never at risk), but room POSITIONS can genuinely change.

Why this matters differently for this feature specifically:
- For ordinary compass edges (N/S/E/W), relative position is a topological invariant the solver can't violate (if A is north of B, it stays north of B) — consistent with that case never being overridable anyway, so no risk there.
- One-way and stub (Up/Down/In/Out) edges — exactly what this feature targets — are more weakly constrained in the position solve (the solver notes "Unknown-direction edges are non-spatial and excluded... exert no graph-distance pull"). Their relative arrangement is more likely to shift between tidy runs than a rigid reciprocal compass pair's.

So: the override's existence (as data) survives tidy for free. Its VALIDITY does not automatically — if tidy moves the destination room to a meaningfully different relative position, a previously-sensible side choice ("East") could become geometrically nonsensical or newly unavailable.

Proposed resolution (not yet implemented, needs design/verification when this is built): re-validate every override immediately after each tidy pass completes — check whether its chosen side is still geometrically sensible (does it still face a direction that makes sense given the NEW relative position) and still available (not newly claimed by something else), and silently fall back to the automatic choice for that specific edge if not, rather than rendering something broken. This should NOT block tidy from moving the rooms in question — the goal is auto-layout staying fully in control of position, with the override only ever affecting which already-decided side a line touches.

Open follow-up for implementation: find exactly where in relayout_auto_observed's pipeline (or right after it returns) the right hook point is to run this re-validation pass, and confirm empirically (not just by reading the solver's comments) how much one-way/stub relative-position drift actually happens across repeated tidy runs in practice — this analysis was done by reading the solver's own code/comments, not by running it against a real graph yet.

--- note 2026-10-01T21:50:18Z ---

Additional invalidation rule, confirmed by the user: if a one-way edge carrying an override is later discovered to actually be RECIPROCAL (the return path turns up, so it's a real two-way compass connection after all), the override must be dropped outright — not re-validated, not preserved if it happens to still look sensible. Compass-direction locking always wins once an edge is known reciprocal; one-way-ness was the entire premise that made the override legal, and losing that premise removes the override's basis to exist at all, unconditionally.

So there are now two distinct triggers for override invalidation, with two different responses:
1. A tidy/relayout pass changes relative position (previous note) → RE-VALIDATE: keep the override if it's still geometrically sensible and available, silently fall back to automatic choice only if not.
2. A one-way edge is discovered to be reciprocal (topology change, not a position change) → DROP unconditionally, no re-validation attempt — the edge has moved to the locked N/S/E/W case, which is never overridable.

Both are instances of the same general principle: an override's legality is a function of the edge's current classification (one-way/stub = overridable; locked compass = not), and that classification must be rechecked whenever it could plausibly have changed, not assumed to stay true once set.

--- note 2026-10-01T21:52:08Z ---

CORRECTION to the tidy-pass invalidation note above (user decision, supersedes the "re-validate and silently fall back" proposal): overrides PRESERVE through a tidy/relayout pass UNCONDITIONALLY, full stop — no automatic geometric re-validation, no silent fallback. If a relayout makes a previously-fine override look bad, that is surfaced to the user as a visible result they can act on, not something the system quietly second-guesses. The only automatic-drop case remains the one already established: a one-way edge discovered to be reciprocal (topology reclassification to the locked compass case) still drops its override unconditionally — that one's about the override's LEGALITY, not its geometric quality, so it's unaffected by this correction.

Net rule, restated cleanly:
1. Tidy/relayout changes relative position → override is kept exactly as set, no matter how it now looks. User fixes it by hand if they don't like the result.
2. One-way edge turns out to be reciprocal → override is dropped unconditionally (no choice to keep it; the edge is no longer a type that can carry one at all).

NEW REQUIREMENT this implies: since overrides are now sticky-by-default rather than auto-revalidated, the user needs an explicit "return this path to auto" action — a way to clear a specific edge's override and hand it back to the router's automatic cost-based choice, distinct from re-picking a different manual slot. This is a third action alongside "arm a path, click a slot" from the UI note above: arm a path that already carries an override, and some control resets it to auto (a key, a specific click target, a menu entry — not yet decided which). This needs to be part of the same interaction model as the original click-to-arm/click-a-slot flow, not a separate feature.

--- note 2026-10-01T22:02:51Z ---

TERMINOLOGY CORRECTED, and the real mechanism is richer than earlier notes assumed — dug into it properly per the user's request rather than guessing from a shallow grep.

"Slot" IS the real, existing codebase term (I'd missed it earlier searching non-recursively; it lives in crates/mapper/src/route/mod.rs, not router.rs). Every routed connector endpoint carries a `u16` `exit_slot`/`entry_slot` (RoutedConnector fields). Slot 0 is always the CENTER of a (room, side) pair; odd/even slots fan outward alternating sides: slot 1 = center+1, slot 2 = center-1, slot 3 = center+2, slot 4 = center-2, etc. (`slot_offset` in crates/app/src/render/map.rs:2169). This is converted to an actual border cell in `box_edge_anchor_at` (same file, ~2197), clamped to the box's own interior cells on that side — `v_max = h/2 - 1` for a vertical side (Left/Right), `h_max = w/2 - 1` for a horizontal side (Top/Bottom), where h/w are the room box's OWN rendered pixel dimensions (varies per room, e.g. with label length). So the true cap on how many distinct slots a given side can hold before they start clamping onto the same cell is `2*max + 1`, a per-room-per-side number, not a fixed constant.

WHO gets which slot on a shared (room, side) is decided by `assign_side_slots` (route/mod.rs:1817) — a substantial, carefully hand-tuned priority system, NOT a simple enumeration: compass exits/marks and reciprocal partners outrank one-way arrivals for the center slot (SQ-1274), a lone one-way arrival can still claim a genuinely free center (SQ-1320), straight-through connectors beat weaving ones for center on compass-only sides, Up/Down interacts specially when sharing a side with compass endpoints (SQ-0216/SQ-0222), and a single-offset endpoint gets tangent-biased toward its partner room's actual direction rather than an arbitrary fixed side (SQ-0224 Part B). This has accumulated real, specific bug-fix history — it is not safe to bypass or reimplement from scratch.

IMPLICATION FOR THIS FEATURE: the override should NOT try to directly poke a slot number into the final render output. The correct integration point is almost certainly to feed `assign_side_slots` a PINNED fact per overridden endpoint — "this endpoint's slot on this side is fixed to N, remove it from the priority sort" — and let the function continue running its existing priority logic for every OTHER (non-pinned) endpoint sharing that side, same as today. "Available" for the UI then means: of the `0..=2*max` range for the chosen side, whichever slot numbers aren't currently claimed by another endpoint (auto-assigned or itself overridden) on that exact (room, side) pair right now — computed by asking the SAME function, not by reimplementing its priority rules separately.

This also means the UI's "click a slot" affordance needs real per-room geometry (box height/width in cells) to know how many markers to even offer on a given side — not a fixed 1-per-side assumption. Revises the earlier note's "4 sides, pick one" framing: side (Top/Bottom/Left/Right) is the first choice, slot-within-side is a second, independent choice with its own availability check, exactly matching the user's own original phrasing ("which side can be used (along with the slot)").

Spec substantially revised after an Opus review caught real problems (full review preserved above). Current state of the doc at docs/design/2026-10-01-manual-connector-slot-override.md:

- SCOPE NARROWED: diagonals dropped (they leave from a box corner, not a side — not a slot problem at all, would need a different routing-candidate mechanism, deferred as a possible separate feature). In/Out dropped (not routed connectors today, render as badges, no attachment to override — would require inventing a whole new connector class). Remaining scope: one-way arrivals (any direction) and same-layer Up/Down, both ends, side AND slot pinnable on each.
- CONFIRMED PRIORITY: the user clarified the actual pain point is SLOT correctness (even when the side is already right), not side selection — repeated attempts to fix this by tuning assign_side_slots itself have caused recurring regressions. Slot control is a first-class requirement, not droppable.
- MECHANISM CORRECTED: side selection happens upstream in route_topology_with's entry_choices (route/mod.rs ~1349), before slots exist — a side pin feeds in there as a forced candidate ranked above the automatic rule. Slot selection happens afterward in assign_side_slots (private, mutates in place) — needs one new input (a pinned endpoint takes its slot directly; other members of that (room,side) group still run the existing priority sort, pinned number excluded from what's left for them). "Available slots" needs no new assign_side_slots capability — it's a scan over the existing routed plan's exit_slot/entry_slot fields against a capacity number.
- CAPACITY RESOLVED: checked zoom_box_size — only Boxes zoom (11x5) has real slot range; Compact's v_max is 0 (already collapses to center); Overview has no boxes at all. So capacity is a fixed constant for this feature, not a dynamic per-zoom/per-host query.
- INVALIDATION DECIDED: a pin whose exact cell is later claimed by a genuine compass/reciprocal endpoint (hard impossibility, two things can't render on one cell) drops to auto — NOT bumped to a different free slot. Keeps the invalidation story one shape: compass/reciprocal legality always wins outright.
- STILL OPEN, biggest gap: NO CONCRETE SPECIMEN yet — nothing has been checked against a real map/room where today's auto slot choice actually produces an avoidable overlap. Needed both to prove the premise and to become the first regression test, per this project's "a frame is a fixture" convention. Also still open: edge-to-connector mapping isn't always 1:1 (stacked-exit suppression) and needs an explicit rule; marker/armed-state visuals undesigned; whether compass-endpoint SLOTS (not sides, which stay locked) need to be in scope too, pending the specimen; public API split proposed for the web project's review (honoring pins = mandatory shared mapper behavior, availability query = should be public API, edit gesture = per-host); cache invalidation (struct_gen bump) and subgraph-survival (render_layer/tidy/mapgen rebuilding edges) are real implementation requirements needing explicit tests.

Next step before this is ready for the web agent: a concrete specimen. Consider asking the user if they have a specific room/game/overlap they were looking at when this came up.
