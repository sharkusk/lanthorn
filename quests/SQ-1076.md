## The report

> \"score bar … sometimes it is rendered across the entire screen but on the real
> game it sits between the artwork. It wasn't a big deal for me visually but maybe
> that is throwing you off.\"

It was not throwing the SQ-1029 measurement off, but it is the same window
geometry seen from the front, and it is real.

## Measured

`machine-screenshots/amiga-shogun-game.png`, Amiga Shogun r295/890321. The white
status band spans **image x 89..628 — 540 px** — with the blue ornaments outside
it on both sides. Calibrating from that band, `native = image - 42`, so the
machine's band runs native **x 47 .. ~587**, i.e. the `(47, 1, 548, 32)` box.

lanthorn's own trace of the same press shows the game setting exactly that:

```
@move_window(win=1, y=1, x=47)
@window_size(win=1, y=32, x=548)
```

…and yet on the boot-menu frame the model reports

```
win1 = (1, 1, 640, 336)     <- full width
win0 = (1, 337, 640, 64)    <- full width
```

so window 1 is later moved back to the full 640 (by `put_wind_prop` — it does not
appear as a `move_window`/`window_size` in the trace). A pty capture of gameplay
(`--story "…Shogun.adf" --size 132x60`) draws the band edge to edge above the
flanks, where the machine draws it between them.

## Why it matters beyond looks

The same full-width window 0 box is what makes SQ-1029's erase span x 1..640 and
wipe the side ornament's bottom 64 rows. If the window geometry is wrong rather
than the erase, both defects have one cause — so **read this quest and SQ-1029
together before fixing either.** The open question there is whether
`erase_window` should cross windows at all; the open question here is whether
window 0/1 should be full width at that moment. They may be the same question.

## Reproducing

```
cargo run -q -p app --example pty_capture -- \
  --story "stories/James Clavell's Shogun.adf" --size 132x60 \
  --keys 'cr,wait:1500,cr,wait:400,…(x12),cr,wait:800,text:look,cr,wait:1200' --png play.png
```

Compare the band's extent against `machine-screenshots/amiga-shogun-game.png`,
calibrating with `native = image - 42`.

## CORRECTION: this is a RENDER defect, not the window geometry

An earlier note on this quest reasoned that the full-width band and SQ-1029's
truncated side art shared one cause — `@split_window` resetting windows 0 and 1
to the full screen width — and that fixing the split would fix both. **Half of
that was wrong, and the measurements say so plainly.**

The split fix landed (windows now tile VERTICALLY, keeping the horizontal box the
game set). With it in place:

* **Shogun, gameplay.** The model is right: `win1 = (47, 1, 548, 32)`, inset
  between the ornaments, exactly the box the game asks for and the machine draws.
  A pty capture at 132x60 still paints the band **edge to edge**, above the
  flanks, where `machine-screenshots/amiga-shogun-game.png` has it 540 px wide
  from native x 47 with the ornaments running up beside it.
* **Arthur, the F2 map screen.** The model is right there too, and it was never
  touched by the split: `win1 = (29, 201, 584, 20)`, with the side poles as
  `win5 = (1, 1, 28, 400)` and `win6 = (613, 1, 28, 400)`. No `split_window` is
  issued on that turn at all. `machine-screenshots/amiga-arthur-map.png` measures
  its white bar at image x 71..652 — **582 px** — which against a 28-px pole is
  `640 - 2*29`, i.e. between the poles. Ours spans the full width.

Two different games, two different routes, one of them with no `split_window`
involved, both with a correctly-inset window 1 in the model and a full-width band
on screen. So the defect is **below the model, in the render**, and the user's
own read — \"these could be unrelated\" — is the right one.

## Where to look

The band reaching the pane edges while its window does not is either the chrome
strip the hybrid ring cuts for the status row, or a background flood painted per
ROW rather than per window box (`fill_explicit_bg_rows` and the erase-fill ground
are the candidates named in `render::v6_layout`). Establish which before
changing anything: a strip drawn too wide and a ground flooded too wide look
identical on screen and are different fixes — the same distinction SQ-0762's pty
harness exists to make.

The user notes it on the **F2–F6 screens** in Arthur specifically, so sweep those
rather than only the gameplay frame.
