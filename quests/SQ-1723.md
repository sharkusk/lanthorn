  Today a story's IFDB record (info.json) and fetched cover (cover.png) live in each copy's own game folder, <catalogue>/<story file>.save/ (cover.rs:73, story_info::info_path), so several copies of one game (a .z3, an Amiga disk image, a later release) each fetch and keep the same record and cover, and refreshing or relinking one leaves the others stale. Documents already solved this (SQ-0184-era design, documents.rs:84-103): they live once per IFDB entry in <documents>/<Title> [<tuid>]/, shared by every copy linked to that entry. Ask: the same for the fetched record and the cover — stored once per IFDB tuid (in or beside that per-entry folder), with each copy's game folder keeping only its own link state (the tuid it is linked to, or not-found / a user's 'Wrong game?' choice) plus its saves, map, notes and per-game settings. A refresh updates every linked copy; a copy relinked to another entry simply points at that entry's folder. Covers stay user data (not the OS cache root, which macOS and users may purge; re-fetching would mean automatic IFDB traffic that hosts may deliberately avoid). Compatibility: read an existing per-copy info.json/cover.png as before (and adopt it into the shared folder on the next fetch or on first use), so no existing data is lost or refetched. Do it together with SQ-1722 (platform-standard roots) so one layout change and one compatibility rule cover both.

--- note 2026-10-07T00:19:04Z ---

Fits multi-user hosting (SQ-1676's catalogue/player split): the per-IFDB-entry folders belong to the shared catalogue root, and so does each copy's IFDB link (which entry a story file is is the same for every player); player roots keep only saves, map, notes and per-game settings. With this, new installs no longer need the default player's save folders to double as the catalogue.
