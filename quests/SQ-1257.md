Design refinement (user question 2026-09-02: can we read the story like the room-lock does?): yes, two structural reads make this mostly deterministic, and the double walk becomes the confirmation rather than the primary test.

1. **Declared vs actual destination.** Inform rooms carry their exits as data: I6 `n_to`/`s_to`/… properties on the room object (an object = fixed destination; a routine = decided by code; a string = a message), I7 a per-room map array indexed by direction. Read the origin room's declared destination for the direction walked (the room-lock already gives the room object; the direction property numbers are library-versioned and must be derived, not assumed — the same way SQ-1241 derived the object layout). If the declared destination is an object and you landed there: real passage, no probe needed. If you landed somewhere else, code overrode the move (Lost Pig teleports via an I7 rule while the map data says otherwise): record nothing, mark unstable. If the exit is a routine (I6) or absent: fall through to 2.
2. **Double walk with OUR seed.** The shadow's RNG is the interpreter's — `@random` is ours in zvm and gvm — so reseed the copy explicitly before the second walk (or walk twice under two seeds) instead of hoping the snapshot didn't capture the RNG state. Different destinations → chance → record nothing. Counting `@random` calls during the move turn is a cheap corroborating signal but too noisy alone (daemons roll every turn).

Order of implementation: 1 first (no probe cost, catches every I7 rule-teleport), 2 for routine exits and as a guard when 1 cannot answer.
