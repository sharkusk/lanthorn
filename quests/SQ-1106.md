## Correcting the premise first

These are not standalone InvisiClues hint browsers. `zork1-invclues-r52-s871125.z5`
boots as **ZORK I, Release 52 / Serial 871125**, fully playable — a v5 Solid Gold
re-release with hints built in. Verified by running it:

```
$ printf 'look\nnorth\n' | ./target/debug/zvm-cli stories/zork1-invclues-r52-s871125.z5
ZORK I: The Great Underground Empire
Release 52 / Serial number 871125 / Interpreter 1 Version A

West of House
You are standing in an open field west of a white house, …
```

So a screen clear one command into normal play is not "what a menu program does".
It is wrong.

## What zvm-cli actually does (the report's premise, checked)

`zvm-cli` clears too — the no-op at `crates/zvm-cli/src/screen.rs:627` is only
`if !self.is_tty`. Under a real pty there is exactly ONE clear in the whole
session and it is at startup:

```
$ printf 'look\nnorth\nquit\ny\n' | script -q /dev/null ./target/debug/zvm-cli … | cat -v | grep -c '\^\[\[2J'
1
```

Startup is where an erase issued during boot belongs, and clearing an
already-empty screen is invisible. The front-ends therefore disagree about
*when*, not *whether*.

## Root cause: the boot path hand-builds a `TurnResult` and omits the drain

`erase_lower_requested` is drained in exactly one place —
`Session::drain_turn`, `crates/app/src/session.rs:1713`:

```rust
let erase_lower = std::mem::take(&mut self.machine.screen.erase_lower_requested);
```

But the boot does not go through `drain_turn`. `crates/app/src/startup.rs:1578`
constructs a `TurnResult` **by hand**, to seed the starting room onto the map,
and hard-codes the field:

```rust
let seed_result = TurnResult {
    transcript: String::new(),
    location: Some(snap),
    erase_lower: false,        // <-- never takes the flag
    …
};
```

So an `erase_window` issued during the game's own startup sets
`machine.screen.erase_lower_requested`, nothing consumes it, and it sits there
until the FIRST REAL TURN calls `drain_turn`, which takes it and fires
`state.mark_screen_clear()` (`turn.rs:81`). The banner and the opening room
description are wiped exactly one command late — the reported symptom.

The v3 original (`zork1-r88-s840726.z3`) does not show it because it issues no
boot-time erase; the v5 re-releases clear before drawing their banner, which is
why both files in this report are v5 Infocom re-releases.

## This is the SQ-0901 / SQ-1020 / SQ-1022 shape again

A hand-built value that omits a fact the real constructor computes, producing a
result that is entirely self-consistent and describes a screen the player never
should have seen. `docs`/CLAUDE.md's refactoring policy names this exact
failure mode; `TurnResult` should be constructible for the seed case without
letting a caller silently drop a field — a `TurnResult::seed(location)`
constructor that drains what `drain_turn` drains, or a boot that simply calls
`drain_turn`.

## Still to confirm (one check, not yet run)

That these two stories really do issue `erase_window` during boot. The mechanism
above is read off the code and matches the symptom exactly, but the final link is
inferred. Assert `machine.screen.erase_lower_requested` is `true` immediately
after boot for `zork1-invclues-r52-s871125.z5` and
`hitchhiker-invclues-r31-s871119.z5`, and `false` for `zork1-r88-s840726.z3`.
That assertion is also the regression test.

## Falsification

Revert the fix and confirm the banner survives turn 1 and vanishes after it —
the originally reported symptom — rather than merely that a flag is set.
