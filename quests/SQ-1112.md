## The gap

`ask_font_check` returns `None` when the terminal cannot be made interactive —
correct, since there is nobody to answer. But `config.toml` is seeded on that
same launch regardless, and "there is no config.toml" IS the never-ask-twice
flag. So a first launch that happens to be piped, redirected or otherwise
non-interactive silently spends the one chance to ask, and the player is never
offered the check on any later interactive run.

Recovery exists and is documented in the code: `--font-check on` and
`/run-font-check`. So this is a missed opportunity rather than a dead end — but
it is a silent one-way door, and the person it happens to has no way to know
they were skipped.

## Why the obvious fix was declined, and why that judgement is right

Making the flag survive needs a **persisted key** — "have we asked yet?" written
into config. That would have re-broken SQ-1104's guard 2: the test harnesses
seed an EMPTY `config.toml` precisely so the first-run condition is false, and an
empty file parses with every key at its default. A default of "not yet asked"
puts the prompt straight back in front of fourteen group binaries, `gallery` and
`pty_capture`.

That is a real tension, not an oversight, and it is why this is filed rather than
fixed in place.

## Directions worth weighing when it is picked up

- Key the flag on something the harness guard already sets, so an empty config
  still reads as "do not ask" while a genuinely fresh one reads as "ask".
- Or make the seeding conditional: do not write `config.toml` at all on a launch
  that could not ask, so the next interactive run is still a first run. Check
  what else depends on the file existing after a first launch before taking this
  one.
- Or accept it and make it visible: a one-line notice on the next interactive
  launch saying the check was skipped and how to run it.

## Do not fix this by weakening the harness guard

SQ-1104's falsification established that the guard is load-bearing in a way a
passing test cannot show: with the driver's seeding line removed,
`pty_emitted_stream` **still reported PASS** while the prompt drew, consumed one
of the harness's four Enter keystrokes and answered itself — leaving
`arrow_set = "filled"  # set by the font check` in the captured user dir. A pty
harness can lose a keystroke and stay green, so nothing downstream would ever
report it. That is why `font_check::the_pty_driver_still_writes_a_config_for_every_harness`
reads the driver's source and fails if the line goes.
