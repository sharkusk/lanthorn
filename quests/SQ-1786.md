--- note 2026-10-14T04:20:07Z ---

Today: fetch_worker decides per story via story_info::needs_fetch on the copy's own game dir (crates/app/src/fetch_worker.rs ~226-229). Copies share a game dir only by basename or a known commercial build (cli-host storage.rs story_key / story_key_for), so a second revision (different IFID) or a same-game file with another name is fetched again, one request each, even though the record and cover land once per entry in the shared store (app::ifdb_store).

Proposal:
- When a viewgame?ifiction record is fetched, record every <ifid> it lists against that entry (IFID → tuid) in the shared store, alongside the record.
- Before fetching a story by IFID, look its IFID up there; on a hit, write the copy's link (info.json) from the stored record and cover with no network request (Outcome: e.g. Linked or Skipped-with-write), exactly as if it had been fetched.
- A forced refresh ("refresh every story") still fetches each entry once per run, not once per copy: copies of an entry fetched earlier in the same order reuse it.
- An id_override / relink of one copy stays per copy (it names THIS copy's entry) and updates only that copy's link; the IFID map follows what IFDB's record says, not manual relinks.
- Keep IFDB's terms: fewer requests, never more; no prefetching of other entries.

Tests: two files with different IFIDs both listed in one fake record → one source call, both linked; a file whose IFID isn't listed → its own call; forced run → one call per entry.
