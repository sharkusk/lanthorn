## The suspicion has a mechanism, and it is in the raster path

`crates/app/src/render/screen.rs`, in the raster transcript builder (`raster_main_text`,
around line 4300 at `5865ed17`), word-wraps **every logical transcript line, every
frame** into a fresh `wrapped: Vec<String>` — and only afterwards computes
`total = wrapped.len()`, a `budget` of `rows - 1`, and slices out the ~40 rows
actually on screen:

    for word in line.split(' ') {
        let width = cols.saturating_sub(reserve_at(&floats, wrapped.len())).max(1) as usize;
        ...
    }
    let budget = rows.saturating_sub(1) as usize;
    let total = wrapped.len();

So the per-frame cost is O(TOTAL transcript), not O(visible rows). A five-thousand
turn session re-wraps five thousand turns of prose to draw forty lines of it.

Two things make it heavier than the loop alone suggests:

* It is not only wrapping. `transcript_runs` carries **per-character** style bytes,
  and `row_bits` materialises a fresh `Vec<u8>` per wrapped row for any line
  carrying emphasis.
* The transcript is really **five** parallel vectors — `transcript`,
  `transcript_styles`, `transcript_runs`, `transcript_para`, `transcript_images` —
  each `resize`d on every push in `push_transcript_kind`.

**There IS a wrap cache**: `State::bump_transcript_gen` bumps `transcript_gen` on
every mutation and its doc cites SQ-0305. The open question — and the reason this
quest starts with measurement rather than a fix — is whether the RASTER path
consults it or whether only the cell path does. Do not assume either way; find out.

There is also no cap on transcript growth. `state.transcript.truncate` appears
twice, both at anchors (clear-screen and rewind), never as a bound.

## What this quest is, and is not

**It is an instrument first.** Build a headless harness that drives a story to
100 / 1,000 / 5,000 / 20,000 turns and reports per-frame render time, allocation
counts and transcript memory, across:

* all three engines — **zvm, gvm and scott**. The user's question was explicitly
  "across all engines" and there is no evidence about any of them. Glulx routes
  through `glk_backend` and Scott through `scott_session`, so they may not share
  the raster builder's behaviour at all.
* both v6 render modes, raster and hybrid, which wrap through different code.

**It is not a fix yet.** Only once the knee is located does it make sense to
choose between honouring the existing cache in the raster path, slicing before
wrapping rather than after, an incremental or rope-backed transcript, or a cap.
Optimising from a reading rather than a profile is how you speed up the wrong
loop.

## Scheduling

`render/screen.rs` is the hot file for SQ-1009's proportional-pen lane. The
HARNESS can be built now against any engine; the fix waits for that lane to land.

Note also that raster is now a first-class mode rather than a fallback, so a
raster-only cost is a real cost, not a corner case.

## MEASURED. Cost grows with total scrollback on all three engines.

Instrument: `crates/app/examples/scroll_bench.rs` (commit `c91d73ab`). Release, 8
repeats, freely redistributable fixtures, all three engines and both v6 modes.

                        cold_ms          build_main_text twice, no change, @20k
    zvm cell            0.6 -> 34.6      60.243 / 60.140 ms
    zvm v6 raster       8.2 -> 28.5      24.001 / 23.591
    zvm v6 hybrid       2.0 -> 17.9      25.136 / 24.486
    Glulx               0.12 -> 2.5       1.120 /  1.109
    Scott               0.17 -> 10.3      8.608 /  8.578

Calling `build_main_text` twice with ZERO state change between shows no speedup at
any size on any engine, and the cost is near-linear in transcript length
throughout (~150-175x for ~190-200x the lines). It only reads
`AppState.transcript`, so the shape is identical across engines. `idle_ms` stays
flat and small everywhere, which rules out the VM. **No knee** — continuous from
100 turns up. Transcript memory grows unbounded with it (17.7 MB at 20,000 turns
on the cell path), consistent with `truncate` never being called as a bound.

## The wrap cache is NOT live in raster, and a keystroke is what pays

`TranscriptWrapCache` (SQ-0305) is consulted only by `render::transcript`, the
CELL path — which hybrid's story text also uses. Verified by reading:
`build_main_text` in `screen.rs` never names `state.transcript_wrap`. That is why
cell and hybrid idle flat at 0.27 ms and 1.7 ms from 100 turns to 20,000, and why
a keystroke is a cache hit there — `TranscriptWrapKey` does not include the input
line.

Raster instead sits behind a coarser whole-canvas gate, and **`screen.rs:4165`
hashes `state.input.value` into the generation key**. So an unchanged transcript
plus one typed character busts the gate and forces a full re-wrap: measured at
**25.058 ms for a single keystroke at 20,000 turns**. Raster is now a first-class
mode that the user plays in, so this is the mode where it is felt.

## *** THE FIX IS BETTER THAN A CACHE — the raster wrap width is INVARIANT ***

The user's observation, and it is the design insight this quest turns on: **in
raster the line width never changes, even across a resize.** Confirmed at
`screen.rs:3970`:

    let cols = (tw / u32::from(state.v6_text.cell().w)).max(1) as u16;

`tw` comes from `story_prose_box` over the **native** v6 screen rect — the game's
own coordinate space, not the terminal's. A resize changes only how the finished
composite is scaled into the pane. Hybrid and the cell path wrap to the TERMINAL's
column count and therefore must re-wrap on every resize; raster never does.
(SQ-1032's vertical-growth mode preserves this — height grows, width is fixed.)

Three consequences, and together they beat "consult the existing cache":

1. **Previously wrapped rows can never change**, so the wrap can be INCREMENTAL
   and append-only rather than recomputed. `cold_ms` becomes O(new lines) instead
   of O(total).
2. **The input line is not part of the wrapped product at all** — `build_main_text`
   takes it separately — so the keystroke case becomes free, not merely cached.
3. The existing cache is a whole-PRODUCT cache keyed on width and generation; it
   must rebuild entirely whenever the transcript changes. Adopting it in raster
   would fix the keystroke case and leave `cold_ms` linear. Incremental fixes both.

### What an incremental wrap must still handle

* **Truncation at anchors.** `state.transcript.truncate` is called at a
  clear-screen anchor and at a rewind. Those invalidate the tail; `line_starts`
  already maps logical lines to wrapped rows and is what the drop should key on.
* **Floats.** `reserve_at(&floats, wrapped.len())` narrows the rows beside an
  inline picture, so a row's width depends on float positions in WRAPPED
  coordinates. Floats are pushed as content is wrapped, so this stays append-only
  — but verify it rather than assuming, because a float that changes position
  would retroactively change earlier rows' widths.
* **Per-character styles.** `transcript_runs` and the `row_bits` slicing are
  parallel to the wrapped rows and must be appended in step.

## Closed — the fix this quest called for shipped under SQ-1034

This quest was written as measurement first, fix second, and only the measurement
carried its trailer: `c91d73ab` added `crates/app/examples/scroll_bench.rs` under
`Quest:`, which advances to `partial` and closes nothing. The fix was then
deliberately scheduled behind SQ-1009's hot file (`render/screen.rs`) and, when it
came, it came as its own quest — **SQ-1034, done 2026-08-24, commit `8391b9f9`**.
Nobody came back to close this one, which is the whole of why it read as
outstanding.

Verified in the tree rather than taken from the note: `build_main_text`
(`screen.rs:4271`) no longer wraps at all. It calls
`render::wrap_cache::raster_wrap_refresh` and windows the cached rows, and its own
comment names SQ-1034 and the 25.058 ms keystroke this quest measured.

`render/wrap_cache.rs` is the one owner of "has the wrap moved, and by how much?"
— one `WrapKey`, one `WrapPlan` (`Reuse` / `Append { from }` / `Rebuild`), two
products. The layout facts live in a single `Copy` `WrapShape` with one
constructor so a caller cannot assemble a subset; `clear_anchor` is a shape field,
so the `transcript.truncate` case this quest flagged rebuilds for free rather than
needing a path of its own; and `WrapContent::tail` fingerprints the last consumed
source line as a GUARD behind the hand-maintained `edits` counter, because every
in-place mutator we have touches that line. `input.value` is deliberately absent
from the key, which is what makes the keystroke free rather than merely cached.

**One thing NOT re-verified at close**: SQ-1034's stated acceptance was to re-run
`scroll_bench` before and after and confirm that BOTH `cold_ms` and the keystroke
cost stop growing with turn count. That belongs to SQ-1034 and is not re-measured
here. If a later scrollback-cost suspicion arises, run the instrument before
reading any code — it exists, it is release-only, and it prints its own build
profile.

Related: SQ-1034 (the fix), SQ-0305 (the cell path's original cache).
