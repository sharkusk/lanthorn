## The suspicion has a mechanism, and it is in the raster path

`crates/app/src/render/screen.rs`, in the raster transcript builder (`raster_main_text`,
around line 4300 at `5865ed17`), word-wraps **every logical transcript line, every
frame** into a fresh `wrapped: Vec<String>` — and only afterwards computes
`total = wrapped.len()`, a `budget` of `rows - 1`, and slices out the ~40 rows
actually on screen:

    for word in line.split(' ') {
        let width = cols.saturating_sub(reserve_at(&floats, wrapped.len())).max(1) as usize;
        ...
    }
    let budget = rows.saturating_sub(1) as usize;
    let total = wrapped.len();

So the per-frame cost is O(TOTAL transcript), not O(visible rows). A five-thousand
turn session re-wraps five thousand turns of prose to draw forty lines of it.

Two things make it heavier than the loop alone suggests:

* It is not only wrapping. `transcript_runs` carries **per-character** style bytes,
  and `row_bits` materialises a fresh `Vec<u8>` per wrapped row for any line
  carrying emphasis.
* The transcript is really **five** parallel vectors — `transcript`,
  `transcript_styles`, `transcript_runs`, `transcript_para`, `transcript_images` —
  each `resize`d on every push in `push_transcript_kind`.

**There IS a wrap cache**: `State::bump_transcript_gen` bumps `transcript_gen` on
every mutation and its doc cites SQ-0305. The open question — and the reason this
quest starts with measurement rather than a fix — is whether the RASTER path
consults it or whether only the cell path does. Do not assume either way; find out.

There is also no cap on transcript growth. `state.transcript.truncate` appears
twice, both at anchors (clear-screen and rewind), never as a bound.

## What this quest is, and is not

**It is an instrument first.** Build a headless harness that drives a story to
100 / 1,000 / 5,000 / 20,000 turns and reports per-frame render time, allocation
counts and transcript memory, across:

* all three engines — **zvm, gvm and scott**. The user's question was explicitly
  "across all engines" and there is no evidence about any of them. Glulx routes
  through `glk_backend` and Scott through `scott_session`, so they may not share
  the raster builder's behaviour at all.
* both v6 render modes, raster and hybrid, which wrap through different code.

**It is not a fix yet.** Only once the knee is located does it make sense to
choose between honouring the existing cache in the raster path, slicing before
wrapping rather than after, an incremental or rope-backed transcript, or a cap.
Optimising from a reading rather than a profile is how you speed up the wrong
loop.

## Scheduling

`render/screen.rs` is the hot file for SQ-1009's proportional-pen lane. The
HARNESS can be built now against any engine; the fix waits for that lane to land.

Note also that raster is now a first-class mode rather than a fallback, so a
raster-only cost is a real cost, not a corner case.
