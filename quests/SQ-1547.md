--- note 2026-09-24T08:10:59Z ---

Citations crates/app/src/, as of 5560bc25.

Observed: when a timed interrupt routine returns true and the @read is terminated, `run_timed_interrupt` calls `abort_timed_input("")` (session.rs:1767), so the text buffer the game reads back is empty even when the player had typed part of a line. The TUI and a headless host through `host::clock::fire_due` behave identically.

Question: what should the text buffer hold when a timed interrupt terminates input? Check ZMSD §15 (@read / @aread, timed input) and §10 input rules, and compare Frotz's behaviour (and one other interpreter, e.g. Bocfel), with a real timed-input story (Border Zone, or a tiny assembled v5 test with a timed aread).

Change (if the standard or reference interpreters keep the partial text): pass the partial line through to the terminated read, and keep the host's own input draft consistent with what the game now holds.

Acceptance: a test with a tiny assembled v5 story (timed aread whose routine returns true after the player has typed "hel") asserting the buffer content matches the verified rule; the TUI's timed-input suites still pass. If the current behaviour turns out to be correct, close with a note citing the spec text, so nobody re-opens it.

--- note 2026-09-24T14:28:02Z ---

Verified against the Z-Machine Standards Document 1.1, §15, the "read"/"aread" opcode entry (https://inform-fiction.org/zmachine/standards/z1point1/sect15.html), fetched and grepped directly from the live page (not from memory):

"In Version 4 and later, if the operands time and routine are supplied (and non-zero) then the routine call routine() is made every time/10 seconds during the keyboard-reading process. If this routine returns true, all input is erased (to zero) and the reading process is terminated at once. (The terminating character code is 0.) [...] If it was interrupted, the cursor is left at the rightmost end of the text typed in so far."

Read together with the immediately preceding paragraph on the "leftover characters" convention ("if byte 1 contains a positive value at the start of the input, then read assumes that number of characters are left over from an interrupted previous input" — an opt-in the GAME performs on a *subsequent* @read call, not something the interpreter does automatically) and the following paragraph ("lexical analysis is performed on the text... A timed-out input returns 0"), the spec's "erased (to zero)" unambiguously means the interpreter zeroes THIS read's buffer/count when a timer routine aborts it — matching session.rs:1767's abort_timed_input(""). The "cursor left at the rightmost end" sentence is about on-screen cursor placement (no extra carriage return printed), not buffer content — it does not contradict the erasure.

dfrotz black-box attempt: used stories/borderzone-r9-s871008.z5 (Release 9/Serial 871008), a real Infocom game whose whole design is a live real-time clock during input (confirmed by its own intro text: "cause the real-time clock to stop running... use the PAUSE command"). Drove dfrotz under a pty (character-at-a-time raw send, no newline), idling mid-line for 8s and then 25s real time while a partial word ("loo", "xyzzy") sat unsubmitted. In both cases no timer interrupt fired — the read only completed once Enter was sent, with the exact characters typed, and nothing async happened during the idle. Conclusion: dumb-interface dfrotz does not appear to exercise @read's real-time interrupt path in a way observable from outside during mid-line idle in this headless environment (consistent with its man page: "does not support... even screen-handling"), so this black-box channel could not settle the question either way; also tried curses `frotz` over the same pty (which does read char-by-char), but MORE-prompt/redraw timing made a clean 25s-idle observation impractical to set up reliably in the time available. The spec text above was treated as decisive per the task's own allowance ("dfrotz plus the ZMSD text is sufficient if that's what you have" — here it was the ZMSD text alone that settled it, dfrotz being inconclusive).

Conclusion: session.rs:1767's abort_timed_input("") is CORRECT per ZMSD §15. No code change made.

Side finding (filed separately, NOT fixed here — out of SQ-1547's scope): crates/zvm-cli/src/main.rs:2157 does the opposite — machine.abort_timed_input(line.trim_end()) — writing the CLI's partial typed line into the buffer on abort, which appears to contradict the same spec text. Filed as SQ-1550.
