## The question

`zvm::screen::V6Cell` became runtime state under SQ-0917 so a profile can declare
its own Version 6 cell. The Macintosh's is settled — `mac/xzip.lst` states
`colWidth := 7; lineHeight := 15 {16}` and four independent measurements off
`machine-screenshots/mac-zorkzero-*.png` agree. **The Amiga's is not**, and it is
the one machine with a real measured discrepancy left.

What is wanted is the DECLARED metric: the bytes Infocom's Amiga interpreter
writes into header `$26` (height) and `$27` (width), which the story reads and
lays its windows out from. That is a different quantity from what the machine
DRAWS, and SQ-0917 is the reason the distinction is worth spelling out — the Mac
declares a fixed 7 while drawing proportional Geneva, and 7 is just Geneva's
average advance.

## What is already measured, and what it does not answer

From `machine-screenshots/amiga-arthur.png` (320x200, pixel-exact OCS capture —
every colour channel a multiple of 0x11, so nothing resampled it):

- **Line pitch is exactly 10.** White text rows 121-129, 131-139, 141-149,
  161-169, 171-179, and the inverse status bar occupies rows 100-109 — one cell,
  independently.
- **Confirmed a second way** on `amiga-arthur-hint.png`: the InvisiClues
  highlight box is 166x20 at that capture's 2x scale = **83x10 native**.
- **The face is proportional**, average advance 4.5 px on prose. Per-word
  measurement ranges 3.75 to 5.25 and tracks word content, which no fixed pitch
  permits. `native_disk_font.rs` reads `char.data` as 10x10 nominal,
  `FPF_PROPORTIONAL`, advance 2..=8, and the capture now agrees with it.

None of that is the declared metric. A proportional face has no single advance,
so the interpreter must have picked a number, and the capture cannot show which.
The highlight box was the best candidate for reading a column grid off the screen
and it turned out to hug the proportional text rather than snap to cells (83 px
for the 14 uppercase characters of `THE CHURCHYARD`, 5.9 px/char — consistent
with the same 2..=8 face, uppercase being wider than the 4.5 prose average).

## The gap this would close

`AMIGA_STD_WINDOW` is (320, 200) and `V6_ART_SCALE` doubles it onto the 640x400
unit screen, where the 8x16 cell gives 80x25 characters. The machine has **20**
text rows. As a ratio, which does not depend on the doubling: lanthorn's line is
16/400 = 4.0% of screen height, the Amiga's is 10/200 = 5.0%. Real Amiga v6 text
is ~25% larger relative to its artwork than lanthorn draws it.

**The gap is entirely vertical.** Columns are already close — the machine fits
~71 characters of average width across 320 px against lanthorn's 80. So if the
declared height turns out to be 10 native (20 in the doubled model), changing
only `$26` makes the row count exact and the width may not need touching at all.
That is a hypothesis to test, NOT a licence to set it: declaring a metric we have
not read is exactly the guess SQ-0901 punishes.

## Routes, ranked

1. **The interpreter's own source.** `github.com/erkyrath/infocom-zcode-terps` is
   where every other machine in `zvm::interpreter` came from — `mac/xzip.lst`,
   `apple/yzip/rel.15/apple.equ` (`MFONT_W EQU 3`, `FONT_H EQU 9`), `st/stx1.s`.
   Whether it carries an Amiga XZIP is unchecked. If it does, one grep ends this.
2. **Read it out of the shipped binary.** Fully local — `blorb::adf` /
   `app::assets::files` already mount the Amiga floppies, so the 68k interpreter
   is in hand. It writes `$26`/`$27` at boot, so the values are literals in that
   file. Either disassemble around the header writes, or narrow via the font-open
   path: `char.data` states nominal 10x10, and an interpreter usually declares
   either `tf_XSize` (the nominal) or a computed average, which is a small set of
   immediates to look for.
3. **More measurement.** Needs a frame where the game positions something by
   COLUMN rather than by pixel, so the count falls out of the geometry. The
   highlight box was not it. Journey's command menu is width-driven (see SQ-0940)
   and might be.
4. **Another interpreter's Amiga profile.** Weakest and probably not worth
   taking: Frotz's is a modern choice, not a period fact, and period facts are
   the entire point of the table.

## Do not conflate with

- **SQ-0917** — the Macintosh cell, which is settled and does not wait on this.
- Arthur's PROPORTIONAL rendering, which stays a GUI question. Adopting real
  per-glyph advances means the ENGINE advances proportionally, and hybrid cannot
  follow (it maps `native_px / cell.w` to one terminal column, which collides
  once run origins stop being cell multiples). That would make zvm's model
  render-mode-dependent, which the crate's no-I/O-policy rule forbids. This quest
  is only about the single declared number.

## A trap waiting for whoever lands the Amiga cell — read before setting the value

SQ-0917 landed the Macintosh's 7x15, and doing so exposed a class of defect that
**a 10-tall Amiga cell walks straight back into**. This is not hypothetical: the
same bug was shipped once and nearly shipped a second time on the same day.

### The face-selection floor is a comparison against a cell dimension

`render/bitfont.rs`'s `blit_glyph_styled` chooses between the 8x16 face (SQ-0932)
and the older 8x8 master by a height floor. It was `ch >= 16`, which read as a
quality rule and was really an assumption that 16 is the only cell in play — so
the Macintosh's 15 fell under it and silently got the 8x8 chain, **which has no
descender below the baseline**. Clipped tails on `g j p q y`, on one machine, in
raster and in every hybrid region the ring rasterises. The user found it by eye;
5983 passing tests did not.

The floor is now `ch >= 12`, chosen because three quarters of a 16-row face
survives there — reasoning about **15**, with no thought given to what sits below.

**A 10-tall cell is below it.** If this quest declares the Amiga at 10 rows
native, every Amiga glyph goes back to the 8x8 fallback and the clipped-descender
defect returns wearing a different machine's name.

### Do not simply lower the floor again

Whether the 16-row face sampled down to 10 rows beats an 8-row master doubled up
to 10 is an **empirical** question. At `ch == 10` the resample keeps 10 of 16
source rows and drops 6, which is a real loss; the 8x8 master is drawn to be
legible at its own size. It could go either way, and today proved twice over that
reasoning about glyph rendering without dumping pixels produces confident wrong
answers — two separate descender tests were written from a mental model and both
PASSED with the bug in place.

Dump both faces at `ch = 10` and look, the way
`a_descender_still_descends_at_the_macintoshs_fifteen_row_cell` was eventually
settled: render `x` and `y`, compare the lowest inked row of each. At 15 the depth
is 3 with the proper face and 1 with the fallback. Measure the same pair at 10
before choosing.

### And the same shape may hide elsewhere

The lesson from SQ-0917's 35 missed sites is that a grep for `FONT_W`/`FONT_H`
cannot see a bare number, and a value-flip falsification cannot see a THRESHOLD
compared against the value. Before declaring an Amiga cell, sweep for both:

- arithmetic — `/ 16`, `/ 8`, `* 16`, `* 8`, `(8, 16)`
- comparisons — `>= 16`, `== 8`, `< 12`, and any other guard whose constant is a
  cell dimension in disguise

`V6Cell::row_of`/`col_of`/`run_px` (added after SQ-0917) handle the arithmetic for
any FIXED cell, so a 10x10 needs no work there. They do NOT handle a threshold,
and they do NOT handle proportional advance — Arthur's Amiga face is 2..=8 px per
glyph, which needs the `FontMetrics` shape described on SQ-0917, not `V6Cell`.

## UNBLOCKED — the Amiga interpreter source exists, and it says 640x200

`github.com/erkyrath/infocom-zcode-terps` has an `amiga/` directory (60 files) carrying both XZIP and YZIP. **YZIP is the Version 6 one**, and `amiga/yzip.h` declares:

    #define AM_YSIZ 200		/* hardwired for YZIP */
    #define AM_XSIZ 640
    #define HIDDEN_TBAR_HEIGHT 4

That is Amiga **hires non-interlaced**: 640 addressable columns, 200 addressable rows, displayed with 2:1 tall pixels. Note `HIDDEN_TBAR_HEIGHT 4` alongside — a margin term, and the Macintosh had `wMarg = 4` playing the same role in `totCols`.

No font metrics are in the header. `colWidth`/`lineHeight` equivalents must be in `yzip.c`, `yzip1.c`, `yzip2.c`, `yzip3.c` or `gfx.c`/`gfx.a`, which are the next files to read.

## But this is in TENSION with three things already measured — resolve before acting

1. **`machine-screenshots/amiga-arthur.png` is 320x200 and is native pixels.** info.txt establishes that from the palette: 18 colours, every channel a multiple of 0x11, no blended value anywhere — a resampled or halved capture would carry off-palette averages. A 640-wide screen captured at 320 wide could not look like that.
2. **Arthur's Amiga art archive is 320x200**, and `PictSource::art_scale` answers (2,2), which is why `ring_scout` reports `screen 320x200 art scale (2,2)` and a native 640x400.
3. **Measured text pitch in that capture is exactly 10 rows**, with the inverse status bar occupying rows 100-109 — one cell — independently.

So we currently model the Amiga v6 screen as 320x200 doubled to 640x400, and the interpreter header says the machine is 640x200. Those cannot both be describing the same thing.

Candidate reconciliations, none verified:

* **`AM_XSIZ`/`AM_YSIZ` are the AMIGA DISPLAY, not the Z-machine screen.** A 640x200 hires screen with 2:1 pixels is geometrically equivalent to 320x200 square-pixel content doubled horizontally — so a 320-wide picture would be drawn at (2,1), each art pixel two screen pixels wide and one tall, and would LOOK square. Our (2,2) would then be right in aspect and wrong in units.
* **Arthur specifically runs lores.** The constant is "hardwired for YZIP", so this seems unlikely, but Arthur r54 is one release and the header is one build.
* **The capture is of a lores screen from a different pressing.** Check the release the emulator was running against `real_media_releases.rs`.

## Why this matters beyond the cell

If the machine is 640x200, then a 10-row font is 10 rows of a 200-row screen — 20 rows of the 400 we currently hand the story — and the cell question and the SCREEN question are the same question. That makes this bigger than header $26/$27 and worth doing carefully: getting the screen wrong moves every v6 rect on the machine, which is the SQ-0901 failure mode.

**Do not change `art_scale` or the Amiga std_window on the strength of this note.** Read the YZIP sources for the font metrics and the screen setup first, and reconcile against the pixel-exact capture, which is the one piece of evidence that cannot be argued with.

## Source read (2026-08-23). Two of our three claims survive; one is refuted; the cell still cannot be answered.

Fetched all of `amiga/`: `yzip.h`, `yzip{,1,2,3}.c`, `gfx.c`, `gfx.a`, `amigazip.c`, `xzip1.c`, `ax{,1,2,3,4}.asm`, plus `apple/yzip/rel.15/` for cross-reference. Nothing 404'd.

### THE BOUNDING FACT: the Amiga YZIP kernel is not archived

`amiga/` carries only the C layer for YZIP. `ax.asm` announces `TTL "XZIP INTERPRETER FOR COMMODORE AMIGA"` — the **v5** kernel, paired with `xzip1.c` (globals `rows`/`columns`) and not with `yzip1.c` (globals `tot_rows`/`tot_cols`, deliberately renamed `/* (was columns, rows) */`). `gfx.c` references `extern struct windowRec *curwp;` and `extern int Hirez;`, neither defined anywhere in the repo. **The code that writes the v6 header words was never archived**, so $26/$27 cannot be answered from this source. Do not let anyone conclude otherwise from a partial reading.

### 1. THE UNIT IS A PIXEL — the division is commented out in place

`yzip1.c:69` — `/* cursor variables (all now in pixels) */`

`yzip1.c:255-262`:

    tot_rows = y_res;	/* /y_char */
    tot_cols = x_res;	/* /x_char */

Against the **v5** interpreter one file over, `xzip1.c:304-305`, which does divide:

    rows	= y_res / y_char;
    columns	= (x_res / x_char) /**-1**/;

Every other use follows: `yzip3.c:264` `x_align = cur_col /* * x_char */`, `yzip3.c:637` `xmouse = (im->MouseX /* /x_char */) + 1`, scrolling by `amiga_scroll(up_pix)`. `y_char = 8` / `x_char = 8` survive (`yzip1.c:648-661`) only as the C layer's fallback newline pitch in `char_out`/`BS_cursor`/`erase_line` — routines the v6 kernel largely bypasses.

### 2. THE SCREEN IS 640x200 HIRES, NON-INTERLACED

`yzip1.c:395-404` opens one `CUSTOMSCREEN` with `ViewModes = HIRES` and nothing else; `yzip1.c:443-449` forces `ns.Height = AM_YSIZ; ns.Width = AM_XSIZ;` with the comment "For YZIP (w/gfx), back to the future!". Depth 4 planes / 16 colours for a graphical game (`yzip1.c:609-613`, `gfx.c:38`).

**`LACE`/`INTERLACE` appear nowhere in any Amiga source in the repo, and the literal `400` does not occur.**

### 3. *** art_scale IS (2,1), NOT (2,2) *** — this refutes our model

`gfx.c:80-88` — `picX /* unscaled (320 max) */` and `picXD /* optionally scaled for display (640 max) */`, `picYD /* (same as picY) */`.

`gfx.c:370-373`, consecutive lines:

    if (gh.scale)
        ge.picXD = ge.picX * 2;		/* scaled up */
    else	ge.picXD = ge.picX;
    ge.picYD = ge.picY;

`gfx.c:920-924` (`opPicInf`, i.e. what `@picture_data` returns the GAME) returns `picYD` and `picXD` — doubled width, undoubled height. `gfx.c:654-657` blits `subRows` in for `subRows` out. `gfx.a:288-298`'s `QuadPic` duplicates pixels **along a row** only. **There is no vertical scaling anywhere in `gfx.c` or `gfx.a`.**

And placement is unscaled pixels in the 640-wide space — `gfx.c:822` "position given in pixel units, 0-origin, relative to current window", `xpos` passed through untouched.

The design is coherent and is the whole point of "1 char unit = 1 pixel": a hires 640x200 pixel is half as wide as it is tall, so 320-wide art doubled horizontally covers the same screen AREA a 320x200 lores frame would, while text drawn at 640 gets twice the horizontal detail. Art in fat units, text in thin ones, one address space.

**Squaring the pixel by doubling VERTICALLY instead gets the aspect right and the coordinate space wrong — every y the game names would be off by 2x.**

### 4. Proportional: not settled, and the archived layer argues against it

`yzip1.c:759-808` loads `ALTNAME "Char.Data"` as a standard Amiga `TextFont` off the game disk, relocating `ln_Name`, `tf_Accessors`, `tf_CharData`, `tf_CharLoc` — and conspicuously **not** `tf_CharSpace`/`tf_CharKern`. `line_out` (`yzip3.c:257-291`) advances `cur_col += len * x_char` with `x_char` fixed at 8 regardless of the selected font. Neither is proof, but neither is what you write for a proportional face.

### 5. THE CONTRADICTION THAT MUST BE SETTLED FIRST

The researcher raised an arithmetic check I had not, and it is the sharpest thing in the report:

`info.txt` measures Arthur's prose at **3.75–5.25 px per character in a 320-wide frame**, and `native_disk_font.rs` reads advances of **2..=8** from `char.data`. Those agree at 1:1 and **disagree at 2:1** — an average advance of ~9 real pixels would exceed the font's own maximum of 8.

So either:
* the capture is a native 640x200 hires frame halved — but then the advance arithmetic does not work, AND info.txt's palette argument (18 colours, every channel a multiple of 0x11, no blended value) says it was not resampled; or
* the capture is 1:1 and **the shipped Arthur screen is 320 wide**, in which case this archived source is not the build that shipped.

`Hirez` being an `extern int` defined nowhere in the repo means a lores path was contemplated. A shipped build may have set it differently.

### Standing instruction, now firmer

**Do not change `art_scale`, `AMIGA_STD_WINDOW`, or declare an Amiga cell on the strength of this.** The source and the pixel-exact capture disagree about the screen, and until that is resolved any change moves every v6 rect on the machine — the SQ-0901 failure mode, at scale.

The productive next step is the contradiction in §5, not more source reading. Candidate routes: check the release/medium the emulator capture was taken from against `real_media_releases.rs`; capture Amiga Arthur again from a known hires configuration; or measure a KNOWN glyph run in the capture against `char.data`'s own advance table to decide 1:1 versus 2:1 directly.

### Also worth knowing (cross-machine)

The Apple YZIP kernel DOES survive and **never writes $26/$27 at all** (`apple/yzip/rel.15/zip.equ:54` defines `ZFWRD EQU 38` and nothing writes it). It carries font size **per window** instead — `windows.asm:23,49` `WINFSIZE ; (WORD) font Height/Width`, with `apple.equ:160-167` `FONT_W EQU 2 / FONT_H EQU 9` in a unit space where 1 horizontal unit = 4 real pixels. That is delivered through window property 15, not the header.

Relevant to us: `gfx.c` dereferences a `windowRec` (for `->attr`, `->gcnt`) that is defined nowhere in `amiga/` — and a per-window font size is exactly what would live in it. If the Amiga followed the Apple's pattern, the answer to this quest may be "per window, not in the header at all".

## CORRECTION to the note above — the screen-model conclusion was wrong

The note above reported the source as refuting our Amiga model and led to SQ-1023. **SQ-1023 is discarded: there was no defect.** `AM_XSIZ 640 / AM_YSIZ 200` is the Amiga's OUTPUT MODE, not the game's coordinate space. The chain is 320x200 internal → 640x200 hires display (half-width pixels) → 640x400 on a modern square-pixel screen, so `art_scale` (2,2) and `AMIGA_STD_WINDOW` (320, 200) are correct and stay.

`gfx.c:370-373`'s `picXD = picX * 2; picYD = picY;` is the internal→display mapping: width doubles because a hires pixel is half as wide, height does not because those 200 rows are already full height. Reading it as an art→screen scale comparable to `art_scale` is what produced the false alarm. See SQ-1023 for the full reconciliation — every capture and every measurement agrees once the mapping is read correctly.

**Strike the "*** art_scale IS (2,1), NOT (2,2) *** — this refutes our model" section above and §5's contradiction.** There is no contradiction; the 320-wide captures ARE the internal frame, which is exactly what they should be.

## What survives, and it is the part that matters for THIS quest

Everything the source says about FONTS and about the missing kernel is unaffected:

* **The Amiga YZIP kernel is not archived.** `amiga/` carries only the C layer; `ax*.asm` is the v5 XZIP kernel. So $26/$27 cannot be answered from this source, full stop.
* **The Apple YZIP — whose kernel DOES survive — never writes $26/$27 at all.** It carries font size PER WINDOW (`windows.asm:23,49` `WINFSIZE ; (WORD) font Height/Width`, `apple.equ` `FONT_W 2 / FONT_H 9`), delivered through window property 15.
* `gfx.c` dereferences a `windowRec` (`->attr`, `->gcnt`) defined nowhere in the archived tree — and a per-window font size is exactly what would live in it.

**So the live hypothesis for this quest is that the Amiga answers per-window rather than in the header**, the same as its Apple sibling. That is a different shape of answer from the Macintosh's `colWidth := 7` and worth knowing before anyone goes looking for a header constant that may not exist.

Also unaffected: `yzip1.c:759-808` loads `Char.Data` as a standard Amiga `TextFont` with a per-character offsets array, relocating `tf_CharData`/`tf_CharLoc` but NOT `tf_CharSpace`/`tf_CharKern`; and `line_out` (`yzip3.c:257-291`) advances `cur_col += len * x_char` with `x_char` fixed at 8. Neither is proof about proportionality, and both are worth re-examining against a shipped build.

## THE MACHINE WRAPS BY PIXEL. No column count reproduces it.

Every full prose line in `amiga-arthur-text.png` ends between 596 and 634 device px
(298-317 in the machine's 320-wide frame) while carrying DIFFERENT character
counts — 71 on the first, fewer on the fourth. They stop at the same pixel
boundary, within one word's width of the margin.

This is why a renderer-only proportional pen cannot look right at any scale. zvm
packs 80 columns of 8 px into Arthur's line; drawn at true machine size (9.4 native
px average) those 80 characters need ~752 px in a 640-wide window, a 17% overflow.
Drawn at 1x they fill 376 of 640 and the type is half-size against the artwork. The
wrap width is what makes proportional text FILL a line.

## But the prose wrap is OURS, not the engine's — the scope is much smaller

Window 0 in v6 is wrap+scroll, so it falls through zvm's grid path to the stream,
and the HOST wraps it: `render::screen::raster_main_text` word-wraps by counting
characters against `cols`. The game never learns the wrap points. So pixel wrap for
prose is an app-side change in one function and needs no zvm change at all.

zvm's per-character pen (`x_cursor += fw`, `V6Text::px_w`, `grid.put`) only governs
the GRID windows — the status line, the inventory columns, the map labels — which
the game positions by pixel and usually prints in one call each. Drawing those
proportionally from the run origin is right without touching the engine. The engine
pen matters only for `@get_cursor` readback and paint-run overlap trimming, and can
follow later.

## THE TEXT SPACE IS PER-GAME (from SQ-1025's Shogun measurement)

Shogun's Amiga prose measures a flat 4.00 px/char in the machine's 320x200 art
frame, with an 8-row line pitch. Topaz is 8 wide, so its text is drawn in the
**hires 640-wide space** where a pixel is half an art pixel — `gfx.c`'s "art in fat
units, text in thin ones". Half the width and all of the height, which cancels to
the 8x16 native cell we already declare. Shogun needs nothing.

Arthur does the opposite. Its own table averages 5.21 px of advance and the capture
measures 4.70 px/char; those agree in the **320 art space** and would be 2.6 in the
hires one. So Arthur's text is in the fat space.

**Therefore "the Amiga's Version 6 cell" is not one number**, and the header
question this quest opened with has no single answer. It is `extern int Hirez;` —
declared in the archived `gfx.c`, defined nowhere in it, which now reads as a
per-game flag rather than a missing constant.

## The rule that follows, and the plan

**The declared metric follows the admitted face.** A machine face is admitted only
when it is PROPORTIONAL, which is exactly what separates Arthur's typeface from
Journey's and Beyond Zork's font-3 sets (fixed 8x8, null metric arrays, and code 65
is a solid block — SQ-1017). When one is admitted the cell height is the face's

## THE DESIGN, decided with the user 2026-08-23

### Decouple the grid column from the pixel cursor

`GridWindow` already carries BOTH representations, and the code says so —
`px_texts` are "exact pixel-positioned runs for the pixel raster (the cells above
stay the cell-mode fallback)". Hybrid draws `cells`, raster draws `px_texts`.

Today `c = (x_cursor - 1)/fw + 1` DERIVES the column from the pixel cursor, which
is why a proportional pen would corrupt the grid: at ~10.4 px against an 8 px
cell, `c` jumps by 1.3 per character and the grid grows holes. So the window must
track them separately — **the pixel cursor advances by the face's advance, the
grid column advances by one per character.**

### The wrap: zvm owns the game's truth, hybrid re-wraps for DISPLAY

The user chose hybrid filling its own width rather than sharing raster's break
points. Consequences, both real:

1. **zvm does not currently keep the unwrapped text.** The grid path wraps AS IT
   PRINTS and emits runs, so there is no logical line left to re-wrap. zvm must
   retain the logical run.
2. **The game observes the cursor**, so only one wrap can be "the" cursor. The
   PIXEL wrap is the game's truth — it is what the machine did and what
   `@get_cursor` must report. Hybrid's column wrap is display only.

**ONE wrap routine, parameterised by the measure** — pixel extent for raster,
column count for hybrid — called twice, not implemented twice. This is the whole
mitigation for the risk the user accepted: two call sites of one function cannot
drift, two functions will, and that drift is exactly what made SQ-1026 and
SQ-1035 a matched pair.

### Do not change the declared WIDTH to paper over this

Tempting, and wrong: no single declared width satisfies the score bar, F5, F4's
pixel columns and the startup spans at once. If a candidate appears to, check it
against all four before believing it — and if one genuinely does, that is a real
finding worth reporting rather than a coincidence to exploit.

### What was measured

`machine-screenshots/amiga-arthur-F4.png` is 720x570 PAL overscan and is 1:1 with
our native 640-wide frame — its score bar runs device 70..651 against our native
28..611, so the border offset is **42**. Measured with PIL, not by eye:

| item on F4          | capture device | capture native | OURS native | ours as window-relative |
|---------------------|---------------|----------------|-------------|-------------------------|
| stat labels         | 70            | 28             | 28          | x_cursor 1              |
| stat values `0`     | 276..285      | 234            | 131         | x_cursor 104 = 13 x 8   |
| gauge rule `\|`      | 524..525      | 482            | 547         | x_size - 520, 520 = 65 x 8 |
| gauge cap `100`     | 510..541      | 468            | 539         | x_size - 512, 512 = 64 x 8 |

The game computes each of those as `k x font_width` (two of them from the right
edge). Ours are on a declared 8. **The capture is on 16, to the pixel, on all
three**: 13x16 = 208 against a measured 207; `584 - 8x16` = 456 against 455;
`584 - 9x16` = 440 against 441 — the +-1 is the 1-based/0-based seam, and the
labels at x_cursor 1 agree exactly in both.

Sixteen is also what the archived source says: `amiga/yzip3.c`'s `line_out`
advances `cur_col += len * x_char` with `x_char` fixed at **8**, and that 8 is in
the machine's 320-wide internal space. Doubled onto our 640-wide native screen it
is 16 — the SAME x2 that turned the face's 10 rows into the declared 20 this quest
already ships. The width was never measured because there was nothing to measure
it against; F4 is that thing.

### It is NOT a regression from this work

Verified by forcing `TextFace::new` to hand zvm a `V6Metric::fixed` — the exact
pre-SQ-1009 engine — and re-measuring: **132 / 548 / 540, identical**. F4's columns
have always been at half the machine's, and the engine pen does not touch them.
(The same run put the score bar's date back at 417, which is the reported symptom,
so the harness was live.)

### Checked against all four, as the brief demands

1. **Score bar** — the game right-aligns from header `$30`, which is now a PEN
   measurement and has no declared width in it. Unaffected: still 389..602. PASS
2. **F4's columns** — x2 lands on the capture. PASS
3. **Startup spans 628/634/204** — pure font/pen measurements. Unaffected. PASS
4. **F5's wrap** — PASS, but only with a one-line change. The pixel wrap's limit is
   `cols x cell.w`, kept there so every fixed-pen machine stays byte-identical
   through the rewrite. At a declared 16 that is `36 x 16 = 576`, and the second
   line is 578 px, so it would break a word early. The limit has to become the
   window's own `x_size - right_margin` — which is the bound
   `v6_advance_prose_cursor` already uses one regime over. The coupling is written
   into the comment at that line so it cannot be missed.

So a single declared width DOES satisfy all four. Not changed here, per the brief.
