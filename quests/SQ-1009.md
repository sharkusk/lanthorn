## The question

`zvm::screen::V6Cell` became runtime state under SQ-0917 so a profile can declare
its own Version 6 cell. The Macintosh's is settled — `mac/xzip.lst` states
`colWidth := 7; lineHeight := 15 {16}` and four independent measurements off
`machine-screenshots/mac-zorkzero-*.png` agree. **The Amiga's is not**, and it is
the one machine with a real measured discrepancy left.

What is wanted is the DECLARED metric: the bytes Infocom's Amiga interpreter
writes into header `$26` (height) and `$27` (width), which the story reads and
lays its windows out from. That is a different quantity from what the machine
DRAWS, and SQ-0917 is the reason the distinction is worth spelling out — the Mac
declares a fixed 7 while drawing proportional Geneva, and 7 is just Geneva's
average advance.

## What is already measured, and what it does not answer

From `machine-screenshots/amiga-arthur.png` (320x200, pixel-exact OCS capture —
every colour channel a multiple of 0x11, so nothing resampled it):

- **Line pitch is exactly 10.** White text rows 121-129, 131-139, 141-149,
  161-169, 171-179, and the inverse status bar occupies rows 100-109 — one cell,
  independently.
- **Confirmed a second way** on `amiga-arthur-hint.png`: the InvisiClues
  highlight box is 166x20 at that capture's 2x scale = **83x10 native**.
- **The face is proportional**, average advance 4.5 px on prose. Per-word
  measurement ranges 3.75 to 5.25 and tracks word content, which no fixed pitch
  permits. `native_disk_font.rs` reads `char.data` as 10x10 nominal,
  `FPF_PROPORTIONAL`, advance 2..=8, and the capture now agrees with it.

None of that is the declared metric. A proportional face has no single advance,
so the interpreter must have picked a number, and the capture cannot show which.
The highlight box was the best candidate for reading a column grid off the screen
and it turned out to hug the proportional text rather than snap to cells (83 px
for the 14 uppercase characters of `THE CHURCHYARD`, 5.9 px/char — consistent
with the same 2..=8 face, uppercase being wider than the 4.5 prose average).

## The gap this would close

`AMIGA_STD_WINDOW` is (320, 200) and `V6_ART_SCALE` doubles it onto the 640x400
unit screen, where the 8x16 cell gives 80x25 characters. The machine has **20**
text rows. As a ratio, which does not depend on the doubling: lanthorn's line is
16/400 = 4.0% of screen height, the Amiga's is 10/200 = 5.0%. Real Amiga v6 text
is ~25% larger relative to its artwork than lanthorn draws it.

**The gap is entirely vertical.** Columns are already close — the machine fits
~71 characters of average width across 320 px against lanthorn's 80. So if the
declared height turns out to be 10 native (20 in the doubled model), changing
only `$26` makes the row count exact and the width may not need touching at all.
That is a hypothesis to test, NOT a licence to set it: declaring a metric we have
not read is exactly the guess SQ-0901 punishes.

## Routes, ranked

1. **The interpreter's own source.** `github.com/erkyrath/infocom-zcode-terps` is
   where every other machine in `zvm::interpreter` came from — `mac/xzip.lst`,
   `apple/yzip/rel.15/apple.equ` (`MFONT_W EQU 3`, `FONT_H EQU 9`), `st/stx1.s`.
   Whether it carries an Amiga XZIP is unchecked. If it does, one grep ends this.
2. **Read it out of the shipped binary.** Fully local — `blorb::adf` /
   `app::assets::files` already mount the Amiga floppies, so the 68k interpreter
   is in hand. It writes `$26`/`$27` at boot, so the values are literals in that
   file. Either disassemble around the header writes, or narrow via the font-open
   path: `char.data` states nominal 10x10, and an interpreter usually declares
   either `tf_XSize` (the nominal) or a computed average, which is a small set of
   immediates to look for.
3. **More measurement.** Needs a frame where the game positions something by
   COLUMN rather than by pixel, so the count falls out of the geometry. The
   highlight box was not it. Journey's command menu is width-driven (see SQ-0940)
   and might be.
4. **Another interpreter's Amiga profile.** Weakest and probably not worth
   taking: Frotz's is a modern choice, not a period fact, and period facts are
   the entire point of the table.

## Do not conflate with

- **SQ-0917** — the Macintosh cell, which is settled and does not wait on this.
- Arthur's PROPORTIONAL rendering, which stays a GUI question. Adopting real
  per-glyph advances means the ENGINE advances proportionally, and hybrid cannot
  follow (it maps `native_px / cell.w` to one terminal column, which collides
  once run origins stop being cell multiples). That would make zvm's model
  render-mode-dependent, which the crate's no-I/O-policy rule forbids. This quest
  is only about the single declared number.

## A trap waiting for whoever lands the Amiga cell — read before setting the value

SQ-0917 landed the Macintosh's 7x15, and doing so exposed a class of defect that
**a 10-tall Amiga cell walks straight back into**. This is not hypothetical: the
same bug was shipped once and nearly shipped a second time on the same day.

### The face-selection floor is a comparison against a cell dimension

`render/bitfont.rs`'s `blit_glyph_styled` chooses between the 8x16 face (SQ-0932)
and the older 8x8 master by a height floor. It was `ch >= 16`, which read as a
quality rule and was really an assumption that 16 is the only cell in play — so
the Macintosh's 15 fell under it and silently got the 8x8 chain, **which has no
descender below the baseline**. Clipped tails on `g j p q y`, on one machine, in
raster and in every hybrid region the ring rasterises. The user found it by eye;
5983 passing tests did not.

The floor is now `ch >= 12`, chosen because three quarters of a 16-row face
survives there — reasoning about **15**, with no thought given to what sits below.

**A 10-tall cell is below it.** If this quest declares the Amiga at 10 rows
native, every Amiga glyph goes back to the 8x8 fallback and the clipped-descender
defect returns wearing a different machine's name.

### Do not simply lower the floor again

Whether the 16-row face sampled down to 10 rows beats an 8-row master doubled up
to 10 is an **empirical** question. At `ch == 10` the resample keeps 10 of 16
source rows and drops 6, which is a real loss; the 8x8 master is drawn to be
legible at its own size. It could go either way, and today proved twice over that
reasoning about glyph rendering without dumping pixels produces confident wrong
answers — two separate descender tests were written from a mental model and both
PASSED with the bug in place.

Dump both faces at `ch = 10` and look, the way
`a_descender_still_descends_at_the_macintoshs_fifteen_row_cell` was eventually
settled: render `x` and `y`, compare the lowest inked row of each. At 15 the depth
is 3 with the proper face and 1 with the fallback. Measure the same pair at 10
before choosing.

### And the same shape may hide elsewhere

The lesson from SQ-0917's 35 missed sites is that a grep for `FONT_W`/`FONT_H`
cannot see a bare number, and a value-flip falsification cannot see a THRESHOLD
compared against the value. Before declaring an Amiga cell, sweep for both:

- arithmetic — `/ 16`, `/ 8`, `* 16`, `* 8`, `(8, 16)`
- comparisons — `>= 16`, `== 8`, `< 12`, and any other guard whose constant is a
  cell dimension in disguise

`V6Cell::row_of`/`col_of`/`run_px` (added after SQ-0917) handle the arithmetic for
any FIXED cell, so a 10x10 needs no work there. They do NOT handle a threshold,
and they do NOT handle proportional advance — Arthur's Amiga face is 2..=8 px per
glyph, which needs the `FontMetrics` shape described on SQ-0917, not `V6Cell`.

Measured, and the framing "the Amiga cell is 10x10" is wrong in both axes.

VERTICAL. `amiga-arthur.png` is a pixel-exact 320x200 native capture (18 colours, every channel a multiple of 0x11 — 4-bit OCS palette, no blended value). Text row pitch in it is exactly 10, and the inverse status bar is rows 100-109, one cell, independently. So the face is drawn 10 rows tall ON THE MACHINE.

But `ring_scout` boots Arthur's Amiga press (release 54, serial 890606) as `screen 320x200, art scale (2,2)` → **native 640x400**, and that native space is what every v6 coordinate is quantized by. One machine row is TWO native rows there, so the cell to declare is 20, not 10 — and we currently declare 16. Told 640x400 on an 8x16 cell the story gets 80x25 where the machine gave it 20 rows.

`amiga-arthur-hint.png` reads pitch 20 and is NOT evidence for this: it is a doubled rendition of the same 320x200 screen (info.txt flags it), so it agrees with the 10 rather than adding a second measurement. Do not cite it as independent.

HORIZONTAL. There is no 10 here at all. info.txt measures prose line 1 as 64 characters spanning x=14..301 — 288 px, **4.5 px/char** — and fixed pitch at the nominal 10 would need 640 px on a 320 px screen, so proportional is load-bearing rather than incidental. `char.data`'s 10 is a BOUNDING BOX, not an advance. In native terms the average advance is ~9.

So this is the Macintosh situation again and must be handled the same way: the DECLARED metric is a separate fact from the drawn face (`colWidth := 7` while painting proportional Geneva). We have no Amiga interpreter listing to read `colWidth`/`lineHeight` off, which is the missing evidence — `mac/xzip.lst` is what settled SQ-0917 and there is no `amiga/` equivalent in erkyrath/infocom-zcode-terps that has been checked. Find that before declaring anything; a cell guessed from the font's bounding box would be wrong horizontally by roughly 2x.

Related, and NOT the same font: Arthur's Amiga `char.data` is a proportional TYPEFACE ('i' narrower than 'm', descenders in row 9). Journey's Amiga `Char.data` is the 8x8 font-3 SET. The Macintosh's FONT 1033 is the font-3 set too — verified by dumping code 65, which is a solid block and not a letterform (SQ-1017).
