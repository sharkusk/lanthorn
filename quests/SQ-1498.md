FINDINGS (investigation lane, 2026-09-16) — SOLVED: neither record is a different shape. Both are ordinary room pictures whose specimen has exactly ONE bad 128-byte sector each. The reading is right; the disk image is damaged.

## What the two records are
- 0x7CBA (file; the scan's 4,746-byte gap after 0x74C1): **room 6, "CRYPT"**. Header `86 12 | 03 00 26 9E | 36 87 0E 00` — size 4742, edges 3,0,38,158 (the normal 280x158 shape, 35x79 = 2765 pairs under NoLiteral), colours the same as its neighbours. 0x7CBA + 4742 = 0x8F40, one byte before room 7's header at 0x8F41: the size is exactly right for the gap.
- 0xF72C (file; = spliced 0xF6AC, the 3,355-byte gap after 0xE872): **room 16, "Dungeon"**. Header `10 0D | 03 00 26 9E | 36 87 0E 00` — size 3344, same shape. 0xF72C + 3344 = 0x1043C; five zero filler bytes; room 17's header at 0x10441.
Three independent confirmations of WHICH pictures they are: (1) the side-A picture table found for SQ-1496 (0x9593 + 2i) names them — entry [6] = `30 FA` → sector 250 byte 42 = 0x7CBA, entry [16] = `21 EF` → sector 495 byte 28 = 0xF72C; (2) disk order: the readable records around them are rooms 5 and 7, and 15 and 17; (3) a best-effort decode (below) is unmistakably the Apple II release's record 6 (cave mouth, stalactites, the "NO SMOKING ORDER OF DRACULA" sign) and record 16 (dungeon: brick walls, iron rings, pit in the floor).

## The damage, byte-exact
Room 6: **sector 258** (file 0x8090..0x8110; record data bytes 972..1100) is a byte-for-byte duplicate of **sector 254** (file 0x7E90) — a stale/mis-seeked read baked into the .atr. The run-length stream is in triple phase 0 (count,hi,lo) from the start of the data to byte 972 and again from 1100 to the end, but the foreign sector's content sits in phase 2, so its pixel bytes are read as counts: that is where the eight "counts" of 195–255 come from (0xC3, 0xF0, 0xFC, 0xFE, 0xFF are pixel patterns) and why the units summed to 6,321 pairs. Units wholly before the sector: 324 → 521 pairs (column 6, pair 47); units wholly after: 1210 → 2177 pairs; so the lost sector held 67 pairs in ~42.7 units (1.57 pairs/unit — a rocky, detailed stretch, plausible).
Room 16: **sector 498** (file 0xF890..0xF910; data bytes 346..474) is 128 zero bytes — unwritten/unread. Before: 115 units → 490 pairs (column 6, pair 16); after: 953 units → 2110 pairs; the lost sector must have held 165 pairs (3.87 pairs/unit — the dungeon's flat brick runs, plausible). Under the ordinary reading the zeros paint 42 black pairs, which is why this one comes up SHORT (2,643 of 2,765) where room 6 came up long.
Pinned by the new specimen test `the_counts_two_unreadable_records_each_lost_exactly_one_sector` (crates/scott/tests/saga_atari_specimens.rs): headers, sizes-fill-the-gap arithmetic, sector 258 == sector 254 ≠ 257, sector 498 all zero with non-zero neighbours.

## Hypotheses ruled out
- Other scheme: read as Standard, 0x7CBA emits 2,302 of 2,880 pairs and runs out of data (4,665 of 4,732 bytes consumed) — no fit; 0xF72C likewise.
- Two records concatenated / scanner lost sync: the declared size equals the gap to the byte on both, the header edges/colours are the neighbours', and the triple phase is continuous everywhere except inside the one bad sector.
- A different geometry for 6,321 pairs (40x79, 80x79, 40x158, 35x158, counts-as-bytes…): none renders a coherent picture; the first ~7 columns of the ordinary 35x79 reading already show the crypt's sign and rocks.
- Different size units / flag bits in the size field: sizes are exact.

## Recommendation for the implementation lane
1. Leave `record_at`'s consistency check alone — it is correctly refusing a damaged record. Do not loosen it to admit these.
2. Since SQ-1496's side-A table names both offsets, the renderer knows they are rooms 6 and 16 without the scan. Offer a best-effort decode for a table-named record that fails the check: decode units from the header until the first bad sector (a sector whose 128 bytes are all zero, or equal to an earlier sector of the same record), skip the sector, then decode the remaining units anchored so the picture ENDS at `layout.pair_count()` (the tail is intact; this puts the hole at columns 6–7 / 6–8 of the canvas, rendered black). I did this in a scratch script and both pictures are recognisable; a two-column dark stripe is the only defect. Detecting "bad sector" generically is cheap: within the record, a 128-byte-aligned file span that is all-zero or duplicates a preceding aligned span of the same record.
3. Alternatively, simply accept the table's offset+size and render the ordinary decode of the intact prefix (521 / 490 pairs) — worse, but zero logic.
4. This is a defect of THIS dump (sha256 37fd7e4f… per stories/scott-dialects/atari/README.txt). A clean image of side B would decode both through the ordinary path with no code change, so any tolerance should be a fallback, not the rule. The specimen suite's `BITMAP_TITLES` still says (Count: 72 records, 2 unreadable) and should keep saying so for this image.
