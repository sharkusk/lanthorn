## The defect

`Delta`'s five modifier channels were plain `bool` and `apply_style` composed them
with `add_modifier` only. So a child could accumulate weight but never shed it, and
there was no way to say "like my parent, but not bold". Two visible consequences:

1. **`bold = false` in `style.toml` did nothing.** Not "did nothing useful" — it
   parsed, lowered, resolved, and was indistinguishable from not writing the line.
2. `tooltip.background`, having just been parented to `dialog.list_selected` to take
   the menu highlight's colours, dragged the highlight's BOLD along with them. Fine on
   one selected row; a bold paragraph on a multi-line tooltip card.

## The information was never missing

`RawDelta` has parsed these as `Option<bool>` since it existed — the TOML layer could
always tell an ABSENT key from an explicit `false`. The answer was thrown away one
layer down by `raw.bold.unwrap_or(false)` in `lower_decls`. So this is less a new
feature than the parser's own answer no longer being discarded on the way in.

## What changed

- `Delta`'s `bold`/`italic`/`underline`/`reversed`/`dim` are `Option<bool>`:
  `None` inherits, `Some(true)` adds, `Some(false)` removes.
- `apply_style` accumulates adds and removes separately and applies the removal
  **last**, so one Delta that both sets and clears is unambiguous rather than
  order-dependent.
- `lower_decls` carries `raw.*` straight through.
- `mods()` maps `false → None`, NOT `Some(false)`. Every existing call site passes
  `false` for modifiers it simply does not care about; reading those as erasures would
  have each row strip its parent's weight. A row that genuinely wants to shed one
  spells `Some(false)` in a `Delta` literal, which is rare enough to be worth seeing.
- The template now emits BOTH `true` and `false` (skipping only unset), because
  `false` is a real default now — omitting it would document a row as inheriting a
  weight it actually sheds.
- `tooltip.background` carries `bold: Some(false)`.
- `render::map`'s `theme_with_overrides` test helper injects `Some(..)` either way: it
  supplies a COMPLETE style, so a modifier the caller left off must be explicitly off.
  Under the old `bool` it lowered to a no-op, meaning a test injecting a non-bold
  style over a bold parent silently got bold back — a latent trap in a test helper.

## Where the highlight's bold came from, since it turned out not to be a decision

Traced to `db4ebd22` (SQ-0643), which consolidated six hand-written
`Style::new().fg(Black).bg(Cyan).add_modifier(BOLD)` literals — saves, history, file
picker, file browser, launch options, config screen, command band — into the single
`dialog.list_selected` row, carrying the modifier across verbatim to preserve
appearance rather than re-deciding it. Nothing reads it and nothing depends on it.

**What IS load-bearing next door:** the highlight must stay a fg/bg SWAP and not
`REVERSED`, because the command band's hover style is `REVERSED` and both can be on
screen at once. Asserted by
`hover_style_is_reversed_and_distinct_from_the_column_selected_style`.

## Tests

- `an_explicit_false_switches_a_modifier_off_where_absence_leaves_it_alone` — the
  three arms, including that an absent key still inherits, which is the whole reason
  the channel is tri-state rather than a bool.
- `the_tooltip_takes_the_highlights_colours_but_not_its_weight` — with a sanity
  assertion that the highlight is still bold, so the case cannot pass vacuously if
  someone later removes the bold upstream.

## Note for SQ-1170

This adds a channel whose `false` is meaningful, so the generalised template sweep
must treat `Some(false)` as a value to exercise rather than as "unset".
