## Measured, against the shipped binary

Two disk images that boot perfectly well **loose**, zipped with nothing else in the archive:

| archive | result |
|---|---|
| `TRINITY1.D64` loose | boots (`lanthorn: random seed …`) |
| `Hitchhikers_Guide_…_1984_Infocom.d64` loose | boots |
| `Arthur - The Quest for Excalibur.adf` loose | boots |
| **the same `TRINITY1.D64`, zipped** | **refused** |
| **the same `.adf`, zipped** | **refused** |

The refusal:

```
no story file inside the zip …/trin.zip (1 entry read; none is a Blorb, a
Z-machine story, a Glulx image or a Scott Adams database)
```

That message is accurate and it names the gap exactly: the zip classifier recognises
**four kinds of story** and **no media at all**. `extract_story` answers "are these
bytes a story", which a disk image is not — an image is a container that must be
MOUNTED, and the zip branch has no path that mounts.

## Why this matters more than it looks

SQ-1085 made a zip "a volume, not a wrapper around one file", and it did that for
stories. Its own lane noted the remaining half at the time — *"a zipped disk image is
a plausible future case, even though the zip path does not mount images today"* — and
raised `MAX_ZIP_ENTRY` to 32 MiB partly on that reasoning (`InfocomMasterpieces.img`
is 12 MB). So the size budget is already right; only the classification is missing.

It is also **the exact shape of what a player actually downloads.** The user's case
that surfaced this: a URL fetch whose zip held a `.g64`. Archive sites ship disk
images inside zips as a matter of course — that is the normal packaging for C64,
Amiga and Apple II media, far more common than a bare image.

**And it blocks SQ-1095 from being useful on the file that motivated it.** Even once
`.g64` is read, `plundered_hearts…g64` arriving inside a zip would still be refused
here. The two quests want to land in a way that leaves the whole chain working:
URL → zip → disk image → mount → story.

## Shape of the fix

The zip branch already inflates each entry and asks `extract_story`. It should also
ask whether the bytes are a **medium** — `blorb::medium` has the FORMATS table and
already recognises images by extension and, where they have one, by magic. An entry
that is a disk image should be mounted and its story taken, with the resource handle
that mount returns (which is the thing SQ-1085 was careful to stop discarding).

Two things to get right rather than assume:

- **Extension vs content.** A `.d64` is raw sectors with no magic at all — `TRINITY1.D64`
  and the Zork Solid Gold side both begin `CBM\0`, and Hitchhiker's begins
  `00 01 01 01 …` — so a d64 cannot be recognised by content and the zip ENTRY NAME
  is the only signal. That is a real departure from SQ-1085's "classify by content,
  never by name" rule, and it is defensible for exactly the formats that have no
  magic; say so at the site rather than quietly reintroducing name-matching.
- **The mount wants a file, not a buffer.** `load_mounted_story` reads a path. An
  entry inflated into memory has none, so either the mount grows a from-bytes path or
  the entry is spilled to a temp file. Decide deliberately; a 12 MB compilation disc
  inflated into RAM is fine, a 600 MB `.iso` is not, and the current per-entry cap
  (32 MiB) already refuses the latter — which may be the honest answer for now.

## Also found while measuring, and NOT this quest

`stories/Zork_I_Solid_Gold_Edition_1986_Infocom_Side_A_Ser.871125-Rel.25.d64` is
refused **loose** — `not a story file … |CBM.....|` — while `Side_B` exists beside it
and `TRINITY1.D64` (same `CBM\0` opening) boots fine. Probably a continuation side
carrying no story, which `d64.rs` documents as having "no header, no checksum and no
name that means anything". Worth confirming it is the expected refusal for a side
rather than a defect, and if so, saying "this looks like side B of a two-disk release
— try the other side" instead of the generic unknown-format message. Filed here as a
pointer only.

## Design decided (user, 2026-08-27) — this SUPERSEDES the "shape of the fix" section above

> "I think we can keep our zip file support basic, where it is used to package raw
> stories and resources together, not compress disk images. So, on a URL download if a
> zip file contains one or more supported disk images (detected via extension), if the
> user chooses to keep the story in the library, unzip the disk images into the library
> and run from there. if the user chooses NO, then we can tell them running disk images
> directly from zip files is not supported."

**The zip LOADER does not change.** A zip stays what SQ-1085 made it: a volume holding
raw stories and their resources, classified by content. It does not learn to mount
media, `extract_story` keeps its four kinds, and the classify-by-content rule is not
weakened. Every problem in the section above about mounting from a buffer, spilling to
a temp file, and 600 MB `.iso` entries simply stops existing.

**The work lands in the URL fetch path instead** — `story_url.rs` and the SQ-1086 keep
dialog — where it is a packaging question rather than a loader question. Detecting by
**extension** is right there and carries none of the SQ-1085 tension: the fetch is
deciding what to unpack, not what a file IS. `blorb::medium::image_extensions()`
already enumerates every spelling.

### Consequence to get right: the prompt has to come EARLIER for this case

Today the flow is fetch → load → boot → *then* offer to keep. For a zip of disk images
the load FAILS before any prompt is reached, so the order must invert: recognise the
archive, ask first, then unpack and run. That is a real change to `boot_story`'s
sequencing and is the main design work in this quest. Reuse the existing
`render::fetch_keep_dialog` chrome rather than growing a second prompt; the wording is
different but the shape is the same, and the collision handling (Keep both / Replace)
already exists and still applies since several files may land at once.

### "One or more" is the interesting case and it falls out for free

A multi-disk release — Journey's five `.dsk`, Zork Zero's four, Shogun's five — is the
normal shape for a zipped disk image, not the exception. Unpacking **all** of them into
the library and launching one is exactly right, because `cli_host::disk_set::mount_at`
already finds an image's siblings on disk (SQ-0864) and a release is not a platter.
Extract the whole set; do not try to pick "the" disk out of the archive.

### The decline path is a message, not a failure

Declining must say plainly that lanthorn does not run disk images from inside a zip and
that keeping it in the library is how to play it — not the generic
`no story file inside the zip …` refusal, which is true and useless here. Say what was
found ("this archive holds 5 disk images") so the offer makes sense.

### Still worth deciding in the lane

- Where a **declined** archive goes. SQ-1086 leaves a declined download in
  `temp_dir()/lanthorn-fetch/` and never deletes it (the running session was booted
  from it). Nothing was booted here, so the same reasoning may not hold.
- Whether a zip holding **both** a story and disk images is a thing to handle or to
  refuse as ambiguous. Probably: the story wins, since that is what the loader can
  already run, but say so rather than letting entry order decide.
- Whether the same offer belongs on a **local** zip of disk images (not just a URL).
  The user's framing is the download path; a local zip hitting the same refusal is the
  obvious next question and the answer should at least be consistent. Do not build it
  unless it is nearly free.

## Extraction is a WHITELIST of one thing (user, 2026-08-27)

> "when checking inside a zip during this process we should only unzip supported disk
> image types (based on extension). no other files should be extracted."

Only entries whose extension is a supported disk image — per
`blorb::medium::image_extensions()` — come out of the archive. Nothing else: no
`readme.txt`, no `cover.png`, no `.nfo`, no manual PDF, no executable, not even a
loose `.z5` sitting beside the images.

Why it is the right rule and not merely tidiness:

1. **It is the security boundary.** An arbitrary archive from an arbitrary URL is
   untrusted input, and "extract everything into the library" is how a dotfile, an
   executable, or a file shadowing a real story lands in a directory the picker scans
   on every launch. A whitelist of image extensions bounds the blast radius to one
   file type.
2. **It keeps the library listable.** Five `.dsk` files extracted show one release.
   Five `.dsk` files plus three text files and a screenshot show a mess the user has
   to tidy by hand.
3. **It keeps the feature honest.** The offer is "keep this game in your library", not
   "unpack this archive". A player who wants the manual can open the zip themselves.

### Consequences

- **Flatten, do not recreate directory structure.** `Journey/disks/journey_s1.dsk`
  becomes `journey_s1.dsk` in the library, through `safe_basename`. This is not only
  simpler than refusing traversal — it is REQUIRED, because a multi-disk set that
  landed in a subdirectory would not be found as siblings by
  `cli_host::disk_set::mount_at` (SQ-0864), and the sibling scan is the whole reason
  extracting the set works at all.
- **Flattening can collide** — `side_a/disk1.d64` and `side_b/disk1.d64` both become
  `disk1.d64`. Decide whether the existing Keep both / Replace handling covers it or
  whether such an archive is refused as ambiguous.
- **The count reported to the user is the count extracted**, not the archive's entry
  count. "this archive holds 5 disk images" must not be said of a zip with 5 images
  and 40 other files.
- **Test the whitelist as a guarantee, not a convention**: a zip holding disk images
  plus a `.txt`, a `.png`, a nested directory and a `.z5`, asserting that exactly the
  images land and nothing else does.
