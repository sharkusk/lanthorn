--- note 2026-09-16T18:17:20Z ---

FINDINGS (investigation lane, 2026-09-16) — SOLVED for all four line-art titles. The (usage, index) → record association is a TABLE ON SIDE B (the picture side itself), not on side A as SQ-1496's bitmap titles keep theirs, and not a hand table. Test-only pins in commit 2686705b (crates/scott/tests/saga_atari_specimens.rs, section "The line-art sides' own picture table"); worktree left in place, nothing pushed.

## 1. The table (measured identical in layout on all four titles: #1 Adventureland v416, #2 Pirate Adventure v408, #3 Mission Impossible v306, #6 Strange Odyssey v119)

Side B file offset **0x290** holds three copies of the AI adventure number (`01 01 01`, `02 02 02`, `03 03 03`, `06 06 06`) — the same marker the bitmap sides carry at 0x290 in front of their first record — and **0x293** holds the table: **190 two-byte entries** `[A, S]`, all-zero = no picture.
- entries [0..99] = ROOM-usage picture index i (0 darkness card, 1..N rooms, 80+ close-ups, 98 inventory backdrop, 99 title);
- entries [100..189] = OBJECT picture index (i − 100), one slot per item index.
Marker + 190 entries = 383 bytes = exactly sectors 6, 7, 8 (0x290..0x410); the boot loader code resumes at 0x410. Side A of these four carries NO copy (no `[adv,adv,adv]` triple anywhere near 0x9590 on any of them; the only triples on side A are inside text/data at unrelated offsets).

Entry `[A, S]` decodes as:
```
sector      = ((A & 3) << 8) | S              // 1-based 128-byte Atari sector
byte        = (A >> 2) * 3                    // byte within the sector, 0..126 — THREE-byte grid, not family C's (A>>3)*7
file_offset = 16 + (sector - 1) * 128 + byte  // the record's first token byte
```
**There is no inventory flag bit** (bit 2 is part of the byte multiplier here): an object picture serves both the room overlay and the inventory screen, exactly as the same four titles' Apple II releases ship one `B<aa><nnn>` file per object with no R/I suffix. Spliced coordinates for anything reading across sector 360: subtract 128 for file offsets ≥ 0xB410 (`saga_atari::spliced_of`); records DO span the VTOC (Adventureland B27 at 0xB37C, Pirate B58 at 0xB2ED, Odyssey B12 at 0xB343) and the splice is load-bearing — walked raw, those three records read the VTOC's bytes as coordinates and leave the canvas; spliced they walk clean (pinned: `a_line_art_record_spanning_the_volume_table_needs_the_splice`).

Falsifications done: (a) the bitmap sides' `(A>>3)*7` arithmetic on the same bytes lands >50% of entries mid-stream on every title (pinned); (b) a +3 byte error in the arithmetic fails both walk tests (tried, reverted); (c) SQ-1497's own "opening picture" at LINE_ART_OFFSET 0x1000 is NOT a picture: it is the middle of entry 0's record (the darkness card, 0x590..0x10AE), which is why it is byte-identical on all four titles — the card is.

## 2. What proves the table means what it says

**(a) Index sets = the Apple II catalogues, slot for slot, on all four titles** (the cross-platform anchor SQ-1496 used, here needing no picture decoded). Walked the four plain Apple releases' DOS 3.3 catalogues (`R<aa><nn>` / `B<aa><nnn>`, same walker as apple_pictures_specimens.rs) and compared:
- Adventureland: rooms 0-33, 80-91, 98, 99; objects 0,2,4,7-14,17,19-29,31,35-49,52,55,56,60,61 (44) — equal.
- Pirate Adventure: rooms 0-26, 80-87, 90, 91, 98, 99; objects 3,4,5,7-15,17-33,37,41,42,44-50,52,53,54,57,58,60-63 (48) — equal.
- Mission Impossible: rooms 0, 2-23 (NO room 1 on either machine), 80-85, 88, 89, 98, 99; 29 objects — equal.
- Strange Odyssey: rooms 0-15, 17-24 (no 16), 35 (rooms 25-34 are "." dummies in the database and have no picture on either machine), 81-88, 91-93, 98, 99; 31 objects — equal.
Three independent gap patterns and four object subsets agreeing between two releases cannot happen by a wrong slot base or a wrong arithmetic.

**(b) Every entry is a record boundary.** In disk order the 310 entries lie end to end: each record walks in fixed 3-byte tokens with ZERO drawing tokens off the 160x96 canvas, to a single `0x00` end byte that lies 0, 1 or 2 zero bytes before the next entry's own offset (never anything else between records; distribution ~15/41/35 on Adventureland). Pinned.

**(c) Content, by eye** (lines-only sketch renderer over the move/line tokens, scratchpad only): Adventureland [0] = "IT'S TOO DARK!" lettering with a black blob; [99] = "ai / Adventure International" globe logo; [98] = "INVENTORY" with a man holding an open sack; [10] = lakeshore with a signpost (room 10 "shore of a lake"; item 53 "Sign says No swimming"); [22] = throne on a dais between pillars and curtains ("throne room"); [24] = a horned devil amid flames ("...Oh Hell!"); B2 = a small glowing pot (Pot of RUBIES) drawn at its room position. Pirate [9] = inside a grass hut with a table ("grass shack"); [20] = a ship's deck with mast and rail ("aboard Pirate ship"); [22] = tombstones on a hill under clouds ("spooky old graveyard"); [26] = a crocodile scene (Never Never Land). Mission Impossible [2] = an office with a desk in a perspective room (the start room; SQ-1497's "desk"). Strange Odyssey [1] = a cockpit with a windscreen and a seat ("one man scoutship"); [35] = a devil with a pitchfork and bats ("lot of TROUBLE!" death card); [98] = a redrawn INVENTORY card. Room text read with `parse_saga_us(side_a, Atari8Bit)` for #1/#2/#6; **#3's side A is the known-damaged database (§12.13, ~50 corrupt bytes) and `parse_saga_us` refuses it ("the two item-location tables disagree")** — its cross-check rests on (a) and the sketches; the implementation lane must not expect to load MI's side A through the strict parser.

**(d) Shared cards are byte-identical across titles**: entry 0 (2,854 bytes incl. END) and entry 99 (2,428 bytes) on all four; entry 98 identical on #1 and #2 (875 bytes), redrawn on #3 (887) and #6 (861). Pinned.

Negative: the Atari drawings are NOT coordinate-scaled copies of the Apple II line sequences (an in-order scaled-endpoint match scores ~0 everywhere) — they were re-authored for the 160x96 canvas, so pixel/sequence correlation against the Apple builds is not available as an automated oracle; the index-set identity is the automated anchor.

## 4. THE GRAMMAR IS NOT THE APPLE'S — SQ-1497's premise is wrong, and this is what blocks drawing (filed as SQ-1525)

Measured over all 310 records: every record is a stream of **fixed three-byte tokens** `[cmd, p1, p2]`, class = cmd & 0xE0, and for the drawing classes (0x80 move, 0xA0 line, 0xC0 brush, 0xE0 fill) **p1 ≤ 159 and p2 ≤ 95 with zero exceptions** — the Atari **GRAPHICS 7 canvas (160x96, four colour registers)**, not the Apple's 280x192. There is no "bit 0 = bit 8 of x": the command byte's low 5 bits carry a small operand (observed 0,1,2,3,4,5,7,9,10 on 0x80/0xA0/0xC0/0xE0 — most likely the colour register / paint for that line or fill; 0xA1..0xA4 lines, 0xE1..0xE4 fills are common). The Apple decoder's 1- and 2-byte attribute tokens do not exist here: `20 10 00` opens almost every room record (33-49 per title; `20 x y` / `21 x y` with in-canvas coordinates also occur, at heads and at tails), `4n 00 00` (n=1..5, operands always 0 0), `6n p q` with n ∈ 0..15 and p,q ∈ 0..15 (top values `69 0A 00`, `6A 09 00`, `6F 0A 00`, `69 07 00`, `6F 0F 09`, `6F 00 00`) — the pair (p,q) looks like the Apple PAINTS pair (even-row pattern, odd-row pattern) but that is a guess. END is a single `0x00` byte at a token boundary (`00`-class byte; two records carry `00 00 69`-shaped junk after END that is just the next record). Rooms open `6x p q | 20 10 00 | 80 x y …`; objects open `80 x y` (the anchor move, as on the Apple) or `6F .. .. | 80 x y`. The seven-byte records (Pirate R24, Odyssey R18-20) are `6x p q | 20 p q | 00`: attribute tokens only = a plain colour field, which is what a lagoon/snowstorm room is.
Consequences: (1) `decode_line_art_opening`/`LINE_ART_OFFSET` decode a fragment under a foreign grammar — the 725 "green pixels" are the tail of the darkness card's lettering read as HCOLOR-1 lines from a default pen; the pinned test still passes byte-for-byte and I annotated its doc rather than removing it (the implementation lane should retire it with the new reader). (2) The saga_atari module docs' claim that this format is "the byte-identical grammar" of item 26 needs correcting. (3) Nothing can reach the picture band until SQ-1525 settles the token semantics; the right method is the one apple_pictures.rs used for M3 — read the game's own renderer on side A as a specimen (no interpreter source), find the 3-byte dispatch on the top three bits, and read off what the 0x20/0x40/0x60 classes and the low-5-bit operands set. Sketching just the move/line tokens already gives recognisable art (section 2c), so a first cut that draws lines only and ignores fills would be usable.

## 5. Implementation sketch for the follow-up lane (index reader only; drawing is SQ-1525)
`scott::saga_atari`: add `LINE_ART_TABLE_MARKER = 0x290`, `LINE_ART_TABLE_OFFSET = 0x293`, `LINE_ART_TABLE_ENTRIES = 190`, `line_art_entry_file_offset(a, s) = 16 + (((a&3)<<8|s) - 1)*128 + (a>>2)*3`, and a `read_line_art_table(side_b) -> Option<LineArtPictureTable>` that checks the marker against `SagaUs::adventure`, walks 190 slots, and validates each entry with a walker like the test's `walk_line_art_record` (3-byte tokens on the spliced side, no drawing token off 160x96, END found before the next entry / within a bound) — refuse rather than draw, as `read_picture_table` does. Usage: slot < 100 → `PictureUsage::Room`; slot ≥ 100 → object (i−100), ONE picture for both in-room and inventory (no flag; `PictureUsage::ObjectInRoom` and `ObjectInInventory` resolve to the same record — decide how `PictSource` expresses that). Index 98 is a real table entry here (unlike family C's fixed 0x984F pointer) and 0/99 are ordinary entries. The record's byte extent = from its offset to the END byte (inclusive) found by the walk; do not add lengths, the pad is 0-2 bytes and the grid restarts per sector. Host side unchanged from SQ-1496: side A ↔ side B pairing by filename twin, `AtariPictureFormat::LineArt` selects this reader. MI's side A will not load through `parse_saga_us` (§12.13) — do not make the table reader depend on the database parsing. Scratch tooling (Python: table.py/grammar.py/tokens.py/xref.py/sketch.py/facts.py, and a DOS 3.3 walker apple.py) lived in the session scratchpad and is not committed; a Rust scratch example was deleted before the commit.
