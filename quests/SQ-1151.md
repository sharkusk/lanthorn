## The evidence, measured off `stories/arthur-r74-s890714.z6`

Arthur's verb column lists **`be`** and **`be?`**. The `?` is not lanthorn's rendering — `zscii_to_char` maps unprintable ZSCII to `'?'`, which was the obvious suspect and is the wrong one. Decoding the dictionary directly:

```
dict @0x4a53   entry_len 10   entries 1059

'be'   @0x4cf1  z-bytes 1d4514a594a5   data 44c70021
'be?'  @0x4cfb  z-bytes 1d4554a594a5   data 44f70001
```

Word 1 is `0x1d45` in both — Z-chars 7, 10, 5 → `b`, `e`, shift-A2. They differ only in word 2: `0x14a5` versus `0x54a5`, i.e. Z-char 5 (more padding) versus Z-char **21**, which in alphabet A2 is a literal `?`. Both carry flags `$44` and they hold different verb numbers, `$c7` and `$f7` — two genuinely distinct verbs in the game's own data.

Only **2 of 1059** entries contain a `?` at all: the bare `?` and `be?`.

## Why it cannot be typed

The dictionary header's separator list, read from the same file:

```
Arthur's input separators (6):  .  ,  "  '  !  ?
```

`?` is a separator, so the tokeniser splits `be?` into `be` and `?` before the parser looks anything up. **No sequence of keystrokes reaches that entry.** Infocom used this deliberately: putting a separator character inside a dictionary word makes it unreachable from the keyboard, so it can serve as a slot the game's own code references without a player stumbling into it.

Clicking it in the band composes a line the parser will split.

## The fix, and why the existing rule misses it

`VerbTable::without_sigil_verbs` already drops this class of thing — `#record`, `#command`, `$verify` — and its doc argues the right principle: *"A rule, not a list… this is structure, needs no maintained vocabulary, and there is nothing to disagree with."*

It cannot catch this one, for two reasons worth stating so the fix is not bolted onto it carelessly:

1. It tests the **first** character against two fixed sigils. Here the offending character is **last**.
2. Its sigils are a constant. Here the character comes from **this story's own separator table**, which varies per game and is already parsed by `zvm` out of the dictionary header.

So the new rule is the same shape but sourced from the story: **drop any dictionary word containing one of that story's own input separators.** No maintained list, nothing to disagree with, and it generalises to whatever separators another game declares rather than to the six Arthur happens to use.

## Worth checking while implementing

* **How wide is this?** Sweep the corpus for entries containing a separator and report the count per story. Two in Arthur may be typical or may be an outlier, and the answer decides whether this is a tidy-up or a real source of noise.
* **Which surfaces are affected.** The verb column is where it was seen, but the same dictionary feeds the vocabulary offer, the word reveal and completion. An untypeable word is wrong in all of them for the same reason — though note the reveal ANNOTATES rather than proposes, so the argument there is weaker and wants thinking about rather than assuming.
* **The bare `?` entry is a different case.** It is a single separator character and probably a real parser token (`?` as a help command in some games). Do not sweep it up by accident; a word that IS a separator is not the same as a word that CONTAINS one.
* Verification is the parser, as always: whatever is dropped should be a word `zvm-cli` genuinely cannot be made to match.
