--- note 2026-10-14T19:29:51Z ---

Today: the fetch worker's link-without-request check (link_from_store, Outcome::Linked, SQ-1786) only runs for stories in the same FetchOrder. The TUI's single-story fetch (f) and any embedding host's one-story refresh send an order with one story, so after it the entry is in the shared ifdb_store, but other copies in the catalogue that the entry lists (other releases or duplicate files of the same game) stay unlinked until a whole-library 'r' runs.

Wanted: after a one-story fetch that writes or refreshes an entry, link every other library copy whose IFID the entry's record lists and that has no link yet (or, when forced, is linked elsewhere? keep: only unlinked copies), exactly as a library-wide order would (write_fetched from the record, no network request, no delay). Copies already linked to the entry keep sharing it as now.

API suggestion for hosts: either (a) a FetchOrder flag / FetchProgress items reporting the extra Linked copies, so a host can refresh their rows, or (b) a pure function, e.g. fetch_worker::link_listed_copies(roots, catalogue entries or story targets, tuid) -> Vec<key or target linked>, that a host calls after its one-story fetch with the library's targets. The host needs to know which copies were linked (to refresh their rows and to include them in an undo of the refresh).

Undo: a host's undo of a one-story refresh should be able to unlink the copies this linked; returning their keys/targets is enough.

Tests: one-story fetch of release A whose entry lists release B's IFID; B unlinked before, linked after with no extra request; a copy already linked elsewhere untouched; NotFound/Failed link nothing.
