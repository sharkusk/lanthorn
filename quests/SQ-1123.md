## The principle behind it, worth stating so it survives

**A control sits where the thing it governs is, or where it would appear.** The
command band opens below the story pane, so its toggle belongs on the bottom
border. The map lives to the right, so its toggle belongs on the right edge. That
is the same reasoning the arrow glyphs already encode — `▲`/`▼` for a panel below,
`◀`/`▶` for one to the side — and the original single-cluster placement fought it.

Guidance and the two v6 controls are not panels and have no direction of their
own, so they take the bottom row beside the band toggle as a natural home for
"things you switch".

## The hazard the first pass already had to dodge

SQ-1123 kept the cluster clear of the splitter's drag zone (`story.right()-1`, 2
columns wide). **The map toggle is now being deliberately placed on that very
edge**, so the collision has to be solved rather than avoided: a vertically
centred control on the right border sits exactly where a vertical splitter is
dragged. Decide how a click is disambiguated — the control taking priority over
the drag start within its one cell is the obvious answer, but it must be
deliberate and tested, and a drag begun *on* the control must not be swallowed.

The bottom border may have its own occupants; check before reserving columns, and
keep the centred group honest when the pane is too narrow to hold it (SQ-1123
drops the cluster below ~15 columns rather than showing half of one — same rule
applies per group now that there are two).

## What must not regress

The suite from the first pass (`crates/app/tests/suites/border_controls.rs`, 12
cases) pins the state glyphs, the v6 gating, the tooltip placement rules and that
every control resolves to a real `slash::COMMANDS` entry. Those assertions stay
true; only the ones about *position* should change.

## All button state persists per-game

The five controls split three ways today, and this resolves it:

| command | today |
|---|---|
| `set-game-colours`, `set-v6-pixel-lock`, `set-game-borders` | persisted per-game |
| `set-v6-render`, `set-guidance` | **session-only** ("the settings screen persists") |

Because the buttons dispatch through `slash::COMMANDS` rather than
reimplementing toggles — which was right and stays right — persisting the buttons
means **persisting the commands**. That is a documented semantic change to
`set-v6-render` and `set-guidance`, whose `usage` strings say "session-only"
today and must be updated.

Explicitly rejected: making the button persist while the command stays
session-only. Two spellings of one toggle disagreeing about permanence is the
divergence this repo keeps paying for.

The mechanism exists — a bare-lines per-game sidecar, `v6_pixel_lock` is the
worked example (SQ-0945, `config.rs:4203`). **Absent key = inherit global**, so a
click writes one key rather than snapshotting everything, and the settings screen
still sets the global default new games inherit. Clicking a button means "for
this game"; that split is the point and belongs in the docs.

Open questions handed to the lane: where the sidecar actually lives
(`config.rs:906` says the save directory, CLAUDE.md says `<game_dir>/`, and they
disagree); what a click does before a save directory exists; and how a
three-state control (`on|off|auto`) can return to `auto`, or the player can never
get back to the global default.

## Why the command semantics may change (user, 2026-08-28)

> we can change the meaning of the commands to match this behavior now, since
> raster is a first class citizen now

Worth recording as the justification rather than leaving it as a bare approval.

**`set-v6-render` was session-only, and that was correct when written.** Raster
began as a *fallback* — the mode you flipped to when hybrid could not cope — and
a temporary escape hatch should not persist.

**What changed is the feature's status, not the code.** Raster is now a
destination in its own right, and SQ-1032 added `extended` beside it. A player
may genuinely prefer raster for one game and hybrid for another, which is a
per-game preference exactly like `v6_pixel_lock` and `game_colours` already are.
So the mode sticks to the game it was chosen for.

`set-guidance` reaches the same place by a different route: guidance is a
standing preference about how you want to play a particular story, not a
temporary toggle.

**Do not write this up as "fixed an inconsistency".** It is a deliberate reversal
that became correct when the feature's status changed, and saying so is more
useful to a future reader than implying the original was a mistake.

The settings screen keeps meaning what it says — the **global default new games
inherit**. The split to state in the docs: the button and the command are "for
this game", the settings screen is "for everything".
