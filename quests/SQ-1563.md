Current code (rev c68d48cf / 8203aae8):
- `LaunchOverrides.honor_game_colours` (crates/app/src/launch_options.rs) is applied by crates/app/src/host/boot.rs when the engine is built.
- A few lines later (~l.1426-1430) boot calls `crate::reload::reload_style(&mut state)` "now that game_dir is set", and `reload_style` (crates/app/src/reload.rs:37) recomputes `config.honor_game_colours` from the per-game sidecar, garglk.ini and the global base only. The one-launch choice is overwritten, so "Game colours: off for this launch" (or on) silently has no effect. The TUI's launch-options dialog goes through the same path, so it has the same bug.
- The lib already has a per-launch hold for exactly this key: `state.game_colours_cli` (the `--game-colours` CLI hold that reload_style respects). A host can work around it by setting that hold and re-running reload_style after boot; that's what an embedding host does today.

Fix: have boot record a launch override of honor_game_colours in that same hold (`game_colours_cli`, or a launch-scoped equivalent) before the reload, so reload_style keeps it for the rest of the session. Editing the key in settings should end the hold, as `host::settings::apply` already does for the CLI hold.

Acceptance:
- Test: boot a story whose per-game/global resolve honour=on with `LaunchOverrides { honor_game_colours: Some(false), .. }` → after boot and after a later reload_style, `config.honor_game_colours == false`.
- Test: a subsequent settings change to honor_game_colours ends the hold.
- TUI launch dialog: choosing Game colours for one launch takes effect.
