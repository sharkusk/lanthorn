Measured in the SQ-1414 lane (2026-09-09) on the 20-snapshot corpus at stories/scott-dialects/spectrum/ (IF Archive games/spectrum/mystsoft.zip, 546,758 bytes).

m1goldba.z80 is .z80 **v2**: PC field (bytes 6-7) is 0, which is the v2/v3 marker; the extra-header length at offset 30 is 0x0017 = 23, which pins it to v2 rather than v3 (v3 is 54 or 55). Memory then follows as page blocks, each `[u16 compressed length][u8 page number][data]`, with 0xFFFF meaning an uncompressed 16,384-byte page. The first block in m1goldba.z80 is length 0x3EB4 = 16,052 for page 4, i.e. genuinely compressed.

Why this blocks everything downstream: Golden Baton's ScottFree .dat header is [0,48,166,78,31,6,1,0,4,200,99,0], and scanning the whole snapshot for a little-endian 12x u16 run matching NumItems/NumActions/NumWords/NumRooms/MaxCarry finds NOTHING. The dictionary signature IS findable in the raw bytes (offset 1576) only because .z80 RLE replaces runs of 5+ identical bytes and passes everything else through literally — so signature detection works on the compressed file while every offset relationship in it is fiction. Any table-layout work must run on the decompressed 48K image.

Licence position: the .z80 container format is documented publicly and independently of any interpreter (Gerton Lunter's format description, widely mirrored, e.g. worldofspectrum). Write from that, cite it and its licence, and do not read garglk's ai_uk/decompressz80.c (GPL). NOTE that decompressz80.c was NOT read by the SQ-1414 lane, so this quest is still open to any implementer.

Same question, unanswered, for the C64 side: if-archive/scott-adams/games/c64/mystadv.zip (183K) holds D64 disk images. `blorb` already parses D64 in this workspace — but `scott` is zero-dep and must not depend on it, so the seam is that `scott` takes a raw memory image and the app/scott-cli does the container extraction. That seam is worth defining even before any loader exists.
