## 0. Method and provenance
Read side A's boot-loaded program as a specimen, the way apple_pictures.rs read `M3`. Side A's boot sector (`$9FF0`, init `$A0F2`) reads raw sectors 6-201 into `$2E00-$8FFF` — NOT the DOS-catalogued `AUTORUN.SYS`, which is an older text-only build whose graphics vectors are `RTS` stubs (`$8940/$8943/$8946`), with #3 and #6 shipping a byte-identical copy; disassembling that first cost an hour. The raw image's picture code (`$7C00-$8940`) is byte-identical on all four titles except the text-window tables. Anchors used: Atari OS `SIOV $E453`, the DCB at `$0300`, `SDLSTL $0230`, `NMIEN $D40E`, `WSYNC $D40A`, `COLPF1/2 $D017/$D018`, the `COLOR0-4` shadows `$02C4-$02C8`, `VVBLKI $0222` — all from the *Atari 400/800 Hardware Manual* / OS listing, none from any interpreter. No interpreter source was consulted (CLAUDE.md GPL rule; docs/internals/clean-room.md). Scratch tooling (extract.py, dis.py — my own 6502 disassembler, records.py, decoder.py) lived in the session scratchpad and is not committed.

## 1. The loader — confirms SQ-1524 from the program side
`$894F` on first use reads side-B sector 6 and compares three bytes against `$3057` (the adventure number) — the `01 01 01` marker — then copies the 190-entry table to `$8D30`. `$8B41` decodes an entry `[A, S]` EXACTLY as SQ-1524 measured: sector = `((A & 3) << 8) | S`, byte = `(A >> 2) * 3` (LSR LSR, then ASL + ADC). `$8A98` is a byte-stream reader over 128-byte sectors that SKIPS SECTOR 360 (`CMP #$68 / CMP #$01` → INC again): the VTOC splice is the machine's own rule. `$8C44` copies the record to `$B000` three bytes at a time until a byte with `AND #$E0 == 0` is stored: END is one byte, everything else is exactly three. Room draw (`$8B69`, vector `$2E24`): dark room → index 0; then `$8BD5` draws every item whose location is the room via `$8C08` (slot `100 + item`), iterating item index HIGH TO LOW (highest first, item 0 last/on top), with NO clear between room and objects. `$8C7C` snapshots the drawn room so it can be restored without disk when only the objects change.

## 2. The screen (why a "colour" is a pair)
The renderer keeps TWO 160x96 two-bit bitmaps, at `$9000` and `$A000` (40 bytes/row, leftmost pixel in the high bits), under a display list of 96 ANTIC mode-E lines (`70 70 70 | 4E 00 A0 | 0E x95 | 8E | 70 | 42 .. text`, at `$7C16`). The immediate-VBI hook (`$7C91`, installed on `$0222`) flips the LMS high byte at `$7C1B` between `$90` and `$A0` EVERY FRAME and loads a different five-byte table into `COLOR0-COLOR4`: `$7C11 = 42 B4 E4 00 00` when showing `$9000`, `$7C0C = 32 84 D4 00 00` when showing `$A000`. So a canvas pixel is the pair (a = value in `$A000`, b = value in `$9000`) and its colour is the eye's average of two GTIA colours flickered at 60 Hz. Mode-E value→register: 0→COLOR4 (bg), 1→COLOR0, 2→COLOR1, 3→COLOR2, hence PALETTE_A = [00,32,84,D4], PALETTE_B = [00,42,B4,E4] by pixel value.

The 16 colour indices are the pairs at `$8561` (a, b): 0 (3,3) · 1 (3,2) · 2 (3,1) · 3 (3,0) · 4 (2,2) · 5 (2,1) · 6 (2,0) · 7 (1,1) · 8 (1,0) · 9 (0,0)=black · 10 (2,3) · 11 (1,3) · 12 (0,3) · 13 (1,2) · 14 (0,2) · 15 (0,1). All 16 (a,b) combinations are covered once, so pixel value = a*4+b is lossless. Default line colour at every record start = 10.

## 3. The grammar (`$8582` token loop: class = byte >> 5, op = byte & 0x1F)
| token | meaning |
|---|---|
| `00` | END (any byte with bits 7-5 clear; stands alone) |
| `20 x y` (op 0) | CLEAR both bitmaps to fill colour p's pair (x,y consumed but unused). Skipped during a recolour pass |
| `21 x y` (op 1) | RECOLOUR MARKER: save p's and q's pair bytes, set flag, JUMP BACK TO THE RECORD'S FIRST TOKEN; on the second pass only lines whose colour == p are drawn, in colour q; clears, pauses and fills are skipped; moves/colour tokens execute; reaching the same `21` again clears the flag and continues. Line colour is NOT reset by the restart (`$859C` re-enters after `$8597`). x,y unused. Ops 2-31: no-op |
| `4n 00 00` | PAUSE — a nested countdown (p1, p2, n) with no pixel effect; animation timing. Skipped during recolour |
| `6c p q` | line colour = c, fill colours = (p, q), all indices 0-15 into the pair table |
| `80 x y` | MOVE the pen (op ignored) |
| `A? x y` | LINE pen→(x,y) in line colour, pen follows. **The op bits are ignored** by the code (corpus has A1..AA from the authoring tool) |
| `Cs x y` | BOUNDED FILL from (x,y), style s: every pixel whose pair code != the LINE colour's pair code |
| `Es x y` | FLOOD FILL from (x,y), style s: every pixel whose pair code == the seed pixel's |
Corpus check (all 310 records): class-1 op ∈ {0,1} only; class-2 op 1-5 with p=q=0 only; class-3 operands all ≤ 15; class-6/7 op ∈ 0..4 only; no record has two `21`s.

Fill STYLES s (patterns `$8774-$8923`, a byte = 4 pixels): 0 solid p; 1 p/q checkerboard (rows alternate `p q p q` / `q p q p`); 2 rows alternate solid p / solid q; 3 vertical `q p q p` stripes; 4 rows alternate solid p / `q p q p`. Two row patterns (even/odd) are swapped every row; at the fill's TOP row they are canonicalised by parity: odd row → swap if `((cur.b − alt.b) & 0x80)` (or the a-bytes when equal); even row → same test with operands reversed (wrapping byte subtraction, a `CMP/BPL`).

THE FILL IS NOT A FLOOD FILL (`$7EBE-$80A1`): (1) walk UP the seed column while pixels match; (2) for the top row, walk LEFT to the span edge, fill RIGHT to the span end (whole-byte fast path when 4-aligned and both bitmap bytes equal the seed bytes, flood mode only); (3) drop to the next row at the span's LEFT edge: if it matches, walk left and fill; else scan right, no further than the previous span's end, for the first match and fill from there WITHOUT walking left; (4) stop when no match is found, or at row 95. A region reachable only above the seed column's top is never filled; the artwork was authored to that reach, so a true flood fill would spill. (One `CMP $A0` at `$8081` is zero-page where `#$A0` is meant; harmless in the corpus.)

THE LINE (`$81C1-$849D`): Bresenham, `err0 = 2·minor − major`, plot then `if err >= 0 { minor±1; err += 2·minor − 2·major } else { err += 2·minor }`, major stepping `major` times then a final plot (both endpoints inclusive). The major axis always walks UPWARD from the endpoint with the smaller major coordinate; x-major when dy < dx (y increments, x steps ±1), y-major when dy ≥ dx (x increments, y steps ±1); ties go to the pen's endpoint.

State that PERSISTS across records: both bitmaps, fill colours (p,q), the pen. Reset per record: line colour (=10), recolour flag. That is how objects draw over rooms; objects open `80 x y` or `6F .. | 80 x y`.

## 5. Two host-side facts the implementation lane must carry
(a) THE DARKNESS CARD (index 0, shared by all four) IS AN ANIMATION THAT ENDS BLACK: lettering + a pair of eyes that appear/vanish over three pauses, then a final `20` clear to black. Its resting frame on the machine is black; the lettering is on the paused frames. `LineArtCanvas::draw_frames` returns a snapshot at each pause plus the end (non-black counts 2158 / 1955 / 1148 / 0); a host should show the last paused frame for a record whose final frame is a plain clear. Other animated records (pauses, no trailing clear): Pirate R80 (28 pauses), R91; MI R80, R88, R89 — final frame is the resting picture.
(b) SIX ROOM RECORDS NEVER CLEAR: Pirate 7/12/13/19 (one maze drawing), Pirate 86 (opens with a flood fill of the seed colour), Odyssey 3. On the machine they draw over the previous room + objects; on a fresh black canvas the un-drawn parts are black. Pinned in `every_line_art_record_plays_under_the_renderers_grammar`.

## 6. What is approximate / not done
- Colour: `pair_rgb` averages `atari_colour(PALETTE_A[a])` and `atari_colour(PALETTE_B[b])`; the machine flickered them. Hue phase is whatever `atari_colour` already uses.
- Pause durations are a countdown loop, not frames; not carried.
- The decoder is not wired to the picture band, `read_line_art_table` (SQ-1524 §5) is still test-only, and `decode_line_art_opening` / `LINE_ART_OFFSET` in saga_atari.rs are still there for the implementation lane to retire (their doc is already annotated by SQ-1524).
- Object draw order (descending item index) is read off `$8BD5` but not exercised by a test.
