--- note 2026-09-24T04:26:11Z ---

Citations are crates/app/src/ unless stated, as of ca723e44. Goal of this series: an embedding host that is not a terminal (a GUI, a network server, a mobile FFI binding) can boot and play a story through the `app` lib with the same rules the TUI uses, instead of re-implementing them. The TUI must run on the same code, so there is one copy of the rules.

Current state
- `render::v6_layout::classify_windows(&[PositionedWindow], V6Cell)` (v6_layout.rs:457), then `render::screen::build_v6_raster_canvas(layout, native, &AppState) -> RgbaImage` (screen.rs:2745). Needs from AppState: colours, v6 text runs, the text face. Rects are in cells. Per-window canvases are already available as `engine::GraphicsWindow.canvas: Arc<RgbaImage>` (engine.rs:363). Glyph data for a host that draws text itself: `native_font::resolve` (native_font.rs:324), `TextFace::advance*` (:822-867), `BitmapFont::glyph` (blorb/src/bitmap_font.rs:32-121).

Change
- Gather exactly what composition reads into a plain struct (colours, text runs with positions, face, cell, native size) that the TUI builds from AppState and another host can build from its own state. Also expose, as data, the per-frame list of text runs with pixel positions and the face they use, so a host can draw V6 text as glyphs over the raster (SQ-0750's rule: never rasterise what the game printed as a character).

Acceptance
- The TUI's raster and hybrid output are unchanged (existing v6 suites and gallery shots).
- A headless test composes a Zork Zero or Journey frame (skip when absent) from the struct alone and matches the TUI's canvas for the same state.
