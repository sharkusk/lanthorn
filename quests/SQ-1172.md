## The proposal (user, 2026-08-31)

> "vastly reduce the complexity of our theming support. lean more on the terminal
> colors for the actual theming. we would keep the game and machine colors fully
> functional as today. but any story text and background colors not set by the game or
> machine would come from the terminal colors themselves. other UI elements would use
> best practices from other TUIs in terms of which terminal colors are used for each
> specific element."

**PARKED, not scheduled** — the user wants to think about it, and asked to wrap up for
the next release first. Do not dispatch this without them saying so.

## Measured, so the estimate does not have to be re-derived

| file | code | tests | fate |
|---|---|---|---|
| `theme/registry.rs` | 614 | 442 | ~90% gone (181 rows → a handful of roles) |
| `theme/template.rs` | 353 | 468 | **100% gone** — no style.toml to seed |
| `theme/toml_schema.rs` | 231 | 196 | ~85% gone |
| `theme/resolve.rs` | 711 | 735 | ~70% gone (parent chains, 3-layer merge, provenance, warnings) |
| `style.rs` | 1023 | 734 | ~40% gone (scheme loading stays, selector plumbing goes) |
| `period.rs` | 347 | 297 | **stays entirely** |

**~3,500–4,000 lines of ~6,250 removed**, plus SQ-1170's ~400-line sweep becomes moot.
181 registry rows, of which **153** are reached by a call site. **361** `theme.get()`
call sites become role lookups — cheaper, but a mechanical sweep across the render tree.

## The strongest argument for it

**SQ-1169, SQ-1170 and SQ-1171 all evaporate.** Every theming defect found on
2026-08-31 was in the SELECTOR layer — a re-root masked by pinned colours, 167
documented-but-unproven keys, two dead rows, modifiers that could not be switched off
— and none was in colour rendering. That is complexity tax on the derivation model,
paid three times in one day.

## The correction that reframes it

**The roles ALREADY are the terminal's colours.** `Roles::from_scheme` gives
`text` → terminal foreground, `chrome` → fg on bg, `line`/`accent` → palette slot 6,
`muted` → slot 8, `alert` → slot 3. So this is not "switch to terminal colours"; it is
"delete the per-element indirection sitting on top of them". The win is in
CONFIGURATION SURFACE, not colour correctness.

## What does NOT shrink — and it is the hard half

`colors.rs` (1447), `period.rs` (645), `garglk_ini.rs` (701) ≈ 2,800 lines, plus the v6
colour regimes, `machine_rule`, `honor_game_colours` and the palette-lock discipline.
That is where this project's genuinely difficult colour bugs have always been, and the
proposal keeps all of it, correctly.

## Three real losses to decide on

- **Per-game style overrides** and the **garglk.ini** layer (701 lines of interop) die
  with the layering.
- **Transcript styling rules** (regex → colour) and **statusbar segments** have no home
  outside the selector schema.
- **It reverses a standing rule the user set**: "every new UI element must be themeable
  via style.toml selectors; never hard-code styles." Theirs to reverse — but it should
  be a decision, not a side effect.

## Recommendation on record

Worth doing, scoped TIGHTER than proposed: collapse the 181-row registry, but **keep
style.toml as a thin file** — the seven roles plus a scheme name, ~60 lines of schema
instead of ~800. That preserves the one thing users actually want (a coherent recolour)
without the per-element matrix, and keeps the "I want my borders green" case that
motivated the whole system originally. Deleting the file outright buys little more.

**Settle the shape in a design doc before any code.** The last 20% of decisions here
determine whether it lands.

## Interaction with open quests

**SQ-1169 is at `partial` and its remaining work would be DISCARDED by this.** Five rows
whose `parent` re-root is masked rather than inert, plus the unsettled question of what
a re-root should mean — all of it is selector-layer. If SQ-1172 goes ahead, close
SQ-1169 as discarded rather than fixing it first. If SQ-1172 is dropped, SQ-1169 still
needs its decision.
