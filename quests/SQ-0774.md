--- note 2026-08-11T15:55:47Z ---

THE BUG: `qwertty-term-vt` 0.4.0, `src/kitty/exec.rs:208` — `debug_assert!(!load.more)` fires on a CHUNKED transmit-and-display (`a=T` with `m=1` continuation chunks). `load_and_add_image` hands back the deferred `display` on EVERY intermediate chunk instead of only the final one. Upstream Ghostty defers it.

REPRODUCER: any real babelmap capture. `kitty_transmit_virtual` (`crates/app/src/render/graphics.rs:1331`) chunks every upload at 3072 bytes, so a debug build trips on chunk 2 of the first image.

BEHAVIOUR WITH THE ASSERTION COMPILED OUT (i.e. release): correct — the premature display finds no stored image and is refused, the final chunk places the image properly. So it is a mis-placed assertion, not a logic error in the release path.

OUR WORKAROUND, which should not be permanent: `[profile.dev.package.qwertty-term-vt] debug-assertions = false` in the workspace `Cargo.toml` (commit 18c4f924), fully commented. Remove it when a fixed version ships.

TO DO: file at github.com/joshka/qwertty-term with the minimal repro (a two-chunk `a=T,m=1` then `m=0` transmit), then bump the dep and drop the profile stanza.

--- note 2026-08-12T16:29:23Z ---

UPSTREAM REPORT FILED by the user, 2026-08-12, at github.com/joshka/qwertty-term. Draft was verified against the 0.4.0 registry source rather than from this quest's earlier notes, and the reproducer was compiled and run in both profiles before sending.

TWO CORRECTIONS to the original note, both now reflected in what was filed:

1. Our chunking is at `crates/app/src/render/graphics.rs:1479`, not `:1331` — the line had drifted.

2. The first reproducer written was WRONG, and only running it caught that. It split the base64 payload 3/3/2; kitty requires every chunk be a multiple of 4 (the base64 quantum). With a malformed split the image is lost entirely EVEN IN RELEASE (images = 0, placements = 0), which would have made the report claim the release path is broken — the opposite of the truth. With 4-aligned chunks (a 3x1 RGB image, 9 bytes → 12 base64 chars → 4/4/4) release is correct (images = 1, placements = 1) and debug panics, so the "misplaced assertion, not a logic error" framing is confirmed rather than assumed.

THE ARGUMENT AS FILED does not rest on Ghostty. It rests on the crate contradicting itself: the branch that OPENS a chunked transfer returns `display: None` while `more` is true, while the branch that CONTINUES one returns `display` — and `LoadResult::more`'s own doc comment reads "True if more chunks are expected (do not respond, do not display)". A maintainer can check that without trusting any external claim.

WHAT CLOSES THIS QUEST (nothing until upstream ships): bump `qwertty-term-vt` past the fixed release in `crates/app/Cargo.toml`, DELETE the `[profile.dev.package.qwertty-term-vt] debug-assertions = false` stanza and its comment block from the workspace `Cargo.toml` (added in 18c4f924), then confirm the pty_stream placement oracle still passes with the crate's debug assertions back ON. That last step is the point — the workaround currently silences every OTHER assertion the crate makes, which are exactly the ones worth keeping while testing.

Status left `partial` rather than `deferred` deliberately: the remaining work is real and owed, it is simply blocked on a third party. Add the issue number here when convenient so the trail is complete.
