## What happens today

`stories/plundered_hearts[infocom_1987](r26)(!).g64` (317,884 bytes), refused at load:

```
lanthorn: cannot read '…(!).g64': not a story file: 317884 bytes beginning
47 43 52 2d 31 35 34 31  |GCR-1541| — no format lanthorn reads claims it. It is
not a Blorb, not a Glulx image, not a Scott Adams database, and its first 64
bytes are not a Z-machine header (ZMSD §11.1)
```

The message is good — it names the magic and says plainly that nothing claims it —
so this is a missing format, not a diagnosis failure. `g64` appears NOWHERE in the
tree (`grep -rn g64 crates/` is empty).

## Why this is much smaller than it looks

**A `.d64` stores decoded 256-byte sectors; a `.g64` stores the raw GCR bitstream**
— sync marks, header blocks, gaps, and whatever copy protection the original had.
That is the only difference that matters. Once a G64 is decoded to a track/sector
image it IS a D64, and `crates/blorb/src/d64.rs` (1,162 lines) already does
everything downstream.

And what it does downstream is the part that would otherwise be hard: it **ignores
Commodore DOS entirely** — all three C64 disks in the corpus have a directory and
none of them uses it — and finds the story by **verifying against the story's own
header checksum**, an oracle a wrong guess cannot pass. That logic is
format-independent, so it needs no change.

So the shape is: parse the G64 container → GCR-decode each track to sectors →
present a D64-shaped image → `D64::story()`.

## This dump is clean, which makes it a good first specimen

Parsed structurally:

| | |
|---|---|
| signature / version | `GCR-1541`, version 0 |
| half-tracks declared | 84, of which **40 carry data** |
| tracks present | 1..40 (an extended 40-track disk; standard 1541 is 35) |
| **HALF-tracks with data** | **0** — no track-level copy protection in this dump |
| speed zones | all four, normally distributed (zone 3 × 17 = tracks 1-17, then 8/7/8) |
| stored track length | 7,692 bytes, a normal GCR track |

Zero half-tracks is the important line: the awkward part of G64 support is disks that
use half-stepping or non-standard sector layouts for protection, and this one does
neither.

## There is a validation oracle already in the corpus

`stories/plunderedhearts-r26-s870730.z3` — **the same release 26**. Whatever the
decoder extracts from the G64 must match it, or at minimum carry release 26 / serial
870730 and pass the header checksum `d64.rs` already verifies. Do not ship a decoder
without pinning it against that file; a GCR decode that is subtly wrong produces
plausible bytes.

## Constraints

- **`blorb` has ZERO dependencies** (its `[dependencies]` is empty), consistent with
  the project's hand-rolled-parsing rule. The GCR decoder is hand-rolled: find sync
  (ten or more `1` bits), decode 5-bit GCR nibbles to 4-bit data (10 GCR bytes → 8
  data bytes), parse the `$08` header block and `$07` data block, verify their XOR
  checksums.
- A format is a **row** in `medium.rs`'s `FORMATS` table, not a branch scattered
  through callers — add it there. Note the `.d64` row presents as Commodore 128 (7)
  on the reasoning at `medium.rs:188` that the medium names a FAMILY (a 1541 hangs
  off a VIC-20, C64, C128 and Plus/4 alike); a `.g64` row should say the same thing
  rather than invent a different answer.
- `stories/` is gitignored, so any real-game case must skip vacuously. A synthetic
  G64 built by GCR-ENCODING a known sector image would test the decoder in CI without
  commercial media, and is worth more than the real-disk case because it can assert a
  round trip.

## Worth deciding rather than assuming

Whether to support the protected cases at all (half-tracks, non-standard sector
counts, deliberately bad checksums used as a protection signature). The corpus has
one clean specimen; building for protection schemes nobody here has is speculative.
Decode what is decodable, and refuse the rest with a message as legible as the one
above.

## Scope decided (user, 2026-08-27): the STORY FILE is the deliverable, nothing else

> "as long as we can read the z-machine story file i don't think we need to worry.
> i'm guessing the copy protection was handled in the interpreter binary."

That is right and it settles the open question above. Infocom's C64 protection lived
in the loader/interpreter, not in the story data — so the story occupies ordinary
GCR sectors and a decoder that reads ordinary sectors is sufficient. The protection
tricks a G64 exists to preserve (half-stepping, deliberately bad checksums, oddball
sector counts) are all in service of the boot side, which lanthorn never executes.

This aligns with what `d64.rs` already does: it never reads the loader, it scans for
a run of sectors that verifies against the story header's own checksum. The same
posture carries over.

**So: decode what decodes, extract the story, and do not build for protection.** A
track whose sectors do not decode is not a failure of the feature — skip it and carry
on, exactly as the checksum scan already tolerates everything that is not the story.
Only refuse outright when no story is found at all, and then with a message as
legible as the current unknown-format one.

Corollary for testing: a G64 with a deliberately undecodable track alongside good
ones should still yield the story. Worth a synthetic case, since it is the behaviour
this decision is actually asking for.
