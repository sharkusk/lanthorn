Root cause fully confirmed, down to a unit test in the codebase that currently PINS the buggy behavior as expected: `window_wrapped_rows_windows_and_top_anchors` (crates/app/src/render/transcript.rs, test module near line 7799):

```
let (vis2, _t, first2) = window_wrapped_rows(&rows, Some(4), 3, 0); // anchor=4, 6 total rows, 3-row viewport
assert_eq!(first2, 4);  // shows rows[4..6] = ["R4","R5"] — 2 rows, anchor pinned to top (correct)
let (_v3, _t3, first3) = window_wrapped_rows(&rows, Some(4), 3, 1); // scroll by just ONE
assert_eq!(first3, 2);  // jumps to rows[2..5] = ["R2","R3","R4"] — a totally different window
```

`window_wrapped_rows` (crates/app/src/render/transcript.rs:1214) has two completely separate code paths:
- `scroll == 0` AND the anchored content (`n - anchor_row`) fits within `rows`: returns EXACTLY `display_rows[anchor_row..n]` — i.e. only the anchor's own few rows, pinned to the top of the viewport (the caller pads the rest with blank space above).
- ANY other case (scroll > 0, OR the anchored content doesn't fit): falls through to generic logic that slices the last `rows` rows out of the WHOLE `display_rows` array ending at `n - scroll`, completely ignoring the anchor.

Because these are two unrelated windowing formulas, going from scroll=0 to scroll=1 is not a one-row change in what's visible — it's a jump from "the anchor's own 2 rows, padded" to "a full 3-row slice from the entire transcript, ending 1 row short of the top." This is exactly the user's reported snap, and exactly why it only happens when the anchored content is SHORT enough to fit the viewport (`n - anchor_row <= rows`): once it overflows, that branch's condition is false even at scroll=0, so scroll=0 and scroll=1 already use the SAME generic formula and differ by only one row, as expected.

**Fix direction** (not yet implemented): make scrolling CONTINUOUS through the anchor boundary when the anchored content fits. Each one-unit increase in `scroll` should reveal exactly one additional row of PRE-anchor history above the still-pinned anchor content, until either (a) `scroll` has walked all the way back to the start of the transcript, or (b) revealing more pre-anchor rows fills the entire viewport, at which point it should naturally match (or hand off cleanly to) the existing generic "last `rows` rows ending at `n - scroll`" formula — rather than the current hard cutover at scroll==0/scroll==1 with two unrelated formulas.

Needs careful attention to: the existing non-regression tests this session's SQ-1656/1660/1661 work added (`sq1656_preserve_clear_top_anchor.rs`, `sq1661_topanchor_followease.rs`, `every_screen_clear_moves_anchor_row_and_top_anchors` in transcript.rs's own test module, `beyondzork_title_repaint.rs` for the TYPED-command-clear non-regression case) — the fix must NOT reintroduce the "old content hidden/preserved incorrectly" bugs those quests fixed; it only needs to smooth the SCROLL TRANSITION into the anchor boundary, not change what's shown at scroll=0 itself. Also needs to interact correctly with `top_anchor_fits`/the pager's follow-ease skip (SQ-1661, pager.rs) — check whether that still makes sense once scrolling through the anchor is continuous, or whether its threshold needs revisiting.
