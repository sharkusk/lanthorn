## What the capture already settles

* **The runs are there.** `win1` is a one-row 581x16 strip at (29,193) carrying **122 paint runs** — Arthur emits its bar one character per run, so 122 is a full bar, not a stub. The model publishes it as `Grid — 122 run(s)`. Nothing is missing upstream of the renderer.
* **It is a 7x15 cell**, i.e. the Macintosh (SQ-0917), and `usable 581px = 83 cols`. `581 / 7 = 83`, so the declared arithmetic is consistent.
* **The window is 16px tall against a 15px cell.** One row, with a pixel over.
* The same runs render correctly on the F2/F3/F4/F5 screens, per the report — so this is the score-bar FRAME, not the runs or the face.

## Where to look

The neighbours matter here. SQ-1035 fixed the hybrid twin of a score-bar defect on Arthur's AMIGA press, and SQ-1051 fixed raster prose losing its tails on this same MACINTOSH press to a character cap standing in for a pixel width. "Only the location shows, reversed, and the rest is blank" is the shape a REVERSE-ROW FLOOD makes when it wins the row: `v6_layout::fill_reverse_row_gaps` fills the gaps around a pure reverse-video row, and `render::screen::row_is_reverse_bar` decides whether a row counts as a band at all. Arthur's bar IS all-reversed and DOES carry text, so it should flood and then be re-stamped — check whether the glyphs are being painted and then covered, rather than never painted.

Note the 16px window against the 15px cell as a candidate off-by-one: a row test written as `>= cell.h` or a rect clipped to `y_size` could take the strip one way and the glyph loop the other.

## Root cause — a granularity regression from SQ-1009, not a score-bar bug

Reproduced on **`InfocomMasterpieces.img`, entry `InfocomMasterpieces/ARTHUR FOLDER/STORY.DATA`** (Macintosh compilation volume), 12 blank-line/return taps from cold, at the Churchyard. That press is the one that can falsify it because its release face (`FONT 524`) is **proportional** — the bare `.z6` under `--interpreter 3` renders the bar correctly and cannot reproduce this at all.

The reporter's dump and my repro differ slightly in run count (122 vs 123) and window rect; the mechanism is identical.

### What was wrong

`build_chrome_canvas` asked SQ-0487's over-art question — *"would an opaque block erase artwork under this run?"* — **once per run**, through `region_has_opaque`, which answers *"is ANY pixel in this rectangle opaque?"*.

That is a fair question about one character cell and a meaningless one about a long run. It was safe for years because a v6 grid publishes **one run per character**, so every probe was one cell wide. **SQ-1009's `pen_chains` began joining those runs into lines**, and the probe silently became a question about whole lines.

Instrumented, the three chains Arthur's bar joins into:

```
RUN py=195 px0=28  span=77  style=1 over_art=false " Churchyard"
RUN py=195 px0=104 span=616 style=1 over_art=true  "        …88 spaces…        "
RUN py=195 px0=458 span=168 style=1 over_art=true  "St Anne's Day, Compline "
```

* the padding chain's DECLARED span is **616 px** — the bar, both poles, and 80 px past the 640-px screen — so of course it found frame art;
* the date chain's declared span (7 px/char) overshoots its own proportional pen and reaches into the right-hand pole;
* both therefore took the *"draw dark ink on the artwork, no block"* arm and came out as page.

Only ` Churchyard`, whose chain is short enough to clear the art, kept its ribbon. Measured on the raster canvas: **78 of 584 px (13%)** of the bar's top scan line were ribbon. That is exactly the report.

The 16-px-vs-15-px cell noted in the quest as a candidate off-by-one was **not** involved.

### The fix

Ask the question **per glyph**, inside the pen walk, over `[pen, pen + max(advance, font_w))`. A chain walks the engine's own pen, so those are the same coordinates the unjoined runs occupied — this restores the pre-SQ-1009 answer for a proportional face and leaves every fixed-pitch face (where nothing joins) byte-identical. The one behavioural change beyond that: a run half over artwork now resolves per cell instead of letting its first opaque pixel speak for the whole run.

### Verification

`v6_arthur_status::mac_arthur_raster_score_bar_is_one_ribbon_not_the_location_alone`, both `honor_game_colours` modes, with a non-vacuity guard (the frame really is the all-reversed bar carrying `Churchyard` and `Compline`) and a boot that goes through `MachineBoot` so the 7x15 cell, the (2,2) art scale and the release face reach story and renderer together.

Falsified: reverting to the per-run probe fails it with `78/584 px` — the reported screen, to the pixel. After the fix the ribbon is 583/584.

Fixed in `6d4937a4`.

## Correction — the first test was machine-dependent, and its premise was false

Caught by the SQ-1047 lane, verified, and fixed. Recording it because the mistake is reusable.

`mac_arthur_at_status` resolved its face with `app::system_fonts::UserDisks::new("")` and then asserted:

```rust
assert!(face.proportional(), "the volume's own FONT is the proportional face SQ-1052 needs");
```

**That sentence is wrong.** `UserDisks::new` reads the real `~/.lanthorn/` whatever key it is given — only `prefer` is emptied — so the proportional face it got was **Geneva 12 off the user's `MacOS_6.0.8_System_Startup.img`**, not the volume's. The volume's own face is `FONT` 524, a **fixed** 7x15. So the case was green here for a reason its own comment denied, and would be red on any machine holding `stories/` without a Mac System disk. (Not red on CI, which carries no `stories/` at all and skips it — which is exactly why the gate never said a word.)

### The synthetic substitute does not work, measured rather than assumed

The obvious repair — synthesise a proportional face, as `native_disk_font.rs` does — was tried and **rejected**. With different advances the GAME lays its own bar out differently:

| face | runs on the bar | padding chain | ribbon |
|---|---|---|---|
| real Geneva 12 | **123** | 88 spaces, declared 616 px | white, 583/584 |
| synthetic | **76** | 38 spaces, declared 266 px | black, never painted |

The synthetic chain stops short of the frame art, so the defect is unreachable — with the fix reverted the case still passed, i.e. it had gone **vacuous**. A fixture that changes the frame is not a stand-in for the frame.

### What it is now — the pair CLAUDE.md asks for

* **The RULE, unconditionally**: `render::v6_layout::tests::a_joined_reverse_chain_resolves_its_block_per_glyph_not_per_run`. Builds its own canvas — one inherited-reverse row of single-character runs laid at the pen's advances so they join into one chain, over art opaque in a single ten-pixel patch near the far end. Asserts the cells clear of the patch keep their blocks and the cells on it still do not (SQ-0487 preserved). Counted, not sampled, because a proportional pen can out-advance the declared cell a block is drawn at. Falsified: the per-run probe gives **0 of 300 px**.
   - Fixture note: the synthetic glyphs must be **mostly blank**. `native_disk_font.rs`'s `proportional_face` inks every row solid because it only ever MEASURES; rendered, a solid glyph paints over the very block under test, and the first version of this case failed for that reason and not for the defect's.
* **The real media, when the machine can**: `v6_arthur_status::mac_arthur_raster_score_bar_is_one_ribbon_not_the_location_alone` keeps the real cascade and now **skips with a message** naming the missing System disk, instead of asserting a falsehood about the volume. It proves a shipped game publishes the shape; it cannot claim to run everywhere and no longer does.

The production fix in `6d4937a4` is unchanged and was never in doubt — it was verified by direct pixel measurement on the real press (78/584 → 583/584) before any test existed.
