## Root-caused to a boundary, on the reported press

`stories/James Clavell's Shogun.adf` — Amiga, **release 295 / serial 890321**.

### The source art is COMPLETE

Picture 3 (`P_BORDER`) is a **full-screen 320x200** image on this press — not the
narrow strip the IBM release ships (which is 23x200) — and decoding it under the
Amiga palette gives a painted profile in its left 40 columns of exactly:

```
23x200
```

One run: 23 columns painted for **all 200 rows**. Picture 4 (`P_BORDER2`) is the
same. So nothing is missing from the archive or the decoder, on either press.

### The COMPOSED canvas is short by four text rows

`render::v6_layout::build_graphics_canvas` over the same frame, profiled in its
left 60 native columns:

```
46x336  0x64
```

46 wide (= 23 x the (2,2) art scale) for **336** rows, then **64 rows of
nothing**. The picture's bottom 32 source rows never reach the composite.

And it is not a per-press accident — it is four text rows on each machine:

| press | art extent | lost | cell h | lost / cell |
|---|---|---|---|---|
| `James Clavell's Shogun.adf` (Amiga r295) | (0, **336**) of 400 | 64 | 16 | **4** |
| `Shogun.toast` (Macintosh r292) | (0, **340**) of 400 | 60 | 15 | **4** |
| `shogun-r322-s890706.z6` (IBM r322) | (0, **400**) of 400 | 0 | — | 0 |

The IBM press loses nothing, which is why the quest's own control — "the Blorb
press is fine" — holds. Note also where each press's window 2 begins: native
y=**337** on the Amiga and y=**341** on the Macintosh, i.e. immediately below
where that press's art stops.

### Ruled out

* **The clip at draw time.** `PictureEvent::win_box` is recorded as
  `(1, 1, 640, 400)` — the full screen — so `draw_image_clipped`'s `(pw, ph)`
  bound is not cutting it.
* **The canvas.** Window 7's own canvas measures **640x400**.
* **The classifier.** At the width the app actually crops (73 native columns
  around a 46-wide ornament) `recognize` answers `ShogunSinglePiece`, correctly.

So the loss is between "the scaled image" and "the composited canvas", with the
canvas full-size and unclipped, and 168 of 200 source rows surviving. The
remaining suspects are the palette the boot draw runs under (`image` vs
`image_under_current_palette` — a colour resolving to alpha 0 would read exactly
like this) and an erase applied after the draw.

## AT WHAT POINT THE TILING OCCURS — it is a consequence, not the cause

`render::v6_border::extend_flank`. It builds the repeat unit from the measured
art extent:

```rust
BorderArt::ShogunSinglePiece => {
    let mut art_strip = RgbaImage::new(w, art.1);   // art.1 == 336, not 400
    …
    shogun(&mut strip, &art_strip, art.1, desired);
}
```

`art.1` comes from `art_extent`, so the tile is **336 rows instead of 400**. The
second copy therefore begins 64 rows early — inside the frame, not below it — and
every copy after that is offset again. That is the medallion recurring down the
column in a pty capture where the machine shows one.

**Fix the 64 missing rows and the tiling question changes shape**: the repeat unit
becomes the whole 400-row ornament, and the extension only has to fill pane height
the machine never had. Do not tune the extender first.

## Instruments

`flank_shape` reports the extent and the classification, and its `--cols` default
of **17** is an instrument default, not the app's crop — at 17 it misreports this
press as `ArthurPoles`, because `hi` measures the CROP and the threshold
`SINGLE_PIECE_MIN_WIDTH` is 24. Pass the app's own width:

```
cargo run -q -p app --example flank_shape -- \
  --story "stories/James Clavell's Shogun.adf" --cols 73 --rows 655
```

A pty capture of the gameplay frame shows the symptom directly:

```

```

## The mechanism, end to end

Measured on `stories/James Clavell's Shogun.adf` (Amiga, r295/890321), the FIRST
keypress — the title screen giving way to the boot menu. Window 7's canvas
profiled in its left 60 native columns:

```
tap 0:  60x400              <- the title splash, fully painted
tap 1:  46x336  0x64        <- the border, minus its bottom 64 rows
```

That turn's ordered picture queue:

```
pic 0 into win7  erase=true   win_box=(1,   1, 640, 400)   <- clear the splash
pic 3 into win7  erase=false  win_box=(1,   1, 640, 400)   <- draw the border
pic 0 into win0  erase=true   win_box=(1, 337, 640,  64)   <- clear win0's strip
pic 0 into win2  erase=true   win_box=(235,337, 169,  48)
```

and the window state it leaves:

```
win0 = (1, 337, 640,  64)     win1 = (1, 1, 640, 336)
win2 = (235, 337, 169, 48)    win7 = (1, 1, 640, 400)
```

**336 is window 1's height**, and the 64 rows lost are exactly window 0's strip.
`session.rs`'s erase_window path —

```rust
if ev.erase && ev.number == 0 {
    self.pictures_canvas.remove(&ev.window);
    …
    if let Some(rect) = self.window_screen_rect(ev.window) {
        self.erase_screen_rect(rect, Some(ev.window));   // SQ-0568
```

— takes that 640x64 screen rect out of **every other window's canvas**, including
window 7's, and nothing ever redraws the border. Every later frame inherits a
336-row flank, which is why gameplay shows it too.

## The machine keeps it, on both frames

`machine-screenshots/amiga-shogun-main.png` — the boot menu, the very frame this
erase produces. The gold ornaments run the full height of the frame, and the menu
text ("You may choose to: / START the game / …") sits in window 0's bottom strip
**with the ornament painted beside it**.

`machine-screenshots/amiga-shogun-game.png` — gameplay. Calibrated off the status
band (image x 89..628 = 540 px, so `native = image - 42`), the left 46 native
columns profile as painted 40-46 wide for essentially every row 1..399. It never
stops at 336.

## The tension this creates, which is why it is not a one-line fix

The cross-window erase is SQ-0568, and its own suite states the case for it:
Arthur's F2 map paints a full-screen background into **window 7**, and switching
back to F1 erases windows 2, 5 and 6 — never 7 — so without the cross-window wipe
the map background stayed under every later screen for the rest of the game.

Those two are structurally identical — erase a window, must/must not remove what
window 7 drew underneath — and a single rule cannot satisfy both. Neither ordering
nor z-order separates them: in both cases window 7 was painted before the erase.

So the next step is evidence, not a patch. Two ways to get it:

1. **A machine capture of Arthur's F1 screen after an F2 → F1 round trip.** If the
   map background is gone there, the cross-window erase is right for Arthur and the
   rule needs a discriminator. If it is still visible, SQ-0568's premise was wrong
   and the fix belongs on Arthur's side.
2. **Check whether `erase_window` should cross windows at all**, versus
   `erase_picture` (which is what §8.8.5.1 actually describes). Today both go
   through the same branch; the number-0 sentinel is `erase_window` and it is the
   one with machine evidence against it.

## And a second, unrelated defect this turned up

`win1 = (1, 1, 640, 336)` and `win0 = (1, 337, 640, 64)` — **full width** — where
the machine's status band is `(47, 1, 548, 32)`, inset between the ornaments. The
user reports the score bar rendering across the entire screen where the real game
sits it between the artwork, and the calibration above confirms it: the machine's
band is 540 px wide starting at native 47. Filed separately.

## The tiling is downstream and should not be touched first

`v6_border::extend_flank` builds its repeat unit as `art_strip` of height `art.1`
— the measured extent, 336 instead of 400 — so the second copy begins 64 rows
early, inside the frame, and every copy after is offset again. Restore the 64
rows and the repeat unit becomes the whole ornament.

## The defect has TWO faces, and which one you see depends on the pane

The user recalled \"the side art stops at the menu on the start screen in hybrid
mode\". Reproduced, and it is the same 64 missing rows as the tiling — not a
second defect.

pty captures of the boot menu, `stories/James Clavell's Shogun.adf` (Amiga
r295/890321), one keypress from launch:

| pane | device rows | extension | result |
|---|---|---|---|
| 132x60 | 1080 vs a 400-row frame | fires | ornament repeats — the medallion three times where the machine shows one |
| 80x24 | 432 | fires | repeats, less obviously |
| **80x22** | **396 — SHORTER than the frame** | **does not fire** | **the ornament STOPS at the menu**, flanks bare below it |

`extend_flank` bails when `desired <= art.1`, and `art.1` is the truncated 336.
So at a pane taller than 336 native rows the extension papers over the hole by
repeating; at or below it, the hole is bare. Either way the 64 rows the erase took
are gone.

`machine-screenshots/amiga-shogun-main.png` is the same frame on the machine: the
gold ornament runs past the menu text to the bottom of the screen.

**This is the cleanest reproduction to fix against**, because it shows the defect
with no extension arithmetic on top:

```
cargo run -q -p app --example pty_capture -- \
  --story "stories/James Clavell's Shogun.adf" --size 80x22 \
  --keys 'wait:1500,cr,wait:2000' --png start22.png
```

and the tall-pane capture (`--size 132x60`, same keys) is the regression to keep
watching afterwards, since a fix that restores the rows must also stop the
repeat.

## FIXED — the split tiles vertically, not to full width

`@split_window` was resetting windows 0 and 1 to `x_coord = 1`, `x_size = screen
width`, reading §8.8.4.1's "tiled together to fill the screen" as full width.
Shogun's Amiga release sets both windows INSET between its ornaments
(`move_window(win=1, y=1, x=47)` / `window_size(win=1, y=32, x=548)`, and the
same for window 0) and only then issues `@split_window(336)`. The reset put
window 0 at `(1, 337, 640, 64)`, and the very next instruction —
`erase_window(lower)` — took that full-width strip out of window 7 through the
shared-screen erase, removing the frame art's bottom four text rows for good.

The tile now sets each window's new top and height and leaves the horizontal box
alone. Measured on `stories/James Clavell's Shogun.adf` (Amiga r295/890321):

| | before | after |
|---|---|---|
| win7 canvas, left 60 cols | `46x336 0x64` | **`46x400`** |
| win0, menu frame | `(1, 337, 640, 64)` | `(47, 337, 548, 64)` |
| win1, menu frame | `(1, 1, 640, 336)` | `(47, 1, 548, 336)` |
| win1, gameplay | full width | `(47, 1, 548, 32)` |

The erase now spans native x 47..594 and never reaches the flank columns at
x 0..46. Both of the defect's faces go with it: a pty capture at **80x22** no
longer stops the ornament at the menu, and at **132x60** the column runs cleanly
to the bottom instead of degenerating — the repeat unit `extend_flank` uses is
the whole 400-row ornament now rather than a truncated 336.

Falsifier: `machine-screenshots/amiga-shogun-main.png` (the exact frame the erase
produces — ornament past the menu text to the bottom) and `amiga-shogun-game.png`
(the flank painted 40-46 wide for essentially every row 1..399).

The standard's own remark carries the rest of the argument: *"Existing Version 6
games seem to use this opcode only for bounding cursor movement."* A vertical tile
satisfies that and leaves every full-width caller — Zork Zero's
`@split_window(400)` splash, advent's Inform library, mysterious01 — byte-identical,
because their windows already span the screen.

## One test had pinned the defect

`v6_side_border_tiling::each_specimen_is_recognised_as_its_own_layout` asserted
Shogun's left flank art rows as `(0, 336)`. That number WAS the bug. Updated to
`(0, 400)` with the reasoning and the capture named beside it.

Full gate: `Starting 6132` → `6132 passed`, count 0.

## What this quest does NOT fix

The status band still renders full width — see **SQ-1076**, which is a RENDER
defect and not this one. Shogun's `win1` is correctly `(47, 1, 548, 32)` in
gameplay and the band still reaches the pane edges; Arthur shows the same with no
