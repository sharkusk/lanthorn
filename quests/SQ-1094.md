## Reproduction

```sh
cargo build -p app
cargo run -p app --example pty_capture -- \
  --story stories/arthur-r74-s890714.z6 --size 100x50 --cell 16x32 \
  --arg --pictures --arg stories/arthur.cg1 \
  --keys "wait:4000,text:n,wait:2500,text:n,wait:4000,cr,wait:2500,cr,wait:2500,cr,wait:2500,cr,wait:2500,cr,wait:3000" \
  --png /tmp/arthur-cga-100x50.png
```

Arthur release 74 / serial 890714 (bare story), CGA plates named explicitly, hybrid,
kitty, 12 keypresses to the Churchyard gameplay frame (`expect` words on screen:
`Churchyard`, `St Anne's Day, Compline`). Note the two `n`s: the first dismisses
lanthorn's resource notice, the second answers the game's restore prompt.

## Measured — it is the pane being TALLER than the frame that does it

Non-background pixel runs down the left margin strip (x 30..125):

| size | left-margin runs |
|---|---|
| 82x28 (frame exactly fills the pane) | `64..395` ornament, `400..799` rule — **nothing below** |
| 100x50 (pane taller than frame) | `71..477` ornament, `483..1324` rule, **`1330..1503` fragment**, then rule again |

At 82x28 the frame fills the pane at a whole 2.0x and no fragment exists. At 100x50
the scale is still 2.0 (capped by `MAX_V6_UPSCALE`) but the pane is 1568x1504 against
a 1280x800 frame, so the border-extension path (SQ-1083) runs — and that is the only
configuration where the fragment appears.

## And it is rendition-specific, which is the useful discriminator

Same story, same size, same keys, only the artwork differs:

| rendition | left margin at 100x50 |
|---|---|
| `stories/arthur.cg1` (CGA) | ornament / rule / **fragment** / rule — three runs with gaps |
| `Arthur.blb` (the default sidecar, 326 images) | one continuous run `71..1503`, clean |

So the Blorb rendition extends its flank correctly down the full height and the CGA
rendition does not. Whatever the extension does, it is reading something different
out of the CGA side-column picture.

## What the fragment IS

Visually it is the **panel-and-bars clasp motif from the TOP banner** — the recessed
rectangle with the little vertical bars under its left edge, which appears twice in
the top ornament. At the bottom it is clipped mid-motif and floats disconnected, with
the plain rule resuming beneath it.

It is NOT a byte-for-byte copy of any region of the left margin: sliding the
174px-tall block against the whole margin gives a best match of 27.5% differing
pixels (and 35.7% vertically flipped), so it is not a straight blit of the top
ornament nor a mirrored bottom corner. It is the same motif drawn at a different
offset or phase.

## Where to start

`render/v6_border.rs` and the flank tiling `render/v6_layout.rs` drives, plus the
`flank_shape` and `border_preview` examples which exist for exactly this. The
question to answer first is what source slice the extension repeats, and why the CGA
side-column picture yields one containing banner ornament where the Blorb's does not
— the two are both 640x400 at 2.0x, so it is not a geometry difference.

Check Zork Zero's Macintosh press at a tall pane too (`docs/tall-terminal-border.png`
is SQ-1083's own gallery frame and reads correctly), to see whether this is CGA-only
or "every rendition except the ones we have shot".

## The user reports this is NOT Arthur-only — Journey has shown it "in several cases"

Reported 2026-08-27 when the Arthur frame was shown. That changes the shape of the
quest: treat the Arthur CGA frame as ONE reproduction of a recurring flank/border
extension defect, not as the defect itself. A fix that special-cases Arthur's CGA
plates and leaves Journey alone has not fixed this.

Journey is also the harder specimen and the better oracle, for reasons already
written down elsewhere in this project:

- **`v6_side_border_tiling` already exists** as a suite, and its `boot()` was one of
  the two harnesses that omitted `native_std_window` in SQ-0901 — so Journey r77 and
  Arthur r63, both **560x384** presses, were being measured at 640x400. That produced
  a fabricated Arthur frame ("a single illustration clear of both edges") that a whole
  quest was fixed and tested against, and hid SQ-0883 and SQ-0899 for two rounds.
  Whatever is done here, boot the harness the full `startup.rs` way and PRINT the
  profile, release and screen size, then check them against a `/dump-windows` capture.
- **A disk image is a different RELEASE, not the same story on other media.**
  `stories/journey-r83-s890706.z6` is release 83 / serial 890706;
  `Journey - The Quest Begins.adf` is release **30** / serial 890322, and the two
  differ in behaviour (r83 narrates through window 0, r30 through window 2 — the whole
  of SQ-0755). Name the exact fixture and release in any finding.
- **SQ-0750 is the standing rule the flanks live under**: in hybrid, never rasterise
  what the game printed as a character. Journey ships four side rules as 8x900 and
  16x900 RGBA bitmaps — ~192 KB per frame to draw 200 `│`s — and the SAME rule is
  drawn as glyphs seven rows lower where it crosses the menu strip. Reserve raster for
  pixels the paint runs cannot account for. A fix that makes the flank correct by
  rasterising more of it has traded one defect for that one.

Journey media present: `Journey - The Quest Begins.adf` (Amiga, r30), `Journey.2mg` /
`Journey.po` (Apple II), `journey_s1..s5.dsk` (the five-floppy Apple II set),
`journey-r83-s890706.z6` + `Journey.blb`, and the DOS plates `journey.cg1`,
`journey.eg1`/`.eg2`, `journey.mg1`.

Note the Arthur finding already says the defect is **rendition-specific** (CGA shows
it, the Blorb does not, at identical geometry). Journey's DOS plates are the obvious
place to look for the same split, and `journey.cg1` is the direct analogue of the
`arthur.cg1` reproduction.

Other suites in the area worth reading before changing anything: `v6_band_tiling`,
`v6_archive_border_sweep`, `v6_frame_border_medium`, `pty_flank_alpha_seam`.
