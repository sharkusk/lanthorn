## The decision SQ-1102 took, and why it is meant to be revisited

SQ-1102 added `gvm::grammar` beside SQ-1040's `zvm::grammar`. The brief asked
for the shared-parser question to be settled deliberately rather than by
default. It was, and the evidence pointed both ways:

**Do NOT abstract the reader.** The two readers share almost nothing once you
look at the bytes:

| | Z-machine | Glulx |
|---|---|---|
| table address | header word $0E | recorded NOWHERE; derived by a three-table chain |
| verb numbering | counts down from $FF | counts down from $FFFF |
| verb table | pointer array, count implied by the first pointer | explicit count, then the pointer array |
| line header | 2 bytes, reverse packed into the action as $400 | 3 bytes, separate flags byte |
| token | 1 + 2 bytes | 1 + 4 bytes |
| dictionary | Z-encoded key, game-chosen record length | $60 tag, plain bytes, `$DICT_WORD_SIZE` |
| formats carried | 5 (incl. four Infocom-era shapes) | 1 |

A trait over "read a byte / read a word at an address" would abstract a handful
of lines out of several hundred, while forcing two zero-dependency crates to
name a shared vocabulary. That is not worth it.

**DO share the answer.** What the two genuinely have in common is the shape of
the result — `Token`, `NounKind`, `Slot`, `SyntaxLine`, `Verb`, `WordRoles` —
and the elementary-token numbering and six token types they both transcribe
from Inform's published tables. Today those exist twice, with identical names
so the conversion is mechanical.

## What to do

A small zero-dependency workspace crate (`ifgrammar`, or similar) holding the
value types and the token semantics, which both `zvm` and `gvm` depend on and
re-export. Note the CLAUDE.md rule is about **external** dependencies; `blorb`
is already an internal crate other crates depend on.

It was deliberately not done inside SQ-1102 because it rewrites
`zvm::grammar`'s just-landed public API, and that is worth doing once on
purpose rather than as a side effect of adding the second reader.

## Do it before SQ-1041 hardens against either type

SQ-1041 and SQ-1042 are the consumers. If they are written against two separate
vocabularies they will grow a conversion layer in `app` that this change would
then make pointless. Cheap now, awkward after.

Pre-release, so the API may break freely (`no-backcompat-before-release`).

## Review finding: the two APIs already diverge in one place a consumer will hit

Diffing the two public surfaces (`sq-1040`'s `zvm::grammar` against `sq-1102`'s
`gvm::grammar`) they match method for method except for four items, three of which
are principled and one of which is not:

**Principled, keep:**
- `zvm` alone has `GrammarFormat` + `Grammar::format()` / `is_infocom()` /
  `is_inform()` — it reads five table shapes; Glulx has exactly one.
- `zvm` alone has `RoutineRef` — Z-machine packed-address routines.
- `gvm` alone has `Tables` + `locate()` — the addresses are *derived* there, so the
  located addresses are part of the answer (and are what `glulxdump -g` needs).

**Not principled, and it will bite SQ-1041:** `gvm::Grammar` has

    pub fn words(&self) -> impl Iterator<Item = &str>

enumerating every dictionary word, and `zvm::Grammar` has no equivalent — its only
`words()` is `SyntaxLine::words()`, which returns that one line's literal tokens
(`Vec<&str>`), a different thing under the same name. So a consumer that wants "every
word this story knows" has one spelling on Glulx and none on the Z-machine, and the
name it would reach for already means something else there.

Fix this as part of the unification: whatever the shared type ends up being, give it
one whole-dictionary enumerator with one name, and rename `SyntaxLine::words()` to
something that cannot be mistaken for it (`literals()` reads correctly — those tokens
*are* the line's literal words).

This is the concrete reason the quest says "before SQ-1041 hardens against either
type": SQ-1041 is the consumer, and it would otherwise pick one spelling per engine
and freeze the divergence.
