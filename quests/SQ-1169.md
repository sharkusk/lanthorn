## The mechanism

`resolve_row` (`crates/app/src/theme/resolve.rs:419`) composes in two steps:

1. the row's **registry default Delta**, applied on top of the resolved parent;
2. each user layer's decl (global → garglk → per-game), highest wins.

A user decl that sets only `parent` re-roots the row correctly — `effective_parent`
honours it — but carries no colour channels of its own. So step 1's pinned `fg`/`bg`
overwrite whatever the new parent supplied, and step 2 has nothing to put back. The
re-root resolves, emits no warning, and changes nothing on screen.

## The eight rows it applies to

Found by a paren-balanced scan of `REGISTRY` for `fg:`/`bg: Some(Color::` inside a
row's default Delta (181 rows scanned):

    status_header
    debug.disasm_executed
    debug.disasm_rd
    debug.disasm_soft
    dialog.shadow
    tooltip.background      ← FIXED, see below
    dialog.list_selected
    transcript_search_highlight

`tooltip.background` was cured incidentally by making it inherit
`dialog.list_selected` instead of pinning a literal pair. **The other seven are still
live**, and `dialog.list_selected` is the one that stings: it is the shared
Black-on-Cyan menu highlight, so a user who wants their menus retuned cannot re-root
it — and now the tooltip inherits from it, so neither moves.

## Why the existing test could never catch it

`user_parent_reroot_override_resolves` (resolve.rs) proves re-rooting works using
**`panel.title`**, whose registry Delta is `Delta::EMPTY`. A row with nothing to pin
cannot demonstrate the pin winning. That is the whole coverage gap in one line: the
mechanism test was written against the case that cannot fail.

`a_reroot_moves_the_colours_of_a_row_that_used_to_pin_them` now covers the shape, but
only for `tooltip.background`.

## The design question, which is NOT settled and is the user's call

What should `parent = "x"` mean on a row whose registry Delta pins colours?

- **(a) A re-root suppresses the registry Delta's colour channels.** Semantically the
  honest reading — "inherit from x" should mean the colours come from x. Risk: it
  silently changes what seven existing rows do for anyone who has already re-rooted
  one (probably nobody, pre-release).
- **(b) Leave resolution alone; stop pinning colours in the registry.** Each of the
  seven gets a parent that already carries the pair, as `tooltip.background` now
  does. More faithful to the existing model, but some of these have no honest
  parent — `transcript_search_highlight`'s Black-on-Yellow is not any role.
- **(c) Warn.** Detect a re-root of a colour-pinning row and emit a `ThemeWarning`,
  the way an unknown parent already does. Cheap, honest, fixes nothing.

(a) and (c) compose. Do not pick one from this note — ask.

## Related

Adjacent but separate: `dialog.list_selected` pins a literal `Color::Cyan` while the
`accent` role resolves through **slot 6** of the active scheme. So a custom scheme
retunes accent everywhere and leaves the menu highlight — and now the tooltip —
stubbornly literal-cyan. Worth deciding alongside, since (b) would force the question.
